# 실패 저장과 1차 재시도 예약

구현·검증일: 2026-09-24. [HTTP 응답 분류](23-업체-HTTP-응답-분류와-시험-계약.md)에 실패 결과 저장과 예약 실행을 연결했다.

## 구현 범위

관찰한 RETRY_1S·RETRY_10S·NO_RESPONSE는 DynamoDB에 사유와 다음 실행 시각을 저장하고 최초 호출 외에 최대 3회 재시도한다. 새 Worker가 같은 Kafka 입력을 받아도 저장된 예약 시각·횟수·기한을 사용한다. 접수 성공한 요청과 결과 없이 종료된 PROCESSING을 자동 재시도 대상으로 바꾸지 않는다.

재시도 소진·대체 발송 코드·영구 거절·1차 기한 경과는 `DECISION_PENDING`에 사유와 판단 시각을 남긴다. **이는 2차 발송이나 고객 최종 결과의 완료가 아니다.** 해당 상태를 인계받아 최초 요청의 2차 허용 조건을 적용하고 TCP 발송·최종화를 진행하는 기능은 다음 작업이다. 현재 이 상태를 자동 탐색·소비하는 후속 Worker는 없다. 기록은 삭제하지 않는다.

## 상태와 외부 호출

| 저장 상태 | 재전달 처리 | 외부 호출 |
|---|---|---|
| 없음 | 최초 조건부 선점, retry_count=0, 최초 인입 기준 deadline 저장 | 기한 내 선점 성공한 Worker만 호출 |
| PROCESSING, 유효 lease | 진행 중 오류, 원본 offset 유지 | 추가 호출 금지 |
| PROCESSING, lease 만료 | 기존처럼 REVIEW_REQUIRED 조건부 저장 | 추가 호출 금지 |
| RETRY_SCHEDULED, 예정 시각 전 | 대기 오류, 원본 offset 유지 | 호출 금지 |
| RETRY_SCHEDULED, 예정 시각 도달·기한 전 | status·version·예정 시각·deadline·횟수 조건으로 선점 | 한 Worker만 호출 |
| RETRY_SCHEDULED, 기한 도달 | PRIMARY_EXPIRED 사유로 DECISION_PENDING 저장 | 호출 금지 |
| ACCEPTED / REVIEW_REQUIRED / DECISION_PENDING | 기존 상태를 유지하며 listener 완료 | 추가 호출 금지 |

선점 후 실제 HTTP 호출 직전에도 기한을 확인한다. HTTP 접수 응답을 받았더라도 기한 이후라면 ACCEPTED 대신 만료 판단을 보존한다. 이미 ACCEPTED 또는 REVIEW_REQUIRED인 항목의 주기적 만료, 업체 웹훅의 만료 경합은 아직 구현하지 않았다. 따라서 이번 기능만으로 전체 3시간·4시간 만료 및 고객 최대 기한을 보장하지 않는다.

## DynamoDB에 남기는 최소 정보

기존 `DELIVERY#deliveryId / ATTEMPT#attemptId` 한 항목에 다음 필드를 추가한다. 재시도마다 항목·payload 복사본을 만들지 않는다.

| 필드 | 의미 |
|---|---|
| retry_count | 재시도 선점 횟수. 최초 0, 최대 3. Kafka 재전달 횟수와 다름 |
| primary_deadline | 최초 선점 때 인입 시각+설정 기간을 epoch ms로 고정 |
| next_attempt_at | 재시도 또는 만료 판단을 다시 확인할 예정 시각(epoch ms) |
| failure_reason | 제한된 오류 분류·소진·만료 사유 |
| failure_observed_at | 관찰·소진 판단 시각. 만료의 경우 고정된 deadline |

실패 결과 저장은 PROCESSING과 version 일치를 요구한다. 실패와 예약을 **한 번의 조건부 Update**로 저장하고 lease를 제거한다. 재시도 선점은 같은 항목의 version과 retry_count를 각각 1 증가시킨다. 이전 호출자의 늦은 성공·실패 저장은 조건 충돌로 차단한다. 최초 정상 흐름은 원본 Put 1회+선점 Update 1회+접수 저장 Update 1회로 유지한다.

`attemptId`와 업체 Idempotency-Key는 현재 1차 경로의 기존 값을 재시도에도 유지한다. 통신 재시도 순번은 retry_count, 소유권 세대는 version으로 구분한다. 업체 중복 제거가 없어도 내부 선점 경합은 차단하지만, 무응답 재시도는 이미 처리된 외부 효과를 반복할 수 있다. 같은 key를 유지하는 것만으로 외부 exactly-once를 주장하지 않는다.

**DynamoDB를 사용하는 이유:** 재시작 이후에도 ‘무응답을 관찰하여 예약한 작업’과 ‘결과 기록 없이 종료된 작업’을 구별하고, 같은 예약을 여러 Worker가 동시에 실행하지 못하게 해야 한다. DynamoDB 조건식은 조건이 참일 때만 항목 변경을 허용한다. 이를 status·version·시각·횟수 조건에 적용하는 것은 프로젝트의 설계 선택이다. [AWS 공식 조건부 변경 설명](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), 확인일 2026-09-24. Redis나 메모리 타이머에 복구 근거를 두지 않는다.

## Kafka를 통한 예약 복구와 처리량 한계

예약 저장 후 listener는 `DispatchRetryPendingException`을 던진다. 기존 무제한 DefaultErrorHandler와 RECORD ack를 유지하므로 원본을 완료 처리하지 않고 다시 읽는다. 재시작한 Consumer도 같은 DB 예약을 확인한다. 별도 retry topic 발행이나 GSI·주기 Scan은 이번 단계에서 추가하지 않았다.

Spring Kafka 문서는 DefaultErrorHandler가 실패 레코드의 재전달을 수행하고, RECORD 모드에서 성공 처리된 레코드의 offset을 commit하는 동작을 설명한다. 프로젝트에서는 실제 broker의 committed offset을 확인해 예약 중 보존과 성공 후 전진을 검증했다. [Spring Kafka 공식 오류 처리 설명](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html), 확인일 2026-09-24.

**처리량 한계:** 대기 중 같은 파티션과 동일 Consumer가 담당한 다른 파티션의 처리가 지연될 수 있다. 재전달마다 실패한 최초 선점 조건부 Update와 consistent Get 비용도 생긴다. 현재 구조는 짧은 예약의 내구성·경합 검증용이며 고 TPS 오류 부하에 적합한 최종 스케줄러가 아니다. 처리량 확장 전 retry 소비 경로를 분리하고, 인계 발행 실패·중복 발행·재시작 복구를 검증해야 한다. Kafka 원본 retention보다 긴 장애를 이 방식 하나로 복구한다고 주장하지 않는다.

## 코드별 동작과 설정

| 분류 | 현재 처리 |
|---|---|
| RETRY_1S / RETRY_10S | 각각 관찰 시각+1초 / +10초 예약, 최대 3회 재시도 |
| NO_RESPONSE | 개발 기본 1초 예약, 최대 3회 재시도 |
| 위 세 분류의 재시도 소진 | RETRY_EXHAUSTED_분류 사유로 DECISION_PENDING |
| FALLBACK_REQUIRED / PERMANENT_REJECTION | 해당 사유로 DECISION_PENDING |
| INVALID_RESPONSE / HTTP_ERROR | 해당 사유로 즉시 REVIEW_REQUIRED |

NO_RESPONSE 간격은 미정 운영 정책을 대체하지 않는 개발 기본값이다. `DISPATCH_NO_RESPONSE_RETRY_DELAY`로 변경한다. `DISPATCH_PRIMARY_TTL` 기본값은 합의한 3시간이며 이미 선점한 요청의 deadline은 설정 변경으로 늘어나지 않는다. 두 값 모두 최소 1ms다.

재시도 예정 시각이 기한 뒤라면 next_attempt_at을 deadline으로 두어 그 시각에 만료를 판단한다. 재시도를 기한에 맞춰 앞당겨 발송하지 않는다. 장기 중단 후 재개도 deadline을 지난 예약은 발송하지 않고 만료 사유를 남긴다.

## 장애 경계

- 무응답 관찰 후 **저장 전** 종료/실패: PROCESSING이 남으므로 lease 만료 후 운영 확인. 자동 재발송 금지.
- 예약 저장은 성공했지만 응답 유실: 다음 재전달의 consistent read로 예약 복구. 횟수 중복 증가 없음.
- 재시도 선점 후 호출 전/결과 기록 전 종료: PROCESSING의 lease 만료 후 운영 확인. 선점한 횟수는 되돌리지 않음.
- 성공 저장 후 Kafka commit 전 재시작/중복 입력: ACCEPTED 확인 후 추가 외부 호출 없이 완료.
- 만료·거절·소진 판단 저장 실패: listener 실패 유지. 기록 성공을 확인하기 전에는 완료 처리하지 않음.

## 검증 결과

```bash
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:39092 \
JAVA_HOME=/path/to/jdk-21 \
./mvnw -q -pl dispatch-worker -am test
```

**69건 통과, 실패·제외 0건:** 공통 10건, Dispatch 단위·HTTP wire 41건, DynamoDB 통합 17건, Kafka+DynamoDB 통합 1건. 전체 프로젝트 테스트 수가 아닌 이번 실행 범위다.

- 20개 동시 Worker의 예정 시각 재선점에서 한 Worker만 성공. 이전 version의 결과 저장 거절.
- 새 서비스 인스턴스를 매번 생성해 RETRY_1S·RETRY_10S·NO_RESPONSE 각각 총 4회 호출 및 소진 후 추가 호출 0회 확인.
- 예약 저장 전 실패·저장 후 응답 유실·재시도 선점 후 결과 미기록 상태를 재현.
- 예약 기한 고정, 기한 도달 시 발송 차단, 늦은 HTTP 접수 응답의 만료 판단 저장 검증.
- 실제 Kafka에서 baseline offset=1 이후 예약 입력은 offset=1 유지. Consumer를 중지·새 인스턴스로 재시작해 예정 시각 전 호출 0회 추가 확인. 제어 시계를 예정 시각으로 이동한 뒤 한 번 재시도하고 offset=2, 같은 입력 재발행 후 추가 호출 없이 offset=3 확인.

Kafka 시험은 UUID 전용 토픽·그룹, DB 시험은 UUID 전용 항목만 만들고 정리했다. Consumer 컨테이너 재생성 검증이며 OS 프로세스 kill·전체 AZ 장애 검증은 아니다. 기존 모니터링 앱을 재배포하거나 성능 시험을 새로 수행하지 않았다.

관측용 outcome에 dispatch_retry_scheduled·dispatch_retry_wait·dispatch_decision_pending을 추가했다. 이는 관측 횟수이며 고유 예약/미해결 건수 gauge가 아니다. 개별 상태는 DB, 흐름은 deliveryId 로그로 대조한다.

다음 구현은 DECISION_PENDING의 내구성 인계와 최초 요청의 2차 허용 계약, TCP 업체 접수다. 재시도 경로 분리·전체 만료·최종 웹훅·고객 통지는 계속 남는다.
