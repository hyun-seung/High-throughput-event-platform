# 워커 동시 처리와 발행 대기 성능 비교

측정일: 2026-09-24. **동시성 3·Ingress linger 5ms를 기본값으로 채택한다. 이 설정에서 100 TPS를 3분간 입력한 18,001건이 모두 대조를 통과했다. linger 0ms도 처리는 통과했지만 일시 적체와 큰 지연이 관측돼 기본값으로 채택하지 않았다.** [첫 기준선](16-1차-성능-PoC-측정-결과.md)의 100 TPS 적체 원인을 확인하기 위한 후속 시험이다. API→Kafka→Ingress→Dispatch→HTTP 업체 접수 저장 범위이며 최종 전달·TCP 2차·고객 결과 통지는 포함하지 않는다.

## 성능 시험을 통해 진행한 과정

| 단계 | 관측·판단 | 수행한 변경 또는 검증 |
|---|---|---|
| 첫 측정 | API 응답은 빨랐지만 100 TPS에서 Ingress 앞 적체가 최대 1,487건 | API 응답 속도와 Worker 처리량을 분리해 분석 |
| 병목 가설 | Consumer 1개가 DB 저장, Kafka 발행 ack, 건별 offset commit을 순차 대기 | 기존 3개 파티션을 활용하는 동시성 비교를 우선 선택 |
| A: 기존 조건 재측정 | 최초 한 번의 결과만으로 설정 효과를 단정하지 않음 | 동시성 1·Ingress linger 5ms, 50/100 TPS 재시험 |
| B: 동시성 변경 | 같은 순차 대기를 파티션별로 나눠 처리할 수 있는지 확인 | 두 Worker만 동시성 3으로 변경, linger 5ms 유지 |
| C: 발행 대기 변경 | Ingress는 건별 `.join()`으로 ack를 기다려 배치 대기가 비용일 수 있음 | 동시성 3 유지, Ingress linger만 0ms. API Producer 유지 |
| 정합성 검증 | 빠르게 처리해도 외부 중복 호출·미설명 누락이 있으면 실패 | 시뮬레이터 중복 제거 off, 모든 입력의 Kafka·DB·업체 횟수 대조 |

동시성 변경은 consumer를 세 개 만들어 파티션을 나누는 방식이다. partition 내 순서는 유지한다. [Spring Kafka 공식 동작](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html). linger는 작은 배치를 모으는 대기 설정이므로 0ms가 일반적으로 최선이라고 결론 내리지 않는다. [Kafka Producer 공식 설정](https://kafka.apache.org/40/configuration/producer-configs/).

**보장 경계:** RECORD ack, 후속 Kafka 발행 ack 대기, DynamoDB 원본 conditional Put·Attempt conditional claim·결과 Update를 유지했다. offset을 일찍 넘기거나 DynamoDB 저장을 생략하는 변경은 하지 않았다. 정상 건당 DB Put 1회·Update 2회도 유지한다.

## 공통 조건과 재현

세 실행 모두 같은 앱 JAR과 시험 도구를 사용하고 실행별 설정·해시·코드 commit을 기록했다. 이전과 같은 로컬 노트북, 단일 Kafka broker, 토픽별 3개 파티션, DynamoDB Local, 앱별 JVM heap 128~512MiB다. 업체 응답 지연은 0ms, 본문 1,009byte, 고객 1개이며 각 실행마다 앱을 새로 시작한다. Kafka/DB volume은 보존하고 시작 시 적체가 없는지 확인한다. 누적 저장량·캐시·JIT·호스트 상태는 완전히 동일하지 않다.

각 실행은 고유/중복 소량 시험 → 10 TPS 60초 워밍업 → 100 TPS 20초 중복 입력 → 50 TPS 180초 → 100 TPS 180초 순서다. 단계가 실패하면 그 실행의 후속 단계는 중단한다. 다음 설정 실행은 직전 적체 해소·증거 보관·정리를 확인한 뒤 별도로 시작한다. [정확한 명령과 도구 설명](15-격리된-성능-PoC-실행과-결과-대조.md).

기계 판독용 전체 결과·설정·구간 분석·원본 해시는 [비교 요약 JSON](성능-측정/2026-09-24-동시성과-발행-대기-비교.json)에 보관한다. 원시 요청/DB/Kafka/지표/자원 자료는 각 실행의 `.poc-results/<runId>/`에 남기고 Git에는 요약을 저장한다.

## 실행과 결과

코드/도구 commit은 세 실행 모두 `1c2b58fe092f69cfe4b0272f7a00e87972c9e5cb`이며 시작 당시 working tree는 clean이었다. 앱 JAR 해시도 동일하다. 앱 시작 로그에서 A는 Consumer 1개에 파티션 3개, B/C는 Consumer 3개에 각 파티션 1개 할당과 Ingress linger 5/5/0을 확인했다.

| 실험 | 동시성 / linger | 실행 ID |
|---|---|---|
| A | 1 / 5ms | `20260924T103522Z-e3363da5` |
| B | 3 / 5ms | `20260924T104455Z-9a21b1bc` |
| C | 3 / 0ms | `20260924T105557Z-9e342587` |

단위는 ms. 인입→접수 저장 시각은 DB의 `updated_at - occurred_at`이며 최종 수신자 전달 시간이나 DB ack 직후 Timer와 같지 않다.

| 실험 | 입력 TPS | 시작 / 응답 기록 | API p95 | 인입→접수 p50 / p95 / p99 | 최대 lag | 판정 |
|---|---:|---:|---:|---:|---:|---|
| A | 50 | 9,001 / 9,001 | 9.45 | 24.30 / 89.29 / 157.72 | 31 | 180초 완료·대조 통과 |
| A | 100 | 3,900 / 3,899 | 8.83 | 11848.39 / 29109.04 / 30653.40 | 1,662 | 약 39.1초 중단·실패 |
| B | 50 | 9,001 / 9,001 | 9.72 | 23.15 / 31.62 / 47.42 | 35 | 180초 완료·대조 통과 |
| B | 100 | 18,001 / 18,001 | 8.58 | 27.23 / 62.40 / 115.49 | 31 | 180초 완료·대조 통과 |
| C | 50 | 9,000 / 9,000 | 9.79 | 18.14 / 28.36 / 53.32 | 30 | 180초 완료·대조 통과 |
| C | 100 | 18,001 / 18,001 | 9.61 | 24.34 / 1728.45 / 3546.03 | 404 | 180초 완료·대조 통과 |

A의 100 TPS는 6회 연속 적체 증가로 중단됐다. 3,900건 모두 DB ACCEPTED·업체 calls=1/effects=1이었지만, 마지막 HTTP 응답 기록 1건이 없어 전체 시험은 실패다. 미기록 응답을 202로 추정하지 않았다. B/C는 각 18,001건 모두 응답·Kafka·DB·업체 대조를 통과했다. 종료 경계의 추가 1건도 포함했다.

100 TPS 20초 중복 입력은 세 실행 모두 2,000개 HTTP 요청·고유 1,000건으로 통과했다. 업체의 중복 제거가 꺼진 상태에서 calls=1/effects=1을 대조했다. 이 단계의 최대 lag는 A 1,001건, B 32건, C 30건이었다.

| 실행 | 소량 고유 입력 / 소량 중복 입력(고유 key) | 워밍업 | 전체 HTTP 시작 / 고유 요청 |
|---|---:|---:|---:|
| A | 10 / 11(6) | 601 | 15,523 / 14,518 |
| B | 11 / 11(6) | 601 | 29,625 / 28,620 |
| C | 11 / 11(6) | 601 | 29,624 / 28,619 |

세 비교 실행의 전체 고유 요청 **71,757건**은 모두 ACCEPTED·외부 호출/효과 1회로 대조됐다. DLT·운영 확인·미설명 데이터 누락·외부 추가 호출은 없었다. 다만 A의 HTTP 응답 기록 미확인 1건은 별도 실패로 유지한다. 정상 시험 대조가 장애 시 무손실·외부 exactly-once를 증명하지는 않는다.

## 구간 지표로 확인한 차이

100 TPS 단계의 Timer 누적 시간 차이 / 호출 수 차이로 구한 평균이다. 입력 전부터 적체 해소 관측까지 포함한다.

| 구간 평균 ms | A: 1 / 5ms | B: 3 / 5ms | C: 3 / 0ms |
|---|---:|---:|---:|
| Ingress 전체 | 11.23 | 11.19 | 7.90 |
| Ingress 저장 | 4.98 | 5.85 | 7.11 |
| Ingress Kafka 발행 | 6.25 | 5.34 | 0.78 |
| Dispatch 전체 | 10.13 | 11.60 | 13.89 |
| Dispatch 선점 | 4.18 | 5.05 | 6.10 |
| 외부 HTTP | 1.71 | 1.59 | 1.70 |
| 접수 결과 저장 | 4.23 | 4.95 | 6.08 |

Consumer별 마지막 commit 이동 평균은 A Ingress/Dispatch 약 5.91/5.92ms, B 약 5.73~5.77/5.00~5.02ms, C 약 5.48~5.57/5.10~5.14ms다. 세 Consumer의 평균을 합산하지 않았으며, Timer와 집계 창이 달라 정확한 한 건 처리 시간으로 더하지 않는다. 개별 값·파티션 할당은 JSON에 보관했다.

A→B에서는 한 건의 Ingress 업무 시간이 비슷하지만 세 파티션을 병렬 처리하면서 적체가 줄었다. **관측 결과는 Consumer 1개의 순차 대기가 주요 제한이라는 가설을 뒷받침한다.** 두 Worker를 함께 늘렸으므로 각각의 기여도를 완전히 분리한 시험은 아니다.

B→C에서는 Kafka 발행 대기가 약 5.34→0.78ms로 줄었다. 그러나 100 TPS 입력 중 약 126초에 lag 105, 131.5초에 404, 139.3초에 30이 관측됐다. C의 토픽별 최대 lag는 Ingress 앞 108, Dispatch 앞 296이며 발생 시각이 다를 수 있다. DB 구간 평균도 증가했다. **linger 변경 자체가 일시 적체를 일으켰는지, 누적 데이터·호스트/DB 상태 영향인지는 이번 순차 실행만으로 확정할 수 없다.** 해당 구간 지표와 자원 자료를 보존했다.

DynamoDB SDK 논리 호출 지표는 정상 요청당 Put 1회·Update 2회를 유지했다. 예를 들어 B/C의 100 TPS 각 18,001건은 Put 18,001회·Update 36,002회였고 일반 실패·조건 불일치·Get은 0회였다. 이는 앱 SDK 호출 계측이며 실제 AWS WCU나 SDK 내부 물리 HTTP 재시도 수가 아니다. 중복 단계에는 조건 불일치·기존 상태 읽기가 별도로 발생한다.

## 채택한 변경과 보류한 변경

- **채택:** 두 Worker의 기본 동시성 1→3. 정상 부하에서 100 TPS 3분 완료와 요청별 대조로 확인했다. 기본값을 바꾼 후 패키지를 다시 빌드했다. 환경변수로 1을 지정하면 이전 조건으로 되돌릴 수 있다. 동일 유효 설정은 B 실행에서 검증했다.
- **보류:** Ingress linger 0ms. 발행 구간은 빨라졌으나 전체 지연 개선이 일관되지 않아 기본값 5ms를 유지한다. 0ms 선택 옵션과 결과는 보존한다.
- **유지:** RECORD 동기 commit·후속 발행 ack 대기·DB 멱등 저장. batch commit이나 비동기 병렬 발송 구조 변경은 이번 범위에 넣지 않았다.

기존 `.env`에서 동시성을 명시했다면 그 값이 기본값보다 우선한다. `.env.example`은 3으로 갱신했고 실제 `.env`는 수정하지 않았다. PoC 도구 기본 동시성은 이전 조건 재현용 1이므로 새 설정 비교는 `--worker-concurrency 3 --ingress-linger-ms 5`를 명시한다.

## 검증 기록과 한계

- 변경 전 패키지 빌드와 Java 단위 시험 42건 통과, 외부 인프라 환경변수 기반 통합 시험 15건은 이번 Maven 실행에서 제외됐다. 이전 단계의 57건 전체 통과 기록과 혼동하지 않는다. 이번에는 위 별도 PoC에서 실제 Kafka·DynamoDB·HTTP 경로를 대조했다.
- Python 대조 시험 8건 통과. 최초 샌드박스 빌드는 Mockito JVM attach 제한으로 실패했고 실행 권한을 확보한 재실행에서 통과했다.
- A 종료 직후 B를 시작하려던 `20260924T104420Z-10bdca24`는 포트 점유 검사에서 실패해 부하를 넣지 않았다. 준비 실패 자료도 보존했다. 기존 프로세스를 강제 종료하지 않고 포트 해제를 확인한 뒤 새 실행 ID로 재시도했다.
- 세 측정 종료 후 적체 해소와 시험 정책 원복을 확인했고, 시험 앱·컨테이너는 종료했다. 데이터·volume·원시 증거는 보존했다.
- 입력률별 단기 정상 시험이다. B의 100 TPS 통과는 최대 처리량·장시간 운영 용량이 아니다. 실제 업체 지연·다중 고객·더 큰 본문·장애 복구는 별도다.
- C도 정합성/완주 기준으로는 통과했다. 다만 현재 도구의 자동 통과 조건에 특정 latency SLO는 없으므로, 통과가 지연 품질까지 만족한다는 뜻은 아니다.
- lag는 샘플 관측값이고 offset 조회는 원자적이지 않다. 적체 해소 시간은 두 번 lag=0 확인까지의 상한이다. 앱·DB·Kafka·부하 도구는 한 호스트를 공유하며 실행 순서와 누적 저장량 차이를 제거한 실험이 아니다.

다음은 채택한 3/5 설정의 반복·더 높은 입력률과 업체 응답 지연 50/200ms 비교다. linger 재평가는 5→0→5 순서 교차 반복과 DB/호스트 지연 관측으로 분리한다. commit 비용을 줄이는 변경에 앞서 중간 실패·재전달·DLT 실패·프로세스 종료 경계에서 원본 보존과 외부 중복 차단을 검증한다. 모니터링 상시 수집·화면·알림의 미구현 범위는 [모니터링 현황](18-모니터링-구현-현황과-구축-순서.md)에 따로 정리했다.
