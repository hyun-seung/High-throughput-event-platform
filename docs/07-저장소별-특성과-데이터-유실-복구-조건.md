# 저장소별 특성과 데이터 유실·복구 조건

검토일: 2026-09-23. 이 문서는 제품의 공식 보장과 프로젝트의 설계 판단을 구분합니다. 운영 구성이 검증됐다는 의미는 아닙니다. 설계 제안은 [ADR-002](adr/ADR-002-저장소-역할과-선택-이유.md), 확인할 요구사항은 [설계 논의 목록](08-함께-결정할-설계-사항.md)을 참고합니다.

적용 범위는 Redis Open Source 7.4, PostgreSQL 17, 로컬 Kafka broker 4.0 및 AWS 관리형 DynamoDB입니다. Redis Cloud/Software나 별도 관리형 서비스의 보장을 OSS 설정에서 추론하지 않습니다. DynamoDB Local은 AWS 서비스의 복제·내구성 보장 검증 수단이 아닙니다. 버전·서비스·토폴로지가 달라지면 근거를 재확인합니다.

프로젝트의 무손실 목표는 **리전 전체 장애를 제외한 범위**로 확정했습니다. [Q3 적용 기준](08-함께-결정할-설계-사항.md#q3-리전-전체-장애를-제외한-무손실-목표)에 저장소별 적용·장애 조합·검증 한계를 기록합니다. 이 목표는 아래 제품 특성을 넘어서는 무조건적 보장을 뜻하지 않습니다.

## 1. 먼저 구분할 용어

| 용어 | 의미 | 이것만으로 보장되지 않는 것 |
|---|---|---|
| 휘발성 메모리 | 전원이 사라지면 내용을 유지하지 못하는 저장 매체 | 프로세스가 메모리를 사용한다고 그 시스템에 디스크 복구 기능이 없는 것은 아님 |
| 영속화 | 디스크 등 지속 저장 장치에 기록 | 최근 성공 응답까지 기록됐는지, 해당 디스크 파괴 후 복구되는지 |
| 내구성 | 성공 처리한 쓰기를 정해진 장애 조건에서 유지 | 모든 사본 동시 파괴, 잘못된 삭제, 외부 HTTP 처리까지의 원자성 |
| 복제 | 여러 사본으로 장애를 견딤 | 비동기 사본이 최신이라는 보장, 삭제·오염 이전 상태로 복구 |
| 백업·PITR | 과거 시점으로 복원 | 최신 성공 응답까지 복원, 즉시 서비스 재개 |
| 원자성 | 관련 변경이 전부 반영되거나 전부 미반영 | 어떤 장애에서도 영구 보존, 서로 다른 시스템까지의 원자성 |
| 일관성 | 동시·연속 작업에서 어떤 값을 관찰할 수 있는가 | 강한 읽기를 한 뒤 다른 Worker가 값을 바꾸지 않는다는 보장 |
| 멱등성 | 같은 논리 요청 반복이 추가 업무 효과를 만들지 않음 | lock만으로 달성, 유한 보존 기록으로 무기한 재처리 보장 |
| RPO | 장애 복구 시 허용하는 데이터 손실 범위 | RPO 0이라도 서비스가 즉시 정상화된다는 보장은 없음 |
| RTO | 서비스 복구까지 허용하는 시간 | 데이터 손실량의 기준과는 별개 |

**설계 판단:** “100% 유실 케이스가 없다”는 무조건적 보장은 이 프로젝트에서 선언하지 않습니다. 성공 응답 시점, 보장할 장애 범위, 보존 기간, 복제와 복원 절차를 명시한 RPO/RTO로 계약해야 합니다. 저장장치에 남는다는 뜻의 비휘발성과 모든 상황의 무손실은 다른 개념입니다.

접수 원본을 복구하는 것과 외부 발송의 중복을 막는 것도 다릅니다. 원본은 복원했지만 발송 완료 기록을 잃었다면 복원 후 재전송이 중복을 만들 수 있습니다. 그러므로 원본·완료 기록·Provider 조회 결과를 함께 대조해야 합니다.

## 2. Redis: 복구 가능하지만 설정과 실패 방식에 따라 다르다

### 2.1 공식 사실 — 로컬 디스크 영속화

| 설정 | 복구 수단 | 손실 가능 구간·제약 |
|---|---|---|
| 영속화 없음 | 살아 있는 사본 또는 외부 원장에서 재생성 | 재기동한 인스턴스 자체에는 복구 로그가 없음 |
| RDB | 특정 시점 snapshot 로드 | 마지막 snapshot 이후 변경은 복구되지 않을 수 있음 |
| AOF `appendfsync no` | OS가 디스크에 반영한 로그 재생 | Redis가 매 쓰기의 fsync 완료를 기다리지 않음 |
| AOF `appendfsync everysec` | 주기적으로 fsync한 로그 재생 | 공식 문서는 일반적인 장애에서 약 1초 분량의 쓰기 손실 가능성을 설명함. 모든 장애의 최대 손실량을 뜻하지 않음 |
| AOF `appendfsync always` | 응답 전 AOF fsync | 로컬 디스크 내구성이 강화되지만 디스크 자체 소실·오래된 replica 승격까지 해결하지 않음 |
| RDB + AOF | 로그 재생과 snapshot 백업 | 구성만으로 리전 재해·실수에 의한 삭제·외부 발송 중복을 해결하지 않음 |

RDB는 상태 snapshot, AOF는 상태를 재구성하는 명령 로그입니다. 복구 파일이 온전하고 필요한 구간이 존재해야 복원할 수 있습니다. `always`는 지연·처리량 비용이 있으므로 `everysec`와 같은 성능으로 간주하지 않습니다. [공식 근거: Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 2.2 공식 사실 — 복제, WAIT, WAITAOF

Redis의 기본 복제는 비동기입니다. primary 성공 응답 직후 replica 반영 전에 primary를 잃으면, 승격된 replica에 해당 쓰기가 없을 수 있습니다. AOF로 primary 디스크에 저장했더라도 새 primary가 그 디스크를 자동으로 이어받는 것은 아닙니다. 복제 연결이 살아 있거나 replica 수가 충분하다는 사실만으로 각 쓰기의 보존을 판단하지 않습니다. [공식 근거: Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

| 기능 | 확인하는 것 | 확인하지 않는 것 |
|---|---|---|
| `WAIT` | 현재 연결의 선행 쓰기를 수신·확인한 replica 수 | replica의 디스크 fsync, 모든 failover에서 그 쓰기를 가진 사본이 승격되는 것 |
| `WAITAOF` | 현재 연결의 선행 쓰기를 AOF에 fsync한 local/replica 수 | 강한 일관성 저장소로의 전환, 확인하지 않은 사본으로의 승격 안전성, 모든 저장장치 동시 소실 |

`WAIT`는 timeout에도 replica 수를 반환하므로 요구 수 이상인지 검사해야 합니다. 공식 문서는 여러 replica가 확인한 쓰기도 failover에서 사라질 가능성이 있으며, `WAIT`가 강한 일관성을 제공하지 않는다고 설명합니다. [공식 근거: WAIT](https://redis.io/docs/latest/commands/wait/)

`WAITAOF`는 Redis 7.2부터 제공됩니다. timeout 시 local/replica fsync 수를 각각 검사해야 하고, 원래 쓰기를 수행한 연결에서 호출해야 합니다. 풀에서 임의의 다른 연결을 가져오면 의도한 쓰기를 확인하는 설계가 아닙니다. blocking이 불가능한 transaction/script 내부에서는 기다리지 않으므로 호출 방식도 중요합니다. 공식 문서는 `WAITAOF` 역시 강한 일관성 저장소를 만들지 않으며 모든 구성원의 fsync를 기다리지 않으면 failover/restart에서 손실이 남을 수 있다고 설명합니다. [공식 근거: WAITAOF](https://redis.io/docs/latest/commands/waitaof/)

**설계 판단:** `WAITAOF`의 조건을 충족하면 특정 사본에 대한 디스크 보존을 더 강하게 확인할 수 있습니다. 이를 “Redis는 항상 유실된다”로 폄하하지도, “어떤 배치에서도 절대 유실되지 않는다”로 확장하지도 않습니다. 확인한 사본의 생존, 승격 규칙, 네트워크 분리 시 쓰기 허용 정책, 저장장치와 운영 절차까지 별도 검증해야 합니다.

### 2.3 TTL, eviction, lock은 다른 문제

Lua script는 실행 중 다른 client 명령이 끼어들지 않게 처리되므로 카운터 검사와 차감 같은 연산에 유용합니다. 대신 긴 script는 서버 작업을 막을 수 있습니다. **설계 판단:** 이 실행 원자성을 디스크·replica 내구성이나 외부 HTTP와의 transaction으로 해석하지 않습니다. [공식 근거: Lua scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/)

메모리 한도 초과 시 eviction 정책에 따라 key가 제거될 수 있습니다. `noeviction`은 자동 퇴거 대신 일부 쓰기를 거절하는 선택이지 무제한 저장이 아닙니다. TTL 만료나 명시적 삭제는 영속화를 켜도 의도대로 적용됩니다. 캐시와 발송 판단 기록을 동일한 eviction 정책으로 관리하면 안 됩니다. [공식 근거: Key eviction](https://redis.io/docs/latest/develop/reference/eviction/)

Redis 공식 분산 lock 문서도 비동기 복제 후 failover로 두 client가 lock을 얻는 예를 설명합니다. lock 만료는 이전 실행자의 중단이나 외부 요청 취소를 증명하지 않습니다. 이 한계는 단순한 Redis `SET NX`를 발송 exactly-once 근거로 사용할 수 없는 이유입니다. [공식 근거: Distributed locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 2.4 프로젝트 판단 — 멱등성 정보 저장 자체를 금지하는 것은 아니다

이 프로젝트에서는 **현재 검토한 OSS Redis 구성을 유일한 발송 완료·미발송 판단 근거로 채택하지 않는 것**을 제안합니다. 근거는 메모리 사용 자체가 아니라 성공 쓰기 유실 가능성, TTL/eviction, 복원 시점 차이와 외부 호출의 원자성 공백입니다.

```text
Provider 발송 성공
→ Redis에 완료 저장
→ 완료 쓰기를 갖지 않은 replica 승격 또는 과거 snapshot 복구
→ 완료 key 없음
→ 미발송으로 판단하여 재전송
→ 실제 중복 발송
```

반대로 외부 호출 전에 Redis에 “완료”를 저장하고 죽으면 발송하지 않았는데 이후 작업을 건너뛸 수 있습니다. 저장 전후 순서만 바꿔서는 해결되지 않습니다. 이것은 다른 DB에도 존재하는 외부 호출과 내부 저장 사이의 공백입니다.

허용할 수 있는 활용 제안:

- 원장에서 다시 만들 수 있는 정책·조회 cache 및 TPS 카운터.
- 내구성 있는 완료 사실에서 파생한 cache. key가 없으면 원장 확인을 수행하고 곧바로 재발송하지 않음.
- 반복 요청을 줄이는 보조 장치. cache의 미확인 `PROCESSING` 기록만으로 Kafka offset을 완료 처리하지 않음.

cache hit만으로 skip하려면 그 값이 내구성 있는 확정 결과에서만 만들어지고, 식별자·보존·버전이 동일하며 원장 복원 후 낡은 cache를 사용하지 않는 조건도 필요합니다. 이 조건이 미확정이면 원장 확인을 생략하지 않습니다.

### 2.5 복구 가능한 Redis의 의미

| 데이터 | 복구 근거 제안 | 복구 중 정책·한계 |
|---|---|---|
| 고객 정책 | PostgreSQL 기준정보 | load/version 검증 전 기본 허용을 할지 차단할지 결정 필요 |
| 조회 cache | DynamoDB 또는 PostgreSQL 확정 상태 | cache miss는 원장 조회로 전환 |
| TPS bucket | 새 bucket 생성 | 이전 token 사용량과 완전히 같은 복구는 아님. 재기동 직후 burst 정책 필요 |
| 확정 월 사용량 | 내구성 있는 사용 이벤트와 집계 checkpoint | raw Kafka 재전달 건수 대신 업무 ID로 중복 제거. replay 끝나기 전 정확한 quota 보장 불가 |
| 발송 완료 여부 | 내구성 있는 실행 상태와 Provider 계약 | Redis 파일만 복구해서 발송 여부를 단정하지 않음 |

외부 원장에서 재생성하는 방법은 **설계 제안**이며 현재 모두 구현돼 있다는 뜻이 아닙니다. 원장 보존 구간, 재생 offset, 진행 중 업데이트 병합, 교체 시점, 재구축 중 요청 정책까지 있어야 실제 복구 절차가 됩니다.

## 3. DynamoDB: 저장하려는 이유와 남는 한계

### 3.1 공식 사실

AWS DynamoDB는 리전 내 여러 AZ에 데이터를 복제합니다. 단일 노드의 AOF와는 장애 영역이 다릅니다. 다만 가용성 SLA를 데이터 유실 확률로 바꾸어 해석하지 않습니다. [공식 근거: Resilience and disaster recovery](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/disaster-recovery-resiliency.html)

성공한 쓰기 응답은 내구성 있게 저장됐음을 뜻합니다. 기본 읽기는 eventual consistency이며, 본 테이블·LSI는 강한 읽기를 선택할 수 있지만 GSI는 그렇지 않습니다. 따라서 GSI에서 작업을 찾았다는 사실만으로 최신 실행 권한을 얻었다고 판단하지 않습니다. [공식 근거: Read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html)

조건부 쓰기는 해당 key의 item을 대상으로 조건이 성립할 때만 변경합니다. 읽고 애플리케이션에서 비교한 뒤 무조건 쓰는 것과 다릅니다. `attribute_not_exists`, 상태와 version 조건으로 원본 중복 생성·동시 claim·낡은 결과 갱신을 제어할 수 있습니다. **프로젝트 판단:** 이 성질이 실행 상태 저장의 핵심 선택 이유이며, 단순히 빠르다는 이유만으로 선택하지 않습니다. [공식 근거: Condition expressions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html)

여러 item을 함께 변경해야 한다면 transaction을 사용할 수 있지만, Kafka 발행이나 Provider HTTP 요청은 그 transaction에 포함되지 않습니다. `TransactWriteItems`의 client token에 의한 멱등 창도 장기 발송 멱등성 기록의 대체물이 아닙니다. [공식 근거: Transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)

### 3.2 최소화를 위해 알아야 할 것

item에는 속성 이름과 값을 포함한 400 KB 제한이 있습니다. **설계 제안:** API payload 상한과 실제 저장 크기를 맞추고, 한 item에 발송 이력을 무한히 추가하지 않습니다. Kafka에는 접수됐지만 DynamoDB에 영원히 저장할 수 없는 입력을 허용하지 않도록 검증·격리 계약이 필요합니다. [공식 근거: DynamoDB constraints](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html)

write 용량은 횟수뿐 아니라 item 크기에 좌우됩니다. `UpdateItem`은 일부 필드만 수정해도 변경 전후 중 큰 item 크기를 기준으로 계산합니다. transaction에는 추가 용량 비용이 있습니다. **설계 제안:** 큰 불변 payload와 자주 변하는 작은 실행 상태를 분리하고, 실패 결과·다음 action처럼 함께 확정되는 필드는 한 write에 합칩니다. API 호출 수, 읽기, 중복·경합, GSI 변경 비용을 포함해 측정합니다. [공식 근거: Read/write operations](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html)

복구 대상만 인덱스 key를 갖도록 하는 sparse GSI가 전체 테이블 scan의 대안입니다. 시간대·bucket별 조회를 설계하되, 인덱스 추가 쓰기 비용과 누락 탐지 방법을 함께 평가합니다. 이는 선택 후보이지 아직 확정된 테이블 설계가 아닙니다. [공식 근거: Sparse indexes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-indexes-general-sparse-indexes.html)

TTL 삭제는 만료 시각에 즉시 실행되는 scheduler가 아닙니다. 만료된 item이 삭제되기 전 읽힐 수 있습니다. **설계 판단:** TTL을 retry 예약 실행이나 정확한 lock 해제 장치로 사용하지 않습니다. 멱등성 기록은 허용된 replay 기간이 끝나기 전에 삭제하지 않습니다. [공식 근거: TTL](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html)

### 3.3 백업·리전 장애·복원

PITR은 활성화가 필요하며 과거 시점의 새 테이블을 복원합니다. 최신 복원 가능 시각은 통상 현재보다 약 5분 이전입니다. **설계 판단:** PITR을 켰다는 사실만으로 재해 시 최신 접수·완료 기록까지 RPO 0이라고 주장하지 않습니다. 복원 시점 뒤의 기록을 보충할 원장과 Provider 대조가 필요합니다. [공식 근거: PITR](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/PointInTimeRecovery_Howitworks.html), [RestoreTableToPointInTime](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_RestoreTableToPointInTime.html)

Global Tables는 MREC와 MRSC를 구분해야 합니다. MREC는 비동기 리전 복제이며 MRSC는 지원 구성에서 RPO 0을 제공합니다. MRSC는 지연·지원 리전 제약이 있고, 검토일 기준 TTL 및 transaction 지원에도 MREC와 차이가 있습니다. **설계 판단:** 리전 간 동시 claim·자동 전환을 단일 리전 조건부 갱신과 동일하게 취급하지 않습니다. DynamoDB만 강화해도 최초 접수 원장인 Kafka가 같은 장애를 견디지 못하면 전체 흐름의 RPO 0은 성립하지 않습니다. [공식 근거: Global Tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html)

## 4. PostgreSQL: 관계형 DB도 구성에 따라 내구성이 달라진다

WAL은 변경 내용을 데이터 페이지보다 먼저 지속 저장하여 crash 후 재적용할 수 있게 합니다. 디스크가 온전한 crash recovery와 디스크 자체를 잃은 뒤 복원은 다른 상황입니다. [공식 근거: WAL](https://www.postgresql.org/docs/17/wal-intro.html)

`fsync=on`과 commit 시점 설정을 확인해야 합니다. `synchronous_commit=off`는 성공 응답한 최근 transaction을 crash 후 잃을 수 있습니다. `synchronous_commit=on`이라도 동기 standby를 지정하지 않으면 원격 사본까지 기다린다는 뜻은 아닙니다. 지정한 동기 standby가 있으면 `on`은 그 사본의 WAL flush를 기다리며, `remote_write`와 `remote_apply`는 각각 대기 지점이 다릅니다. [공식 근거: WAL settings](https://www.postgresql.org/docs/17/runtime-config-wal.html)

기본 streaming replication은 비동기이므로 failover 시 미복제 commit의 손실 가능성을 평가해야 합니다. 동기 복제는 확인할 standby가 없을 때 commit 지연·중단과 맞바꾸는 선택입니다. 서비스 가용성을 위해 자동으로 비동기 모드로 낮추면 최초 RPO 조건도 바뀝니다. [공식 근거: Standby replication](https://www.postgresql.org/docs/17/warm-standby.html)

백업과 연속 WAL archive가 있으면 보존된 구간까지 PITR이 가능합니다. WAL archive 누락·지연이나 backup 소실은 별도 위험이므로 실제 복원 시간을 측정해야 합니다. [공식 근거: Continuous archiving](https://www.postgresql.org/docs/17/continuous-archiving.html)

**프로젝트 판단:** PostgreSQL은 최종 이력, 운영 조회, 기준정보에 적합한 후보이며 실행 원장 역할도 기술적으로 가능합니다. unique constraint와 transaction으로 멱등 기록·업무 결과·outbox를 함께 저장할 수 있습니다. 다만 외부 Provider 호출은 그 transaction 밖에 남습니다. 이미 PostgreSQL을 운영한다는 이유로 무조건 모든 write를 옮기거나, 반대로 고처리량이라는 이유만으로 원천 배제하지 않습니다. workload별 부하·복제·복구 비용을 비교합니다. [공식 근거: Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html)

## 5. Kafka: 최초 접수 원장으로 사용할 때의 조건

`acks=all`은 쓰기 시점의 ISR에 대한 확인이며, `min.insync.replicas`와 복제 배치를 함께 설계해야 합니다. producer idempotence는 producer 재전송 중복을 다루는 기능으로, API 재요청 전체나 Provider 업무 효과의 멱등성을 대신하지 않습니다. [공식 근거: Producer configs](https://kafka.apache.org/40/configuration/producer-configs/)

**버전별 구현 주의(4.0.2 확인):** `min.insync.replicas`만 복제 수보다 높여서는 요구 사본 수를 강제할 수 없습니다. 4.0.2의 `effectiveMinIsr`는 설정값과 실제 복제 수 중 작은 값을 사용합니다. 2026-09-24 로컬 replica=1 시험 토픽에서 min ISR=2 설정 적용 후에도 쓰기 성공을 관측했고 공식 소스로 확인했습니다. 복제 장애 검증은 실제 사본 배치·ISR 감소를 함께 만들어야 합니다. [Apache Kafka 4.0.2 Partition 소스](https://github.com/apache/kafka/blob/4.0.2/core/src/main/scala/kafka/cluster/Partition.scala), [시험 경과](26-업체-결과-웹훅의-인증과-Kafka-접수.md).

Kafka의 전달 보장은 살아 있는 복제본과 올바른 leader·offset 처리 조건에 의존합니다. Kafka transaction으로 입력 offset과 출력 Kafka record를 함께 처리할 수 있지만 외부 DB·HTTP의 원자적 완료까지 포함하지 않습니다. **프로젝트 판단:** Consumer는 업무 완료 또는 내구성 있는 다음 작업 인계 후에 offset을 넘기며, crash 때 재발행되는 이벤트에는 업무 멱등성을 적용합니다. [공식 근거: Kafka design](https://kafka.apache.org/40/design/design/)

시간·용량 retention으로 오래된 segment가 제거될 수 있고 Consumer가 아직 처리하지 못했다는 이유만으로 영구 보존되지 않습니다. **설계 제안:** 접수·Retry·DLT·완료 이벤트 각각의 보존 기간과 archive/replay 경로를 정해야 합니다. lag 경보나 신규 접수 중단만으로 이미 보관 중인 데이터의 삭제를 막을 수는 없습니다. [공식 근거: Topic retention](https://kafka.apache.org/41/configuration/topic-configs/)

## 6. 저장소별 장애 비교

아래는 위 공식 기능을 프로젝트에 적용한 분석입니다. 모든 운영 배치에 대한 무조건적 보장표가 아닙니다.

| 상황 | Redis OSS | AWS DynamoDB | PostgreSQL | Kafka |
|---|---|---|---|---|
| 프로세스 crash, 디스크 온전 | RDB/AOF 반영 시점까지 복구 | 관리형 서비스의 성공 쓰기 내구성 | WAL·commit 설정에 따른 crash recovery | 복제·로그 조건에 따른 재개 |
| 주 저장 노드·디스크 소실 | 살아 있는 사본의 최신성, 승격, backup 필요 | 리전 내 다중 AZ 복제 | 확인된 standby 또는 backup/WAL 필요 | 살아 있는 ISR와 leader 정책 필요 |
| 성공 응답 직후 failover | 비동기 복제 공백 존재, WAIT/WAITAOF도 범위 확인 | 글로벌 MREC/MRSC·리전 범위 구분 | 동기/비동기 및 승격 대상에 따라 다름 | acks·ISR·leader 정책에 따라 다름 |
| 논리적 삭제·오염 | 복제·AOF에도 삭제가 반영될 수 있음 | 복제만으로 복구되지 않음, PITR/backup 검토 | replica에도 반영, backup/PITR 검토 | 삭제·retention·잘못된 기록에 대한 보관·복원 필요 |
| 외부 처리 후 내부 기록 전 종료 | 단독 해결 불가 | 단독 해결 불가 | 단독 해결 불가 | 단독 해결 불가 |

마지막 행은 내부 저장소만으로 외부 중복 0회를 보장할 수 없다는 한계입니다. 이 프로젝트는 외부 조회와 신뢰할 수 있는 외부 멱등성이 없는 조건에서 무응답 재시도·운영 확인·만료 후 조건부 2차 발송을 선택했습니다. 이 업무 정책과 남는 외부 중복 가능성은 [Q6 결정](08-함께-결정할-설계-사항.md#q6-확정-내용과-남은-결정)에, 저장소 장애 시 실제 중단·재개 설계는 [운영 절차](09-저장소-장애-시-중단-범위와-복구-절차.md)에 기록합니다. [공식 근거: AWS idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 7. 현재 로컬 구성과 운영 보장을 혼동하지 않기

[compose.yml](../compose.yml)은 로컬 개발 환경입니다. Redis는 단일 인스턴스에 AOF를 켜며 fsync 정책은 파일에서 별도 지정하지 않습니다. Kafka·PostgreSQL도 단일 인스턴스이고 DynamoDB는 Local입니다. named volume은 컨테이너 교체 시 데이터를 유지하는 수단이며 호스트 디스크·전체 머신 소실에 대한 원격 backup이 아닙니다.

이 구성을 통해 기능과 crash 재처리를 실험할 수 있지만, multi-AZ failover나 리전 재해의 무손실을 입증할 수는 없습니다. 공식 제품 기능, 저장소 설정 파일, 실행 중 실제 설정, 장애 실험 결과를 각각 기록해야 합니다.
