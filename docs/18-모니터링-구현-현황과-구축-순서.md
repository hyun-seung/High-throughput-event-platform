# 모니터링 구현 현황과 다음 구축 순서

기준일: 2026-09-24. 현재는 **앱 계측과 성능 시험 중 수집·대조가 구현된 단계**다. 상시 수집 서버·대시보드·운영 알림이 구축된 상태는 아니다. 이미 사용하는 지표의 이름과 조회 방법은 [성능 지표 문서](14-성능-지표와-시뮬레이터-관측-방법.md), 파일 수집 방식은 [PoC 실행 문서](15-격리된-성능-PoC-실행과-결과-대조.md)를 따른다.

## 무엇을 볼 수 있나

| 대상 | 구현·확인한 내용 | 현재 한계 |
|---|---|---|
| API | HTTP 상태·지연, Kafka 발행 ack 시간 | API 202는 최종 발송 완료가 아님 |
| Ingress | 원본 저장·후속 발행·전체 listener 시간, 처리 중 실행 수, DLT 성공/실패 | offset commit 대기는 listener 시간 밖이므로 Kafka client 지표를 함께 봄 |
| Dispatch | claim·외부 HTTP·결과 저장 시간, 신규 접수·중복 skip·운영 확인 관측 | 결과 웹훅·TCP 2차·고객 통지는 아직 업무 구현과 계측이 없음 |
| DynamoDB | SDK 작업별 횟수·지연·일반 실패·조건 불일치 | 물리 HTTP 재시도 횟수, 실제 AWS 용량·throttling 대시보드는 없음 |
| Kafka | client commit 지연 등 자동 지표, PoC에서 committed offset 기준 적체·가장 오래 기다린 record 나이 수집 | broker/exporter 상시 수집 없음. client fetch lag와 업무 완료 적체를 구분해야 함 |
| 앱 자원 | JVM·프로세스 지표, PoC에서 CPU/RSS와 Docker 자원 기록 | 시험 외 시간의 중앙 장기 보관 없음 |
| 업체 시뮬레이터 | key별 호출·처리 효과 수, 중복 제거 on/off, 응답 지연 | 메모리 관측이고 실제 업체 조회 기능이 아님 |
| 정합성 | 시험 요청별 Kafka·DB·업체 증거 대조 | 운영 전체의 상시 대사·복구 도구는 없음 |

앱 네 개에 `/actuator/prometheus`와 health가 있다. 관리 서버는 loopback에 바인딩하고 API에는 JWT 인증을 유지한다. 지표는 프로세스 재시작 시 초기화되므로 멱등성 원장이나 유실 판정 근거로 사용하지 않는다. 요청 ID·고객 ID를 label로 추가하지 않는다.

## 이번 성능 개선에 어떻게 사용했나

1. API 응답 시간과 요청별 최종 저장 시각 차이를 비교해 접수와 처리 지연을 구분했다.
2. Kafka group committed offset을 기준으로 주된 적체가 Ingress 앞에 있음을 찾았다.
3. Ingress 저장·Kafka 발행 시간과 client commit 대기를 확인해 건별 순차 I/O 대기를 병목 후보로 좁혔다.
4. 동시성과 발행 대기 설정을 나눠 변경하고 같은 요청 크기·입력률로 비교했다. 결과는 [동시 처리와 발행 대기 비교](17-워커-동시-처리와-발행-대기-성능-비교.md)에 남긴다.
5. 성능 지표가 좋아져도 요청별 DB·업체 대조가 실패하면 통과시키지 않는다.

## 다음 구축 순서

아래는 **미구현 작업 목록**이다. 실제 설정·화면·알림이 존재한다고 해석하지 않는다.

1. Prometheus 상시 수집과 Grafana 대시보드: API 입력/오류, 신규 업체 접수 TPS, 인입→접수 지연, 구간별 지연, consumer별 commit 지연, JVM/자원을 한 화면에 연결한다. Kafka group committed lag 수집도 상시화한다.
2. 장애 알림: 처리량이 입력을 못 따라가는 지속 적체, 가장 오래된 대기 시간, 처리 정지, DLT 인계 실패, 운영 확인 발생, DB/Kafka 오류, 수집 자체 실패를 구분한다. 임계값·유지 시간은 정상·장애 시험으로 정하고 발송 채널은 별도 연결한다.
3. 운영 조회: REVIEW_REQUIRED의 실제 미해결 건수·발생 시각·만료까지 남은 시간·조치 결과를 조회한다. 현재 counter는 관찰 횟수이므로 고유 미해결 건수로 쓰지 않는다.
4. 중앙 로그·요청 추적: deliveryId/attemptId와 Kafka partition/offset으로 로그를 연결한다. 본문·토큰은 수집 대상에서 제외한다. 분산 tracing은 필요한 구간과 샘플링을 정해 추가한다.
5. 최종 상태·기한 계측: 결과 웹훅, TCP 2차, 재시도, 업무 만료, 고객 결과 통지가 구현될 때 단계별 성공/실패/지연을 추가한다.

현재 loopback 관리 포트를 Docker의 Prometheus에서 바로 읽을 수 있다고 가정하면 안 된다. 배포 형태에 맞는 접근 경로와 API 지표 인증 방식을 먼저 구성해야 한다. 모니터링을 위해 관리 포트 전체를 무인증 공개하지 않는다. 목표 무손실·기한 내 결과 전달은 대시보드만으로 충족되지 않으며, 저장·복구·만료 처리와 장애 검증이 필요하다.
