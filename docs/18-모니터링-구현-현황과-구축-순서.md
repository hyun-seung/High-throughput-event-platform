# 모니터링 구현 현황과 다음 구축 순서

> 초기 관측 현황 기록입니다. 현재 화면·수집 범위는 [19 대시보드 안내](19-그라파나-대시보드-실행과-PPT-항목-대응.md), 전체 업무 구현 상태는 [01 진행 현황](01-현재-구현-상태와-남은-작업.md)을 봅니다. 아래 “TCP·웹훅 업무 미구현” 등의 표시는 작성 당시 기준입니다.

기준일: 2026-09-24. 현재는 **앱 계측·성능 시험 대조에 더해 로컬 Prometheus·Grafana 7개 화면·Loki 로그·11개 경보 규칙을 실행하는 단계**다. 운영 환경의 고가용성 수집·외부 알림 전달은 후속이다. [대시보드 실행과 PPT 대응](19-그라파나-대시보드-실행과-PPT-항목-대응.md)에 화면·실행법·검증·한계를 정리했다. 이미 사용하는 지표의 이름과 조회 방법은 [성능 지표 문서](14-성능-지표와-시뮬레이터-관측-방법.md), 파일 수집 방식은 [PoC 실행 문서](15-격리된-성능-PoC-실행과-결과-대조.md)를 따른다.

## 무엇을 볼 수 있나

| 대상 | 구현·확인한 내용 | 현재 한계 |
|---|---|---|
| API | HTTP 상태·지연, Kafka 발행 ack 시간 | API 202는 최종 발송 완료가 아님 |
| Ingress | 원본 저장·후속 발행·전체 listener 시간, 처리 중 실행 수, DLT 성공/실패 | offset commit 대기는 listener 시간 밖이므로 Kafka client 지표를 함께 봄 |
| Dispatch | claim·외부 HTTP·결과 저장 시간, 신규 접수·중복 skip·운영 확인 관측 | 결과 웹훅·TCP 2차·고객 통지는 아직 업무 구현과 계측이 없음 |
| DynamoDB | SDK 작업별 횟수·지연·일반 실패·조건 불일치 | 물리 HTTP 재시도 횟수, 실제 AWS 용량·throttling 대시보드는 없음 |
| Kafka | client commit 지연 등 자동 지표, PoC에서 committed offset 기준 적체·가장 오래 기다린 record 나이 수집 | 읽기 전용 collector가 10초마다 offset·대기 시간을 수집. broker 내부 지표는 후속. client fetch lag와 업무 완료 적체를 구분해야 함 |
| 앱 자원 | JVM·프로세스 지표, PoC에서 CPU/RSS와 Docker 자원 기록 | 로컬 Prometheus 7일/1GB 보관 설정. 운영 중앙 수집은 후속 |
| 업체 시뮬레이터 | key별 호출·처리 효과 수, 중복 제거 on/off, 응답 지연 | 메모리 관측이고 실제 업체 조회 기능이 아님 |
| 정합성 | 시험 요청별 Kafka·DB·업체 증거 대조 | 운영 전체의 상시 대사·복구 도구는 없음 |

앱 네 개에 `/actuator/prometheus`와 health가 있다. 기본 개발 실행의 관리 서버는 loopback에 바인딩하고 API에는 JWT 인증을 유지한다. 별도 모니터링 Compose에서는 Docker 내부에서만 관리 포트에 접근하고 API는 JWT relay로 수집한다. 지표는 프로세스 재시작 시 초기화되므로 멱등성 원장이나 유실 판정 근거로 사용하지 않는다. 요청 ID·고객 ID를 label로 추가하지 않는다.

## 이번 성능 개선에 어떻게 사용했나

1. API 응답 시간과 요청별 최종 저장 시각 차이를 비교해 접수와 처리 지연을 구분했다.
2. Kafka group committed offset을 기준으로 주된 적체가 Ingress 앞에 있음을 찾았다.
3. Ingress 저장·Kafka 발행 시간과 client commit 대기를 확인해 건별 순차 I/O 대기를 병목 후보로 좁혔다.
4. 동시성과 발행 대기 설정을 나눠 변경하고 같은 요청 크기·입력률로 비교했다. 결과는 [동시 처리와 발행 대기 비교](17-워커-동시-처리와-발행-대기-성능-비교.md)에 남긴다.
5. 성능 지표가 좋아져도 요청별 DB·업체 대조가 실패하면 통과시키지 않는다.

## 추가로 구현한 관측

Grafana는 PPT의 통합 관제·서비스·업체·고객·오류코드·인프라·메시지 추적을 제공한다. Kafka stale 관측 숨김, DB backend 연결 경보, Redis 제한 우회·판단 지연, 고객별 로그 TOP, 메시지 단계 audit 로그를 추가했다. 고객·메시지 ID는 Prometheus label에 넣지 않는다. DDB 모니터링용 Scan·추가 쓰기도 없다.

Prometheus 경보는 수집 실패·지속 적체·최장 대기·DLT 인계 실패·운영 확인·DDB 오류·접수 지연·Redis/PG 연결 실패·Redis 제한 우회를 평가한다. 대시보드 표시는 가능하지만 외부 알림 채널은 연결하지 않았다.

## 다음 구축 순서

1. 모니터링 동시 실행 검증: 50/100 TPS 각 3분의 완주·정합성은 통과했다. Kafka 4.0.2 패치 후 같은 부하에서 데이터·로그 검사를 통과했다. 다만 100 TPS 접수 저장 p95 2.23초·최대 lag 292로 일시 정체 분석이 먼저다. [재검증 결과](21-카프카-패치와-성능-재검증.md). 수집 on/off 비용 비교는 별도다.
2. 운영 경보 전달: Alertmanager와 전달 채널, 담당자·임계값·반복 억제를 정하고 실제 장애 시험으로 검증한다.
3. 운영 상태 조회: REVIEW_REQUIRED의 고유 미해결 건수·발생 시각·만료까지 남은 시간·조치 결과를 조회한다. 로그 관측 횟수를 대체 원장으로 쓰지 않는다.
4. 최종 상태·기한 계측: 결과 웹훅, TCP 2차, 재시도, 업무 만료, 고객 결과 통지가 구현될 때 단계별 성공/실패/지연을 추가한다.
5. AWS·컨테이너 인프라: MSK/MemoryDB/RDS/EKS·AZ 지표와 중앙 수집의 가용성·접근 제어를 연결한다. 장애 이력 이후 MTTD/MTTR을 계산한다.

현재 로컬 구성이 다중 AZ 무손실·기한 내 고객 결과 전달을 보장하지는 않는다. 저장·복구·만료 구현과 장애 검증을 계속해야 한다.
