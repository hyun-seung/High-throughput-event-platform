# 요구사항과 전체 설계

기준: 2026-10-08. 현재 구현 상태는 [진행 현황](01-현재-구현-상태와-남은-작업.md), 정상·실패·복구 경로는 [케이스별 Call Flow](53-신규-메시지-케이스별-Call-Flow.md)에 기록합니다.

## 용어 기준

업무 대상은 **메시지**, 제품은 **메시징 서비스**입니다. 고객이 요청에 넣는 `messageId`와 내부에서 발급하는 `clientMsgId`는 서로 다릅니다. `clientMsgId`는 최초 접수, 업체 발송·웹훅, 저장소 이력, 과금 대상 기록에 공통으로 쓰는 실행 ID입니다. 요청 입구마다 별도 `traceId`를 발급해 로그를 추적합니다. Kafka에 실리는 단위는 레코드라고 부릅니다.

## 접수와 참조 데이터

`MSG-RECEIVE-API`는 JWT에서 고객 ID를 확인하고 Redis의 10초 TPS·`messageCategory`별 월 Quota를 원자적으로 증가·판정합니다. 이후 본문·고객 중복을 확인하고 DynamoDB `ORIGIN`을 조건부로 저장한 뒤 `message.received.v1`에 직접 발행합니다. Kafka 발행 실패·응답 불명확은 별도 발행 복구 앱이 ORIGIN을 읽어 같은 `clientMsgId`로 재발행합니다. API는 계약 테이블을 조회하지 않습니다.

요청 본문의 `messageId`는 UTF-8 최대 40바이트이며, `recipientNumber`, `messageCategory`(`GENERAL`, `NOTI`, `ADV`, `ALERT`), `payload`, 선택적 `secondarySendPayload`를 받습니다. `clientMsgId`는 하이픈 없는 UUID 32자리이고 업체 필드명도 `clientMsgId`입니다. 2차 전문이 없으면 1차 실패가 최종 실패가 됩니다. `messageType`의 별도 값은 아직 정하지 않았습니다.

`PRE-SEND-MANAGER`가 계약·발송 정보를 조회합니다. 계약은 PostgreSQL CDC로 Redis에 갱신하며 Redis 누락 시 PostgreSQL을 조회합니다. 전화번호별 통신사도 CDC Redis 캐시에서 읽고 매핑이 없으면 SKT로 시작합니다. 계약 없음·비활성·만료 등 발송 불가라도 2차 전문이 있으면 2차 TCP 가능 여부를 판단합니다.

## 발송과 결과

PRE-SEND-MANAGER는 통신사별 HTTP 명령 토픽으로 같은 규격의 전문을 보냅니다. `MSG-SKT-SENDER`, `MSG-KT-SENDER`, `MSG-LGU-SENDER`는 하나의 JAR을 서로 다른 URL·Pod·소비 그룹으로 실행합니다. 각 Sender는 Redis와 DynamoDB STEP 상태로 시도 중복을 제어합니다. 업체 HTTP 200을 받으면 시간·응답을 DynamoDB에 기록하고 Kafka 결과는 발행하지 않습니다. 이 경우 업체 웹훅이 1차 호출의 최종 결과입니다. 명시적 비-200 실패와 5초 무응답은 Sender가 `MSG_RESULT`에 직접 발행합니다.

업체 웹훅은 `WEBHOOK-RECEIVE-API`가 1~100건을 요청당 Kafka 1레코드로 `MSG_RESULT`에 발행합니다. 각 결과에는 `clientMsgId`·`status`가 있고 실패라면 숫자 5자리 `error.code`와 `error.message`가 있습니다. API는 Kafka 저장 확인 후 응답하며, 개별 메시지 판단은 `MSG-RESULT-MANAGER`가 수행합니다. `66001`은 SKT → KT → LGU+ 중 미시도 통신사로 이동하고 세 곳을 모두 시도하면 `40002`로 1차 실패를 확정합니다. `66002`와 HTTP 무응답은 실패 판단 1분 뒤 같은 통신사로 최초 발송 이후 최대 3회 재시도하고, 소진하면 각각 `40001`·`40003`입니다. 나머지 6만 대역 실패는 1차를 닫습니다.

1차 실패 뒤 `secondarySendPayload`가 있으면 `MSG-TCP-SENDER`로 인계합니다. TCP는 현재 임시 길이+JSON 전문으로 발송하고 같은 호출의 거의 즉시 응답을 `MSG_RESULT`에 보냅니다. 실제 TCP 규격은 업체 규격서 확인 후 교체해야 합니다. 우리 서비스 오류는 1만~5만 대역, 1차 업체는 6만 대역, 2차 업체는 7만 대역을 사용합니다. 상세는 [오류 코드 계약](54-메시징-오류-코드와-결과-인계-계약.md)을 따릅니다.

## 완료와 고객 통지

결과 Manager는 최종 결과를 `MSG-RESULT-FINALIZED`에, 고객 웹훅 대상은 `WEBHOOK-SEND`에도 인계합니다. `MSG-COMPLETE-MANAGER`는 `TBL_MSG_HIST`에 최종 메시지당 1건을 저장하고 **1차 최종 성공**에 한해 `TBL_CDR_HIST`에 `clientMsgId`당 최대 1건의 과금 대상을 기록합니다. 금액 산정은 하지 않습니다. SQL 저장과 발행 확인 후 DynamoDB 처리 원본을 정리하며 삭제 실패에는 TTL 경로를 둡니다. `MSG-WEBHOOK-SENDER`는 같은 고객 최대 100건을 묶어 고객 URL로 발송하고 `TBL_WEBHOOK_HIST`에 결과를 기록합니다. 고객 웹훅에는 별도 토큰을 쓰지 않습니다.

업체가 같은 `clientMsgId`의 발송 중·성공 중복을 약 2시간 차단한다고 파악했지만 보장 조건은 실제 계약 확인이 필요합니다. 실패 후 같은 ID는 재사용합니다. 업체 웹훅에 회차 식별자가 없으므로 이전 시도의 늦은 웹훅이 다음 시도의 결과와 겹칠 위험이 남습니다. 이미 확정한 최종 결과는 늦은 웹훅으로 바꾸지 않습니다.
