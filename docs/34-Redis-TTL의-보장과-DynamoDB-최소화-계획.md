# Redis TTL의 보장과 DynamoDB 최소화 계획

## 1. 적용 방향

사용자 요구는 DynamoDB 최소화, 리전 전체 장애를 제외한 유실 방지, 1차 HTTP·2차 TCP 외부 발송의 멱등성입니다. Redis를 사용할 수 있는 부분은 적극적으로 사용하되, Redis 전체 데이터가 사라져도 업무를 잃거나 발송 허가가 새로 생기지 않도록 합니다.

- **Redis:** 만료·재시도 대상의 빠른 검색, 원장에서 재구축 가능한 캐시, TPS/Quota 제어.
- **DynamoDB:** 현재 발송 원장 안에서 원자적으로 판단해야 하는 선점·횟수·기한·결과·완료 보호. 중간 쓰기는 병합하거나 제거합니다.
- **PostgreSQL:** 이력, 고객 결과 웹훅 묶음·재전송, 원본 정리 예약. 기존처럼 DynamoDB 추가 사용 없이 유지합니다.
- **Kafka:** 최초 접수와 단계 인계. Redis 등록 성공만으로 유실 방지 인계를 완료하지 않습니다.

여기서 ‘DynamoDB 유지’는 **현재 DDB 발송 원장을 유지하는 아키텍처에서**의 결정입니다. 다른 내구성 DB로 원장 전체를 옮기는 것은 기술적으로 가능하지만, 완료 여부만 Redis로 옮기는 것과는 다른 설계 변경입니다.

## 2. TTL을 신뢰한다는 말의 범위

Redis TTL은 캐시 유효 기간에 사용할 수 있습니다. 만료 판정이 임의로 부정확하다는 의미로 설명하면 안 됩니다. 공식 문서상 만료 정확도·접근 시 만료, 만료 알림의 지연·손실은 서로 다른 보장입니다. [직접 인용과 공식 근거](07-저장소별-특성과-데이터-유실-복구-조건.md#231-redis-ttl은-무엇을-보장하는가--2026-09-25-보강)에 분리했습니다.

| 사용 예 | 판단 | 이유 |
|---|---|---|
| 정책/조회 캐시를 TTL로 정리 | 사용 가능 | cache miss는 원장 조회로 복구 |
| TPS 카운터·보조 완료 캐시의 수명 제한 | 사용 가능 | 카운터 손실 정책 또는 원장 fallback이 있음 |
| TTL 만료 알림을 부가 신호로 활용 | 가능하지만 필수 경로로 삼지 않음 | 놓쳐도 내구성 일정에서 재발견해야 함 |
| 키가 없으면 요청을 EXPIRED로 확정 | 사용하지 않음 | 미등록·퇴거·복구 손실과 정상 만료를 구별 못함 |
| 만료 알림만으로 2차 발송 | 사용하지 않음 | 성공 웹훅과 경합·알림 누락·중복 실행을 처리할 내구성 조건이 없음 |
| 멱등 기록을 Redis에만 두고 TTL로 제거 | 사용하지 않음 | 오래된 요청의 재전달이 새 발송이 될 수 있음 |

정확한 TTL 판정은 정확한 시각의 작업 실행 완료를 뜻하지 않습니다. Redis·DynamoDB 어느 쪽도 워커 backlog, 네트워크 지연, 고객 서버 장애까지 없애지는 못합니다.

## 3. 어느 구간을 어디에 둘 것인가

| 구간 | Redis 활용 | 유지할 내구성 근거 | 줄일 대상 |
|---|---|---|---|
| API 최초 접수 | 기존 TPS/Quota 유지 | Kafka ack | DDB 쓰기는 이미 0회 |
| 요청 원본·동일 키 내용 검증 | 검증된 원본/fingerprint 캐시 후보 | 현재 META의 원본·최초 시각·fingerprint | 반복 원본 읽기, 큰 원본과 제어 정보 결합 |
| 1차·2차 최초 선점 | 같은 요청의 짧은 동시 접근을 완화하는 보조 용도만 | **DDB 완료 확인과 Attempt 생성의 원자성** | 이미 존재하는 Attempt에 대한 불필요한 최초 생성 시도 |
| 재시도 대기 | **Sorted Set으로 실행 예정 시각 검색** | **DDB next_attempt_at·횟수·deadline·version 및 호출 전 선점** | 대기 중 재전달·실패 트랜잭션·반복 Get |
| 만료 대기 | **Sorted Set으로 기한 도래 요청 검색** | **DDB 원래 deadline·단계·최신 상태의 조건부 전환** | 고빈도 GSI polling. 기한은 기다리는 동안 계속 쓰지 않음 |
| 1차 만료 후 2차 전환 | 실행 후보 전달 | **DDB fallbackAllowed·고정 업체·2차 deadline·2차 선점** | 만료 판단→경로 고정→선점의 중간 변경 병합 |
| HTTP/TCP 접수 응답 | 확정 상태 조회 캐시 후보 | **DDB 접수/실패/운영 확인 상태** | 응답 저장 자체를 캐시로 대체하지 않음 |
| 업체 웹훅 결과 | 처리 완료 사실의 캐시 후보 | **DDB 회차·상태·version을 검증하는 결과 반영** | 별도 Receipt marker 구조·동일 정보의 중복 조회 |
| 최종 만료·최종 결과 확정 | 확정 결과 캐시 | **DDB 완료 보호+내구성 최종 이벤트 인계** | 별도 만료 저장 후 다시 닫는 중간 Update |
| 완료된 요청의 반복 유입 | **검증된 완료 캐시로 DDB 접근 생략 후보** | **작은 DDB 완료 META 계속 유지** | 반복 Put 실패·Get/선점 시도 |
| 최종 이력·고객 웹훅 | 모니터링/조회 캐시만 후보 | PostgreSQL 이력·고정 batch·횟수·lease | 이미 DDB 0회. SQL 원장을 Redis로 교체하지 않음 |
| 완료 원본 정리 | 정리 후 캐시 갱신/제거 | SQL 정리 예약 + DDB 조건부 정리 | 큰 META 갱신 비용·정리의 중복 조회 |

외부 호출 뒤 결과 저장 전 중단의 불명확성은 Redis 선택으로 해결되지 않습니다. 기존 무응답 재시도·운영 확인·만료 정책과 외부 중복 가능성의 경계는 그대로입니다.

## 4. Redis 일정 관리의 구체적인 연결

Sorted Set은 값을 score 순으로 관리하고 범위 조회할 수 있습니다. [Redis 공식 Sorted Set 설명](https://redis.io/docs/latest/develop/data-types/sorted-sets/). 이것을 durable scheduler 자체로 간주하지 않고 DDB 일정의 검색용 사본으로 사용합니다.

```text
DDB: 선점/결과/예약 저장과 같은 쓰기에 원래 deadline·next_attempt_at 보관
  ├─ Redis: deliveryId / route / task kind / version, score=실행 예정 시각
  └─ DDB GSI: Redis 누락을 찾을 복구 경로 유지

Redis에서 due 후보 검색
  → DDB 현재 상태·버전·예정 시각 조건 확인
  → 상태 전환 / 발송 선점 성공
  → 필요한 외부 호출 또는 최종 인계

Redis 누락·장애
  → DDB GSI 주기 점검 또는 대체 경로로 재발견
  → 같은 조건부 전환으로 수렴
```

### 쓰기 순서와 누락 방지

1. 업무 상태·재시도 횟수·기한을 **먼저 DDB에 확정**합니다. 기존 업무 쓰기에 필요한 시각이 있으므로 Redis 등록을 위해 DDB outbox 항목을 무조건 하나 더 만들지 않습니다.
2. 이후 Redis에 후보를 등록합니다. Redis 등록 실패 또는 등록 전 종료는 DDB GSI 점검이 복구합니다. Redis 성공 여부가 API의 Kafka 접수 보장을 대체하지 않습니다.
3. 후보는 DB의 저장된 절대 시각에서 만듭니다. Redis 재구축 시 현재 시각+3시간/4시간으로 계산하지 않습니다. 2차는 최초 1차 결과 판단 시각 기준을 유지합니다.
4. Redis 후보가 오래됐거나 중복됐어도 DDB의 상태·version·기한 조건을 통과한 실행자만 처리합니다. DDB 확인 실패를 발송 허가로 해석하지 않습니다.
5. 후보를 미리 pop한 뒤 워커가 죽어도 GSI 점검에서 복구해야 합니다. 재전달용 Redis 처리 중 목록을 추가할 수 있지만 그것만으로 유실 방지를 주장하지 않습니다. 최초 구현은 업무 commit 전 후보를 없애지 않는 방식을 우선 검토합니다.
6. 후보 삭제 시 새 예약을 지우지 않도록 version을 구분합니다. 오래된 버전이 남아도 DB 조건으로 무시하고 정리합니다. Sorted Set 키 전체에 임의 TTL을 걸어 활성 일정을 함께 없애지 않습니다.

### Redis가 정상으로 보여도 복구 점검은 계속

Redis 연결 성공이 목록의 완전성을 보장하지 않습니다. failover·flush·부분 복구·DDB commit 후 등록 전 종료는 조용히 후보를 누락시킬 수 있으므로 **Redis 장애 시에만 DDB를 조회하는 설계로는 부족합니다.** 평상시에도 GSI 복구 점검을 유지합니다.

전체 Redis 소실 시 신규 변경은 새 목록에 반영하고, 기존 대상은 GSI의 due 조회로 재발견합니다. 필요하면 제한된 미래 구간까지 목록을 다시 채웁니다. 페이지 커서·처리량 제한·잘못된 작업 건너뛰기·동시 신규 등록의 version 검증을 적용하고, 전체 테이블 Scan을 정상 복구 방식으로 만들지 않습니다.

GSI는 최종적 일관성입니다. 한 번 조회에서 안 보였다고 작업이 없다고 단정하지 않고 겹치는 구간을 재조회합니다. 실제 결정은 본 테이블의 조건부 쓰기로 처리합니다. [DynamoDB 읽기 일관성](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html).

### 읽기를 줄이는 대가

현재 기본 tick의 16개 shard Query를 낮은 빈도의 복구 점검으로 바꾸면 유휴/정상 시 DDB 읽기가 줄 수 있습니다. 하지만 GSI 자체를 유지하는 동안 일정 갱신에 따른 **GSI 쓰기 비용은 남습니다.** Redis 쓰기·조회·운영 비용도 추가됩니다.

점검 주기를 길게 하면 누락된 만료 후보의 발견이 늦어집니다. 지연은 점검 주기뿐 아니라 GSI 반영, 페이지 순회, 대기열, 워커 처리 시간에 영향을 받습니다. Redis 오류 시 DB 경로를 빠르게 활성화하더라도 조용한 누락의 최악 지연을 없애지는 못합니다. 만료 후 고객 수신을 정확히 그 시각까지 보장한다는 표현을 하지 않습니다. 지연 허용치는 임의로 확정하지 않고 실제 누락·backlog 시험 결과와 함께 다룹니다.

재시도 대기 중 Kafka offset을 넘기는 변경도 Redis 등록만으로 하지 않습니다. DDB에 재시도 일정과 복구 가능한 원본이 확정되고, GSI 복구 경로가 켜져 검증된 경우에만 내구성 인계 완료로 처리하도록 설계합니다. 현재 listener 재전달 방식과 함께 비교해야 합니다.

## 5. 완료 캐시의 조건

완료 캐시는 같은 요청의 불필요한 DDB 접근을 줄이는 후보입니다. 다음 조건을 모두 지켜야 합니다.

- 내구성 있는 완료 확정 이후에만 생성합니다. 접수 성공 ACCEPTED나 PROCESSING을 전체 완료로 캐시하지 않습니다.
- deliveryId, 최초 requested eventId, 요청 fingerprint 버전·값, 완료 eventId, 복원 세대를 포함합니다. fingerprint 확인 없이 동일 키라는 이유로 다른 내용의 요청까지 성공 처리하지 않습니다.
- **최초 적용은 작은 META로 정리까지 끝난 완료 사실**로 범위를 제한하면 불변성을 확인하기 쉽습니다. TTL은 캐시 보관 기간이며 DDB 완료 기록 보관 기간이 아닙니다.
- cache miss·오류·불일치는 DDB 원장 확인으로 돌아갑니다. miss를 미발송으로 간주하지 않습니다.
- DB 복원·환경 전환 시 캐시 namespace/세대를 바꾸거나 전부 무효화합니다. 과거 원장과 미래 캐시가 섞이면 실제 처리되지 않은 건을 완료로 건너뛸 수 있습니다.
- 변경 가능한 진행 상태의 캐시 hit만으로 Kafka offset을 완료하지 않습니다.

이 캐시는 중복 비율이 높을 때 이득이 있고, 첫 정상 요청의 쓰기 횟수를 줄이지는 않습니다. Redis 미사용/장애에도 결과가 같아야 합니다.

## 6. DynamoDB 쓰기·읽기 최소화 순서

| 순서 | 변경 | 감소 대상과 범위 | 보존할 조건 |
|---|---|---|---|
| 1 | 종료 가능한 흐름에서 `releaseMeta`를 최종화 REMOVE에 통합 | 이전 계측과 같은 terminal-first 순서에서는 정상 8→7 성공 API, 14→13항목 후보 | 이미 앞선 tick에서 색인을 해제했다면 절감은 없음. 진행 중 원본의 반복 복구 방지는 유지 |
| 1 | 2차가 terminal이면 `waitForSecondary` 생략 | 해당 종료 순서에서 Update 1회 후보 | 진행 중 2차의 대기 시각 고정은 유지 |
| 1 | 기존 Attempt의 재시도 경로를 직접 판정 | 최대 대표 경로의 의도된 실패 트랜잭션 6회 및 대기 반복 비용 감소 후보 | 처음 생성할 때 완료 검사+선점 원자성 유지. 정상 첫 호출에 조회를 추가하는 비용도 비교 |
| 1 | 원본·최종화 조정·정리의 중복 Get/Query 제거 | 읽기 호출·payload 전송 감소 | 조회 결과를 무조건 신뢰하지 않고 최종 쓰기 조건 유지 |
| 2 | Redis due 목록과 평상시 GSI 누락 점검 연결 | 고빈도 검색과 재시도 대기 조회 감소 | GSI·원장 일정·누락 복구 유지. Redis 등록으로 쓰기 2중화의 원자성을 주장하지 않음 |
| 2 | 검증된 완료 캐시 연결 | 완료 요청의 반복 DDB Put/선점 실패 및 Get 감소 | 동일 내용 검증·복원 세대·miss fallback |
| 3 | 최종 만료와 최종화의 같은 Attempt Update 병합 | 별도 만료 저장 후 닫기의 중간 Update 1회/적용 단계 후보 | deadline·상태·version 조건, FINAL 생성·완료 보호와 원자 처리 |
| 3 | 1차 만료·2차 경로 고정·2차 최초 선점 병합 | 여러 API 및 같은 부모 항목의 중간 수정 감소 후보 | fallbackAllowed, 최초 판단 시각, 업체 고정, 완료 확인, 단일 2차 선점. 외부 호출은 commit 후 |
| 4 | 큰 BODY와 작은 제어 항목 분리 | 업데이트/조건 확인의 용량 비용 감소 후보 | 생성/삭제 인계·복구·이관. 항목 수나 초기 API는 늘 수 있음 |
| 4 | Receipt marker와 FINAL 구조 축소 | 개별 Put·삭제·트랜잭션 범위 감소 후보 | 업체 receiptId 전역 충돌 검사 유지 여부, 이전 회차 replay, 후속 인계 복구 |

앞의 개선을 서로 독립적인 절감량처럼 전부 더해 최종 횟수를 예고하지 않습니다. 실행 순서·원자성 경계가 바뀌기 때문입니다. AWS는 부분 Update에도 item 전체 크기를 반영하며 트랜잭션에 추가 용량을 요구하므로 API 감소와 과금 감소도 구분합니다. [DynamoDB 용량 산정](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html).

### 없애지 않을 보호 장치

- 외부 1차·2차 호출 전의 내구성 선점과 완료 여부 검사.
- 재시도 횟수와 원래 deadline. Redis 복구로 예산·기한 초기화 금지.
- 만료·웹훅·응답 간 경합을 막는 상태·version 조건.
- 최종 결과가 SQL 이력/통지에 도달할 때까지의 내구성 인계 근거.
- 정리 후 작은 완료 기록과 원문 내용 충돌을 판단할 fingerprint.
- SQL 저장을 확인하기 전 원본을 지우지 않는 조건.

## 7. 장애 시 처리와 검증 항목

Redis를 TPS/Quota에 사용할 때의 ‘장애 시 제한 없이 진행’ 정책은 그대로 유지합니다. 일정 관리 장애에는 **기한·횟수·선점 검사를 우회하지 않고 DDB 경로로 전환**합니다. 두 용도의 장애 정책은 다릅니다.

| 검증 | 통과 조건 |
|---|---|
| DDB commit 직후 Redis 등록 전 종료 | GSI에서 대상 재발견, 기한·횟수 유지 |
| Redis 전체 flush/재시작/오래된 사본 복원 | 원본·완료 결과 유실 없음, 기한 재계산 없음, 누락 작업 회복 지연 기록 |
| TTL 구독자 연결 종료 | 업무 완료에 영향 없음; 필수 전달 수단으로 사용하지 않음 |
| Redis 후보 pop/처리 중 워커 종료 | 복구 점검 또는 재전달로 회복, 발송 권한은 DDB로 결정 |
| 같은 만료 후보 여러 워커 처리 | 조건부 전환/2차 선점 하나로 수렴 |
| 성공 웹훅과 만료 동시 처리 | 기존 기한·회차 규칙대로 한 결과에 수렴, 늦은 웹훅 상태 변경 없음 |
| 미래 시각을 가진 낡은 Redis 후보 | DB 복구 점검으로 실제 기한 대상 발견, 캐시 때문에 영구 지연되지 않음 |
| 완료 캐시 소실 | 원장 확인으로 동일 결과, 재발송 없음 |
| 완료 캐시 hit인데 요청 본문 변경 | 충돌 판정 유지 |
| 원장 복원 후 과거 캐시 재사용 | namespace/세대 검증으로 잘못된 완료 skip 방지 |
| Redis 용량 부족·명령 timeout | 원장 업무 진행 유지, Redis 재생성 가능, DDB fallback 부하 계측 |
| 정상/최대 대표 경로 재계측 | 성공/실패 API·항목 변경·읽기·소비 용량을 별도 비교 |

메트릭은 Redis 등록 실패, due backlog/oldest age, DB fallback 수, 누락 복구 수·지연, 완료 캐시 hit/miss, DDB 실패 트랜잭션과 소비 용량을 추가하는 방향입니다. 상세 ID는 메트릭 label로 넣지 않습니다. 일정 Redis를 TPS Redis와 공유할 때는 메모리·지연 간섭을 시험하고 필요하면 분리합니다. `noeviction`도 쓰기 거절 가능성을 없애지는 않습니다. [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/).

이번 변경은 공식 근거·설계·구현 순서 정리입니다. Redis 일정·완료 캐시·쓰기 병합의 신규 실행 시험은 아직 하지 않았고, 구현 후 위 항목을 통과해야 현재 동작으로 표시합니다. [이전 실제 계측](33-DynamoDB-사용-횟수와-최소화-검토.md)은 변경 전 기준선으로 보존합니다.
