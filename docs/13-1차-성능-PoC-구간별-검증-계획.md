# 1차 성능 PoC 구간별 검증 계획

> 2026-09-25 진행 순서 갱신: 이 문서는 개발 초기에 실행한 구간 PoC 계획과 이력이다. 전체 목표는 **10,000 TPS**로 확정했고, 앞으로의 본격 성능 튜닝·Pod별 한계·전체 확장 측정은 **전반적인 개발 완료 후** 진행한다. 최신 작업 순서는 [전체 만 TPS 목표와 Pod별 성능 검증 계획](41-전체-만-TPS-목표와-Pod별-성능-검증-계획.md)이 우선한다. 아래의 목표 미정·개발 중 부하 확대 방침은 당시 기록이다.

작성일: 2026-09-24. 사용자 요청에 따라 **1차 HTTP 발송 경로의 측정 준비가 되면 성능 테스트를 실행한다.** 이 문서는 실행 계획이다. 첫 실행의 수치와 한계는 [측정 결과](16-1차-성능-PoC-측정-결과.md)에 별도로 기록했다. 기능·장애 회귀 테스트와 성능 부하 실행을 구분한다.

## 1. 첫 번째 PoC의 범위

```text
부하 생성기 → API 인증·Redis 제한 → Kafka 접수 ack
→ Ingress → DynamoDB 원본 확인 → Kafka Dispatch 발행
→ Dispatch 실행 선점 → HTTP 업체 시뮬레이터 → 접수 결과 저장
```

이번 종료 기준은 **업체 HTTP 접수 응답을 받아 Attempt에 ACCEPTED를 저장한 시점**이다. 수신자 최종 전달 성공, 결과 웹훅 처리, TCP 2차 발송, 고객 결과 통지까지 완료된 시간으로 표현하지 않는다. 해당 기능은 구현 후 같은 측정 틀에 추가한다. Kubernetes·CDC·운영용 대시보드 전체는 첫 PoC의 선행 조건이 아니다.

## 2. 구간별 테스트 범위

| 구간 | 입력·끝점 | 테스트 방법 | 주요 지표 | 현재 상태 |
|---|---|---|---|---|
| A. API 접수 | HTTP 요청 시작 → Kafka ack 후 202 | 유효 JWT로 고유 key 요청. 인증·TPS/Quota를 포함한 경로 측정 | 요청/202/429/503 TPS, API p50/p95/p99, Kafka publish 지연 | 기능·HTTP/Kafka ack 계측과 API 부하 도구 준비 완료 |
| B. Ingress | 접수 토픽 → DB 확인 및 Dispatch ack | 별도 시험 토픽에 동일 형식 이벤트를 공급하고 Ingress 처리 측정 | 처리 TPS, DB 지연·요청 수, 후속 발행 지연, lag·가장 오래된 대기 시간 | 기능·DynamoDB 중복·DLT 검증과 구간/DB·broker lag 계측 완료, 직접 입력 도구는 후속 |
| C. Dispatch | Dispatch 토픽 → HTTP 접수 결과 DB 저장 | 고유 deliveryId로 직접 공급. 정상·지연 응답을 분리해 측정 | 외부 호출 TPS, HTTP 지연, claim/결과 저장 지연, 활성 호출 수, lag | lease 만료 재호출 차단·구간/DB·broker lag 계측 완료, 직접 입력 도구는 후속 |
| D. 연결 경로 | A 시작 → C의 접수 결과 저장 | API에서만 입력하고 구간별 수치와 ID별 결과를 대조 | 실제 처리 TPS, 인입→접수 결과 저장 지연, 적체·회복 시간, 미설명 요청 수 | 연결 경로 도구와 소량 대조 완료, 기준선 측정 대상 |
| E. 중복·실패 검증 | 동일 key 재요청, 느린 업체, Worker 중단 | 먼저 소량 정확성 시험. 통과한 시나리오만 제한된 부하로 확대 | 외부 호출 횟수, 중복 효과, DLT/운영 확인 건수, offset 보존 | 일부 회귀 시험만 존재, 장애 중 처리량 측정은 후속 |
| F. 전체 발송 업무 | 1차→재시도→TCP 2차→웹훅→고객 통지 | 기능별 구현 완료 후 D와 같은 기준으로 확장 | 최종 결과 TPS·기한 준수·고객 수신 확인 지연 | 핵심 기능 미구현, 이번 PoC 범위 밖 |

B·C 직접 입력은 API를 우회한 구간 시험이다. 그 처리량을 API 접수 성능 또는 전체 처리량으로 합쳐 보고하지 않는다. 기존 업무 토픽·Consumer Group의 offset을 변경하지 않고 시험 전용 자원과 실행 식별자를 사용한다.

## 3. 성능 테스트 시작 조건

다음 조건을 모두 확인한 뒤 첫 부하를 실행한다. 도구 구현과 격리 환경 소량 검증을 완료했다. 실행 방법은 [PoC 도구 문서](15-격리된-성능-PoC-실행과-결과-대조.md)를 따른다.

- [x] lease 만료만으로 동일 Attempt를 다시 호출하지 않고, 결과 미기록 건을 내구성 있는 운영 확인 상태로 남긴다. 상태 저장 실패를 로그 후 정상 완료로 취급하지 않는다.
- [x] API 접수·Ingress·Dispatch·시뮬레이터의 처리량과 지연 지표를 노출한다. 구간별 오류·DLT·운영 확인·중복 skip도 구분한다. [계측과 소량 검증](14-성능-지표와-시뮬레이터-관측-방법.md) 완료.
- [x] 실행별 지표 시계열과 broker의 consumer group lag를 수집·보관한다.
- [x] 부하 스크립트, 고유 key/중복 key 생성 규칙, 실행 ID, 요청 크기·고객 수·지속 시간을 재현 가능하게 고정한다.
- [x] 시뮬레이터에 실행별 응답 지연 설정, 총 호출·고유 attempt key·처리 효과의 별도 관측을 추가한다. 중복 제거를 끈 소량 시험도 통과했다. 실행 중 동적 장애 스케줄은 후속이다.
- [x] 부하 종료 후 적체가 해소되는지 확인하고 요청 ID 집합을 대조하는 결과 수집기를 준비한다. 모니터링 label에 deliveryId를 넣지 않고 ID별 대조 자료를 별도로 보관한다.
- [x] 현재 기능의 로컬 `smoke --metrics`와 회귀 시험이 통과했고 미지원 범위를 문서화했다. 부하 도구 추가 후 부하 시작 직전 다시 확인한다.

보관 기간·운영 목표 TPS가 미정이어도 이 준비는 진행한다. 완료 기록은 자동 삭제하지 않는다. 범위가 정해지지 않은 오래된 요청의 자동 재발송을 시험 편의로 허용하지 않는다.

## 4. 환경과 입력 고정

실행마다 commit, JDK·Kafka·DB 버전, CPU/RAM과 JVM heap, 컨테이너 자원 제한, 앱 수·Consumer 동시성, 토픽 파티션/복제 수, Kafka/DB 설정을 기록한다. 로컬의 Kafka 단일 broker·복제 1과 DynamoDB Local 결과는 운영 다중 AZ 처리량·내구성 증명이 아니다. DynamoDB Local은 처리 용량을 실제 서비스처럼 적용하지 않는다. [AWS 공식 차이 설명](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.UsageNotes.html).

개발 시작 입력은 고객 1개, 본문 약 1KiB, 고유 key, 2차 미사용, 정상 HTTP 응답으로 둔다. 큰 본문·다수 고객·중복은 별도 시나리오로 추가한다. 로컬 기본 TPS 100·월 Quota 100,000이 측정 상한이 되지 않도록 **시험 고객의 정책만** 의도에 맞게 설정하고 전후 값을 보관한다. 인증은 유지하며 token 발급은 측정 시간 밖에서 준비한다. 정책 제한 자체의 시험은 별도로 실행한다.

부하 생성기는 일정 도착률 기반 k6 시나리오를 우선 사용한다. 응답이 느려졌다는 이유로 입력 부하가 자동 감소하지 않도록 하고, 목표 투입률·실제 투입률·`dropped_iterations`를 함께 기록한다. 도구 버전은 스크립트 추가 시 고정한다. [k6 open/closed 모델 근거](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/). k6 1.8.1과 Python 의존성을 고정한 [설치·실행 도구](15-격리된-성능-PoC-실행과-결과-대조.md)를 추가했다. 아래 값은 개발용 실행 계획이다.

## 5. 실행 순서

1. **소량 대조:** 10~100건을 보내 202 응답과 실제 업체 호출·Attempt 상태를 ID별로 대조한다. 같은 key 반복 요청은 별도로 시험한다.
2. **워밍업:** 낮은 부하로 1분 실행하고 측정 구간과 분리한다. 이전 실행의 미처리 데이터가 섞이지 않는지 확인한다.
3. **기준선:** 10→50→100 TPS를 각각 3분 측정한다. 입력 종료 후 최대 5분간 적체 해소를 관찰한다. 해소되지 않으면 미처리 상태와 수를 남기고 다음 증가 단계를 중단한다.
4. **점진 증가:** 기준선이 안정적이면 200→500→1,000 TPS로 늘린다. 이 숫자는 목표 성능이나 통과 보장이 아니다. 5,000/10,000 TPS는 앞 단계의 병목·자원 조건을 확인한 뒤 별도 실행한다.
5. **변수별 비교:** 업체 지연 0/50/200ms, Worker 동시성, 파티션 수, 본문 크기를 한 번에 하나씩 바꾼다. 시뮬레이터와 부하 생성기 자체의 CPU·heap·메모리 보관량도 확인한다.
6. **회복 시험:** 정상 기준선 확보 후 업체 지연 증가·Worker 재시작 등을 한 종류씩 주입한다. 결과 불명 요청은 별도 집계하며 외부 중복 제거가 이를 가리지 않는지 확인한다.
7. **재현:** 안정 구간과 포화 직전 구간은 같은 조건으로 다시 실행해 편차와 지속 가능한 처리량을 비교한다.

측정 도중 디스크·메모리 고갈 위험, 미설명 누락·예상 밖 중복, 지속적으로 증가하는 lag 또는 부하 생성기의 투입 실패가 나타나면 증가를 중단한다. 중단한 실험도 원본과 결과를 보존한다. 로그 출력·전수 DB scan·운영 조회로 측정 경로를 과도하게 방해하지 않도록 ID 대조는 주로 입력 종료 후 수행한다.

## 6. 지연과 정합성 계산

- API 지연은 요청 시작부터 202/오류 응답까지 측정한다. 202 TPS와 외부 접수 결과 저장 TPS를 별도 그래프로 표시한다.
- 전체 연결 지연은 최초 인입 시각부터 Attempt의 ACCEPTED 저장 시각까지다. 단계별 타이머는 단조 시계를 사용하고, 프로세스 간 timestamp 차이는 시계 동기화 조건을 함께 기록한다. 첫 PoC에서는 최종 전달 완료 지연으로 부르지 않는다.
- Kafka lag는 record 기준이며 고유 Delivery 수와 다르다. 중복 입력은 논리 요청 ID로 묶고, DLT 중복은 원본 topic·partition·offset으로 묶는다.
- 202를 받은 고유 요청 각각이 `업체 접수 결과 저장 / 진행 중 / 운영 확인 / DLT 격리` 중 어디에 있는지 대조한다. 격리 이벤트와 기존 정상 요청이 공존할 수 있으므로 단순 count 합산 대신 ID별 상태 우선순위로 분류한다. 어느 곳에도 설명되지 않는 요청은 실패로 기록한다.
- 503·HTTP 응답 미수신 요청도 별도 명세에 보존한다. 실제 Kafka/DB에 남았을 수 있으므로 미접수로 단정하거나 대조 대상에서 없애지 않는다.
- 시뮬레이터의 전체 호출 수·고유 요청 수·실제 처리 수와 내부 Attempt를 비교한다. 시뮬레이터의 중복 제거 덕분에 내부 중복 호출을 0회로 잘못 보고하지 않는다.
- 정상 시나리오는 적체 해소 후 202 고유 요청이 모두 업체 접수 결과로 수렴해야 한다. 장애 시나리오는 운영 확인·격리를 성공 처리량에 합산하지 않고 별도 결과로 남긴다.

## 7. 결과 기록 형식과 다음 작업

실행 ID별로 입력 명세, 환경·commit·설정, k6 요약, 지표 시계열, ID별 대조 결과, 장애 주입 시각, 병목 판단을 보관한다. JWT·실제 고객 본문은 결과물에서 제외한다. 실행 명령은 [PoC 도구 문서](15-격리된-성능-PoC-실행과-결과-대조.md)에 있으며 원시 자료는 `.poc-results/<실행 ID>/`에 보관한다. 요약 결과는 별도 문서로 남긴다.

| 실행 ID·commit | 구간·시나리오 | 목표/실제 입력 TPS | 202/업체 접수 TPS | API/연결 p95·p99 | 최고 lag·해소 시간 | 오류·격리·운영 확인 | 누락·중복 | 병목·환경 |
|---|---|---|---|---|---|---|---|---|
| 20260924T100423Z-67c09df1 / 8cd1d89 | D, 고유 key 정상 기준선 | 10·50·100 TPS | 10·50 통과, 100 조기 중단 | [결과 표](16-1차-성능-PoC-측정-결과.md) | 최대 21·34·1,517, 모두 해소 관찰 | DLT/운영 확인 0, 중단 시 HTTP 응답 기록 1건 미확인 | 대조한 DB·업체 누락/추가 호출 0 | Ingress 순차 대기·건별 commit 후보 |

**Dispatch lease 만료 후 자동 재발송 차단**은 2026-09-24 구현·검증했다. **구간별 계측·시뮬레이터 관측과 소량 대조**도 완료했다. **격리 부하 스크립트·broker lag/시계열 수집·요청별 결과 대조**도 구현했고 소량 검증을 통과했다. **첫 기준선 측정도 완료**했으며 10·50 TPS 통과, 100 TPS 적체 증가 중단을 확인했다. 후속 동시성 1 재측정·3 비교에서 동시성 3의 100 TPS 3분 통과도 확인했다. [변경 과정과 비교 결과](17-워커-동시-처리와-발행-대기-성능-비교.md)에 이어 기록한다. 다음은 높은 입력률과 실제 업체 지연 조건, 장애 경계 검증이다. 시작 조건이 갖춰지면 사용자 요청에 따라 첫 성능 테스트를 실행한다. 단계별 측정 실패는 원인 수정과 재측정으로 이어가며 전체 기능 완성까지 기다리지 않는다.
