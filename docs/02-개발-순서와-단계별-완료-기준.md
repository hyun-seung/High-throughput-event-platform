# 개발 순서와 단계별 완료 기준

## 진행 원칙

- Kafka ack를 최초 접수의 내구성 근거로 사용합니다.
- 내부 계산에는 상태 write를 추가하지 않고 외부 부수 효과와 복구 경계에 저장합니다.
- 모든 단계는 정상 경로, 중복 event, 프로세스 종료와 의존성 장애를 검증합니다.
- 세부 운영값 미정을 전체 구현의 차단 조건으로 두지 않습니다. 완료 기록은 기간 합의 전 자동 삭제하지 않고, 되돌릴 수 있는 설정값은 개발 기본값으로 분리합니다. 선행 신뢰성 경계의 검증과 남은 장애 시험을 명시하며 단계적으로 구현합니다.

## 현재 기준선

완료된 항목:

- Delivery 도메인 용어와 `deliveryId`, `eventId` 분리
- Client `Idempotency-Key` 기반 안정적인 Delivery ID
- Kafka-first API 접수와 ack 후 `202 Accepted`
- `delivery.requested.v1`과 `delivery.dispatch-requested.v1` 분리
- DynamoDB `DELIVERY#id / META` 단일 conditional insert
- Producer `acks=all`, idempotence, zstd 설정
- Provider HTTP timeout과 Idempotency-Key 전달
- Mock Provider 중복 제거 on/off(기본 off), 응답 지연, key별 호출·처리 효과 관측
- Dispatch Attempt conditional claim, lease, version과 완료 skip
- Kafka, Redis, PostgreSQL, DynamoDB Local Compose와 named volume
- 로컬 인프라 healthcheck와 host port 재정의
- 로컬 DB/Redis 초기화와 Provider 접수까지의 smoke 검증
- Maven Wrapper 3.3.4 / Maven 3.9.16 고정 및 JDK 21 검사
- 구간/DB/HTTP Prometheus 계측과 `smoke --metrics` 검증

## Phase 1. Ingress 신뢰성 검증

**목표:** Kafka-first 접수와 DynamoDB projection의 중복/종료 경계를 검증합니다.

작업:

1. [완료] Kafka publish 동기 실패·비동기 실패와 HTTP 비동기 timeout을 명시적 503으로 변환합니다. 같은 key·내용으로 재요청하도록 안내합니다.
2. [완료] DynamoDB Local에 대한 동시 중복·입력 충돌·재요청 시 최초 인입 시각 보존 테스트를 추가했습니다. 전체 Kafka 전달 경로 통합 시험은 별도입니다.
3. [부분 완료] 실제 DynamoDB 저장 직후 중단 상태와 Dispatch 발행 ack 유실을 테스트에서 재현해 재호출을 검증합니다. Kafka와 실행 프로세스의 실제 강제 종료·offset 복구 시험은 남아 있습니다.
4. [완료] Ingress error handler·DLT ack 확인·원본 바이트 보존을 구현하고 실제 Kafka의 DLT 저장 실패/복구와 offset을 검증했습니다. [운영 replay 절차](12-접수-실패-격리와-DLT-재처리-절차.md)를 작성했습니다. 실행 도구는 만료·운영 조회 기능과 함께 후속 구현합니다.

완료 조건:

- Kafka ack 없는 요청에는 `202`를 반환하지 않습니다.
- 같은 Client 요청 N회가 하나의 DynamoDB 원본으로 수렴합니다.
- 같은 Idempotency-Key와 다른 payload는 충돌로 격리됩니다.
- crash 후 Dispatch event가 누락되지 않습니다.

## Phase 2. Dispatch Attempt와 Sender 멱등성

**목표:** Kafka 재전달이 외부 호출을 불필요하게 중복시키지 않습니다.

작업:

1. `DISPATCH_ATTEMPT` item과 상태 모델을 구현합니다.
2. [완료] 최초 conditional claim과 version을 구현했습니다. 2026-09-24 lease 만료 재선점을 제거하고 REVIEW_REQUIRED 저장·재전달 오류 보존을 적용했습니다.
3. [부분 완료] HTTP 시뮬레이터에 중복 방지 on/off·응답 지연·호출/효과 횟수 관측을 구현했습니다. 2차 TCP 서버·클라이언트·업체 구분·효과 후 연결 종료·응답 ID 불일치도 추가했습니다. 최종 결과 웹훅과 추가 장애 모드는 남았습니다. 업무 결과 조회 API는 제공하지 않으며 관리 포트의 시험용 횟수는 발송 판단에 쓰지 않습니다.
4. [부분 완료] 실제 DynamoDB에 호출 전/결과 저장 전 중단 상태를 만들고 외부 중복 제거 없이 재처리를 검증했습니다. 운영 프로세스의 실제 kill 시험은 남았습니다.
5. [부분 완료] HTTP 접수·1초/10초 재시도 대상·대체 발송 대상·영구 거절·무응답·판단 불가 분류와 시뮬레이터 업무 코드를 구현했습니다. [시험 계약과 검증](23-업체-HTTP-응답-분류와-시험-계약.md). 분류 결과의 DB 저장·예약 실행은 연결했고 TCP 업무 응답 분류도 연결했습니다. TCP 연결/쓰기 성공만으로 접수 성공을 기록하지 않습니다.

완료 조건:

- 외부 중복 방지를 끈 조건에서 완료 기록이 남은 요청과 유효한 선점 중의 중복 요청이 추가 외부 호출을 만들지 않습니다.
- 외부 처리 후 내부 결과 저장 전 종료는 별도 UNKNOWN 실험으로 분리합니다. 외부 중복 방지를 켠 실험의 성공으로 내부 보장을 대체하지 않습니다.
- 완료된 Attempt는 Provider를 재호출하지 않습니다.
- 만료된 PROCESSING lease는 안전한 조정 경로로 이동합니다.
- timeout/reset은 성공이나 실패로 임의 단정하지 않고 `UNKNOWN`으로 남습니다.

## Phase 3. Retry와 UNKNOWN 조정

**목표:** 확정된 일시 실패와 처리 여부 불명을 서로 다르게 다룹니다.

작업:

1. [부분 완료] 1초/10초 코드 및 무응답 기본 1초 간격, 최초 외 최대 3회, 1차 기한 전 호출 제한을 구현했습니다. 단계별 deadline·주기 만료도 구현했고 jitter는 후속입니다.
2. [부분 완료] 동일 Attempt에 next_attempt_at을 저장하고 원본 Kafka 재전달로 실행합니다. Consumer 재시작·동시 선점·저장 응답 유실을 검증했습니다. [상세와 처리량 한계](24-실패-저장과-1차-재시도-예약.md). 별도 retry 소비 경로와 고 TPS 조건은 후속입니다.
3. Q6에 따라 관찰·기록된 무응답은 재시도하고, 결과 미기록 상태에서 종료된 작업은 운영 확인 대상으로 인계합니다. 웹훅 장기 미수신은 만료 처리합니다. 재시도 3회, 1차 인입 시각·2차 1차 결과 판단 시각 기준 만료, 만료 후 웹훅 로그 후 폐기를 적용하며 외부 결과 조회나 테스트 전용 처리 기록에 의존하지 않습니다.
4. DLT/DEAD 조회와 수동 replay 감사 이력을 추가합니다.

완료 조건:

- 일시 실패가 지정 시각 이후 재처리됩니다.
- 영구 실패는 불필요하게 재시도하지 않습니다.
- 무한 Retry가 없습니다.
- 운영 확인 중에도 기한이 유지되며 만료 후 수동 처리로 이전 단계를 재개하지 않습니다.
- 1차·2차 기간을 독립 설정하고 테스트 기준 3시간·4시간으로 전체 최대 7시간을 검증합니다. 자동화 시험은 짧은 서로 다른 기간 또는 제어 가능한 시계를 사용합니다.
- 고객 결과 제공 계약 확정 후, 운영자 미처리 상황에서도 기한 내 종료 결과를 제공하는지 검증합니다.
- `UNKNOWN`의 사유와 최종 조정 결과를 조회할 수 있습니다.

## Phase 4. Provider Fallback과 장애 격리

**부분 구현:** fallbackAllowed의 원본 보존·멱등 충돌, 1차 판단에 고정한 2차 업체·기한, TCP 접수·별도 선점·재시도를 연결했습니다. [검증과 범위](25-대체-발송-허용과-TCP-2차-접수.md). 이후 [웹훅 실패에 의한 전환과 복구](27-웹훅-결과-반영과-재시도-대체-발송-복구.md)도 연결했습니다. 주기 만료·요청 최종화도 구현했습니다. 고객 통지·업체별 동시성 제한·회로 차단은 후속입니다.

**목표:** Primary 장애를 다른 Delivery와 Provider로 확산시키지 않고 대체 경로를 사용합니다.

작업:

1. tenant, delivery type과 destination별 routing 정책을 구현합니다.
2. Provider별 timeout, connection pool, concurrency limit와 circuit breaker를 적용합니다.
3. routeOrder와 Provider별 attempt를 기록합니다.
4. 최초 메시지의 2차 허용 설정과 응답·결과 웹훅의 오류 코드별 재시도/전환 정책을 적용합니다. 코드표·지연·한도·전체 deadline은 후속 논의로 확정합니다.
5. 첫 무응답은 재시도하고, 1차 무응답 재시도 3회를 소진하면 허용 요청은 즉시 TCP 2차 발송으로 전환합니다. 1차 만료 시에도 허용 요청은 2차 발송합니다. 운영 확인 중인 건도 동일하게 만료 전환하며, 수동 처리가 만료 기한을 연장하지 않도록 합니다.

완료 조건:

- 2차 전환 대상 실패 코드·1차 만료·1차 무응답 재시도 3회 소진 시, 최초 메시지에서 허용한 경우에만 Secondary로 전환됩니다.
- 2차 비허용 요청은 전환되지 않으며, 1차 재시도 코드는 지정 시간 뒤 재시도로 처리됩니다.
- 느린 Provider가 API와 다른 Provider 처리량을 소진하지 않습니다.
- 만료 작업의 중복 실행은 2차 발송을 중복 예약하지 않습니다. 결과 불명 1차의 만료 후 대체 발송에는 외부 중복 가능성이 남음을 별도 측정합니다.
- 모든 경로 소진 시 전체 이력과 `DEAD` 사유가 남습니다.

## Phase 5. Receipt와 결과 수렴

**부분 구현:** receipt-api의 인증·Kafka 접수에 이어 Dispatch 앱의 별도 Result Consumer를 추가했습니다. 호출 회차, 중복·만료 후 폐기, Attempt 성공·실패 판단 및 후속 발송 복구를 검증했습니다. [결과 반영 범위](27-웹훅-결과-반영과-재시도-대체-발송-복구.md). [시뮬레이터 자동 웹훅·실제 흐름 12개](28-시뮬레이터-자동-웹훅과-발송-결과-통합-검증.md)를 검증했습니다. [요청 전체 최종화·주기 만료·finalized 인계](29-주기-만료와-요청-최종화-및-Kafka-인계.md)를 구현했습니다. 기존 항목의 색인 보강 후 활성화하며 고객 통지는 후속입니다.

**목표:** 비동기 결과와 순서 역전에도 최종 상태가 일관됩니다.

작업:

1. [부분 완료] Receipt API의 업체별 Bearer 인증과 Kafka-first 응답을 구현했습니다. 본문 서명·운영 TLS·키 교체는 후속입니다.
2. [완료] `delivery.receipt-received.v1`과 Result Processor, 요청 전체 최종화를 구현했습니다.
3. [완료] provider+receiptId marker와 Attempt 상태의 원자 저장, 내용 충돌 및 중복 후속 실행 보호를 구현했습니다.
4. [완료] 발송 응답보다 최종 결과를 먼저 보내는 Provider mode를 구현했습니다. HTTP·TCP 접수 응답보다 먼저 온 HTTP 결과 웹훅이 반영되고 늦은 접수 응답이 상태를 덮어쓰지 않음을 실제 흐름으로 검증했습니다.
5. [완료] 작은 FINAL outbox와 `delivery.finalized.v1` 인계를 구현했습니다. broker ack 이전에는 PENDING을 유지하며, 확인 유실 시 같은 ID·본문을 재발행합니다.

완료 조건:

- Receipt 재전송 N회에도 최종 상태와 논리적 후속 event가 하나입니다.
- 만료 전 Receipt/HTTP 순서 역전 규칙을 검증합니다. 만료 후 해당 단계의 웹훅은 로그만 남기고 폐기하며 업무 결과를 갱신하지 않습니다.
- Receiver 응답 시간은 downstream 처리 시간과 분리됩니다.

## Phase 6. 독립 후속 처리와 PostgreSQL 이력

**부분 구현:** 별도 `delivery-result-worker` 그룹에서 PostgreSQL 이력과 고객 통지 PENDING을 한 트랜잭션으로 저장한다. 동시 중복·전체 rollback·내용 충돌·SQL commit 후 소비자 재시작과 offset 복구를 검증했다. [구현·검증 범위](30-최종-이력과-고객-통지-대기-기록의-원자-저장.md). [고객 HTTP 묶음 통지·재전송과 복구](31-고객-HTTP-묶음-통지와-재전송-복구.md)도 구현했다. [작은 완료 기록과 원본 정리 인계](32-완료-기록-유지와-발송-원본의-안전한-정리.md)도 구현·검증했다. 전체 쓰기 워커 교체 후 활성화한다. 전체 흐름 관측·부하·실제 프로세스 종료 검증, batch 저장 성능 검증, 사용량/통계 소비자는 후속이다.

**목표:** 최종 결과를 기능별로 독립 소비합니다.

작업:

1. History, Usage, Client Callback, Statistics를 별도 Consumer Group으로 구성합니다.
2. PostgreSQL batch insert/update와 idempotent key를 구현합니다.
3. 한 Consumer를 중지해 다른 Group의 진행 여부를 검증합니다.

완료 조건:

- 한 Group의 장애가 다른 Group offset에 영향을 주지 않습니다.
- PostgreSQL 재처리에도 중복 이력이 생기지 않습니다.
- backlog replay 절차가 검증됩니다.

## Phase 7. Redis Admission과 Usage 정합성

**목표:** 빠른 유입 제어와 내구성 있는 사용량 계산을 분리합니다.

작업:

1. token bucket key와 월 quota key에 TTL을 적용합니다.
2. tenant 등급별 Redis fail-open/fail-closed 정책을 확정합니다.
3. Kafka accepted event 기반 usage 집계와 Redis 보정 절차를 구현합니다.
4. fixed/sliding window를 비교 실험합니다.

완료 조건:

- 동시 요청에서 admission 한도가 원자적으로 적용됩니다.
- Kafka 접수 실패가 확정 사용량으로 남지 않습니다.
- Redis 중단 시 문서화된 정책대로 동작합니다.

## Phase 8. 관측성

**목표:** 장애와 병목을 dashboard에서 진단합니다.

**부분 선행 구현(2026-09-24):** 로컬 Prometheus·Grafana 7개 화면·Alloy/Loki·11개 경보 규칙을 구성했다. HTTP 1차 접수까지의 단계 로그, committed lag/oldest age, DB/Redis 제한 우회 관측을 제공하며 실제 Redis 장애·복구로 경보를 확인했다. [실행법과 PPT 대응](19-그라파나-대시보드-실행과-PPT-항목-대응.md). 후속 업무의 전체 상태 보존 관계·최종 E2E·분산 trace·운영 외부 알림은 남아 있으므로 Phase 전체 완료는 아니다.

작업:

1. Actuator/Micrometer, Prometheus와 Grafana를 구성합니다.
2. 구조화 로그, trace propagation, Loki/Fluent Bit를 구성합니다.
3. lag, oldest age, retry/recovery/unknown과 end-to-end p99를 표시합니다.
4. alert와 runbook을 작성합니다.

완료 조건:

- 한 deliveryId의 전 구간 로그를 찾을 수 있습니다.
- 의도한 장애에서 대응 경보가 발생합니다.
- accepted, terminal, known in-flight, unknown, dead의 보존 관계를 확인합니다.

## Phase 9. Batch와 성능 기준선

**1차 PoC는 앞당겨 진행:** [구간별 검증 계획](13-1차-성능-PoC-구간별-검증-계획.md)의 시작 조건이 갖춰지면 HTTP 1차 접수 경로부터 측정합니다. TCP 2차·전체 후속 기능·Kubernetes 완성을 기다리지 않습니다. 2026-09-24 첫 측정에서 10·50 TPS는 통과했고 100 TPS는 적체 증가로 중단했습니다. [첫 결과](16-1차-성능-PoC-측정-결과.md)에 범위·수치·한계를 기록했습니다. 이후 동시성 1 재측정과 3 비교를 수행했고, 동시성 3에서는 100 TPS 3분을 통과했습니다. [후속 비교](17-워커-동시-처리와-발행-대기-성능-비교.md)에 변경 이유와 채택 판단을 남깁니다.

**목표:** 전달 보장을 유지하며 처리량을 단계적으로 올립니다.

작업:

1. k6 시나리오와 결과 저장 형식을 고정합니다.
2. 100/1k/5k/10k TPS를 순서대로 실행합니다.
3. Producer batch/linger/compression, Consumer poll/fetch와 DB batch를 한 변수씩 실험합니다.
4. Provider capacity에 맞춰 concurrency와 backpressure를 조정합니다.

완료 조건:

- 환경, commit, 설정, 입력과 결과를 함께 보존합니다.
- 각 부하에서 유실/중복, p95/p99와 lag 회복 시간을 기록합니다.
- 병목 근거와 다음 scale 대상을 설명합니다.

## Phase 10. Kubernetes와 KEDA

**목표:** partition과 lag를 기준으로 안전하게 scale-out합니다.

kind/k3d, Helm, graceful shutdown, KEDA lag scaling과 ArgoCD를 순서대로 적용합니다. replica 상한은 활성 partition 수와 Provider concurrency를 함께 고려합니다.

## Phase 11. Fault Injection

[저장소 장애 시 중단 범위와 복구 절차](09-저장소-장애-시-중단-범위와-복구-절차.md)를 구현·검증합니다. 장애 격리·offset 보존·상태 복원·제한된 재개를 실제 장애로 확인하고, Redis TPS·Quota 전부 우회와 장기 장애 복구 후 만료를 검증합니다. 미정인 복구 시간·장기 장애 대상 구분은 합의 후 통과 기준에 반영합니다.

**목표:** Kafka, Redis, PostgreSQL, DynamoDB, Provider와 Consumer 장애에서 보존과 수렴을 증명합니다.

[장애 시나리오와 검증표](03-장애-상황별-검증-계획.md)를 자동화하고 accepted Delivery의 위치와 복구 결과를 기록합니다.

## Phase 12. CDC

**목표:** 핵심 Delivery flow와 분리된 기준정보 동기화를 검증합니다.

PostgreSQL logical replication → Debezium → Kafka Connect → Consumer → Redis를 구성하고 connector 재시작, schema change와 중복 event를 검증합니다.

고객 HTTP 결과는 같은 고객끼리 최대 100건으로 짧게 묶어 발송합니다. 최초 전송 후 고객 결과 웹훅 재전송은 최대 20회이며, 재시작·재전달에도 횟수를 유지합니다. 완료 후 원본·활성 상태 정리, 이력 한 줄 및 미통지 결과의 내구성 인계는 [상세 설계](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)를 따릅니다. [작은 DynamoDB 완료 기록 유지](11-멱등-정보-보관과-완료-후-정리-방식.md)는 확정했으며, 보관 기간과 재처리 허용 범위는 추가 합의합니다.
