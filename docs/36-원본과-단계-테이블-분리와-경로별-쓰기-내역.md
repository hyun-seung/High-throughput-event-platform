# 원본과 단계 테이블 분리와 경로별 쓰기 내역

갱신일: 2026-09-25. DynamoDB 물리 테이블을 **`ORIGIN`, `STEP`**으로 분리했다. 단일 `delivery_state` 안의 논리 항목 이름만 바꾼 것이 아니다. 이전에 측정한 정상 5회·7항목, 복잡한 대표 경로 24회·28항목은 테이블 분리 후에도 유지된다.

## 1. 실제 테이블과 키

| 테이블 | 저장 내용 | 키 |
|---|---|---|
| `ORIGIN` | 최초 원문·인입 시각·대체 발송 허용·현재 실행 UUID·최종 완료 보호 | `pk=DELIVERY#requestKey`, `sk=META` |
| `STEP` | 1차/2차 선점·업체·회차·version·deadline·응답·웹훅·최종 결과 이벤트 | `pk=DELIVERY#실행UUID`, `sk=ATTEMPT#단계UUID` |

각 테이블에 `lifecycle_due_v1` GSI(KEYS_ONLY)를 둔다. Redis 일정이 없어졌을 때 ORIGIN의 미발송 원본과 STEP의 만료·최종 인계 대기를 모두 찾는다. 테이블당 16 shard, 합계 32개의 조회 대상을 사용하며 cursor를 분리한다. 이로 인해 복구용 읽기는 달라질 수 있지만 정상 쓰기 횟수는 늘지 않는다.

DLT 초기 원본의 수동 복원은 예외적인 운영 경로다. 발송 보류 ORIGIN Put 후 SQL 이력을 대조하고, Update로 보류를 해제하면서 GSI를 설정한다. 보류 중에는 발송 선점도 차단한다. 이 2회 쓰기는 아래 정상 경로에 추가되지 않으며, 상세 조건·중단 복구는 [DLT 복구](50-DLT-원장-대조와-기존-실행-복구.md)를 따른다.

`META`, `ATTEMPT#...`는 키 호환을 위한 내부 값이다. 구형 v1의 `FINAL`, `RECEIPT#.../META`는 STEP 테이블로 분류한다. 신규 v2는 이 두 종류를 새로 만들지 않는다.

DynamoDB는 같은 계정·리전의 여러 테이블을 한 `TransactWriteItems`에 포함할 수 있다. 선점, 성공 웹훅 결과 확정, 최종 삭제의 원자성은 테이블을 나눈 뒤에도 같은 트랜잭션으로 유지한다. [AWS 공식 문서](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).

## 2. ‘5회·7항목’의 뜻

- **쓰기 API 5회:** `PutItem`, `UpdateItem`, `TransactWriteItems`를 성공시킨 횟수다.
- **항목 변경 7회:** 그 API 안에서 실행한 Put/Update/Delete 수의 합이다. 삭제도 포함한다.
- **서로 다른 행 7개라는 뜻은 아니다.** 정상 경로는 ORIGIN 1행과 1차 STEP 1행, 총 2행을 여러 차례 변경한다.
- `ConditionCheck`, Get, Query는 항목을 변경하지 않으므로 ‘항목 변경’에서 제외한다. 조회·조건 검사 비용은 따로 존재한다.

두 항목을 한 트랜잭션으로 변경하면 **API 1회 / 항목 변경 2회**다. 아래 값은 직렬 대표 경로의 성공 쓰기이며 과금 WCU나 운영 호출의 절대 상한이 아니다.

## 3. 정상: 1차 HTTP 접수 → 성공 웹훅 → SQL 저장 → 정리

| 순서 | 시점과 변경 내용 | API | ORIGIN 변경 | STEP 변경 | 항목 합계 |
|---|---|---:|---:|---:|---:|
| 1 | Kafka 접수 후 **ORIGIN Put**: 원문·최초 시각·실행 UUID 저장 | 1 | 1 | 0 | 1 |
| 2 | HTTP 호출 전 **STEP 생성 Update**: PROCESSING, retryCount=0, version, lease, deadline 저장. 같은 트랜잭션에서 ORIGIN 실행 UUID·미완료 조건 검사 | 1 | 0 | 1 | 1 |
| 3 | HTTP 접수 응답 후 **STEP Update**: ACCEPTED, provider_processed_at 저장 | 1 | 0 | 1 | 1 |
| 4 | 성공 웹훅: **STEP Update**로 DELIVERED·웹훅 회차·불변 최종 이벤트·SQL 인계 대기를 저장하고, **ORIGIN Update**로 완료 보호와 복구 인덱스 정리를 함께 처리 | 1 | 1 | 1 | 2 |
| 5 | PostgreSQL 이력·통지·정리 예약 commit 확인 후 **ORIGIN Delete + STEP Delete**를 한 트랜잭션으로 실행 | 1 | 1 | 1 | 2 |
| 합계 | | **5** | **3** | **4** | **7** |

표의 2번은 SDK에서 `Update`로 실행하지만 `attribute_not_exists` 조건으로 없는 STEP을 처음 만드는 동작이다. ORIGIN은 검사만 하므로 그 시점에 쓰기가 추가되지 않는다.

Kafka 최종 결과 발행 ack는 DDB에 별도 업데이트하지 않는다. 완료 Redis 표식 설정과 TTL 유지도 DDB 쓰기에는 포함되지 않는다. SQL 저장·고객 HTTP 묶음 통지·최대 20회 재전송은 PostgreSQL을 사용하므로 위 DDB 값에 추가되지 않는다.

## 4. 복잡한 대표 경로: 24회·28항목

다음 조건을 모두 거친 시험이다. 모든 요청이 이 경로를 밟는다는 뜻은 아니다.

1. 대체 발송 허용 요청이다.
2. 1차에서 최초+재시도 3회, 총 4번 HTTP 호출하고 매번 접수 응답을 받는다.
3. 앞의 실패 웹훅 3회는 재시도 코드다. Kafka에 다음 회차를 고정해 전달하며 DDB 예약 Update는 하지 않는다.
4. 4번째 웹훅은 운영 확인 대상으로 분류되어 STEP을 REVIEW_REQUIRED로 바꾸고, 최초 인입+3시간에 만료한다.
5. 1차 판단 시각 기준 2차 deadline을 고정하고 TCP 2차를 시작한다. 2차도 총 4회 접수·3회 재시도·운영 확인을 거쳐 4시간 뒤 만료한다.
6. 최종 결과를 확정하고 SQL 저장 후 원본과 두 STEP을 삭제한다.

| 처리 구간 | API | ORIGIN 변경 | 1차 STEP 변경 | 2차 STEP 변경 | 항목 합계 |
|---|---:|---:|---:|---:|---:|
| 원본 최초 Put | 1 | 1 | 0 | 0 | 1 |
| 1차 최초 선점 | 1 | 0 | 1 | 0 | 1 |
| 1차 재시도 실행 선점 3회: 고정 회차·version을 조건부 증가 | 3 | 0 | 3 | 0 | 3 |
| 1차 접수 응답 ACCEPTED 저장 4회 | 4 | 0 | 4 | 0 | 4 |
| 1차 마지막 웹훅 → REVIEW_REQUIRED | 1 | 0 | 1 | 0 | 1 |
| 1차 deadline → DECISION_PENDING / PRIMARY_EXPIRED | 1 | 0 | 1 | 0 | 1 |
| 2차 업체·단계 ID·deadline을 **1차 STEP에** 고정 | 1 | 0 | 1 | 0 | 1 |
| 2차 최초 선점 | 1 | 0 | 0 | 1 | 1 |
| 2차 재시도 실행 선점 3회 | 3 | 0 | 0 | 3 | 3 |
| 2차 TCP 접수 응답 ACCEPTED 저장 4회 | 4 | 0 | 0 | 4 | 4 |
| 2차 마지막 웹훅 → REVIEW_REQUIRED | 1 | 0 | 0 | 1 | 1 |
| 2차 deadline → DECISION_PENDING / SECONDARY_EXPIRED | 1 | 0 | 0 | 1 | 1 |
| 최종화 트랜잭션: ORIGIN 완료 보호 + 1차 STEP 닫기 + 2차 STEP에 최종 결과 저장/닫기 | 1 | 1 | 1 | 1 | 3 |
| SQL commit 후 ORIGIN·1차 STEP·2차 STEP 삭제 트랜잭션 | 1 | 1 | 1 | 1 | 3 |
| 합계 | **24** | **3** | **13** | **12** | **28** |

총 재시도 6회에서 실패 웹훅을 받았다는 이유로 DDB를 한 번 더 갱신하지 않는다. **다음 발송 직전의 선점 6회만** 표에 잡힌다. 마지막 운영 확인·만료·최종화는 다른 상태 변경이므로 각각 포함된다.

정상 5회·7항목에 비해 최종화와 삭제가 각각 3항목짜리 트랜잭션이 된다. 따라서 이 경로는 `API 24회 + 최종화의 추가 2항목 + 삭제의 추가 2항목 = 항목 변경 28회`다. 실제 서로 다른 행은 ORIGIN 1행, STEP 2행으로 총 3행이다.

## 5. 다른 복잡한 경로도 구분

| 경로 | API / 항목 변경 | ORIGIN / STEP 변경 | 차이 |
|---|---:|---:|---|
| 정상 1차 성공 | **5 / 7** | 3 / 4 | 한 STEP, 성공 웹훅과 최종화를 통합 |
| 양 단계 모두 무응답, 각각 최초+3회 | **14 / 18** | 3 / 15 | ACCEPTED 저장이 없음. 소진 판단·대체 전환·최종화를 수행 |
| 총 8회 접수·웹훅, 마지막 2차 성공 | **21 / 25** | 3 / 22 | 1차 마지막은 FALLBACK, 2차 마지막은 DELIVERED. 성공 웹훅과 최종화 통합 |
| 총 8회 접수·웹훅, 양 단계 운영 확인·만료 | **24 / 28** | 3 / 25 | 위 4절 상세 경로 |

중복 소비, 조건 경합, 저장 응답 유실, 장애 복구 시 호출은 더 발생할 수 있다. ‘복잡한 대표 경로’를 모든 상황의 최대 호출 횟수로 사용하면 안 된다. WCU는 트랜잭션 여부·항목 크기·GSI 등도 반영한다. [비용과 필요 이유](33-DynamoDB-사용-횟수와-최소화-검토.md).

## 6. 기존 데이터와 실행 환경 이관

이 변경은 테이블명만의 온라인 rename이 아니다. 기존 `delivery_state`를 삭제하거나 공용 서비스를 자동 재시작하지 않았다. 로컬 시험용 ORIGIN·STEP은 초기화 코드로 생성하고 테스트 소유 데이터만 넣고 지웠다.

기존 데이터가 있는 환경에서는 구형·신형 앱을 섞어 동작시키지 않는다. 원본과 실행 상태가 서로 다른 테이블 집합으로 분리되면 활성 중복 보호와 복구가 끊길 수 있다. 다음 절차로 동일한 상태를 옮긴 뒤 새 버전으로 재개한다.

1. API 및 모든 쓰기 worker, lifecycle·정리 worker를 중지하고 소비 offset과 데이터 백업을 확보한다. Kafka 보관 기간 안에 작업한다.
2. 로컬 이관 도구의 기본 dry-run으로 분류와 대상 충돌 여부를 확인한다. 구형 v1 원본/완료 META는 ORIGIN, STEP·FINAL·receipt marker는 STEP에 복사한다. 본문과 기한·회차를 변경하지 않는다.
3. 쓰기가 모두 멈춘 상태에서 `--apply --writers-stopped`로 복사한다. 기존 대상은 내용이 일치할 때만 재개를 허용하고, 충돌 시 덮어쓰지 않는다. 원본 테이블은 삭제하지 않는다.
4. 대상 데이터 대조와 양쪽 GSI 활성 상태를 확인하고 전체 앱을 새 버전으로 재개한다. 양쪽 테이블에 필요한 IAM 권한도 적용한다.
5. 새 테이블에서 처리가 진행된 뒤에는 그대로 구형 앱으로 되돌리지 않는다. 롤백하려면 다시 쓰기를 멈추고 새로 변한 상태와 Kafka 소비 상태를 별도로 맞춰야 한다.

```bash
# 아래 도구는 localhost DynamoDB 전용이다. AWS 운영 이관을 자동 실행하지 않는다.
.poc-tools/venv/bin/python scripts/dynamodb/split_origin_step.py --endpoint http://localhost:18000
# 실제 모든 writer 중지와 dry-run 확인 후에만 실행
.poc-tools/venv/bin/python scripts/dynamodb/split_origin_step.py --endpoint http://localhost:18000 --apply --writers-stopped
```

처음 구성하는 로컬 환경은 `delivery.dynamodb.initialize-tables=true`로 ORIGIN·STEP 및 각 GSI를 만든다. 기존 인덱스 보정 도구 `scripts/dynamodb/lifecycle_index.py`도 두 테이블을 처리한다. PoC·smoke·결과 대조 도구 역시 분리된 테이블을 읽는다.

## 7. 검증

전체 Maven package의 Java **283개**, Python 증거 대조 **10개**·실제 로컬 이관 **3개**가 통과했다. 실패·오류·skip은 0개다.

실제 DDB Local에서 네 경로의 쓰기 API·항목 변경·테이블별 변경 수를 다시 측정했다. 정상 ORIGIN 3회/STEP 4회, 복잡한 만료 경로 ORIGIN 3회/STEP 25회를 확인했다. 두 물리 테이블 저장 위치, 테이블 간 웹훅 트랜잭션의 부분 성공 방지, 양 테이블 GSI 페이지 조회도 시험한다.

이관 도구는 UUID별 임시 원본 테이블로 dry-run→복사→반복 실행, 대상 충돌 시 무덮어쓰기, 복사 응답 유실 후 재개를 검증했다. 기존 `delivery_state` 실데이터를 자동 복사하거나 삭제한 시험은 아니다.

실행 명령·시험 집계·계측 원본은 [테이블 분리 검증 기록](검증-결과/2026-09-25-원본-단계-테이블-분리-검증.json)에 남긴다.
