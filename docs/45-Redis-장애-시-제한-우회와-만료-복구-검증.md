# Redis 장애 시 제한 우회와 만료 복구 검증

2026-09-25. [DynamoDB 장애 경계](44-DynamoDB-장애-시-발송-차단과-만료-복구-검증.md)에 이어 Redis 연결 불가 시 TPS·Quota 우회, 실행 중 멱등성, 일정 없는 만료와 정상 복귀를 검증한다. 성능 튜닝·Pod별 한계 측정은 개발 완료 후 진행한다.

## 1. 시험 범위

도구는 `scripts/poc/redis_recovery.py`다. 실행별 Compose·포트·볼륨을 만들고 project/service label로 소유권을 확인한 Redis 컨테이너만 stop/start한다. 앱 여섯 개는 재시작하지 않고 같은 PID를 유지한다. Kafka·DynamoDB·PostgreSQL은 실행 상태를 유지한다.

| 구간 | 확인할 동작 |
|---|---|
| 장애 전 | 실제 API에서 Quota 429/3002, TPS 429/3001을 각각 확인. 두 제한을 켠 채 Redis 중단 |
| R-01: 중단 중 정상 발송 | 유효 JWT 요청이 제한을 우회해 202. 성공 결과·고객 HTTP·SQL 이력·DDB 정리까지 완료 |
| R-02: 중단 중 만료·활성 중복 | 웹훅 없는 요청 접수 후 동일 ClientMsgId·내용 재요청. ORIGIN 실행 ID 유지·업체 호출 1회. Redis 일정 없이 DDB 복구 조회로 원래 기한의 EXPIRED 확정·고객 통지·정리 |
| 복구 후 제한 | 같은 AOF 볼륨의 기존 Quota 정책을 수정하기 전에 다시 429/3002 확인. 이후 TPS·Quota 각각 차단을 재확인 |
| R-03: 복구 후 정상 완료 | 허용 정책으로 전환 후 새 요청 완료·Redis 완료 TTL 생성. 같은 ClientMsgId 재요청은 추가 업체 발송 없이 차단 |

시험에서만 1차 만료 30초·2차 40초·DDB 누락 복구 조회 3초를 사용한다. 운영 기본값 3시간/4시간·10분은 바꾸지 않는다. 모든 요청은 2차 비허용이며 외부 업체 중복 제거는 끈다.

TPS 시험은 빈 버킷과 초당 0.001개 보충·용량 1개를 사용해 소량 요청에서도 차단을 재현한다. 이는 시험 fixture이며 TPS 용량 시험이나 운영 설정 권고가 아니다. Quota는 한도·사용량 각각 1로 만든다. 최초 및 복구 후의 거절 요청은 Kafka 업무 접수 건수에 포함하지 않는다.

## 2. Redis 없는 완료의 의미

현재 합의는 **진행 중 멱등성은 DynamoDB, 완료 후 추가 기간의 중복 차단은 Redis**다. Redis가 불가용해 완료 표식 쓰기가 실패해도 SQL 이력·통지·정리 예약이 저장됐다면 ORIGIN·STEP 정리는 계속한다. Redis 쓰기 실패를 이유로 발송 원본을 영구 보관하도록 바꾸지 않는다.

따라서 Redis 중단 중 끝난 R-01·R-02에는 복구 후에도 완료 TTL이 없을 것으로 예상한다. 이는 Redis에 성공적으로 저장한 표식의 유실과는 다르다. 처음부터 저장하지 못했고 현재 자동 재구축도 하지 않는 경우다. **이 시점에 같은 ClientMsgId를 다시 보내고 DynamoDB 선점도 통과하면 새 발송이 허용될 수 있다.** 사용자가 허용한 완료 후 보조 캐시 정책이며 SQL 이력이 별도로 남는다는 사실이 재발송을 막지는 않는다. 이번 시험은 해당 두 요청을 정리 후 다시 발송시키지는 않으며 표식 부재까지 관찰한다.

장애 중 우회한 요청의 Quota 사용량도 자동 소급 복구하지 않는다. 복구 후 기존 카운터 1이 유지되는지 확인하며, 실제 전체 월 사용량이 정확히 복원됐다고 표현하지 않는다. R-03의 새 완료 표식은 정상 생성되는지 별도로 검증한다.

## 3. 판정과 실행 방법

- API의 `delivery_admission_duration_seconds_count{outcome="redis_unavailable_bypass"}`가 중단 중 요청 3회만큼 증가해야 한다. 진행 중 중복 재요청도 1회로 센다.
- Ingress·Dispatch·Result의 `delivery_cache_errors_total` 증가를 확인한다. Redis가 실제로 불가용한 동안 원장 기반 처리가 끝나야 한다.
- 각 고유 요청의 SQL 결과와 실제 204 고객 수신 본문을 대조하고, HTTP 호출/효과 각 1회·TCP 각 0회, ORIGIN·STEP 삭제, SQL 통지 DELIVERED·정리 DONE을 확인한다.
- R-02의 resultAt/deadline은 최초 STEP deadline과 같아야 한다. 진행 중 중복 요청이 실행 ID나 기한을 바꾸면 실패다.
- 복구 후 API health도 확인한 뒤 제한 시험을 실행한다. Redis 컨테이너만 준비되고 앱 연결은 아직 복구되지 않은 순간을 정책 재적용으로 오판하지 않는다.
- 최종 SQL 고유 이력 3건과 접수 ID 집합을 대조한다. 요청·발송·업체 웹훅·최종 결과 토픽 모든 파티션 lag가 0이어야 한다. offset 조회 도구는 subscribe/commit하지 않는다.

```sh
# JDK 21, Docker, scripts/poc/setup.py 도구 준비 후
./mvnw -DskipTests package
.poc-tools/venv/bin/python -m unittest discover -s scripts/poc -p 'test_*.py'
.poc-tools/venv/bin/python scripts/poc/redis_recovery.py
```

환경·도구/JAR 해시, Redis 상태, 제한 거절 응답, 장애 중 계측 원문, 활성 중복의 원장, SQL·고객 결과, 복구 후 완료 TTL 부재를 실행별 `.poc-results/`에 보존한다. 종료 시 소유 앱·컨테이너만 정지하고 볼륨은 유지한다.

## 4. 이번 시험으로 확인하지 않는 것

동일 볼륨 재기동이며 빈 Redis로의 복원·오래된 replica 승격·AOF 손실·메모리 부족·권한 오류를 주입하지 않는다. 현재 RequestLimiter가 모든 Redis 오류 유형을 동일하게 우회하는지까지 입증하지 않는다. 인증·Kafka 저장을 생략하는 시험도 아니다.

Redis 장애 중 만료 복구는 운영 기본 10분 조회 주기를 포함한 지연이 생길 수 있다. 시험용 3초 결과를 운영 만료 통지 시간으로 환산하지 않는다. 처리량·Pod 성능·다중 AZ 내구성은 별도 검증 대상이다.
