# 성능 지표와 시뮬레이터 관측 방법

작성일: 2026-09-24. [1차 PoC 계획](13-1차-성능-PoC-구간별-검증-계획.md)의 계측 준비를 구현했다. 이 문서는 지표의 의미와 소량 검증 방법이며 성능 측정 결과가 아니다.

## 1. 수집 방식과 근거

Spring Boot Actuator와 Micrometer Prometheus registry를 사용한다. 처리 구간의 Timer는 실행 횟수·누적 시간·histogram을 제공하고, 비동기 Kafka 발행은 future의 ack 완료까지 잰다. **프로젝트 판단:** 업무 데이터를 더 저장하지 않고 각 프로세스 메모리에서 계측해 DynamoDB write를 늘리지 않는다. [Spring Boot 지표 자동 설정](https://docs.spring.io/spring-boot/reference/actuator/metrics.html), [Micrometer Timer](https://docs.micrometer.io/micrometer/reference/concepts/timers.html).

지표는 재시작하면 초기화되며 발송·멱등 상태의 근거가 아니다. DB 저장 직후 프로세스가 종료되면 성공 counter가 증가하지 않을 수도 있다. 따라서 무손실·중복 여부는 요청 ID별 Kafka/DB 상태와 시뮬레이터 관측을 대조해야 한다. Prometheus 서버는 설치하지 않았다. 후속으로 [격리 PoC 도구](15-격리된-성능-PoC-실행과-결과-대조.md)에 파일 기반 시계열 수집과 k6 부하 생성을 추가했다.

업무 ID·고객 ID·payload·오류 메시지를 지표 label에 넣지 않는다. 사용자 입력 수만큼 지표가 늘어나는 것을 막기 위해 `stage`, `result`, `outcome`, DB `operation`을 코드에 정의된 값으로 제한한다. 시뮬레이터의 key별 호출 수는 별도 관리 조회에 둔다. [Micrometer 지표 이름과 tag 주의사항](https://docs.micrometer.io/micrometer/reference/concepts/naming.html).

## 2. 조회 포트와 실행

기존 방식으로 빌드 후 네 앱을 실행한다. 관리 서버는 모두 `127.0.0.1`에 바인딩하고 업무 포트와 분리한다. API 관리 조회에는 기존 JWT 인증을 유지한다. Worker와 시뮬레이터의 관리 조회는 로컬에서 인증 없이 가능하다. `env`, `configprops`, 쓰기 endpoint는 노출하지 않는다. [Spring Boot 관리 포트·주소 설정](https://docs.spring.io/spring-boot/reference/actuator/monitoring.html).

| 앱 | 관리 포트 기본값 | 포트 설정 환경변수 | 노출 endpoint |
|---|---:|---|---|
| API | 19080 | `DELIVERY_API_METRICS_PORT` | `/actuator/health`, `/actuator/prometheus` — JWT 필요 |
| Ingress | 19081 | `INGRESS_METRICS_PORT` | `/actuator/health`, `/actuator/prometheus` |
| Dispatch | 19082 | `DISPATCH_METRICS_PORT` | `/actuator/health`, `/actuator/prometheus` |
| 시뮬레이터 | 19090 | `SIMULATOR_METRICS_PORT` | 위 두 개와 `/actuator/simulator`, `/actuator/simulator/{key}` |

Worker는 HTTP endpoint 제공을 위해 웹 서버를 추가했다. 기본 업무 포트는 로컬 `8091`/`8092`이며 `scripts/local.sh`에서는 `INGRESS_HTTP_PORT`/`DISPATCH_HTTP_PORT`로 바꾼다. 이 포트에는 발송 업무 API가 없다. 성능 결과에 웹 서버·계측으로 늘어난 자원도 포함한다. `health`의 UP만으로 Kafka partition 할당이나 전체 처리 준비를 판단하지 않는다.

```bash
# 네 앱 실행 후: 새 key로 요청 2건만 보내는 기능 검증
bash scripts/local.sh smoke --metrics

# Dispatch의 현재 지표 확인
curl --noproxy '*' --fail http://127.0.0.1:19082/actuator/prometheus

# 시뮬레이터의 설정·누적 호출/처리 수 확인
curl --noproxy '*' --fail http://127.0.0.1:19090/actuator/simulator
```

smoke는 인증 토큰을 메모리에서 사용하고 출력하지 않는다. 기존 smoke와 동일하게 새 key의 Kafka/DB 자료가 남으며 시험 고객 Quota를 2회 사용한다. `--metrics` 검증은 기본 포트 또는 표의 환경변수를 사용한다. Spring의 직접 `MANAGEMENT_SERVER_PORT` override를 사용할 때는 스크립트의 앱별 포트도 맞춘다.

## 3. 구간별 지표 의미

아래는 Prometheus에서 보이는 이름이다. Timer에는 `_count`, `_sum`, `_bucket`, `_max`가 붙는다. 모든 앱에 `application` label을 부여하며, 공통 stage·outcome은 미사용 앱에서도 0으로 등록된다.

| 지표 | label/구간 | 의미 |
|---|---|---|
| `http_server_requests_seconds` | `uri`, `status`, `method` 등 | HTTP 요청 처리 시간과 202/429/503/401 등 응답 수. 업무 경로 `/api/v1/deliveries`만 선택해 관리 조회를 제외 |
| `delivery_admission_duration_seconds` | `outcome` | API 제한 판단 시간·횟수. allowed/차단/redis_unavailable_bypass/error를 구분하며 async 재진입은 제외 |
| `delivery_stage_duration_seconds` | `stage`, `result=success/failure` | 아래의 구간별 실행 시간·횟수. 재전달도 각각 포함 |
| `delivery_stage_active` | `stage` | 현재 해당 구간에서 완료를 기다리는 실행 수. DB 상태의 PROCESSING 건수가 아님 |
| `delivery_outcomes_total` | `outcome` | 후속 발행, DLT 인계, 신규 접수 저장, 중복 skip, 운영 확인 등 처리 분류 |
| `delivery_dynamodb_duration_seconds` | `operation`, `result` | 논리 SDK 요청별 시간·횟수. SDK 내부 재시도 포함 시간이며 물리 HTTP 시도 수·WCU/RCU가 아님 |
| `delivery_acceptance_latency_seconds` | 앱 공통 label | 최초 인입 시각부터 **신규 업체 접수 결과 저장 직후**까지. 최종 전달 시간이 아님 |
| `delivery_acceptance_invalid_timestamp_total` | 앱 공통 label | 인입 시각이 없거나 현재보다 미래여서 지연 계산에서 제외한 횟수 |

`stage`는 `api_publish`(Kafka ack), `ingress_process`(listener 업무 처리), `ingress_store`(저장 또는 기존 원본 조회), `ingress_publish`(Dispatch 발행 ack), `dispatch_process`, `dispatch_claim`, `dispatch_http`, `dispatch_store`다. 성공한 claim에는 중복·운영 확인 판정도 포함된다. `dispatch_process` 성공도 신규 발송 성공만 뜻하지 않으므로 처리량은 outcome을 함께 본다. `dispatch_http`는 timeout·전송 오류·업체 접수 거절을 failure로 기록한다.

`outcome`은 `ingress_forwarded`, `ingress_dlt`, `ingress_dlt_failed`, `dispatch_accepted`, `dispatch_duplicate`, `dispatch_in_progress`, `dispatch_review`다. DLT 저장 ack 이후만 `ingress_dlt`이며 실패는 별도다. `dispatch_accepted`는 결과 저장까지 성공한 새 발송만 증가한다. `dispatch_review`는 운영 확인 상태를 관찰한 횟수이지 고유 운영 확인 요청 수가 아니다.

DB `operation`은 `put_item`, `get_item`, `update_item`, `describe_table`, `create_table`, `other`로 제한한다. `result=condition_failed`는 멱등성 경합을 일반 저장 장애인 `failure`와 구분한다. 정상 흐름의 Put 1회·Update 2회는 계속 유지된다. DB 계측은 API에서 별도 저장을 만들지 않는다.

구간 Timer는 단조 시계를 사용하고, 인입→접수 지연은 프로세스 간 wall clock 차이라 시계 동기화가 필요하다. 접수 지연 histogram 상한은 7시간이며 업무 만료를 구현한 것은 아니다. 다음은 Prometheus에 시계열을 수집한 이후 사용할 예다. 로컬 Prometheus와 Grafana 구성은 [대시보드 실행 문서](19-그라파나-대시보드-실행과-PPT-항목-대응.md)를 따른다.

```promql
# 신규 업체 접수 결과 저장 TPS
sum(rate(delivery_outcomes_total{application="dispatch-worker",outcome="dispatch_accepted"}[1m]))

# HTTP 업체 호출 구간의 성공 p95(초)
histogram_quantile(0.95, sum by (le) (
  rate(delivery_stage_duration_seconds_bucket{application="dispatch-worker",stage="dispatch_http",result="success"}[1m])
))
```

JVM·프로세스·Kafka client 지표도 자동 노출된다. Kafka client의 lag는 fetch 위치 기준일 수 있어 업무 처리 완료나 committed offset의 적체와 같다고 가정하지 않는다. **broker의 group offset과 끝 offset 비교, 첫 미커밋 record의 Kafka timestamp 기반 대기 시간, 실행별 시계열 보관은 후속 [PoC 도구](15-격리된-성능-PoC-실행과-결과-대조.md)에 구현했다.**

## 4. 시뮬레이터 설정과 관측

| 설정 | 기본값 | 의미 |
|---|---:|---|
| `SIMULATOR_DEDUPLICATE` | `false` | 기본적으로 같은 key를 다시 호출하면 매번 처리 효과가 생김. true일 때만 최초 정상 응답 재사용 |
| `SIMULATOR_RESPONSE_DELAY_MILLIS` | `0` | 처리 기록 후 응답 전 대기. 0~60,000ms. 실행 간 값을 바꿔 0/50/200ms 비교 가능 |
| `SIMULATOR_MAX_TRACKED_KEYS` | `200000` | 프로세스가 보관하는 최대 고유 key 수. 1~1,000,000 |

기존 payload의 `forceFail=true`는 500 응답이며 처리 효과는 없다. **응답 지연은 효과 기록 뒤에 적용**하므로 고객 측 HTTP timeout이 업체 미처리를 뜻하지 않는다. 지연 비교 시 Worker read timeout·lease와 시뮬레이터 HTTP thread 수를 함께 기록한다. 처리 전/후 연결 강제 단절, TCP·웹훅·동적 장애 스케줄은 아직 없다.

`simulator_calls_total`은 controller에 바인딩된 요청이 ledger에 들어온 횟수다. JSON 파싱·필수 헤더 단계에서 거절된 HTTP 요청은 HTTP 지표에만 나온다. `simulator_effects_total`은 실제 처리 효과, `simulator_deduplicated_total`은 외부 중복 제거로 생략한 효과, `simulator_forced_failures_total`은 강제 실패, `simulator_capacity_rejections_total`은 보관 용량 초과다. `simulator_tracked_keys`는 보관 중인 고유 **attempt key** 수이며 실패만 있었던 key도 포함한다. 전체 Delivery 수와 혼동하지 않는다.

`/actuator/simulator`는 위 집계와 설정을 제공하고 `/{key}`는 해당 key의 `calls`, `effects`만 제공한다. 업무 payload나 결과 조회 응답이 아니며 시험 결과 대조용이다. Dispatch에는 이 관리 조회를 호출하는 코드가 없고, 발송 여부·복구 판단은 이 정보에 의존하지 않는다.

보관 한도에서 새로운 key는 503으로 거절하고 기존 자료를 자동 삭제하지 않는다. 기존 key 관측은 계속 가능하다. 독립 실행 전 앱을 재시작하거나 입력 규모에 맞게 한도를 설정하며, 재시작 전 자료를 수집한다. 메모리 자료는 내구성·운영 멱등성의 근거가 아니고, 재시작을 포함한 시험은 실행 구간을 분리해서 해석한다.

## 5. 검증과 다음 작업

`smoke --metrics`는 API 관리 조회의 무인증 401, 요청 2건의 202·Kafka ack 지표, Ingress 저장/발행, Dispatch 신규 접수 저장과 중복 skip, DynamoDB 정상/조건 실패 호출 수, histogram 노출을 확인한다. 마지막으로 **외부 중복 제거를 끈 상태에서 해당 attempt의 calls=1·effects=1**을 대조한다. 지표 delta는 다른 트래픽이 있을 수 있어 하한으로 검사하고, 시뮬레이터의 해당 key는 정확히 1회인지 검사한다.

단위 시험은 비동기 ack 대기·실패 원인 보존·활성 수 반환, 잘못된 시각, 결과 저장 실패의 성공 집계 방지, 시뮬레이터 동시 호출 20건의 중복 제거 on/off와 한도·실패·지연을 검사한다. 실제 앱 소량 검증도 통과했다. 후속 부하 도구와 소량 대조를 거쳐 첫 측정까지 진행했다. [측정 결과와 한계](16-1차-성능-PoC-측정-결과.md)에 10·50 TPS 통과와 100 TPS 중단을 기록했다.

상시 수집·대시보드·알림을 포함한 구현 범위와 미구현 작업은 [모니터링 현황](18-모니터링-구현-현황과-구축-순서.md), 지표를 이용한 성능 개선 과정은 [후속 비교](17-워커-동시-처리와-발행-대기-성능-비교.md)에 정리했다.
