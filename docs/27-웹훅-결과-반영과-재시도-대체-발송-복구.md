# 웹훅 결과 반영과 재시도·대체 발송 복구

> 2026-09-25 v2 적용: ORIGIN/STEP, Kafka 고정 회차 재시도, STEP 최종 이벤트와 SQL 이후 삭제, Redis 완료 TTL을 구현했다. 아래 이전 저장 구조는 v1 기준선이다. 현재 단계별 경계·장애 대응은 [최신 구현·검증](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md)을 우선한다.

> 이 문서는 978f44e 시점의 결과 처리 구현 기록이다. 후속 자동 웹훅과 실제 흐름 검증은 [시뮬레이터 통합 검증](28-시뮬레이터-자동-웹훅과-발송-결과-통합-검증.md)에 기록했다.

구현·검증일: 2026-09-24. 업체 웹훅을 실제 Attempt에 연결해 성공 반영, 실패 코드별 재시도·허용된 2차 발송, 중복·만료 후 폐기를 구현했다. **Attempt의 전달 성공과 고객에게 최종 결과를 통지하는 전체 완료는 다르다.** Delivery 최종화 event·이력·고객 통지·주기 만료는 후속이다.

## 실제 처리 흐름

```text
receipt-api 인증·형식 검증 → Kafka ack 후 202
→ Dispatch 앱의 별도 Receipt Consumer
→ Attempt·업체·단계·호출 회차·기한 확인
→ 중복 기록과 Attempt 변경을 한 DynamoDB 트랜잭션으로 저장
→ 필요한 재시도/2차 발송을 기존 Dispatch 경로로 실행
→ 인계가 완료된 뒤 Receipt Kafka offset 완료
```

현재 Result Processor는 `dispatch-worker` 프로세스 안에 있다. Topic은 `delivery.receipt-received.v1`, group은 `delivery-receipt-result-worker`이며 기존 발송 Consumer와 별도 factory·offset을 쓴다. RECORD ack, 자동 commit 비활성, 오류 시 입력 유지 방식을 적용한다. 설정 `dispatch.receipts.topic`, `dispatch.receipts.concurrency`(기본 3)로 조정하며 전역 `spring.kafka.listener.auto-startup=false`는 두 소비자 모두 중지한다. 별도 Result 앱으로의 확장·자원 격리는 아직 아니다.

## 호출 회차가 필요한 이유

기존 attemptId는 같은 업체·단계의 재시도에도 유지된다. 따라서 attemptId만 돌려받으면 첫 호출의 늦은 실패가 현재 재시도의 실패처럼 보일 수 있다.

HTTP 요청 JSON과 TCP 요청 프레임에 `invocation`을 추가했다. 최초 호출은 1, 세 번의 재시도는 2·3·4다. 내부에서는 이미 저장하는 retry_count+1을 사용하므로 회차용 별도 DB 항목이나 쓰기는 추가하지 않는다. HTTP의 Idempotency-Key와 TCP의 attemptId는 계속 동일하다. 업체 웹훅에는 해당 요청의 invocation을 그대로 넣는다.

```json
{
  "receiptId": "provider-result-0001",
  "deliveryId": "d8f89940-b10f-4b88-a1a8-30bf482cb68a",
  "attemptId": "c7a9f3a3-cf17-4e3a-99ce-c2153bb57180",
  "invocation": 2,
  "outcome": "FAILED",
  "code": "RETRY_1S",
  "occurredAt": "2026-09-24T00:00:00Z"
}
```

위 UUID는 형식 예시다. 실제 발송 요청에서 받은 ID를 사용해야 한다. event schemaVersion은 1로 유지한 선택 필드 확장이다. 구형 웹훅의 invocation 생략은 **아직 재시도하지 않은 최초 호출만** 허용한다. 재시도한 Attempt에서 회차 없는 웹훅은 추측하지 않고 Kafka 입력을 유지해 운영 확인 대상으로 남긴다. 이미 지난 명시적 회차는 폐기하고, 아직 보내지 않은 미래 회차는 오류로 보존한다. 구형 primary_deadline·route_order 생략 항목도 읽는다.

## 상태를 바꾸는 규칙

Attempt는 deliveryId·attemptId·provider·routeOrder가 모두 일치해야 한다. receipt의 attemptId도 기존 안정적인 ID 생성 규칙과 대조한다. 성공 202를 반환했던 수신 API 자체는 이 업무 검증을 하지 않으므로, 존재하지 않는 ID도 결과 소비 단계에서 격리 대상이 될 수 있다.

| 입력·현재 상태 | 처리 |
|---|---|
| DELIVERED 성공 웹훅 | 현재 회차의 PROCESSING·ACCEPTED·REVIEW_REQUIRED·미실행 RETRY_SCHEDULED를 DELIVERED로 변경 |
| FAILED + RETRY_1S / RETRY_10S | 최초 외 최대 3회, receivedAt 기준 지연 예약 후 기존 Dispatch 경로 실행 |
| FAILED + FALLBACK, 1차 | DECISION_PENDING 저장 후 원본 fallbackAllowed가 true일 때만 TCP 2차 연결 |
| FAILED + REJECTED | DECISION_PENDING. 고객 최종 실패 인계는 후속 |
| 미지의 실패 코드 | REVIEW_REQUIRED. 임의 재시도·대체 발송하지 않음 |
| 2차 FALLBACK | DECISION_PENDING. 3차 발송 없음 |
| 이미 DELIVERED 또는 DECISION_PENDING | 새 웹훅으로 닫힌 판단을 되돌리지 않음 |
| HTTP 응답으로 RETRY_SCHEDULED인데 같은 회차의 실패 웹훅 도착 | 기존 예약 유지. 지연을 다시 계산하거나 예약을 추가하지 않음 |
| 같은 회차에 이미 웹훅 판단을 저장함 | 다른 receiptId가 와도 재적용하지 않음. 결과 정정 API는 없음 |

**구현 판단:** 같은 호출의 실패 코드가 서로 충돌할 때는 먼저 저장한 판단을 유지한다. 단, HTTP 응답이 만든 아직 실행 전 재시도는 같은 회차의 성공 웹훅으로 취소할 수 있다. 새 회차를 이미 선점했다면 이전 회차의 성공도 현재 회차를 덮어쓰지 않는다. 이 규칙과 회차 판별은 외부의 중복 제거 기능에 의존하지 않는다.

웹훅 변경은 Attempt version을 증가시킨다. 이후 늦게 도착한 HTTP/TCP 접수 응답·실패 저장은 이전 version으로 쓸 수 없다. 발송 Consumer 재전달도 DELIVERED를 보고 추가 발송하지 않는다. 이미 네트워크로 나간 호출이나 정지했다가 재개한 이전 Worker의 외부 실행까지 취소하는 보장은 아니다.

## 만료와 처리 대기

새 결과는 **receivedAt과 결과 처리 진입 시각이 모두 저장된 단계 deadline보다 이른 경우만** 반영한다. 경계 시각과 같으면 만료다. 비교 시각은 해당 처리 호출의 시각이며 실제 DB 완료·고객 통지 시각의 상한 보장은 아니다. 1차는 최초 인입+3시간, 2차는 고정된 1차 판단+4시간이라는 기존 기준을 사용한다. 업체 occurredAt으로 기한을 연장하지 않는다.

**구현 판단:** 만료 전에 수신됐더라도 장애·큐 대기로 처리 시각이 기한을 넘겼으면 만료를 우선한다. 장기 장애 복구 후 이미 지난 일을 만료 처리한다는 기존 요구를 보수적으로 적용한 개발 기준이다. 처리 전에 수신됐다는 이유로 뒤늦게 상태를 성공으로 되돌리지 않는다. [설계 논의 항목](08-함께-결정할-설계-사항.md)에 판정 기준을 함께 기록한다.

새 늦은 웹훅은 상태·이력·멱등 marker를 쓰지 않고 로그만 남긴다. 기한 확인을 위한 consistent read는 필요하다. 이미 API가 Kafka에 인계한 전송 기록은 존재하지만 업무 결과로 반영하지 않는다. 늦은 1차 결과를 버리는 동안에도 아직 유효한 2차 결과는 독립적으로 처리한다.

**복구 예외는 새 늦은 결과의 적용이 아니다:** 만료 전에 이미 트랜잭션으로 판단을 저장했고 후속 발송 인계만 남은 동일 웹훅은, 저장된 결정을 이어서 실행한다. 기존 Dispatch의 기한 검사로 이미 만료된 호출을 차단한다. 이미 고정한 2차 deadline을 재시작 시각으로 바꾸지 않는다.

주기 만료 작업은 아직 없다. 따라서 ACCEPTED·REVIEW_REQUIRED가 웹훅 없이 남는 경우를 자동 탐색해 종료하거나 고객에게 최대 기한 내 통지하는 기능까지 구현한 것은 아니다.

## DynamoDB 저장을 추가한 이유와 비용

새로 상태를 바꾸는 웹훅에만 다음 두 항목을 하나의 `TransactWriteItems`로 처리한다.

| 항목 | 보관 내용·목적 |
|---|---|
| 기존 DELIVERY#id / ATTEMPT#id | 상태·version·receipt eventId·호출 회차·실제 결과 코드·수신/업체 시각·다음 재시도 시각 |
| RECEIPT#eventId / META | 정규화한 결과 내용의 SHA-256, delivery/attempt ID, 판단 상태, 후속 Dispatch 재개 여부, 생성 시각 |

marker에 원문 메시지 payload·자격증명·전체 웹훅을 복사하지 않는다. provider+receiptId로 만든 기존 eventId 계약을 유지하며, 같은 ID가 다른 Delivery·결과 내용으로 재사용되면 원래 판단을 덮어쓰지 않는다. 재전송마다 달라지는 receivedAt은 fingerprint에서 제외하고 업체 occurredAt과 invocation은 포함한다. 재전송 시 원래 내용을 유지해야 한다.

**왜 두 항목을 원자적으로 쓰는가:** marker만 먼저 쓰고 죽으면 상태를 반영하지 않은 결과를 중복이라고 건너뛸 수 있다. 상태만 먼저 쓰면 receiptId 재사용 충돌을 전역으로 판정할 근거와 후속 인계 의도가 따로 남지 않을 수 있다. 현재의 업체 단위 receiptId 계약과 Attempt 상태를 함께 보호하기 위해 트랜잭션을 선택했다. AWS는 트랜잭션의 모든 변경이 함께 성공하거나 실패하는 동작을 설명한다. 외부 HTTP/TCP 호출은 이 트랜잭션에 포함되지 않는다. [AWS TransactWriteItems](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html), 확인일 2026-09-24.

**최소화와의 절충:** 논리 쓰기 대상은 2항목이며, 일반 Put/Update 2회와 같은 비용으로 계산하면 안 된다. DynamoDB 트랜잭션은 각 항목에 준비·커밋 쓰기를 수행한다. 항목 크기·조건 실패·재시도에 따라 비용이 달라지며 실제 consumed capacity와 AWS 처리량은 이번 로컬 시험에서 측정하지 않았다. [AWS 트랜잭션 동작과 용량](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html), 확인일 2026-09-24.

접수 API의 DB 쓰기는 계속 0이다. 늦은 결과·지난 회차·이미 닫힌 판단에는 새 marker가 없다. 중복 재전달은 consistent read 후 기존 결정을 사용한다. 재시도·2차 발송에 원래 필요한 Attempt 저장은 별도다. Redis는 결과 멱등 판단에 사용하지 않는다. 작은 marker의 보관 기간과 완료 기록 정리는 기존 운영 정책 미정 항목이며 자동 TTL 삭제를 추가하지 않았다.

## 중간 장애 복구

- 트랜잭션 응답 유실: 상태와 marker가 이미 저장됐을 수 있다. 재전달에서 fingerprint가 같은 marker를 읽고 후속 인계를 재개한다.
- 저장 후 Dispatch 호출 전 중단: Kafka 입력을 완료하지 않아 새 소비자가 같은 저장된 결정을 이어받는다.
- 재시도 대기: receipt 입력을 유지한다. 시간이 되면 기존 Attempt를 조건부 선점한다. 재전달만으로 횟수·기한을 늘리지 않는다.
- 2차 효과 후 저장 실패: 기존 PROCESSING lease·운영 확인 경로를 따른다. 업체 효과를 조회하거나 무조건 다시 보내지 않는다.
- ID 충돌·아직 없는 Attempt·미래/불명 회차·잘못된 계약·DB 오류: 오류를 성공으로 처리하지 않고 입력을 유지한다. 별도 Receipt DLT와 운영 조치 도구는 아직 없다.

입력 유지 방식은 해당 파티션의 뒤 요청을 지연시킨다. 재시도 전용 경로·DLT·주기 복구가 후속이며 무기한 Kafka 보관을 보장하지 않는다. 기존 보관 기간·디스크 용량과 lag를 감시해야 한다. META·Attempt·receipt marker는 고객 결과/이력의 내구성 인계가 구현되기 전에 삭제해서는 안 된다.

## 실행·적용·관측

새 `receipt-api`와 `dispatch-worker` JAR를 빌드해 기존 local.sh로 실행한다. 최초 수신 형식·업체별 키는 [수신 API 문서](26-업체-결과-웹훅의-인증과-Kafka-접수.md)를 따른다. 새 API의 invocation 수용을 먼저 적용한 뒤, 회차를 보내는 새 Worker/업체 계약을 함께 적용한다. 이전 Worker가 보낸 재시도에 회차가 없는 웹훅을 임의로 최신 호출과 연결하지 않는다. 구버전 Worker는 DELIVERED 상태를 읽지 못하므로 혼합 실행·롤백을 무검증으로 진행하지 않는다.

이 구현은 기존 서비스에 자동 배포하지 않았다. 시뮬레이터는 요청의 invocation을 읽지만 아직 최종 웹훅을 자동 발행하지 않는다. Receipt topic에 있던 과거 입력도 새 group의 시작 위치에 따라 처리될 수 있으므로 잘못된 시험 ID·구형 회차 없는 재시도 기록을 사전 확인해야 한다. 이번 검증은 기존 업무 topic offset을 reset하지 않았다.

`receipt_process` 구간 지연과 성공 반영·판단 저장·중복·만료/지난 회차 폐기 관측 counter를 제공한다. 새 트랜잭션 SDK 호출은 `operation="transact_write_items"`로 구분한다. 관측 수는 원장의 고유 성공 수·고객 통지 성공률이 아니며 응답 유실 시 과소/과대 관측할 수 있다.

Grafana 외부 업체 화면에 웹훅 결과 처리 TPS·성공 반영 TPS·늦은 웹훅 폐기·트랜잭션 p95를 추가했다. 총 **7개 화면·96개 패널·84개 질의**다. 4개 PromQL은 기존 Prometheus에서 성공 응답을 확인했으며 구형 앱이므로 시계열은 0개였다. Grafana 컨테이너를 재시작하지 않았고 화면 provisioning 검증은 이전 Docker 런타임 문제로 미완료 상태를 유지한다.

## 검증 결과

**최종 171건 통과, 실패·제외 0건.** API 9·공통 11·Ingress 19·Dispatch 100·Receipt 19·시뮬레이터 13건이다. 전체 169건과 package를 통과한 뒤 TCP 응답보다 먼저 온 성공 결과와 구형 deadline 항목 호환 시험 2건을 추가해 Dispatch·공통 모듈을 다시 검증했다. 그 사이 운영 코드는 변경하지 않았다.

- 실제 DynamoDB에서 16개 동시 중복 웹훅이 한 번의 version 증가·한 marker로 수렴.
- HTTP/TCP 접수 응답보다 먼저 온 성공 웹훅, 뒤늦은 접수/실패 저장의 조건 실패, 재전달의 추가 발송 없음.
- 1차 실패 웹훅의 허용/비허용 대체 발송, 고정된 2차 기한, 최대 세 번 재시도, 2차 재시도와 3차 미발송.
- 구형 최초 웹훅 호환, 회차 불명·미래 회차·provider receiptId의 다른 Delivery 재사용 보존, 이전 회차 무시.
- 만료 시각 경계·만료 전 수신 후 큐 대기 결과의 DB 미변경, 늦은 1차 폐기와 정상 2차 성공의 독립 처리.
- 트랜잭션 응답 유실 후 후속 인계 복구. HTTP가 만든 재시도와 웹훅 실패의 중복 예약 차단.
- 실제 Kafka에서 판단 저장 후 인계 전 예외를 주입해 offset=1 유지 확인. 소비자를 정지하고 새 소비자로 시작해 offset=2와 2차 효과 1회 확인. 실제 OS kill 시험은 아니다.
- HTTP·TCP 실제 요청 본문의 invocation 전달, Receipt API의 회차 보존·범위 검증.

재시도·대체 호출 수 시험은 외부 중복 제거가 없는 클라이언트 대역을 사용했다. Kafka/DynamoDB는 실제 로컬 서버이며, HTTP/TCP 전송 계약은 별도 소켓 시험으로 검증했다. 시뮬레이터가 자동 웹훅을 생성하는 전체 E2E 시험이나 고 TPS·다중 AZ·리전 장애 시험은 아니다.

새 Dispatch JAR를 임시 포트에서 기동해 health=UP·receipt_process 지표를 확인했다. 업무 Kafka 소비는 끄고 실행했고 해당 자식 프로세스만 종료했다.

```bash
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:39092 \
JAVA_HOME=/path/to/jdk-21 ./mvnw -q package
```
