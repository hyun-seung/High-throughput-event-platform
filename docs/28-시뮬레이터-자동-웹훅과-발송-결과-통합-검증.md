# 시뮬레이터 자동 웹훅과 발송 결과 통합 검증

> a72d702 시점의 검증 기록이다. 후속 주기 만료·최종화는 [29번 문서](29-주기-만료와-요청-최종화-및-Kafka-인계.md)에 기록했다.

HTTP 1차·TCP 2차 시뮬레이터가 접수한 발송의 ID와 호출 회차로 실제 HTTP 결과 웹훅을 보내도록 연결했다. 외부 업체의 중복 제거를 끈 상태에서 내부 재전달·웹훅 중복이 추가 발송을 만들지 않는지 검증한다. 기본값은 비활성이므로 기존 접수 전용 성능 PoC의 부하 조건은 유지된다.

## 실행 설정

`.env.example`의 다음 값을 설정하고 `receipt-api`, `external-api-simulator`, `dispatch-worker`의 새 JAR를 실행한다. 기존 local.sh 실행 방법은 [로컬 환경 문서](06-로컬-개발-환경-실행-방법.md)를 따른다.

| 설정 | 기본값·의미 |
|---|---|
| `SIMULATOR_RECEIPTS_ENABLED` | false. true면 정상 접수된 발송의 결과를 자동 전송 |
| `SIMULATOR_RECEIPTS_PRIMARY_URL` | 1차 업체용 수신 API의 전체 URL |
| `SIMULATOR_RECEIPTS_SECONDARY_URL` | 2차 업체용 수신 API의 전체 URL |
| `RECEIPT_PRIMARY_SECRET`, `RECEIPT_SECONDARY_SECRET` | 수신 API와 공유하는 서로 다른 32~256자 키. 예제에 실제 키를 저장하지 않음 |
| `simulator.receipts.max-tracked` | 10,000회차. 발송 예약한 회차의 프로세스 내 기록 상한 |
| `simulator.receipts.max-pending` | 100건. 지연·HTTP 전송·재시도 중인 작업 전체 상한 |
| `simulator.receipts.max-attempts` | 웹훅 복사본당 최초 포함 최대 3번 전송 |
| `simulator.receipts.timeout-millis` | 전송별 2초. 응답 본문이 멈추는 경우도 시간 제한·취소 |
| `simulator.receipts.retry-delay-millis` | 웹훅 전송 실패 후 1초 대기 |

URL은 서버 설정에서만 읽고 메시지 본문에서 받지 않는다. HTTP redirect를 따라가지 않으며 업체별 키가 다른 목적지로 전달되는 것을 방지한다. 개발용 HTTP는 로컬 시험에 사용한다. 활성화하면 deliveryId·attemptId는 정규 UUID, invocation은 1~4여야 한다. 비활성일 때 기존 시뮬레이터 요청 계약을 유지한다.

웹훅의 202는 수신 API의 Kafka 접수 확인이다. 408·429·5xx·통신 실패·202 이외의 예상 밖 응답은 같은 본문으로 정해진 한도 내 재전송하고, 나머지 4xx는 해당 복사본의 전송을 중단한다. 시뮬레이터 전송 한도는 시험 설정이다. **고객 결과 통지의 최초 전송 후 최대 20회 재전송 정책과 별개**이며 고객 통지는 아직 구현하지 않았다.

## 메시지별 시험 시나리오

아래 필드는 원본 payload에 넣는다. 2차는 별도 `simulatorTcp…` 필드를 사용해 1차 실패 설정을 상속하지 않는다.

| HTTP 1차 필드 | TCP 2차 필드 | 값·기본값 |
|---|---|---|
| `simulatorReceiptCodes` | `simulatorTcpReceiptCodes` | 회차별 결과 배열 1~4개. 기본 `["DELIVERED"]`. 배열보다 회차가 크면 마지막 값 반복 |
| `simulatorReceiptDelayMillis` | `simulatorTcpReceiptDelayMillis` | 최초 웹훅까지 0~300,000ms, 기본 100ms |
| `simulatorReceiptCopies` | `simulatorTcpReceiptCopies` | 동일 결과를 1~5번 전송, 기본 1 |
| `simulatorReceiptCopyGapMillis` | `simulatorTcpReceiptCopyGapMillis` | 복사본 사이 0~60,000ms, 기본 100ms |
| `simulatorResponseDelayMillis` | `simulatorTcpResponseDelayMillis` | 접수 응답을 0~60,000ms 지연, 기본 0ms |

결과 코드는 `DELIVERED`, `RETRY_1S`, `RETRY_10S`, `FALLBACK`, `REJECTED`, `UNKNOWN`, `NONE`이다. NONE은 웹훅 미발송, UNKNOWN은 운영 확인 판정 시험이다. 기존 `simulatorResultCode`·`simulatorTcpResultCode`는 동기 접수 응답을 제어하고 위 배열은 최종 웹훅을 제어한다. 동기 접수 실패에는 자동 웹훅을 보내지 않는다.

예를 들어 아래 요청은 1차 실패 웹훅 후 허용된 2차 발송으로 넘어가고, 2차 실패 웹훅 후 1초 재시도하여 성공한다. 최초 메시지의 `fallbackAllowed=true`가 필요하다.

```json
{
  "simulatorReceiptCodes": ["FALLBACK"],
  "simulatorReceiptCopies": 3,
  "simulatorTcpReceiptCodes": ["RETRY_1S", "DELIVERED"]
}
```

웹훅 지연 0ms·접수 응답 지연 4,000ms를 조합하면 응답 순서 역전을 검증할 수 있다. HTTP 응답 지연에는 기존 전역 `SIMULATOR_RESPONSE_DELAY_MILLIS`도 더해진다. TCP는 기존 exchange timeout이 소켓을 닫을 수 있다. `simulatorTcpMode=close-after-effect`도 효과를 기록한 후 최종 웹훅은 보내며 접수 응답만 생략한다.

## 멱등·용량·복구 범위와 선택 근거

- 같은 단계·attemptId·invocation은 같은 receiptId를 사용한다. 한 프로세스에서 예약은 한 번만 하고, 명시적인 복사본과 통신 재시도에는 occurredAt을 포함한 동일 본문을 사용한다. 새 호출 회차는 별도 receiptId이므로 이전 실패와 새로운 결과가 충돌하지 않는다.
- 이 예약 중복 제거는 **웹훅 생성**에만 적용한다. 업체 발송 효과 중복 제거는 기존 `SIMULATOR_DEDUPLICATE` 설정이며 통합 시험에서는 false다. 결과 처리의 DB marker와 Attempt 조건부 갱신 검증을 대체하지 않는다.
- bounded semaphore로 대기 작업과 추적 항목을 제한한다. 추적 항목은 자동 축출하지 않는다. 상한 초과는 지표와 HTTP 503/TCP 응답 중단으로 드러나며, 업체 효과가 이미 생긴 뒤 예약이 실패할 수 있다. 이 경우 효과 중복이 생길 수 있으므로 성능 시험의 성공 표본으로 처리하면 안 된다.
- 시뮬레이터 상태는 메모리다. 프로세스 종료 시 미전송 웹훅이 사라지고, 재시작 후 같은 회차의 occurredAt이 달라지면 수신 측 충돌로 남을 수도 있다. **업체의 영속 outbox·무손실 재전송 구현이 아니다.** 종료 시 진행 작업을 취소하고 독립 시험마다 새 프로세스를 사용한다.
- 시뮬레이터에 DynamoDB 쓰기를 추가하지 않았다. 업무 멱등성 판단은 실제 Worker의 기존 저장 경계를 시험하고, 업체 측 시험 작업까지 업무 원장에 저장해 보장이 강화된 것처럼 보이지 않게 한다. 기존 receipt marker·Attempt 트랜잭션의 선택과 공식 근거는 [결과 처리 설계](27-웹훅-결과-반영과-재시도-대체-발송-복구.md)에 있다.

지표는 `simulator_receipt_events_total{outcome=...}`, `simulator_receipt_pending`, `simulator_receipt_tracked`다. outcome은 scheduled, http_attempt, acknowledged, retry, exhausted, rejected, suppressed, queue_full, tracking_full, cancelled, failed를 사용한다. acknowledged는 Kafka 접수 응답 횟수이며 고유 발송 성공 수가 아니다. 새 Prometheus 출력은 통합 시험 증거에 저장했다. 기존 Grafana 앱 배포·화면 갱신은 이번 변경에 포함하지 않았다.

## 재현 가능한 실제 흐름 검증

```bash
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:39092 \
JAVA_HOME=/path/to/jdk-21 ./mvnw -q package

JAVA_HOME=/path/to/jdk-21 .poc-tools/venv/bin/python scripts/poc/receipt_flow.py \
  --kafka localhost:39092 --dynamo http://localhost:18000
```

Python 환경은 [PoC 도구 준비](15-격리된-성능-PoC-실행과-결과-대조.md)의 `.poc-tools/venv`와 requirements를 재사용한다. 로컬 Kafka·DynamoDB 및 기존 `delivery_state` 테이블이 필요하다. 실행기는 임시 포트의 새 JVM 3개와 UUID topic·group을 사용한다. Dispatch·Receipt consumer의 topic/group은 설정으로 변경할 수 있고 기본 업무 이름은 유지했다.

**검증 시작점은 DispatchRequested다.** Ingress가 저장할 META를 시험용 ID로 직접 준비한 뒤 실제 Kafka에 입력한다. 실제 Worker → HTTP/TCP 업체 → 인증 Receipt API → Kafka → 결과 Consumer → 실제 DynamoDB까지 검증한다. 고객 최초 인입 API·JWT·Redis·Ingress 구간을 포함한 새 전체 시험은 아니다. 그 구간의 기존 PoC는 별도다.

시험 전용 topic은 각 1개 파티션으로 고정하고, 업무·결과 두 consumer의 committed offset과 end offset을 대조한다. 초기 실행에서 Receipt API의 기본 3개 파티션과 시험 probe의 1개 파티션이 어긋날 가능성을 발견해 수신 API에도 `receipt.partitions=1`을 전달하도록 보강했다. 보강 전 실행은 최종 증거로 사용하지 않았다.

기존 Docker 서비스는 재시작하지 않고 기존 업무 topic을 소비·삭제하거나 offset을 reset하지 않는다. 종료 시 자신이 시작한 프로세스와 topic/group, 생성한 Delivery·Attempt·receipt marker의 정확한 키만 정리한다. DB scan은 하지 않는다. `.poc-results/receipt-flow-…/`에 JAR·실행기 해시, 상태·호출/효과·offset 대조, 앱 로그, Prometheus 출력, 정리 결과를 보존한다. 무작위 인증 키는 증거에 저장하지 않는다.

## 검증 결과와 다음 작업

**자동 테스트 180건 통과, 실패·제외 0건. 실제 흐름 12개 통과.** 전체 179건 package 후 응답 본문 정지 시험과 전체 응답 제한 시간을 보강하여 시뮬레이터·공통 모듈을 다시 package했다. 최종 JAR로 아래 통합 시험을 실행했다.

최종 실행 ID: `receipt-flow-f4e676347d8d47a8ae4d77d2f46a1cf9`. 웹훅 202 응답 **25건**, Receipt Kafka 저장 **25건**, 최종 consumer lag 0. 시험 데이터 정리 오류 0건. [커밋된 검증 결과와 해시](검증-결과/2026-09-24-자동-웹훅-통합-검증.json).

| 실제 흐름 | 1차 / 2차 호출 수 | 확인 결과 |
|---|---|---|
| 같은 웹훅 3회 + Dispatch 재전달 | 1 / 0 | DELIVERED 상태·version 유지 |
| FALLBACK 웹훅 중복 + 대체 허용 | 1 / 1 | 2차 DELIVERED |
| FALLBACK 웹훅 + 대체 비허용 | 1 / 0 | 추가 업체 호출 없음 |
| 1차 RETRY_1S → DELIVERED + 이전 회차 지연 중복 | 2 / 0 | retry_count=1, 추가 재시도 없음 |
| HTTP FALLBACK → TCP RETRY_1S → DELIVERED | 1 / 2 | 2차 retry_count=1 |
| 1차 RETRY_1S 지속 | 4 / 0 | 재시도 3회 소진, DECISION_PENDING |
| TCP 접수 응답 유실 + 성공 웹훅 | 1 / 1 | 2차 DELIVERED, 추가 발송 없음 |
| 웹훅 1.5초 지연 | 1 / 0 | ACCEPTED → DELIVERED |
| HTTP 접수 응답보다 이른 성공 웹훅 | 1 / 0 | 응답을 4초 늦추는 동안 약 0.115초에 DELIVERED, 후속 덮어쓰기 없음 |
| TCP 접수 응답보다 이른 성공 웹훅 | 1 / 1 | 응답을 4초 늦추는 동안 약 0.112초에 DELIVERED, 후속 덮어쓰기 없음 |
| NONE 미발송 | 1 / 0 | 관찰 기간에 ACCEPTED 유지 |
| 만료 후 결과 도착 | 1 / 0 | Attempt 불변, receipt marker 미생성 |

소켓 테스트에는 503 재전송 본문 동일성, 401 중단, 지연·중복, 용량 상한, TCP 응답만 유실, 응답 본문이 끝나지 않는 서버의 timeout을 포함했다. 위 순서 역전 시간은 해당 실행에서 상태를 관찰한 시간이며 성능 기준선이 아니다. 기존보다 처리량이 높아졌음을 측정하는 부하 시험도 아니다. 다중 AZ·리전 장애·업체 영속 복구는 이 결과로 보장하지 않는다.

미수신 시험은 ACCEPTED 유지, 만료 후 웹훅 시험은 상태와 marker 미변경을 확인한다. **주기 만료 처리 자체는 아직 없다.** 다음 작업은 1차·2차 주기 만료와 요청 전체 최종화, 내구성 있는 finalized 인계다. 이어 고객별 최대 100건 HTTP 통지·최대 20회 재전송, 이력과 완료 기록 정리를 연결한다.
