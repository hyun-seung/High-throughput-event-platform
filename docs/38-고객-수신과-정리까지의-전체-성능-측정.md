# 고객 수신과 정리까지의 전체 성능 측정

2026-09-25. [전체 흐름 기능 검증](37-전체-호출-흐름의-격리-실행과-전수-대조.md) 다음 단계다. 기존 100 TPS 성능 결과는 업체 접수까지였으므로, 고객 최종 결과 수신과 발송 데이터 삭제까지 같은 속도가 나오는지 별도로 측정한다.

이 문서는 개선 전 기준선이다. 이후 성공 웹훅의 즉시 인계 변경과 같은 조건의 재측정은 [39번 문서](39-성공-결과의-즉시-Kafka-인계와-복구-검증.md)에 기록한다.

## 1. 재현과 실행 범위

```sh
# JDK 21, Docker 및 scripts/poc/setup.py의 도구 준비 후
./mvnw -DskipTests package
.poc-tools/venv/bin/python -m unittest discover -s scripts/poc -p 'test_*.py'
.poc-tools/venv/bin/python scripts/poc/full_flow_load.py --rates 10 100 --seconds 5

# 같은 입력, Redis 후보 조회 주기만 50ms로 바꾼 격리 비교
.poc-tools/venv/bin/python scripts/poc/full_flow_load.py --rates 10 100 --seconds 5 --lifecycle-poll-ms 50
```

실행마다 별도 Compose 프로젝트·포트·볼륨·테이블·토픽을 사용한다. 첫 컨테이너 시작 정체는 37번 문서의 상태 확인·1회 재시도로 대응한다. 종료 후 소유 프로세스·컨테이너만 정지하고 증거·볼륨은 보존한다.

k6의 constant-arrival-rate로 10 TPS·100 TPS를 각각 5초 입력한다. 예정 입력은 50건·500건이며 경계 시각의 1건 추가 iteration은 기존 대조 규칙대로 전수 포함한다. HTTP 대기가 길어져도 입력 목표를 낮추지 않으며 dropped iteration·응답 누락·202 이외 응답은 실패다. 요청 payload는 기존 `load.js`의 960자 message, 정상 HTTP 1차 성공만 사용한다. 업체 중복 제거는 끄고 고객 결과 수신기는 모든 요청에 204를 반환한다.

Ingress·Dispatch·Result consumer 동시성 3, lifecycle 동시성 기본 4, Redis 후보 조회 기본 1초, DDB 복구 조회 10분이다. 1차/2차 deadline은 3시간/4시간으로 두어 적체를 짧은 시험용 만료로 덮지 않는다. `--lifecycle-poll-ms`는 격리 앱의 비교 측정용이며 코드 기본값을 바꾸지 않는다.

## 2. 따로 보는 구간

모든 단계 지연은 k6가 해당 요청을 시작한 시각을 공통 기준으로 한다.

| 지표 | 종료 시각 / 의미 |
|---|---|
| API 응답 | k6 http_req_duration. Kafka 접수 확인까지 |
| 업체 결과 | resultAt. 업체 결과 웹훅 수신 시각 |
| 결과 확정 | finalizedAt. 불변 최종 결과 생성 시각; Kafka 발행 완료 시각과 다름 |
| SQL 저장 | delivery_history.stored_at. 최종 Kafka 소비 후 저장 |
| 고객 수신 | 테스트 수신기가 결과 묶음을 받고 204를 응답한 시점 |
| 데이터 정리 | delivery_cleanup_outbox.completed_at. ORIGIN·STEP 정리 완료 |

`completionTpsIncludingDrain`은 입력 시작부터 모든 고객 통지·데이터 정리와 Kafka 적체 해소를 관찰할 때까지의 시간으로 나눈 처리량이다. k6 기동과 2초 단위 관찰 오차가 포함되므로 시스템의 최대 지속 처리량으로 해석하지 않는다.

약 2초 간격에 수집 시간까지 더해져 생성되는 samples에는 요청·발송·결과 웹훅·최종 결과 Kafka lag, 누적 SQL 이력/통지/정리 건수, 업체 호출 수, Redis 일정 수가 들어간다. 여섯 앱의 Prometheus 원문을 샘플별 gzip으로 남긴다. SQL·조회·지표 수집 비용도 실행 환경에 포함되며, 수집이 15초 이상 멈추거나 wall/monotonic 시간이 1초 이상 어긋나면 측정을 실패 처리한다.

## 3. 전수 대조

- 시작 manifest와 API 응답의 iteration·요청 키를 대응시키고, 입력 수·k6 iteration·응답 수가 일치해야 한다.
- API requestKey 집합과 SQL 이력 집합이 일치해야 한다. 같은 수라도 ID가 다르거나 실행이 중복되면 실패다.
- 모든 결과가 1차 DELIVERED이고 고객 수신 본문이 SQL 결과와 같아야 한다.
- 모든 통지 DELIVERED·정리 DONE 이후, 요청별 업체 호출 1회·TCP 호출 0회·ORIGIN/STEP 부재를 다시 확인한다.
- 검증용 DynamoDB 읽기는 적체 해소 관찰 뒤 수행한다. 이 추가 조회를 업무 경로의 읽기 횟수로 합산하지 않는다.

k6 입력·요약, 단계별 지연 p50/p95/p99/max, Kafka/Redis 적체, 원본 SQL 결과, Prometheus 샘플, 환경·JAR/소스 해시, 정리 결과를 `.poc-results/<실행 ID>/`에 보존한다. 결과 대조기는 잘못된 ID 집합, 중복 이력, 고객 미수신/불일치, 정리 미완료, 음수 지연을 거부하는 시험을 포함한다.

## 4. 해석 범위

5초씩 한 번 측정하는 짧은 부하 시험이다. 워밍업·반복 실험·장시간 steady state·혼합 실패·AWS 장애를 포함하지 않는다. 10 TPS와 100 TPS 단계의 JVM 워밍업 상태도 같지 않다. 높은 입력 TPS를 받았다는 사실과 그 속도로 고객 결과까지 계속 처리할 수 있다는 사실을 구분한다.

DynamoDB Local의 처리 속도를 AWS RCU/WCU 비용·분산 성능으로 환산하지 않는다. 실제 프로세스 종료, 운영자의 수동 결과 처리, 다중 AZ 무손실은 별도 검증 항목이다.

`LifecycleScheduler`는 tick에서 사용 가능한 동시 작업 슬롯만큼 후보를 제출한다. 슬롯이 부족하면 남은 후보는 Redis에 보존하고 다음 tick에서 다시 시도한다. 기본 4개 슬롯·1초 간격에서는 작업 자체가 빨리 끝나도 다음 조회까지 쉬는 시간이 생길 수 있다. 50ms 비교는 이 처리량 제약을 확인하기 위한 실험이며, DDB 누락 복구 주기는 두 실행 모두 10분이다. 정상 후속 결과 발행과 장시간 만료 감시가 같은 Redis 후보 큐를 사용한다는 점도 함께 평가한다.

## 5. 측정 결과

두 실행 모두 요청별 고객 수신·SQL 결과·업체 호출·DDB 삭제 전수 대조를 통과했다. 정상 외부 호출은 요청당 한 번, SQL 이력/통지/정리는 입력 ID 집합과 일치했다. 기본값 실행은 51+500건, 50ms 실행은 50+501건으로 각각 총 551건이다. 경계 iteration도 제외하지 않았다. Python 시험 29개(기존 22개 + 부하 대조 7개)도 통과했다.

| Redis 주기 | 입력 | 실제 건수 | API p95 | 업체 결과 p95 | 고객 수신 p95 | 정리 p95 | 입력+배출 관찰 처리량 |
|---|---|---:|---:|---:|---:|---:|---:|
| 1초 | 10 TPS ×5초 | 51 | 676ms | 3.37초 | 14.22초 | 14.71초 | 2.67 TPS |
| 1초 | 100 TPS ×5초 | 500 | 68ms | 15.30초 | 118.23초 | 118.65초 | 3.86 TPS |
| 50ms | 10 TPS ×5초 | 50 | 735ms | 2.06초 | 4.22초 | 6.75초 | 3.86 TPS |
| 50ms | 100 TPS ×5초 | 501 | 41ms | 14.24초 | 15.45초 | 41.58초 | 10.09 TPS |

기본 100 TPS 구간의 입력+배출 관찰 시간은 129.67초, 50ms 구간은 49.68초였다. API 202가 빨라도 최종 결과 처리량이 같은 것은 아니다. 두 실행 모두 지속 100 TPS 완료 성능을 달성했다고 볼 수 없다.

### DynamoDB 읽기와 쓰기

각 실행의 첫 부하 직전~마지막 배출 샘플 사이 앱의 계측 카운터 차이다. startup 테이블 생성과 검증 도구의 후속 전수 조회는 제외한다. GetItem·Query 등 읽기 API 호출 수를 합산했으며 ConditionCheck를 별도 읽기 API로 더하지 않았다.

| 항목 / 총 551건 | 기본 1초 | 비교 50ms |
|---|---:|---:|
| 읽기 API 호출 | 5,083 | 6,938 |
| 요청당 평균 읽기 API | 9.23 | 12.59 |
| 성공 쓰기 API 호출 | 2,755 | 2,755 |
| 요청당 성공 쓰기 API | 5.00 | 5.00 |
| 실패한 트랜잭션 API 호출 | 13 | 155 |

조회 주기를 줄이자 읽기 호출은 약 **36.5% 증가**했다. 실패 트랜잭션 수도 늘었지만 현재 operation/result 계측만으로 실패를 모두 같은 원인으로 분류하지 않는다. 성공 쓰기 5회와 실패 호출·조건 확인·GSI·항목 크기를 반영한 실제 AWS 청구량은 구분해야 한다. 이 숫자는 RCU/WCU나 금액이 아니다.

### 확인한 대기 구간과 다음 개선

1. **최종 결과 Kafka 인계:** 기본 설정에서는 업체 호출·성공 웹훅 처리가 끝나고 Kafka lag도 0인 상태에서 Redis 후보와 SQL 미저장 건이 남았다. 코드의 4개 작업 슬롯·1초 tick 구조와 약 4건/초의 배출 패턴이 일치한다. 50ms 비교에서 고객 지연이 크게 줄어 이 주기가 주요 제약이라는 판단을 뒷받침한다.
2. **완료 데이터 정리:** 빠른 조회에서는 고객 통지와 SQL 이력이 전부 완료돼도 cleanup만 남았다. 정리 worker는 tick당 최대 20건을 순차 처리한 뒤 기본 1초를 기다린다. 이것이 다음 처리량 개선 대상이다.
3. **앞단도 추가 측정 필요:** 100 TPS 입력 중 요청/발송 Kafka 적체가 있었고 업체 결과 p95도 약 14~15초였다. 뒤쪽 두 구간 개선만으로 지속 100 TPS가 보장되지는 않는다.

**기본 Redis 1초·DDB 10분 설정은 유지했다.** 정상 결과를 주기 조회만 기다리지 않고 즉시 인계하는 경로와, 실패 시 기존 STEP·복구 일정으로 재인계하는 경계를 다음 작업에서 다룬다. 정리 worker도 원자적 삭제·SQL lease를 유지한 채 제한된 동시 처리/연속 배출을 검토한다. 단순 고빈도 조회를 운영 기본값으로 바꾸는 방향은 채택하지 않았다.
