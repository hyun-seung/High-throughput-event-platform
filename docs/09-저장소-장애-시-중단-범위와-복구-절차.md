# 저장소 장애 시 중단 범위와 복구 절차

기준: 2026-09-26 신규 v2 경로. 현재 구현의 중단·재개 경계와 남은 운영 준비를 구분한다. 제품의 내구성 조건·공식 근거는 [저장소 특성](07-저장소별-특성과-데이터-유실-복구-조건.md), 요청 한 건의 흐름은 [Call Flow](04-요청-접수부터-최종-결과까지의-전체-흐름.md)를 따른다.

## 1. 중단하는 범위

다른 필수 의존성이 정상이라는 조건이다. 저장소 한 곳이 실패했다고 전체 서비스를 일괄 중단하지 않으며, 필요한 내구성·선점을 확인할 수 없는 작업을 보류한다.

| 장애 | 계속 가능한 구간 | 보류·실패하는 구간 | 남겨야 할 근거 |
|---|---|---|---|
| Kafka 인계 불가 | 이미 저장된 DB 결과 보존 | 접수·웹훅 Kafka ack 불가 시 503. 실패한 후속 발행을 완료로 처리하지 않음 | Kafka 입력, ORIGIN·STEP의 원문·불변 최종 이벤트 |
| DynamoDB 읽기·쓰기 불가 | 인증·Kafka가 정상인 신규 접수와 업체 웹훅 수신 | ORIGIN 저장, STEP 선점, 결과 반영·재시도·만료 판단·정리 중 필요한 DDB 작업 | Kafka 입력·DLT와 기존 ORIGIN·STEP |
| PostgreSQL 불가 | 유효 JWT로 인증 가능한 요청, Kafka·DDB가 정상인 발송·업체 결과 처리 | 신규 토큰 발급 등 SQL 의존 기능, 이력 commit, 고객 통지 상태 변경·정리 예약 처리, DLT 이력 대조 | 최종 Kafka 입력과 ORIGIN·STEP, 이미 저장된 SQL 예약 |
| Redis 불가·소실 | TPS·Quota 제한을 우회한 접수, DDB 조건을 만족하는 발송 | Redis 일정·완료 표식이 보장되지는 않음. DDB 조건은 우회하지 않음 | DDB 복구 인덱스·실행 상태, SQL 최종 이력 |
| 복수 장애 | 모든 필수 조건을 만족하는 작업만 | 원장 확인이 안 되는 발송·삭제·인계 | 마지막으로 확인된 내구성 저장소 |

PostgreSQL 장애 중에도 새 로그인을 무조건 보장한다는 뜻은 아니다. Redis 제한 우회도 인증·Kafka ack·DDB 선점까지 생략하는 정책이 아니다. 적체가 보관 용량을 위협하면 별도 접수 제한이 필요하며, 자동 용량 제어가 모두 구현된 상태는 아니다.

## 2. 장애 구간에서 지키는 처리 순서

**Kafka:** 접수·업체 웹훅은 broker 저장 확인 뒤에만 성공 응답한다. timeout은 미저장의 증거가 아니므로 같은 요청 키로 재요청할 수 있다. ingress 오류는 제한된 재전달 후 DLT로 넘기며, DLT ack 실패 시 원본 offset을 유지한다. 최종 결과는 STEP에 남아 같은 ID·본문으로 다시 Kafka에 인계할 수 있다.

**DynamoDB:** 외부 호출 전 선점이 확인되지 않으면 호출하지 않는다. 조건 불일치는 기존 처리·경합일 수 있어 일반 연결 장애와 구분한다. 외부 호출 뒤 결과를 기록하지 못한 건을 새 발송으로 해결하지 않는다. 시작만 남은 불명확한 실행은 운영 확인·원래 기한의 만료 경로로 간다. DB 쓰기 timeout의 성공 여부가 불확실할 수 있다는 제품 특성은 [공식 오류 처리](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Programming.Errors.html)를 참고한다.

**PostgreSQL:** 이력·통지·정리 예약을 하나의 SQL 트랜잭션으로 저장한다. commit 전에는 최종 Kafka 입력을 완료하지 않고 DDB 원본도 보존한다. commit 후에는 고객 통지와 DDB 정리가 독립적으로 진행한다. DDB 삭제 후 SQL 정리 완료 응답이 불확실해도 같은 실행의 정리만 재확인하며, 새 실행을 지우지 않는다.

**Redis:** 만료 후보 조회는 기본 1초, DDB 누락 복구 조회는 시작 직후 한 번과 이후 기본 10분이다. Redis가 비어 있지 않아도 일부 일정 누락을 찾는다. 복구 후보의 실제 상태·회차·기한은 DDB에서 판정한다. 10분은 조회 간격이며 페이지 적체·장애를 포함한 완료 상한이 아니다.

SQL 저장 이후 Redis 완료 표식 설정에 실패해도 DDB 정리를 진행하는 것이 합의된 v2 정책이다. 이후 Redis 표식이 없고 DDB 조건까지 통과하면 새 실행이 허용된다. 장애 중 완료 표식과 우회한 Quota를 자동으로 완전히 재구축하는 기능은 없다. [현재 멱등 정책](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md).

### 지속 장애 중 Redis와 Lifecycle 호출 제한

Redis의 애플리케이션 호출과 Lifecycle의 복구 조회/작업에 프로세스 내부 백오프를 적용한다. 실패가 계속되면 기본 지연 상한이 1→2→4→8→16→30초로 증가하고, 매회 그 값의 50~100%를 무작위로 기다린다. 대기 후에는 각 제한기에서 한 건만 복구를 확인하고 성공하면 정상 호출을 재개한다. 이전에 시작된 요청의 늦은 성공·실패가 새 장애 상태를 해제하거나 지연을 계속 늘리지 않도록 세대를 구분한다. 대기 시간은 단조 시계를 쓰며, 업무 deadline은 기존 저장 값을 사용한다.

| 대상 | 장애 중 동작 | 복구 후 동작 |
|---|---|---|
| Redis 일정·완료 표식과 TPS/Quota | 같은 앱의 제한기를 공유. 대기 중 Redis 호출을 생략하고 기존 fallback 사용. TPS/Quota는 제한 없이 우회하며 잘못된 정책 응답은 오류 유지 | 다음 호출 한 건으로 확인. 정상 정책의 TPS/Quota 차단도 다시 적용. 누락된 일정은 DDB 인덱스로 복구 |
| Lifecycle DDB 복구 조회 | 한 샤드 조회 실패 시 나머지 샤드 조회 중단. 실패한 페이지 cursor 보존. 기존 기본 10분 주기도 계속 적용 | 샤드 순환과 페이지 탐색 재개. 복구 시점에는 Redis 후보보다 먼저 워커 자리를 확보해 Redis 누락 건의 기아 방지 |
| Lifecycle 개별 처리 | DDB 연결/5xx/throttling 또는 Kafka·인계 timeout이면 백오프. 자리가 모두 사용 중이거나 복구 확인 중에는 후보 조회도 보류 | 한 작업 성공 후 설정된 concurrency로 재개. 양쪽 기한이 지난 건은 외부 호출 없이 원래 기한으로 만료 |

조건 불일치나 개별 데이터 오류는 Lifecycle 전체의 저장소 장애로 처리하지 않는다. DDB 페이지 cursor를 진행해 오래된 오류 한 건이 다음 페이지를 계속 가리지 않도록 한다. Redis의 같은 잘못된 후보를 영구 격리하는 기능은 별도 범위다.

| 설정 | 기본값 | 의미 |
|---|---|---|
| `delivery.redis-recovery.initial-delay` / `max-delay` | `1s` / `30s` | Redis 공유 제한기의 초기·최대 지연 상한. 앱 실행 인자 `--delivery.redis-recovery.max-delay=30s` 등으로 지정 |
| `dispatch.lifecycle.failure-initial-delay` / `failure-max-delay` | `1s` / `30s` | Lifecycle 조회·작업의 각각 독립된 제한기. 환경 변수 `DISPATCH_LIFECYCLE_FAILURE_INITIAL_DELAY` / `DISPATCH_LIFECYCLE_FAILURE_MAX_DELAY` |
| `dispatch.lifecycle.recovery-poll-ms` | `600000` | 내구성 인덱스 복구 주기. 백오프가 이 주기를 단축하지 않음 |

지연 설정은 `1ms ≤ 초기 ≤ 최대 ≤ 1h`를 만족해야 한다. 정상 요청마다 DDB나 SQL에 백오프를 저장하지 않으며 정상 DDB **5회·7항목** 쓰기 예산은 유지한다. 재시작 시 제한기 메모리는 초기화되고 기존 DDB·Kafka·SQL 상태에서 복구한다. Pod별로 독립하므로 전체 호출 수는 Pod 수와 기존 동시 실행 수에 영향을 받는다. 이미 진행 중인 요청은 해당 클라이언트 timeout·재시도 설정에 따라 끝난다.

Prometheus 지표는 `delivery_redis_calls_skipped_total{operation=...}`, `delivery_redis_recovery_delay`, `delivery_lifecycle_query_recovery_delay`, `delivery_lifecycle_work_recovery_delay`와 `delivery_lifecycle_events_total{outcome="poll_deferred"|"query_deferred"|"query_failed"|"work_failed"}`다. delay의 단위는 초이며 대기가 끝나고 확인 중이면 0일 수 있으므로 0을 정상 복구 증거로 보지 않는다. 기존 Grafana Explore에서 조회할 수 있으며 전용 패널·경보 연결은 후속이다.

이 변경은 **애플리케이션에서 다음 저장소 호출을 시작하는 빈도**를 제한한다. SDK 내부 호출 예산은 아래 DynamoDB 항목에서 별도로 설정한다. Lettuce·Kafka 내부 재접속 설정 점검과 다중 Pod 동시 재시작·실제 장시간 단절에서의 재접속 수 측정은 남아 있다. 지연 중 생략된 Redis 쓰기는 자동 재전송하지 않는다. DDB 누락 복구와 합의된 완료 표식 소실 정책을 그대로 적용한다.

### SQL 통지·정리와 DLT의 장애 호출 제한

같은 백오프를 SQL 통지·정리 워커와 DLT 인계·재개에 적용했다. 각 워커의 제한기는 독립적이며, 연결 실패·시간 초과·저장소 과부하를 인식한다. SQL 데이터 충돌, DDB 조건 불일치, 원문 형식 오류를 저장소 전체 장애로 간주하지 않는다. 이미 진행 중인 작업은 취소하지 않으며, 지연 중에는 새 선점·시도 예산 변경·추가 백오프 저장을 하지 않는다.

| 대상 | 장애 중 동작 | 복구 경계 |
|---|---|---|
| 고객 통지 | SQL 실패 후 전체 고객의 새 선점을 잠시 보류. HTTP 실패 응답은 기존 고객 묶음별 재전송 일정으로 처리 | 기존 SQL lease가 끝나기 전에는 재발송하지 않음. 이후 동일 묶음 ID·본문과 남은 최대 21회 시도 예산 사용 |
| DDB 정리 | SQL/DDB 장애를 감지하면 해당 lane을 멈추고 새 SQL 선점을 보류. 선점된 건은 기존 재시도 예약을 시도하고 실패하면 lease를 보존 | DDB 삭제 응답 유실도 기존 SQL 예약으로 재확인. 이력·고객 통지 예약과 실행 ID·STEP 조건을 유지 |
| DLT 인계 | 내부 오류가 `UNCONFIRMED`로 반환되어도 기반 저장소 장애면 첫 건에서 중단. 대기 중 SQL/Kafka 조회를 생략 | 이미 commit된 원문·cursor 보존. 복구 확인 주기는 최대 1건 분류와 최대 1건 원문 조회 |
| DLT 재개 | 첫 기반 저장소 실패 이후 같은 묶음의 남은 작업을 호출하지 않음. 최소 경과 시간은 유지 | 최대 1건 PENDING으로 복구 확인. 저장된 동일 command·실행 ID·원래 인입 시각 사용 |

| 환경 변수 | 기본값 | 대상 |
|---|---|---|
| `CUSTOMER_NOTIFICATION_FAILURE_INITIAL_DELAY` / `CUSTOMER_NOTIFICATION_FAILURE_MAX_DELAY` | `1s` / `30s` | SQL 통지 워커. HTTP의 retry-delay와 별도 |
| `DELIVERY_CLEANUP_FAILURE_INITIAL_DELAY` / `DELIVERY_CLEANUP_FAILURE_MAX_DELAY` | `1s` / `30s` | SQL 선점·DDB 정리 워커 |
| `DLT_FAILURE_INITIAL_DELAY_MS` / `DLT_FAILURE_MAX_DELAY_MS` | `1000` / `30000` | DLT 인계와 PENDING 재개의 각각 독립된 제한기 |

DLT 연속 실행은 기존 주기와 남은 백오프 중 긴 시간을 기다린다. 인계가 기반 저장소 장애로 보류되면 그 주기의 PENDING 재개도 생략한다. 정상 인계 조회가 별도 재개 제한기를 해제하지 않는다. 단발 수동 plan/apply·운영 조회에는 이 반복 워커 제한기를 적용하지 않는다. [DLT 출력 해석](50-DLT-원장-대조와-기존-실행-복구.md#장애-중-대기와-출력-해석)을 참고한다.

추가 지표는 `delivery_notification_recovery_delay`, `delivery_cleanup_recovery_delay`와 각 `delivery_*_events_total{outcome="poll_deferred"}`다. delay는 초 단위이며 0만으로 정상 여부를 판정하지 않는다. 지표 노출까지 구현했고 전용 Grafana 패널·경보는 후속이다. 백오프는 메모리 상태이므로 정상 경로의 DDB **5회·7항목**과 SQL 쓰기는 증가하지 않는다. 고객 HTTP를 이미 받았는지는 우리 SQL만으로 확정할 수 없으며, 응답/기록 유실 후 동일 묶음 재전송의 실제 효과 중복 방지는 고객의 ID 중복 처리에도 의존한다.

### DynamoDB SDK 호출 시간과 내부 재시도

공통 Spring DynamoDB client에 호출 전체 시간·회차별 시간·SDK 최대 시도 수를 명시했다. 연결·소켓 timeout만으로 SDK 재시도까지 포함한 작업 시간을 제한할 수 없기 때문이다. AWS 공식 문서는 API 전체 timeout이 재시도·대기를 포함하며, 전체/회차별 API timeout은 기본으로 설정되지 않는다고 설명한다. [AWS timeout 설명](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/timeouts.html).

| Spring 설정 (`delivery.dynamodb.*`) | 기본값 | 적용 판단 |
|---|---|---|
| `api-call-timeout` | `10s` | 재시도 대기를 포함한 SDK 메서드 호출 하나의 예산 |
| `api-call-attempt-timeout` | `5s` | HTTP 시도 하나의 예산. 응답 바이트가 계속 도착해 소켓 timeout이 안 나도 적용 |
| `max-attempts` | `3` | 최초 포함 최대 3회. 외부 업체 발송 재시도 3회와 별개 |
| retry strategy | `STANDARD` | SDK의 재시도 가능 오류 분류·지수 지연·재시도 억제 사용 |

이 기본값은 프로젝트의 장애 대응 출발점이며 성능 최적값이나 AWS 권장 시간이라는 뜻은 아니다. `--delivery.dynamodb.api-call-timeout=10s` 같은 Spring 인자로 바꿀 수 있다. 양의 시간, `연결/풀 대기/소켓 ≤ 회차 ≤ 전체`, `1 ≤ max-attempts ≤ 10`을 시작 시 검사한다. 전체 예산·SDK의 실패 억제에 따라 최대 시도 수 전에 끝날 수 있다. 10초는 여러 DB 호출을 포함하는 워커 전체·업무 deadline의 상한이 아니고, 프로세스 정지나 OS 스케줄링까지 포함한 실시간 보장도 아니다.

STANDARD는 SDK가 권장하는 일반 전략이며 최대 시도 수를 지정할 수 있다. SDK의 회로 차단은 내부 재시도를 억제하고 최초 시도는 허용하므로, 앞서 구현한 애플리케이션 호출 제한과 함께 필요하다. [AWS 재시도 전략](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/retry-strategy.html). 인증·조건 불일치를 임의로 재시도 가능 오류로 바꾸지 않는다. 실제 사용한 SDK는 `2.54.12`다.

timeout은 미저장 증거가 아니다. 선점 결과가 불확실하면 외부 발송으로 넘어가지 않고 기존 Kafka/DLT·원장 복구를 따른다. 이미 쓰기가 반영됐거나 원격 요청이 나중에 끝날 수 있으므로 같은 실행·조건부 처리·기존 감사 재개를 유지한다. 정상 경로 DDB **5회·7항목**은 논리적 성공 쓰기 기준으로 유지되며 장애 중 전송 시도·과금 상한을 뜻하지 않는다.

기존 `delivery_dynamodb_duration_seconds_count`는 SDK 메서드 호출 수다. 새 `delivery_dynamodb_transport_attempts_total{operation=...}`는 SDK `beforeTransmission` 횟수로 내부 재시도를 포함한다. 후자는 전송 계층 진입을 센 값으로, 서버 수신·성공 쓰기·소비 용량을 증명하지 않는다. 전용 Grafana 패널은 후속이며 Explore에서 두 지표를 구분해 조회할 수 있다.

적용 범위는 ingress·dispatch·result의 공통 Spring client다. 별도 생성하는 운영 CLI client는 기존 예산을 유지하며 같은 설정을 자동 상속하지 않는다. DLT CLI에는 기존 전체 10초·회차 5초 제한이 있고 재시도 전략 통일은 아직 하지 않았다. Lettuce·Kafka와 별도 운영 client 점검을 이어간다.

## 3. 복구 후 재개 순서

1. **원인과 저장 사본을 확인한다.** 연결만 돌아온 것인지, 데이터 손실·오래된 사본 승격·스키마 변경이 있었는지 구분한다. 운영 복제·승격·권한과 용량 확인은 배포 환경의 절차가 필요하다.
2. **완료된 결과를 먼저 보존한다.** STEP 최종 이벤트, SQL 이력·통지·정리 예약을 대조한다. 이미 성공한 요청을 장애 후 일괄 만료·재발송하지 않는다.
3. **원래 기한으로 판단한다.** 1차 인입+3시간, 2차 1차 판단+4시간을 유지한다. 1차 만료를 늦게 처리해도 2차 기준은 원래 1차 deadline이다. 양쪽 기한이 모두 지났으면 업체를 호출하지 않고 만료한다.
4. **미인계와 미완료를 재개한다.** Kafka 재전달·Redis 후보·DDB 복구 조회·SQL 예약을 사용한다. DLT는 자동으로 사라지지 않으므로 별도로 확인한다.
5. **적체와 실제 결과를 확인한다.** lag·최장 대기, 결과 불명, DLT, 통지 소진·정리 보류, 요청별 이력·고객 수신을 확인한다. 누락을 offset 강제 이동이나 데이터 초기화로 숨기지 않는다.

운영 확인 중에도 deadline은 진행된다. 만료 후 웹훅은 로그·관측만 남기고 버린다. 장기 장애 후의 만료·통지가 실제 벽시계 기한 내 전달을 뜻하지는 않는다. 아직 기한이 남은 정상 요청을 일괄 만료할 범위는 미정이다.

### DLT와 고객 통지

DLT의 **ORIGIN 없음은 미발송 증거가 아니다.** [Java 복구 도구](50-DLT-원장-대조와-기존-실행-복구.md)는 기존 실행을 재개하며, 활성화된 SQL 이력 보존 범위에서는 초기 실패 원본도 조건부 복원한다. 발송 보류 원본을 예약한 뒤 SQL 주 DB를 다시 대조하고 활성화한다. intake는 DLT 원문과 독립 cursor를 SQL에 함께 저장하고 적격 건을 인계한다. NEW·PENDING/STARTED는 저장된 원문으로 재개하며 HELD·체크포인트 없는 구형 조치는 별도 확인한다. 이력 삭제·백업 복원 시에는 intake를 포함한 모든 복구 프로세스를 중단하고 복구를 비활성화한 뒤 보존 범위를 다시 확인한다.

DLT 조회 위치가 Kafka 보관 범위를 벗어나면 자동으로 다음 offset으로 옮기지 않는다. `RETENTION_GAP` 또는 `OFFSET_AFTER_END`와 범위를 출력하고 중단한다. SQL에 이미 저장한 원문은 계속 복구할 수 있지만 보존 전에 삭제된 원문은 별도 백업·접수 이력으로 확인해야 한다. SQL 보류 수·최장 보류 시각은 CLI에 출력하며 Grafana·외부 경보 연결은 후속이다.

SQL 보류 상세는 `operate-dlt.sh held/status`로 확인한다. 보류 원인을 해소했으면 최신 updatedAt·고유 actionId·조치자·사유를 지정해 재검토를 요청한다. 상태 변경과 감사는 함께 저장되며, intake가 기존 기한·멱등 조건으로 다시 판단한다. 응답 미확인은 같은 actionId로 재시도한다. 실행 예시는 [DLT 운영 절차](50-DLT-원장-대조와-기존-실행-복구.md#8-보류-조회와-감사-가능한-재검토)에 있다.

### 결과 불명·통지 소진·정리 대기 조회

2026-09-26부터 `inspect-delivery.sh`로 요청별 발송 상태와 고객별 운영 대상을 읽을 수 있다. Java CLI만 실행하고 Spring 앱·Kafka listener·scheduler는 시작하지 않는다. 외부 실행 도구는 Bash다. 로컬 PoC용이며 DB 접속 권한을 운영 사용자 인증·역할 검증으로 대체했다고 보지 않는다. 현재 조회는 V11까지 적용한 result worker SQL schema와 빌드된 JAR가 필요하다.

```sh
export JAVA_HOME=/path/to/jdk21
export OPS_DB_URL=jdbc:postgresql://localhost:5432/delivery
export OPS_DB_USER=delivery
export OPS_DB_PASSWORD=delivery  # 로컬 개발 계정
export OPS_DB_SCHEMA=delivery_results
# request만 필요. 아래 두 SQL 목록 명령에는 DynamoDB 연결이 필요 없음
export OPS_DYNAMODB_ENDPOINT=http://localhost:8000

bash scripts/inspect-delivery.sh request 42 '<requestKey UUID>'
bash scripts/inspect-delivery.sh notifications 42 - 20
bash scripts/inspect-delivery.sh cleanup 42 - 20
```

`requestKey`는 ORIGIN에 사용하는 UUID이며 외부 ClientMsgId 원문과 구별한다. 목록의 `-`는 첫 페이지다. `hasMore=true`이면 `nextAfterId`를 다음 호출에 넣는다. 응답 최대 100건, 요청별 SQL 이력 최대 20개, 현재 실행 STEP 최대 100개로 제한하고 더 있는지 표시한다. 목록은 고객별 범위로 조회하며 조회 사이의 변경까지 고정하는 스냅샷은 아니다.

| 명령 | 관찰 내용과 해석 |
|---|---|
| request | 현재 ORIGIN 실행, STEP 상태·버전·기한·lease·재시도·보류 사유, 해당 요청의 과거 SQL 결과·통지·정리 상태 |
| notifications | EXHAUSTED 묶음 ID·고객·건수·사용한 시도 수·오류 코드·변경 시각. 전송 본문과 목적지 URL은 출력하지 않음 |
| cleanup | PENDING 정리 예약의 결과/실행 ID·version·다음 시도·lease·생성 시각. DUE/BACKOFF/LEASED/LEASE_EXPIRED/MISSING_NOTIFICATION/RESOLUTION_PENDING 구분 |

결과 불명 후보는 `PROCESSING`인데 lease가 지났을 때 `RESULT_UNCONFIRMED`, 이미 운영 확인 상태이면 `REVIEW_REQUIRED`로 표시한다. 처리 중 단계의 기한이 지났으면 `EXPIRY_DUE`다. **조회는 만료 확정·재발송·결과 변경을 수행하지 않는다.** 만료는 기존 Lifecycle 경로에서 처리한다.

정리 PENDING은 정상 대기·임대 중일 수도 있어 “영구 보류”나 실패 원인으로 단정하지 않는다. 현재 예약에는 compactor의 상세 실패 사유가 저장되지 않으므로 결과 ID로 worker 로그를 대조한다. MISSING_NOTIFICATION은 정리에 필요한 SQL 통지 예약이 없는 관찰이다. DONE은 목록에서 제외한다.

정상 요청별 활성 조회는 ORIGIN 강한 일관성 GetItem 2회와 해당 실행 STEP Query 1회다. 전체 DynamoDB Scan이나 복구 GSI 순회는 하지 않는다. ORIGIN의 고객·실행·완료/복구 보류 표시가 도중에 바뀌면 STEP 결과를 버리고 `CHANGED_DURING_READ`를 반환한다. 각 읽기는 일관된 읽기지만 **SQL과 DynamoDB를 합친 원자적 스냅샷은 아니다**. STEP 자체의 진행·완료는 조회 직후에도 바뀔 수 있으므로 표시 시각의 관찰로 사용한다.

ORIGIN이 없으면 `NO_ACTIVE_ORIGIN`과 남아 있는 SQL 이력을 함께 반환한다. 완료 정리 후라면 이력이 있고, 이력까지 없더라도 미접수·유실·최종 실패를 단정할 수 없다. 저장소 오류는 빈 정상 결과로 바꾸지 않고 종료 코드 1로 실패한다. 정상 판독은 0, 사용법 오류는 2다.

원문 payload·고객 전송 본문·lease 소유 토큰은 출력하지 않는다. 조회는 상태·재전송 예산·기한·정리 예약을 바꾸지 않으며 정상 경로의 애플리케이션 DB 쓰기는 늘지 않는다. V9는 EXHAUSTED 목록용 SQL 인덱스만 추가한다. 결과 불명 확정은 아래 별도 조치 CLI로 실행한다. 통지 소진 후 추가 전송과 인증·권한 연결은 남아 있다.

고객 HTTP 실패는 이미 완료한 업체 발송의 재실행 사유가 아니다. 같은 고객 묶음·결과 ID로 최초+최대 20회 재전송하고, 소진하면 SQL에 EXHAUSTED와 결과를 보존한다. 재시작으로 시도 예산을 초기화하지 않는다. [통지 계약](31-고객-HTTP-묶음-통지와-재전송-복구.md).

### 정리 대기 수동 재조치

저장소 연결 복구 등 원인을 확인한 뒤, SQL에 보존된 결과의 정리를 앞당겨 다시 시도하도록 요청할 수 있다. 위 조회와 같은 `OPS_DB_*` 환경을 사용하는 별도 Java CLI다. 외부 실행 도구는 Bash이며 애플리케이션 워커를 함께 시작하지 않는다.

```sh
bash scripts/inspect-delivery.sh cleanup 42 - 20
# 조회한 resultEventId와 version, 이번 조치를 식별하는 새 UUID를 넣는다.
bash scripts/retry-cleanup.sh retry 42 '<resultEventId UUID>' 0 '<actionId UUID>' operator.test 'DynamoDB 연결 복구 확인'
```

조회 결과와 같은 고객·버전이며 PENDING이고, 유효한 lease가 없으며, SQL 이력과 고객 통지 예약이 함께 있을 때만 허용한다. 한 SQL 트랜잭션으로 다음 시도를 현재 시각으로 당기고 만료된 lease 토큰을 제거하며 버전을 올린 뒤 `delivery_cleanup_action`에 조치 ID·고객·결과 ID·기대 버전·작업자·사유·시각을 저장한다. 감사 저장에 실패하면 예약 변경도 rollback된다. 실제 처리에는 활성화된 기존 cleanup worker가 필요하다.

| 응답 | 의미와 후속 행동 |
|---|---|
| QUEUED | 감사와 재시도 예약이 commit됨. 정리 완료를 뜻하지 않으므로 이후 조회·로그 확인 |
| ALREADY_QUEUED | 같은 조치 ID와 모든 인자가 이전 성공 조치와 동일함. 이미 DONE이 되어도 다시 예약하지 않음 |
| ACTION_CONFLICT | 조치 ID에 다른 대상·버전·작업자·사유 등을 사용함. 원래 인자를 확인 |
| STALE_OR_INELIGIBLE | 버전 변경·다른 고객·DONE·유효 lease·SQL 증거 누락 중 하나. 다시 조회하고 상태 확인 |
| BUSY | 같은 조치의 잠금이 사용 중. 동일 ID·인자로 재확인 |

성공/기존 성공은 종료 코드 0, 조건 거절은 3, 실행 오류는 1, 사용법은 2다. 연결 끊김 등으로 응답을 못 받았다면 **새 조치 ID를 만들지 말고 동일 ID·인자로 다시 실행**한다. 거절된 요청은 상태를 바꾸지 않으며 성공 감사 행도 만들지 않는다. 사유에는 고객 원문·비밀 정보를 넣지 않는다.

재조치는 외부 발송이나 고객 통지 횟수·만료 기한을 바꾸지 않는다. DynamoDB에 직접 쓰지 않으며 기존 compactor의 실행 ID·완료 증거·STEP 버전 검사를 그대로 거친다. 증거가 불일치하면 원본을 보존하고 다시 대기한다. 만료된 lease의 이전 워커는 제거된 토큰으로 SQL 완료/재시도 상태를 바꿀 수 없다. 이미 진행 중인 DynamoDB 요청의 취소를 보장하지는 않으며 기존 조건부 정리가 경합을 보호한다.

V10은 SQL 예약의 `version`과 감사 테이블을 추가한다. 자동 워커는 기존 선점·완료·재시도 UPDATE에 버전 증가를 포함하므로 정상 경로의 SQL 호출 수와 DDB **5회·7항목**은 그대로다. 수동 조치 때만 예약 UPDATE와 감사 INSERT가 추가된다. 구버전 worker는 버전을 증가시키지 않으므로 V10 적용과 새 result worker 배포를 완료한 뒤 이 CLI를 사용한다.

현재는 localhost PostgreSQL에 접속하는 PoC 명령이다. `actor`는 입력한 감사 식별자이며 인증된 운영자 신원은 아니다. 운영 배포용 역할·접근 제어와 조치 UI/API는 별도 연결이 필요하다.

### 결과 불명 수동 확정과 미확정 감사 복구

`resolve-delivery.sh`는 **신규 v2의 REVIEW_REQUIRED 또는 lease가 지난 PROCESSING**에 대해 운영자가 확인한 최종 성공·실패를 반영한다. 단순 접수 ACK를 성공으로 확정하는 명령이 아니며, 추측으로 실행하지 않는다. 인자는 `inspect-delivery.sh request`에서 확인한 고객·requestKey·현재 실행 ID·attemptId·version을 사용한다. 확인한 근거는 사유에 남기되 원문·비밀 정보는 넣지 않는다.

위와 같은 `OPS_DB_*`, `OPS_DYNAMODB_ENDPOINT` 환경과 JDK 21을 사용한다. 외부 실행 도구는 Bash이며 업무 로직은 Java다.

```sh
bash scripts/inspect-delivery.sh request 42 '<requestKey UUID>'
bash scripts/resolve-delivery.sh decide 42 '<requestKey UUID>' '<deliveryId UUID>' '<attemptId UUID>' 2 '<actionId UUID>' SUCCEEDED operator.test '외부 처리 내역에서 최종 성공 확인'
# 최종 실패 확인이면 SUCCEEDED 대신 FAILED. 다른 의도에는 별도 actionId 사용.
bash scripts/resolve-delivery.sh pending 42 - 20
bash scripts/resolve-delivery.sh resume 42 '<actionId UUID>'
```

1. SQL `delivery_resolution_action`에 대상·기대 버전·결정·작업자·사유를 PENDING으로 먼저 commit한다. SQL 저장 실패 시 DynamoDB는 변경하지 않는다. 같은 ID의 인자를 바꾸면 ACTION_CONFLICT다.
2. 같은 조치의 SQL 행을 잠근 뒤 DynamoDB 트랜잭션으로 ORIGIN의 고객·실행·v2·미완료·DLT 미보류 조건과 STEP의 버전·상태·deadline·lease 조건을 검사한다. 판단 시각이 deadline 이상이면 새 결정은 반영되지 않는다. STEP 버전 증가·결과·조치 ID·판단 시각·즉시 복구 일정은 함께 저장한다.
3. SQL 감사를 APPLIED 또는 REJECTED로 확정한다. DynamoDB 응답 유실이나 SQL 후속 저장 실패 시 PENDING을 남겨 같은 조치를 재개한다. 이미 STEP에 같은 조치 ID가 있으면 다시 변경하지 않고 감사만 확정한다. APPLIED는 STEP 반영 완료이며, 고객 통지 완료를 뜻하지 않는다.

| 확인한 결정 | 이후 기존 처리 |
|---|---|
| SUCCEEDED | STEP DELIVERED → Lifecycle 최종 이벤트 → SQL 이력·고객 통지·정리 |
| 1차 FAILED | STEP DECISION_PENDING/FALLBACK_REQUIRED. 최초 요청에서 대체를 허용했을 때만 2차 발송. 2차 기한은 수동 판단 시각 + 설정된 4시간 |
| 2차 FAILED | STEP DECISION_PENDING/OPERATOR_CONFIRMED_FAILED → 최종 실패. 새 단계나 재시도 예산을 만들지 않음 |

기존 만료 기한·재시도 회차를 연장하거나 초기화하지 않는다. 실제 웹훅·자동 만료·다른 운영자가 먼저 상태/버전을 변경하면 수동 조치가 덮어쓸 수 없다. 성공 확정 뒤 늦게 저장하려는 발송 응답도 이전 버전으로는 반영되지 않는다. 이전 v1·ACCEPTED·RETRY_SCHEDULED·완료/정리된 실행은 이 명령의 신규 확정 대상이 아니다.

반영 뒤에는 활성화된 Lifecycle worker가 필요하다. CLI는 직접 업체를 호출하거나 Kafka로 최종 결과를 보내지 않는다. STEP의 내구성 복구 일정에 인계하며, Redis에 즉시 깨우기를 추가하지 않았으므로 기본 10분 주기의 DDB 복구 순회와 적체에 따른 지연이 있을 수 있다. 기한은 원래 값과 저장된 판단 시각으로 계산하며 복구 시각으로 다시 시작하지 않는다.

**PostgreSQL과 DynamoDB의 변경은 하나의 원자적 트랜잭션이 아니다.** 이를 숨기지 않고 미확정 조치를 조회·재개한다. 현재 STEP 버전이 그대로인 상태에서 조건 검사가 실패하면, 과거 타임아웃 요청이 늦게 반영될 가능성을 배제할 수 없는 경우 `PENDING_RECONCILIATION`을 반환한다. 자동 만료 등으로 버전이 바뀌거나 조치 표시가 확인된 뒤 `resume`으로 확정한다. 시간 경과만으로 “미반영” 감사 기록을 만들지 않는다. 기한 검사는 트랜잭션 요청 직전 애플리케이션 판단 시각 기준이며 저장소의 서버 commit 시각을 강제하는 기능은 아니다.

PENDING 감사가 있는 같은 고객·실행은 cleanup worker가 선점하지 않으며 조회에는 `RESOLUTION_PENDING`으로 보인다. **최종 이력 저장·고객 통지·자동 만료는 계속 진행**한다. 정리 재조치 CLI로 예약을 앞당겨도 이 보호를 우회하지 않는다. 운영자는 PENDING 목록을 확인해 같은 조치 ID로 재개해야 하며, 현재 자동 감사 재개 스케줄러는 없다. 판단을 재개한 뒤에도 근거 확인이 필요한 건은 기존 만료 흐름을 유지한다.

명령 종료 코드는 APPLIED/ALREADY_APPLIED/정상 목록 0, REJECTED/ACTION_CONFLICT/PENDING_RECONCILIATION 3, 저장소·실행 오류 1, 사용법 2다. 오류를 받았다고 새 조치 ID를 만들지 말고 `pending`과 기존 ID의 `resume`으로 확인한다. 목록은 고객별 최대 100건의 ID cursor 방식이며 사유 원문은 출력하지 않는다. 성공·거절 감사는 SQL에 보존한다.

V11 마이그레이션과 새 result worker의 정리 보호를 모두 배포한 뒤 사용한다. 정상 경로 DDB **5회·7항목**과 SQL 호출 수는 그대로이며, cleanup의 기존 SELECT에 PENDING 감사 존재 검사를 더한다. 수동 확정에만 SQL 감사 쓰기와 **ORIGIN 조건 검사 + STEP 1항목 갱신의 DDB 트랜잭션 1회**가 추가된다. 이는 일반 성공 경로 쓰기 예산에 포함하지 않는다. 현재 CLI의 `actor`는 입력 감사 식별자이고 인증된 신원이 아니며, 운영 역할·접근 제어 연결은 남아 있다.

## 4. 연결 복구와 데이터 복원은 다르다

- **Kafka:** 실제 로그 볼륨과 보존 범위·소비 offset을 확인한다. 기존 로컬 환경은 로그 경로에 익명 볼륨이 겹쳤던 이력이 있어, 무심코 컨테이너를 재생성하지 않도록 기동 검사가 있다. [기존 데이터 이관 절차](47-Kafka-장애-시-접수-보류와-결과-복구-검증.md#3-시험-중-발견한-kafka-데이터-마운트). 보관 기간은 소비 완료를 기다리지 않으므로, 긴 장애에는 보관 연장·별도 보관과 용량 계획이 필요하다.
- **DynamoDB:** PITR은 과거 상태를 새 테이블로 복원하는 절차다. 이후 이미 외부에서 처리한 사실을 자동 복원하지 않는다. 격리 상태에서 보존 원본·SQL 결과와 대조하고, 확인 불가능한 건은 운영 확인한다. 시뮬레이터의 시험 전용 관측 API를 업무 결과 조회로 우회 사용하지 않는다.
- **PostgreSQL:** 성공 commit을 보존한 사본인지 확인하고 이전 primary의 쓰기를 차단한 뒤 승격한다. 기본 비동기 복제나 오래된 백업만으로 무손실을 단정하지 않는다. 유일 키·트랜잭션으로 commit 응답 유실의 중복 반영을 제어한다.
- **Redis:** AOF/RDB·복제는 복구 수단이지만 최근 성공 쓰기·모든 장애의 무손실 보장은 아니다. TPS/Quota 우회, 완료 후 재발송 허용, 처리 중 DDB 보호를 각각 적용한다.

공식 기능과 복원 제약: [Kafka topic 설정](https://kafka.apache.org/40/generated/topic_config.html), [DynamoDB PITR](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/PointInTimeRecovery_Howitworks.html), [PostgreSQL 복제](https://www.postgresql.org/docs/17/warm-standby.html)·[PITR](https://www.postgresql.org/docs/17/continuous-archiving.html), [Redis 복제](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/). 프로젝트 적용 판단은 위 절차와 구분해 읽는다.
