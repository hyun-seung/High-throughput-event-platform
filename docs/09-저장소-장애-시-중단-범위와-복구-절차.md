# 저장소 장애 시 중단 범위와 복구 절차

작성·공식 근거 검토일: 2026-09-23.

이 문서는 **운영 설계안**이다. 사용자와 확정한 원칙, 제품의 공식 동작, 구현 제안, 현재 코드의 차이를 구분한다. 아래 자동 중단·복구가 모두 구현됐다는 뜻은 아니다. 저장소 역할은 [ADR-002 제안](adr/ADR-002-저장소-역할과-선택-이유.md), 제품별 내구성은 [저장소 특성](07-저장소별-특성과-데이터-유실-복구-조건.md), 업무 정책은 [설계 결정 목록](08-함께-결정할-설계-사항.md)을 따른다.

## 1. 확정한 운영 원칙

- 리전 전체 장애를 제외한 무손실을 목표로 하며, 가능한 한 서비스를 계속한다. 필요한 내구성 조건을 만족하지 못한 **해당 작업**을 중단하고 정상 구간은 유지한다.
- 접수 원본을 안전하게 저장하지 못하면 접수 성공을 반환하지 않는다. 외부 발송에 필요한 실행 상태를 안전하게 기록·판단하지 못하면 새로운 외부 호출을 시작하지 않는다.
- 원본·실행 상태·재시도 계획·최종 결과를 보존한다. 메모리에 쌓고 성공 응답하거나 완료 근거 없이 Kafka offset을 넘기는 것은 복구 방법이 아니다.
- 1차 HTTP, 2차 TCP 발송이며 2차 TCP 응답은 접수 확인이다. 최종 결과는 HTTP 웹훅으로 받는다. 외부 결과 조회 API는 없고 외부 중복 방지에 의존하지 않는다.
- 관찰·기록된 무응답은 3회 재시도한다. 1차 무응답 소진 시 허용 요청은 즉시 2차로 전환한다. 시작 기록만 남은 프로세스 종료 건은 운영 확인 대상으로 찾는다.
- 운영 확인도 만료를 막지 않는다. 테스트 기준 1차 3시간, 2차 4시간이며 전체 최대 7시간이다. 기준 시각을 재시작·재처리로 연장하지 않는다. 만료된 단계의 늦은 웹훅은 로그만 남기고 폐기한다.

**후속 확정:** 장기 장애에 묶인 작업은 복구 후 만료 처리한다. Redis TPS·Quota는 장애 시 전부 우회한다. 고객 결과는 동일 고객 최대 100건의 HTTP로 짧게 묶어 전송하고 최대 20회 재전송한다(최초 포함 최대 21회). 횟수·미통지 결과는 재시작 후에도 복원해야 하며, 한도 소진 후 결과 보존·운영 처리는 [통지 설계 제안](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)을 따른다. **아직 정할 것:** 장애 대상 구분, 작은 DynamoDB 완료 기록의 보관 기간, 복구 시간, HTTP ack·재전송 세부 계약. 확정된 업무 만료 시간을 장애 복구의 허용 시간과 같은 것으로 간주하지 않는다.

## 2. 한눈에 보는 중단 범위

다른 의존성이 정상이라는 조건에서 읽는다. 하나의 노드 장애에도 필요한 사본과 경로가 살아 있으면 그 사실만으로 서비스를 중단하지 않는다. '보류'는 원본을 보존한 채 해당 작업의 새 실행을 막는다는 뜻이다.

| 장애 | 신규 접수 | 새로운 외부 발송 | 업체 결과 웹훅 | 이력·조회 및 복구 근거 |
|---|---|---|---|---|
| Kafka의 해당 토픽이 내구성 있는 쓰기를 제공하지 못함 | 원본 토픽 저장 확인 불가이면 성공 응답 금지 | 필요한 작업 인계가 불가능한 구간 보류. 안전한 기존 실행은 아래 조건으로 마무리 | 내구성 인계 불가이면 수신 성공 응답 금지 | DB에 확정된 조회는 가능. 원본/미발행 작업 복구 필요 |
| DynamoDB 실행 상태 읽기·쓰기 장애 | Kafka와 접수 인증·정책이 안전하면 계속 가능 | 새 claim·상태 판단·결과 기록이 필요한 작업 보류 | Kafka 원장에 안전하게 받은 뒤 결과 반영은 대기 가능 | 실행 상태 조회는 불가/지연을 표시. Kafka 원본과 기존 실행 기록 보존 |
| PostgreSQL 장애 | 유효한 인증·정책을 다른 정상 경로에서 검증할 수 있는 요청은 가능 | PostgreSQL 실행 의존성이 없는 경로는 계속 | Kafka·실행 DB가 정상이면 계속 | 이력·정산 소비 보류. 신규 인증 발급·정책 변경 등 DB 의존 기능 제한 |
| Redis 장애·데이터 소실 | TPS·Quota 제한 전부 우회. 인증·내구성 확인은 유지 | 실행 원장이 안전한 경로는 계속. Redis 기반 TPS·Quota는 우회 | 필수 인증·내구성 인계가 가능하면 계속 | 캐시 조회는 원장으로 제한적 전환. 원본에서 재구축 |
| 여러 저장소 동시 장애 | 각 필수 조건을 모두 만족하는 작업만 수행 | 실행 기록과 복구 근거가 없으면 보류 | 독립된 내구성 인계가 없으면 성공 응답 금지 | 인메모리 우회나 복구 시점이 다른 사본의 무조건 결합 금지 |

이력 DB 장애를 이유로 HTTP/TCP 발송까지 일괄 중단하지 않는다. Redis 장애 시 TPS·Quota 우회는 사용자 확정 정책이다. 인증이나 내구성 확인까지 생략하는 정책은 아니다. 접수 가능 여부는 **해당 요청에 필요한 의존성**으로 판정한다.

## 3. 공통 감지·중단·재개 절차

### 감지

연결 확인만으로 정상 판정하지 않는다. 실제 읽기·쓰기 오류, 지연, throttling, 복제 상태, consumer lag, 가장 오래된 미처리 작업, 만료까지 남은 시간, 보관 여유를 함께 본다. DB 전체 장애와 특정 테이블·파티션·고객 요청의 장애를 구분한다. 오류율 임계치·관찰 시간·복구 확인 횟수는 운영 설정으로 두며 수치는 미정이다.

### 중단

1. 장애가 난 의존성을 사용하는 새 작업을 제한한다. 일시 오류는 제한된 backoff로 재확인하며 재시도 폭주를 막는다.
2. Consumer는 해당 파티션의 신규 처리를 pause하거나 안전하게 중단한다. poll·heartbeat와 프레임워크 제약을 지키고, 재할당 시 진행 중 작업을 인계한다. 처리 스레드를 장시간 sleep시키는 방식은 피한다.
3. offset은 업무 완료 또는 **검증된 내구성 인계** 뒤에만 넘긴다. 뒤쪽 record가 먼저 끝났다고 앞의 미완료 record를 건너뛰어 commit하지 않는다. Retry/DLT 발행 실패도 원본 완료가 아니다.
4. 이미 시작한 외부 호출은 없던 일로 되돌릴 수 없다. 응답을 받으면 원래 시도의 결과 저장만 재시도하며, DB 오류 복구를 외부 재발송으로 대체하지 않는다.
5. 결과 기록에 실패하고 프로세스까지 종료되면 원장의 시작 기록으로 운영 확인 대상을 찾는다. 프로세스 로그만 남았다는 이유로 원본을 완료 처리하지 않는다.

**공식 근거:** Kafka는 입력 offset과 Kafka 출력의 transaction을 지원하지만 외부 DB·HTTP/TCP까지 원자화하지 않는다. pause/resume과 poll·commit 제약은 클라이언트 계약에 따른다. [Kafka 4.0 설계](https://kafka.apache.org/40/design/design/), [KafkaConsumer API](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html). 위 작업 순서는 이 계약에 대한 프로젝트 적용안이다.

### 재개

1. 복구된 저장소의 접속뿐 아니라 데이터 최신성·복제·권한·스키마·실제 확인 쓰기를 점검한다.
2. 오래된 primary/Worker가 동시에 변경하지 않도록 기존 경로를 차단한다. 내부 version 검사는 외부에서 이미 진행 중인 호출을 취소하지 못한다.
3. 저장된 완료, 미발행 후속 작업, 재시도 예정, 결과 미확인, 만료 대상을 나누어 대조한다. claim이 생성되지 않은 접수 원본도 누락 탐지에 포함한다.
4. 결과 반영·미발행 작업·만료 판정과 발송 재개를 같은 상태 규칙으로 처리한다. 도착해 있던 결과를 무시한 채 일괄 재발송하지 않는다. 만료 전 수신 후 큐에서 대기한 웹훅의 판정 기준은 별도 미정 사항이다.
5. 소량으로 재개하고 오류율·lag·원장 정합성·외부 처리 건수를 보며 처리량을 늘린다. 늦은 작업을 따라잡기 위해 무제한 동시 호출하지 않는다.

## 4. Kafka 장애

### 감지와 중단 기준

대상 파티션 leader, ISR, controller quorum, 저장 공간, produce 오류와 consumer lag를 확인한다. broker 한 대가 없어도 필요한 조건이 유지되면 계속 서비스한다. 원본 쓰기 확인이 불가능하면 신규 요청은 일시 실패로 응답하고 같은 고객 멱등키로 재요청할 수 있게 한다. 오류 코드·재요청 안내는 API 계약에서 확정한다.

Producer timeout은 '저장되지 않음'의 증거가 아니다. 서버가 저장했으나 응답만 유실됐을 수 있으므로 고객 재요청과 재발행을 동일 논리 요청으로 중복 제거한다.

### 단계별 동작

- **접수:** 원본 토픽의 저장 확인 전 `202` 금지. 메모리 큐로 우회하지 않는다.
- **웹훅 수신:** 내구성 인계가 안 되면 성공 ack하지 않는다. 시뮬레이터에 비성공 응답·응답 유실 시 웹훅 재전달을 구현해야 한다. 전송 재시도 기간·간격은 미정이며 재전달이 없으면 결과 원본 수신을 보장할 수 없다.
- **DB 저장 후 후속 Kafka 발행 실패:** 미완료 인계로 남긴다. 재처리에서 DB가 이미 완료라는 이유만으로 다음 발행을 생략하지 않는다. 같은 상태에서 안정적으로 후속 이벤트를 재구성하거나 outbox를 쓰는 안을 검증한다. 구현 전에는 이 복구 경로가 존재한다고 가정하지 않는다.

**Ingress 구현 반영:** 일시 처리 오류는 짧게 재전달한 뒤 DLT에 내구성 있게 인계합니다. DLT ack 실패 시 원본 offset을 유지합니다. DB 장애로 격리된 건은 복구 후 [DLT 운영 절차](12-접수-실패-격리와-DLT-재처리-절차.md)에 따라 원래 기한·완료 상태를 확인해야 하며 자동으로 신규 발송하지 않습니다. 실제 Kafka에서 DLT 파티션 부재·복구에 따른 offset 보존과 재개를 검증했습니다. 자동 replay·만료 인계 도구는 아직 없습니다.

- **이미 외부 호출 중인 작업:** DynamoDB가 정상이면 응답과 후속 발행 필요 상태를 보존한다. offset commit이 실패해 재전달되어도 완료된 외부 호출은 반복하지 않는다.
- **신규 발송:** Kafka 장애 중 새 작업을 계속하려면 다음 인계까지 복구 가능한 실행 경로가 검증돼야 한다. 해당 경로가 없으면 영향받는 Dispatch를 보류한다. 별도의 임시 큐를 자동 신설하지 않는다.

### 복구 순서와 금지 사항

정상 사본·leader/quorum을 확보한 뒤 쓰기 확인 조건, 보존 범위와 소비 offset을 대조하고 미인계 작업부터 재개한다. offset을 최신으로 강제 이동하거나 살아 있는 로그·볼륨을 삭제해 재생성하는 것은 무손실 복구가 아니다. 데이터가 없는 사본의 강제 승격, 내구성 설정 완화는 이 목표의 일반 복구 수단으로 사용하지 않는다.

retention 여유가 부족하면 신규 부하 제한에 더해 기존 record 보관 연장 또는 검증된 별도 보관을 수행해야 한다. 접수를 멈춰도 이미 저장된 record의 시간 기반 삭제는 진행될 수 있다. **보관 정책과 용량 한도는 Q7에서 결정해야 한다.**

**공식 사실:** `acks=all`과 `min.insync.replicas`로 확인 조건을 정하며 미달 시 쓰기가 실패할 수 있다. topic retention은 시간·크기에 따라 삭제된다. RF=3·minISR=2는 예시 구성이지 모든 장애의 무손실 증명이 아니다. [Kafka 4.0 topic 설정](https://kafka.apache.org/40/generated/topic_config.html). 위 복구·접수 정책은 프로젝트 판단이다.

## 5. DynamoDB 장애

### 중단 범위

throttling·일시 5xx·timeout과 잘못된 요청·권한 오류를 구분한다. 일시 문제만 제한 재시도하고 잘못된 요청을 무한 반복하지 않는다. conditional check 실패는 경합·이미 처리됨일 수 있으므로 DB 전체 장애로 판정하지 않고 해당 상태를 확인한다.

원본 Kafka가 안전하고 보관 용량·인증·정책 조건을 만족하면 API 접수는 계속할 수 있다. Ingress projection, 새 Dispatch claim, 실행 상태 기반 재시도·2차 전환·만료 변경은 필요한 DynamoDB 작업을 못 하는 동안 보류한다. 웹훅은 Kafka에 안전하게 수신하고 Result Processor의 DB 반영을 기다릴 수 있다.

외부 전송 전에 claim 저장이 timeout이면 실제 저장 여부를 확인한다. 현재 시도의 소유권을 확인하지 못했으면 호출을 시작하지 않는다. 외부 전송 후 결과 저장이 timeout이면 같은 조건부 변경의 반영 여부부터 확인하며 외부 발송을 재호출하지 않는다. 확인 자체가 불가능하면 미확인 상태를 유지한다.

**공식 사실:** DynamoDB의 일부 서버 오류에서는 쓰기가 성공했을 수도 있어 재시도 전 항목 확인과 조건부 쓰기 등이 필요하다. [DynamoDB 오류 처리](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Programming.Errors.html). 프로젝트에서는 이를 claim 소유권과 완료 기록의 재확인에 적용한다.

### 복구 순서

읽기·조건부 쓰기와 부하 수용 상태를 확인하고 완료/미완료 기록을 대조한다. 원본 projection 누락, 결과 반영 backlog, 후속 발행 누락, 예약 작업을 제한된 속도로 처리한다. GSI 조회만으로 소유권·최종 상태를 확정하지 않고 기본 항목의 최신 상태와 조건부 변경으로 판단한다.

AWS DynamoDB 내부 사본을 운영자가 임의 승격하는 절차는 없다. 서비스 오류·용량·클라이언트 설정을 복구하는 경우와 과거 시점 테이블 복원을 구분한다.

### 과거 시점 복원은 별도 절차

PITR은 새 테이블로 과거 상태를 복원한다. 백업 시점 이후 이미 외부에서 처리한 사실은 자동 복원되지 않으므로 새 테이블로 연결만 바꿔 일괄 발송하면 안 된다. [DynamoDB PITR](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/PointInTimeRecovery_Howitworks.html).

복원 테이블을 격리해 원본·독립적으로 보존한 결과·전환 기록과 대조하고, 이미 실행됐을 수 있으나 입증 불가능한 건은 운영 확인 대상으로 남긴다. 외부 조회 API가 없으므로 테스트 서버의 숨은 관측 기록을 운영 복구에 사용하는 우회는 금지한다. 복원 이후 기록을 복구할 원천이 없다면 RPO 0 충족으로 보고하지 않는다.

## 6. PostgreSQL 장애

### 중단 범위

목표 설계의 이력·정산 저장이 실패하면 그 Consumer Group과 완료 데이터 정리를 보류한다. 트랜잭션 완료 전 offset을 넘기지 않고 Kafka의 결과 이벤트를 보존한다. Kafka와 실행 DB가 정상이고 다른 필수 의존성이 없으면 외부 발송·웹훅 처리는 계속한다. 사용자가 확정한 [작은 DynamoDB 완료 기록 유지](11-멱등-정보-보관과-완료-후-정리-방식.md)에 따라 완료 여부는 실행 원장에서 판단한다. 이력 적재 장애만으로 그 판단을 생략하거나 완료 기록을 삭제하지 않는다. 정리 적체가 용량·내구성 조건을 위협하면 영향받는 경로에 backpressure를 적용한다. 이력 조회는 실패/지연을 표시하며 빈 결과를 '발송 이력 없음'으로 오해하게 하지 않는다.

**현재 코드의 주의점:** PostgreSQL은 `auth-module`에서도 사용한다. DB 장애 시 새 로그인·토큰 발급 등은 영향을 받는다. 이미 발급된 유효 JWT로 DB 없이 검증 가능한 경로만 유지할 수 있으며, 토큰 만료·권한 검증을 생략하지 않는다. 향후 정책 원본을 PostgreSQL에 두면 정책 변경과 새 정책 로드도 별도 제한한다.

### 복구 순서

1. primary, WAL, 디스크·연결 고갈과 복제 상태를 확인한다. 단순 접속 복구와 primary 손실을 구분한다.
2. failover가 필요하면 성공 commit을 보존한 적격 사본인지 확인하고, 이전 primary의 쓰기를 차단한 뒤 승격·접속 경로 전환을 수행한다. 오래된 사본을 가장 빨리 연결된다는 이유로 승격하지 않는다.
3. 연결 풀의 오래된 연결을 정리하고 읽기·쓰기, 스키마와 제약 조건을 확인한다.
4. commit 응답 유실 건은 안정적인 업무 키·유일성 제약으로 중복 반영을 막는다. 이력 쓰기 재시도가 외부 발송 재시도로 연결되지 않도록 한다.
5. 이력·정산 backlog를 제한된 속도로 재생하고 원본 이벤트 집합과 반영 건수를 대조한다.

**공식 사실:** streaming replication은 기본 비동기이며 미복제 commit 손실 가능성이 있다. 동기 복제의 확인 조건과 승격 가능한 사본을 함께 설계해야 한다. PITR에는 base backup과 필요한 WAL이 필요하다. [PostgreSQL 17 복제](https://www.postgresql.org/docs/17/warm-standby.html), [연속 보관과 PITR](https://www.postgresql.org/docs/17/continuous-archiving.html).

프로젝트 판단으로, 실행 원장까지 PostgreSQL에 통합하는 대안을 채택하면 장애 중단 범위도 DynamoDB 실행 원장 장애 수준으로 넓어진다. 현재의 이력용 중단 표를 그대로 재사용하면 안 된다. 저장소 선택과 운영 비용은 함께 비교한다.

## 7. Redis 장애 또는 데이터 소실

### 현재 동작과 목표 정책

현재 [RedisRequestLimiter](../event-api/src/main/java/event/api/requestcontrol/redis/RedisRequestLimiter.java)는 연결 실패·일부 timeout에서 요청 제한을 우회한다. 사용자는 장애 시 TPS·Quota 제한을 모두 우회하는 방향을 확정했다. 현재 코드가 처리하지 않는 장애 유형도 포함해 이 동작을 일관되게 검증해야 한다. 인증과 원장 쓰기 조건은 유지한다.

| Redis 용도 | 제한 운영안 | 복구 방법 |
|---|---|---|
| 조회·정책 캐시 | 유효한 캐시/버전 또는 원장 조회를 제한적으로 사용. 인증·권한 검증은 생략하지 않음 | 검증된 원본에서 다시 적재 |
| TPS | Redis 장애 중 제한 전부 우회. 별도 축소 TPS를 적용하지 않음 | 복구 후 정상 정책 재적용과 버킷 초기화 규칙 검증 |
| Quota·사용량 | Redis 장애 중 제한 전부 우회. 한도 초과 가능성을 허용 | 사용 이벤트가 있으면 대조·재생 가능. 정확한 보정 정책은 미정 |
| 완료·중복 방지 보조 캐시 | cache miss를 미발송으로 해석하지 않고 실행 원장 확인 | 복구 원장과 버전을 맞춰 재구축 |

### 복구 순서

Redis가 재접속됐다는 이유만으로 캐시와 카운터를 신뢰하지 않는다. role·승격 사본·영속화 상태와 필요한 정책 key를 확인한다. 오래된 캐시를 새 원장에 섞지 않도록 버전/세대를 구분하고, 필요한 데이터부터 제한적으로 재구축한다. 대량 cache miss가 DynamoDB/PostgreSQL 장애로 번지지 않게 조회량을 제한한다.

과거 스냅샷의 Quota를 그대로 현재 값으로 사용하거나 0으로 초기화해 정확한 사용량이라고 표현하지 않는다. 원본 사용 이벤트가 없다면 정확한 복구를 주장할 수 없다. TPS 초기화와 월 사용량 복구는 다른 문제다.

**공식 사실:** Redis 기본 복제는 비동기이며 WAIT만으로 모든 failover의 성공 쓰기 보존을 보장하지 않는다. [Redis 복제](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/). TPS·Quota 우회는 사용자 결정이며 캐시·사용량 복구는 별도 원본과 함께 검증할 설계다.

## 8. 장애 중 만료와 고객 결과

기한은 계속 흐른다. 1차는 인입+3시간, 2차는 1차 결과 판단+4시간을 테스트 기준으로 한다. 1차 만료 전환의 기준은 원래 1차 만료 시각이며, 복구 시각으로 바꾸지 않는다. 1차와 2차 기한을 모두 넘긴 뒤 복구했다면 기한을 새로 부여해 뒤늦게 외부 발송을 시작하는 방식은 기존 만료 규칙에 맞지 않는다.

만료 상태와 2차 전환을 기록할 저장소가 불가용하면 안전한 변경 자체가 보류될 수 있다. **데이터 보존과 7시간 내 고객 실제 결과 수신은 별도 보장**이다. 고객 결과 제공 경로까지 장기 중단되면 문서에 기한을 적는 것만으로 제시간 수신을 보장할 수 없다.

**사용자 확정:** 장기 장애에 묶인 미완료 작업은 복구 후 만료 처리하고 HTTP 고객 통지로 이어간다. 원래 만료 시각을 유지하고 장애 때문에 뒤늦게 1·2차 발송을 다시 시작하지 않는다. 이미 확정된 정상 완료 결과는 보존한다. '장기 장애' 판정 기준과 장애 중 새로 접수돼 기한이 남은 요청까지 포함할지는 추가 정의가 필요하다. 고객별 최대 100건의 짧은 묶음 전송과 완료 데이터 정리는 [후속 설계](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)를 따른다.

## 9. 복합 장애와 복구 완료 판정

복구 순서는 고정된 'Redis부터 기동' 같은 순서가 아니라, 해당 작업의 의존성으로 결정한다.

- Kafka만 복구되면 안전한 신규 원본 접수·웹훅 수신부터 유지할 수 있다. 실행 DB가 없으면 외부 발송 재개는 보류한다.
- 실행 DB만 복구되면 기존 완료·미완료 확인과 기록 가능한 진행 중 결과부터 보존한다. Kafka 인계가 불가한 새 흐름은 내구성 대체 경로가 검증되지 않았다면 보류한다.
- Kafka와 실행 DB 복구 후 결과·만료·미인계 상태를 대조하고 발송을 점진 재개한다. PostgreSQL 이력 backlog나 Redis 캐시 전체 재구축이 끝날 때까지 불필요하게 전부 기다리지 않는다.
- 고객 결과 제공에 PostgreSQL이 필수인 설계를 선택하면 그 경로는 PostgreSQL 복구도 필요하다. 목표 구조의 의존성이 바뀌면 중단 표를 갱신한다.

복구 완료는 healthcheck 성공만으로 선언하지 않는다. 접수 집합이 완료·진행·운영 확인·격리·만료 중 어디에 있는지 설명 가능해야 한다. 미발행 후속 이벤트, 원본 대비 누락, 복원 시점 불일치, 보관 만료 위험, 오류 재증가를 확인한다. 외부 실제 중복은 시뮬레이터 관측 지표로 별도 측정한다.

## 10. 구현·검증 상태와 남은 선택

현재 로컬 [Compose](../compose.yml)는 Kafka·Redis·PostgreSQL 단일 노드와 DynamoDB Local이다. 현재 코드에는 Kafka 접수 확인, 일부 conditional claim·완료 skip이 있으나, 이 문서의 자동 장애 격리·원장 복구·만료·TCP·웹훅·이력 처리 전체는 미구현이다. [현재 상태](01-현재-구현-상태와-남은-작업.md)와 [장애 시험 계획](03-장애-상황별-검증-계획.md)에 구현·검증 증거를 연결한다.

다음 시험은 정상 복귀뿐 아니라 데이터와 외부 효과를 확인해야 한다.

1. Kafka 저장 응답 유실, 후속 이벤트/DLT 발행 실패, 보관 기한에 근접한 backlog.
2. DynamoDB claim·결과 쓰기 전후 timeout, 외부 처리 직후 DB 장애, 과거 테이블 복원.
3. PostgreSQL commit 응답 유실·failover와 이력 재생, 인증 기능만 불가한 상황의 격리.
4. Redis 연결 장애·오래된 replica 승격·빈 데이터 재시작·재구축 폭주.
5. 복합 장애, 운영자 변경과 만료 경합, 복구 때 이미 두 단계 기한이 지난 요청.
6. 각 경우의 원본 보존, offset 인계, 불필요한 재발송, 고객 결과 지연·제공 성공 여부.

남은 선택은 장기 장애 대상 구분(Q4/Q5), 사용량 보정·복구 시간(Q5), 완료 기록·원본·이력 보관 기간과 재처리 허용 범위(Q7), 목표 부하와 최소 저장 설계의 비용 검증(Q8), 오류 코드·재시도 간격이다. 운영 명령·배포 배치와 실제 복구 시간은 구현·장애 시험 후 이 문서에 추가한다.
