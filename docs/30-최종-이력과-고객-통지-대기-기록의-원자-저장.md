# 최종 이력과 고객 통지 대기 기록의 원자 저장

작성일: 2026-09-25. 대상: `delivery-result-worker`, PostgreSQL 17, Spring Boot 4.1.0.

## 이번에 연결한 구간

```text
Dispatch의 작은 DynamoDB FINAL
→ delivery.finalized.v1 (Kafka, 동일 결과 재발행 가능)
→ delivery-result-worker / 별도 Consumer Group
→ PostgreSQL 트랜잭션 시작
  → delivery_history 1건
  → customer_notification_outbox PENDING 1건
→ COMMIT 성공
→ Kafka offset commit
```

이번 구현은 고객 HTTP 발송 전에 결과와 통지할 작업을 확보하는 단계다. 발송 결과 이력과 통지 예약을 같은 트랜잭션에 넣어, 이력만 있고 통지할 작업이 없는 중간 상태를 방지한다. 고객 HTTP 호출, 묶음 선점, 재전송 스케줄러, DynamoDB 정리는 다음 단계다.

원본·Attempt·receipt marker·FINAL은 아직 삭제하지 않는다. FINAL의 `PUBLISHED`는 Kafka 저장 확인이며 PostgreSQL 저장 확인이 아니다. 향후 정리 워커는 이력·통지 예약의 저장 확인과 완료 기록 유지 조건을 별도로 만족해야 한다.

## 왜 PostgreSQL에 함께 저장하는가

호처리의 선점·상태 전이는 기존 DynamoDB에 남긴다. 이번 저장은 완료된 발송의 조회용 이력과 독립적인 고객 통지 작업이므로 PostgreSQL에 둔다. 이 워커의 DynamoDB·Redis 읽기/쓰기는 0회다. Redis 복구 가능성에 통지 작업 보존을 의존하지 않는다.

PostgreSQL 트랜잭션은 여러 변경을 모두 반영하거나 모두 취소하며, 미완료 변경을 다른 트랜잭션에 노출하지 않는다. 이 기능을 이력과 통지 예약에 적용한다. [PostgreSQL 17 공식 트랜잭션 설명](https://www.postgresql.org/docs/17/tutorial-transactions.html). 다른 저장소 두 곳에 순차 기록하는 방법보다 이번 두 기록의 일치 여부를 단순하게 검증할 수 있다는 것이 프로젝트의 선택 이유다.

Kafka와 PostgreSQL 사이에는 분산 트랜잭션을 쓰지 않는다. Spring Kafka의 `RECORD` 방식은 listener 처리가 반환된 후 offset을 commit한다. 따라서 SQL commit 후 listener를 반환하고, 그 사이 실패하면 재전달을 받아 DB 유일 키와 불변 내용 비교로 중복을 처리한다. [Spring Kafka 공식 offset 설명](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html#committing-offsets).

상세 대안과 내구성 조건은 [ADR-018](adr/ADR-018-이력과-고객-통지-예약의-원자-저장.md)에 남겼다.

## 테이블과 중복 처리

기본 스키마는 `delivery_results`다. 기존 인증용 `public.users`와 분리하며 Flyway의 버전별 SQL로 생성한다. JDBC와 Flyway가 같은 `RESULT_DB_SCHEMA`를 사용한다. 운영에서는 승인된 스키마에 대한 이관 권한과 실행 권한을 배포 절차에 맞게 분리해야 한다.

| 기록 | 주요 내용 | 중복 방지 |
|---|---|---|
| `delivery_history` | 고객·발송 ID, 최종 DELIVERED/FAILED/EXPIRED, 사유, 단계·업체, 인입/결과/최종화/기한, 불변 결과 JSON | delivery_id PK, result_event_id UNIQUE |
| `customer_notification_outbox` | result_event_id, PENDING, 사용 시도 0회, 다음 시각 | result_event_id PK 및 이력 FK |

이력 JSON은 발송 본문이 아니라 작은 `DeliveryFinalized` 결과다. 조회용 열과 함께 보존해, PostgreSQL 시간 열의 마이크로초 정밀도보다 작은 차이까지 원래 이벤트 내용으로 비교한다. 동일 결과의 JSON 필드 순서나 공백은 중복 판단에 영향을 주지 않는다.

`INSERT ... ON CONFLICT (delivery_id) DO NOTHING`으로 최초 이력만 삽입한다. 신규라면 통지 예약을 추가하고 함께 commit한다. 기존이면 최초 결과 전체와 새 결과를 비교한다. 내용이 다르면 충돌로 실패하며 어느 쪽도 덮어쓰지 않는다. 같으면 기존 통지 예약의 존재를 확인하고 성공한다. 이미 진행한 횟수·다음 시각·상태는 갱신하지 않는다.

동시 삽입의 승자가 commit한 후 다음 SELECT에서 읽을 수 있도록 `READ COMMITTED`를 명시한다. [PostgreSQL 17 격리 수준과 ON CONFLICT 동작](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED). 이 구현은 중복 건마다 UPDATE를 수행하지 않는다.

기존 이력만 있고 통지 예약이 없으면 불변 조건 위반으로 멈춘다. 이미 전송하고 지운 기록인지 알 수 없으므로 새 PENDING을 임의로 만들지 않는다. 현재 이력·통지 예약 모두 자동 삭제하지 않는다. 향후 보관·정리 정책은 이 중복 처리와 함께 변경해야 한다.

통지 테이블은 총 21회(최초 + 재전송 20회)까지 저장 가능한 제약을 가진다. 현재 워커는 PENDING/0만 만든다. DELIVERED·EXHAUSTED 값은 후속 HTTP 처리용이며 아직 그 전이를 실행하지 않는다. 재전송 시점·선점·부분 응답 계약까지 구현됐다는 의미가 아니다.

## 실패 시 어떻게 멈추고 복구하는가

| 상황 | 남는 상태 | 복구 |
|---|---|---|
| 두 INSERT 중 하나 실패 | SQL 전체 rollback, Kafka offset 미진행 | DB 원인 해소 후 같은 event 재처리 |
| SQL commit 후 offset 확인 전 실패 | 이력·예약 존재, Kafka 재전달 가능 | 동일 내용 확인 후 offset 진행 |
| 결과 JSON 오류·ID 불일치·내용 충돌 | 해당 record offset 미진행 | 원인 조사·지원 코드/보존 인계 경로 마련 후 재개 |
| DB 연결 실패·timeout | 성공으로 처리하지 않음 | PostgreSQL 복구 후 기존 group으로 재시작/재시도 |
| 통지 대기 중 이력 중복 수신 | 기존 통지 진행 상태 유지 | 새 통지를 만들지 않음 |

현재 최종 결과 소비의 내구성 있는 DLT 인계는 없다. 오류는 기본 1초 간격으로 계속 재처리하며 로그만 찍고 건너뛰지 않는다. 잘못된 메시지는 같은 파티션의 후속 결과를 지연시킬 수 있다. 원인 해결 없이 offset을 앞으로 이동하거나 group을 바꾸는 것을 복구 절차로 사용하지 않는다.

기본 DB connection 대기는 3초, JDBC 연결 5초·socket 대기 15초, SQL 트랜잭션 timeout은 10초다. 트랜잭션 timeout은 모든 네트워크 지연을 정확히 10초로 끊는 보장이 아니다. 기본 소비 동시성은 3, 연결 풀 최대 6, 한 poll 최대 10건이다. DB 장애 동안 별도 발송 소비자는 진행할 수 있지만 적체 용량과 Kafka 보관 기한을 넘으면 안 된다.

현재 finalized topic의 기본 보관은 7일이다. offset만 유지한다고 Kafka 데이터가 영구 보존되지는 않는다. 장애가 retention에 접근하면 보관 기간·용량을 먼저 확보하고, topic의 시작 offset과 group offset을 대조해야 한다. 이미 범위를 벗어났으면 자동 reset으로 정상 복구됐다고 판단하지 않는다. FINAL에는 결과가 남아 있지만 PUBLISHED의 PostgreSQL 누락을 자동 대조·재발행하는 도구는 아직 없다.

## 실행과 관측

먼저 [주기 만료·최종화 문서](29-주기-만료와-요청-최종화-및-Kafka-인계.md)의 GSI 이관과 활성화 조건을 만족시켜 finalized topic을 준비한다. 새 워커가 임의 설정으로 topic을 자동 생성하지 않으며 topic 부재는 시작 실패다.

```bash
# .env의 PostgreSQL·Kafka 포트가 실행 환경과 일치해야 한다.
bash scripts/local.sh run delivery-result-worker
```

기본 설정: `RESULT_DB_SCHEMA=delivery_results`, `RESULT_HTTP_PORT=8095`, `RESULT_METRICS_PORT=19085`, `RESULT_CONCURRENCY=3`. group은 `delivery-result-worker-v1`, topic은 `delivery.finalized.v1`이다. 변경할 때는 `RESULT_CONSUMER_GROUP`, `FINALIZED_TOPIC`을 사용하며 발행 측 `dispatch.lifecycle.topic`도 동일하게 맞춘다.

관리 포트는 loopback이며 `/actuator/health`, `/actuator/prometheus`를 제공한다. `delivery_result_records_total{outcome="stored|duplicate|conflict|failed|invalid"}`과 `delivery_result_store_duration_seconds`로 저장·재처리를 관측한다. 지표에는 고객/발송 ID를 태그로 넣지 않는다. 카운터는 처리 시도 횟수이며 고유 미처리 건수가 아니다. 대기 건수는 PostgreSQL에서 별도 조회해야 한다.

새 워커의 Prometheus endpoint까지 검증했다. 기존 Grafana 스택에 워커를 상시 배포하거나 새 수집 대상을 등록한 상태는 아니다. HTTP 통지 구간까지 연결한 후 대기 건수·가장 오래된 대기 시각·재전송/소진 지표를 추가할 예정이다.

## 이번 검증의 범위

`FinalizedCodecTest` 3개, 실제 PostgreSQL의 `FinalizedPostgresTest` 9개를 추가했다. 후자는 Kafka가 필요한 3개 시험을 포함한다.

| 시험 | 확인한 결과 |
|---|---|
| 1·2차와 3가지 최종 결과 | 이력·PENDING 쌍, 원래 나노초 시각 보존 |
| 동시 중복 24건 | 이력 1건·예약 1건, 중복 23회 |
| 완료/소진 통지의 재전달 | 상태·시도 횟수·예약 시각 불변 |
| 고객·사유·1나노초 차이 충돌 | 최초 이력 보호, 통지 추가 없음 |
| 예약 INSERT 제약 오류 | 이력 INSERT까지 rollback, 해소 후 재저장 |
| 기존 예약 누락 | 새 통지 생성 없이 실패 |
| 실제 Kafka + SQL 오류 후 복구 | offset 1 유지 → 복구 후 2 |
| SQL commit 직후 예외·소비자 재생성 | offset 2 유지 → 재시작 후 3, 이력·예약 각 3건 |
| 잘못된 JSON·내용 충돌 재전달 | 반복 실패에도 offset 미진행 |
| 빈 스키마에서 실제 앱 기동 | Flyway 생성, Kafka 수신, SQL 쌍 저장, Prometheus HTTP 200 |

```bash
POSTGRES_TEST_URL=jdbc:postgresql://localhost:15432/delivery \
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:39092 \
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
JAVA_HOME=/path/to/jdk-21 ./mvnw -q package
```

시험은 UUID 전용 스키마·topic·group만 만들고 정리한다. 환경변수가 없으면 실제 저장소 시험이 제외되므로 테스트 총수와 제외 수를 함께 확인한다. [검증 기록](검증-결과/2026-09-25-최종-이력과-통지-대기-원자-저장.json)에 실행 조건과 전체 결과를 남긴다.

SQL commit 직후 실패는 listener 예외 주입과 Kafka container 재생성으로 재현했다. JVM kill, PostgreSQL 서버/디스크 장애, 다중 AZ 승격, 전체 발송→SQL의 새로운 성능 PoC를 실행한 것은 아니다. 이번 결과로 신규 구간의 TPS나 리전 외 모든 장애의 무손실을 주장하지 않는다.
