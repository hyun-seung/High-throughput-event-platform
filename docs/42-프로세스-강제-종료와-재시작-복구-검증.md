# 프로세스 강제 종료와 재시작 복구 검증

2026-09-25. [전체 만 TPS 검증](41-전체-만-TPS-목표와-Pod별-성능-검증-계획.md)에 앞서 기능·복구 개발을 마무리하기 위한 작업이다. 메서드의 예외 주입에 더해 실제 JVM 프로세스를 `SIGKILL`로 종료하고 새 JVM으로 재시작한다. 성능 튜닝·부하 시험은 포함하지 않는다.

## 1. 검증 도구와 격리 범위

`scripts/poc/process_recovery.py`는 [전체 흐름 도구](37-전체-호출-흐름의-격리-실행과-전수-대조.md)의 실행 환경을 재사용한다. 실행별 Compose 프로젝트·포트·볼륨·테이블·토픽을 만들고, 도구가 직접 생성해 보관한 `Popen` 객체에만 종료 신호를 보낸다. PID 검색으로 다른 JVM을 찾거나 공유 컨테이너를 재시작하지 않는다.

세 번의 SIGKILL과 세 번의 재시작을 기록한다. 종료 코드가 `-9`가 아니면 강제 종료 성공으로 인정하지 않는다. 재시작은 동일 JAR·환경·consumer group을 사용하며 이전 offset을 되감지 않는다. 실행 명령과 인증 환경은 메모리에만 유지하고 저장 자료에는 token을 남기지 않는다.

```sh
# JDK 21, Docker, scripts/poc/setup.py의 도구 준비 후
./mvnw -DskipTests package
.poc-tools/venv/bin/python -m unittest discover -s scripts/poc -p 'test_*.py'
.poc-tools/venv/bin/python scripts/poc/process_recovery.py
```

시험에서만 1차 만료 90초·2차 만료 30초·발송 lease 10초·DDB 누락 복구 3초를 적용한다. 업체 HTTP 읽기 timeout은 30초, 고객 HTTP timeout은 10초·통지 lease는 20초다. 운영 기본 만료 3시간/4시간·DDB 복구 10분 등은 변경하지 않는다. 업체 중복 제거는 끈다.

## 2. 실제 종료 지점과 판정

| ID | 종료 지점 | 종료 중 확인 | 재시작 후 통과 조건 |
|---|---|---|---|
| P-01 | 결과 worker를 먼저 종료한 뒤 정상 요청 접수 | STEP에 불변 최종 결과 존재, 최종 Kafka lag >0, SQL 이력 0건 | 보존한 결과와 같은 SQL 이력·고객 수신, DDB 정리 완료 |
| P-02 | 고객 수신기가 결과 본문을 읽고 HTTP 응답을 보류한 상태에서 결과 worker 종료 | SQL 묶음 `IN_FLIGHT`, 시도 1회. 종료 전후 같은 묶음·본문·lease | 기존 lease 만료 후 같은 묶음 ID·본문으로 시도 2회, 204 확인 후 통지 완료 |
| P-03 | 업체 효과 1회 발생을 관찰한 뒤, HTTP 응답·STEP 접수 저장 전에 발송 worker 종료 | STEP `PROCESSING`, retry 0, 결과 없음, 발송 Kafka 입력 미완료 | 재전달 후 자동 재발송 없이 상태·버전·회차·기한 유지. 원래 기한에 EXPIRED 확정·고객 수신·정리 |

P-01은 **최종 이벤트 발행 이후 SQL 소비 전에 worker가 없는 상황**이다. SQL commit 도중 kill 또는 Kafka broker 데이터 유실을 주입한 시험으로 확대 해석하지 않는다.

P-02의 첫 요청은 고객이 본문을 수신했지만 응답을 보내지 않는다. 검증 자료의 `status=0`은 HTTP 상태 코드가 아니라 **응답 보류 표시**이며 성공 ACK로 세지 않는다. 두 번째 실제 204와 SQL DELIVERED를 모두 확인한다. 고객이 같은 본문을 두 번 받을 수 있다는 사실도 증거에 남긴다. 묶음 ID·내용 보존과 내부 재전송 상태의 멱등성을 확인하는 것이며 고객의 외부 효과까지 exactly-once라고 주장하지 않는다.

P-03은 시뮬레이터의 `calls/effects` 관측으로 시험 주입 지점을 확인한다. 운영 발송 worker에 업체 결과 조회 기능을 추가한 것이 아니다. 업체 HTTP 응답은 효과 뒤 60초 지연하고 웹훅은 보내지 않으며, 응답 또는 read timeout 전에 worker를 죽였는지는 종료 전후 동일한 PROCESSING 상태로 확인한다.

v2는 lease 만료 후 재전달을 운영 확인 대상으로 판단하지만 **DDB STEP 자체는 PROCESSING으로 보존**한다. lease 만료만으로 retry 회차·버전을 갱신하지 않고, 원래 deadline의 만료 경로를 유지한다. 이번 시험도 재시작 후 이 상태를 기한 전에 직접 관찰해야 통과한다. 운영 확인 전용 조회·수동 조치 API의 완성까지 입증하는 시험은 아니다.

## 3. 결과 대조와 보관

- 각 요청의 고유 실행 UUID, STEP, Kafka committed/high offset, SQL 이력·통지·정리 상태를 대조한다. offset 조회용 consumer는 subscribe/commit하지 않는다.
- 3건 모두 업체 HTTP 호출·효과 각 1회, TCP 호출·효과 0회여야 한다.
- 최종 SQL 결과와 실제 고객 수신 본문이 같고, ORIGIN·STEP 삭제와 Redis 완료 표식이 확인돼야 한다.
- P-02는 서로 다른 묶음 ID·본문, 잘못된 시도 횟수, 응답 미확인 상태를 성공으로 인정하지 않는다.
- P-03은 재전달로 상태·버전·retry·deadline·lease가 바뀌거나 업체 호출이 늘면 실패다. 만료 결과의 resultAt/deadline은 최초 STEP의 deadline과 같아야 한다.
- 최종 3건의 이력 ID 집합을 맞추고 요청·발송·결과 웹훅·최종 결과 Kafka lag가 모두 0인지 확인한다.

환경·JAR/도구 해시, 종료/재시작 PID·시각, 종료 경계의 STEP·묶음·offset, 고객 수신 원문, SQL 이력, 시나리오 결과를 `.poc-results/<실행 ID>/`에 보존한다. 실패 실행도 `failure.json`과 로그를 남긴다. 종료 시 소유 프로세스·컨테이너만 정지하고 볼륨을 보존한다.

이 검증으로 Kubernetes eviction·노드/AZ 장애·Kafka 복제본 장애·저장소 장애 중 복구를 입증하지 않는다. 해당 시험과 운영 확인 기능은 후속 개발·검증 항목으로 남는다.
