# 100 TPS 일시 적체 구간 분석

분석일: 2026-09-24. [Kafka 패치 후 시험](21-카프카-패치와-성능-재검증.md)의 보존 자료를 다시 비교했다. 추가 부하를 발생시키거나 실행 설정을 바꾸지 않았다.

## 확인 결과

일시 적체 구간에서는 원본 저장·발송 선점·접수 결과 저장의 DB 호출 시간과 API의 Kafka ack 대기가 함께 늘었다. 외부 HTTP 평균 증가는 상대적으로 작았다. 이 결과만으로 DynamoDB Local 자체, 디스크, Kafka commit 또는 JVM을 단일 원인으로 확정할 수는 없다. 멱등 저장·Kafka ack 경계는 유지한다.

## 재현 방법과 시간 기준

```bash
python3 scripts/monitoring/analyze_stalls.py \
  .poc-results/20260924T121505Z-075d4b00/monitored-100 \
  > /tmp/platform-stall-analysis.json
```

`requests.jsonl`의 최초 start 시각(UTC 12:21:44.246)을 0초로 잡는다. 기존 문서의 35.7초·178.7초는 첫 수집 샘플을 기준으로 한 값이며, 실제 입력 시작 기준으로는 약 29.0초·172.0초다. 각 앱의 연속 Prometheus snapshot에서 timer sum 증가량을 count 증가량으로 나누어 구간 평균을 구한다. 요청 p95와는 다른 수치다.

수집은 순차적이므로 앱별 scrape·lag·Docker stats가 정확히 같은 순간은 아니다. stdout audit에는 단계별 구조화 필드가 없어 완료 관측의 공백만 비교한다. 공백은 특정 스레드의 정지 시간이나 고유 요청 수의 증거가 아니다. 파티션별 처리 시간·개별 DB 호출 trace·디스크 지연은 이 자료로 복원할 수 없다.

## 같은 구간의 비교

시간은 입력 시작 후 초, 지연은 해당 수집 구간의 평균 ms다. lag는 구간 끝에서 관측한 committed lag다.

| 구간 끝 | lag | API Kafka ack | 원본 DB 저장 | Dispatch 발행 ack | 발송 선점 | 외부 HTTP | 결과 DB 저장 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 20.0초 | 28 | 6.2 | 9.4 | 5.2 | 7.3 | 1.9 | 7.6 |
| 29.0초 | 233 | 16.2 | 15.1 | 5.5 | 10.0 | 2.1 | 10.5 |
| 43.0초 | 36 | 5.7 | 5.9 | 5.1 | 5.1 | 1.7 | 5.0 |
| 166.1초 | 22 | 5.7 | 7.5 | 5.0 | 6.3 | 1.7 | 6.3 |
| 172.0초 | 292 | 26.4 | 28.6 | 5.7 | 18.5 | 2.4 | 24.4 |
| 179.9초 | 20 | 5.7 | 11.9 | 4.8 | 9.9 | 1.7 | 10.3 |
| 184.9초 | 0 | — | — | — | — | — | — |

최대 적체 292건은 Ingress 앞 200건·Dispatch 앞 92건이다. 약 168초 부근에 audit 완료 관측 사이 최대 공백이 API 0.54초·Ingress 1.19초·Dispatch 1.64초였다. 160~170초 입력 중 API audit는 1,000회였지만 Ingress 757회·Dispatch 734회로 뒤처지고 이후 따라잡았다.

172초 부근 수집 구간의 GC pause 합계는 API 186ms·Ingress 2ms·Dispatch 5ms다. Worker의 GC 합계만으로 1초 이상 관측 공백을 설명하지 못한다. 인접 Docker 표본에서 DynamoDB Local CPU 26.73%, Kafka 15.73%, API 16.48%였으며 그 표본만으로 CPU 포화도 확인되지 않았다. 순간적인 자원 대기와 공통 호스트 영향은 배제하지 않는다.

## 개발에 반영할 판단

- 100 TPS 3분 입력은 배출·정합성·런타임 로그 검사를 통과했다. 순간 적체와 긴 꼬리 지연은 남아 있으며 최대 처리량 검증은 아니다.
- 기존 증거로 확인 가능한 지연 위치를 기록하고 업무 기능 개발로 돌아간다. 이번 분석을 근거로 DB write나 ack를 줄이지 않는다.
- 다음 성능 실험에서는 동일 100 TPS에서 호출별 지연·파티션별 진행·commit 시간과 호스트 자원을 함께 수집한다. 그 뒤 같은 조건 재현 및 한 변수씩 비교하여 원인을 좁힌다. 200 TPS 이상 확대와 업체 지연 조건은 별도 시험이다.
