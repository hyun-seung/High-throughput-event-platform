# 장애 상황별 검증 계획

시험 시 중단 범위와 재개 순서는 [저장소별 운영 절차](09-저장소-장애-시-중단-범위와-복구-절차.md)를 함께 검증합니다.

신규 v2의 실제 JVM SIGKILL·재시작 시험은 [프로세스 복구 검증](42-프로세스-강제-종료와-재시작-복구-검증.md)에 분리합니다. 결과 소비 전 중단, 고객 본문 수신 후 응답 불명, 업체 효과 후 내부 결과 미저장 경계를 다룹니다. 아래의 초기 시나리오와 Kubernetes/저장소 장애 전체를 검증 완료한 것으로 간주하지 않습니다.

PostgreSQL 서비스 중단 시 접수·발송·만료 진행과 Kafka·DDB 결과 보존, 같은 DB 볼륨 복구 후 앱 재시작 없는 인계는 [PostgreSQL 장애 검증](43-PostgreSQL-장애-중-결과-보존과-자동-복구-검증.md)에서 다룹니다. commit 응답 유실이나 replica 승격 시험과 구분합니다.

ORIGIN 저장 후 선점 전 DynamoDB 중단과, 업체 접수 후 원래 기한까지 중단하는 경계는 [DynamoDB 장애 검증](44-DynamoDB-장애-시-발송-차단과-만료-복구-검증.md)에서 다룹니다. 원본 저장 전 DLT 격리·재처리와 AWS 복원 시험까지 포함하지 않습니다.

Redis 연결 불가 중 TPS·Quota 우회, 진행 중 중복 차단, 일정 없는 만료와 재연결 후 정책 적용은 [Redis 장애 검증](45-Redis-장애-시-제한-우회와-만료-복구-검증.md)에서 다룹니다. 장애 중 못 쓴 완료 표식·Quota 사용량의 자동 재구축까지 검증했다고 해석하지 않습니다.

Kafka 중단 중 접수/웹훅 503, 동일 ID 재전송과 DB 만료 결과 보존·자동 인계는 [Kafka 장애 검증](47-Kafka-장애-시-접수-보류와-결과-복구-검증.md)에서 실제 3개 경계를 통과했습니다. 단일 broker의 같은 볼륨 재시작이며 ISR/리더 선출·ack만 유실하는 시험과 구분합니다.

각 테스트는 입력 수, accepted 수, Provider의 실제 부수 효과 수, terminal 수, known in-flight 수, quarantined 수를 함께 기록합니다. 프로세스 로그만으로 성공을 판정하지 않습니다.

|---|---|---|---|---|---|
| F-01 | API | Kafka 발행 실패 | `202` 응답 금지 | Client retry | ack 없는 accepted 0 |
| F-02 | API | Kafka ack 후 응답 전 종료 | Client 재요청 가능 | 안정적인 deliveryId와 downstream dedupe | DynamoDB 원본 1 |
| F-03 | Producer | broker timeout/ack 유실 | 결과 불확실, 중복 발행 가능 | 같은 ID 재발행+Consumer dedupe | 내부 상태 1 |
| F-04 | Ingress Consumer | DynamoDB 저장 또는 Dispatch 발행 후 commit 전 종료 | record 재전달 | conditional insert와 idempotent publish | Dispatch 논리 효과 1 |
| F-05 | Sender | claim 후 Provider 호출 전 종료 | 내부에는 완료 기록 없는 PROCESSING | F-06과 구분 가능한지 검증, Q6 적용 | 시험 주입 지점을 운영 시스템이 안다고 가정하지 않음 |

| F-07 | Network | Provider 수신 후 response timeout | `UNKNOWN` | 결과 웹훅 대기·Q6 처리 (조회 API 없음) | 성공/실패 임의 단정 금지 |

| F-09 | Provider | slow response | Provider별 concurrency 제한 | 회복 후 drain | API와 타 Provider 격리 |

| F-12 | Result Processor | DB 갱신 후 commit 전 종료 | event 재전달 | conditional update | 이력 중복 0 |

## Sender 필수 실험

외부 중복 방지를 끈 조건을 기본 검증으로 사용합니다. 켠 조건은 보조 기능 비교 실험이며 내부 보장의 근거를 대신하지 않습니다. 모든 조건에서 운영 발송 로직의 외부 결과 조회는 금지합니다.

| 외부 중복 방지 | 주입 상황 | 검증 기준 |
|---|---|---|
| 끔 | 내부 완료 저장 후 Kafka 재전달 | 내부 기록으로 재호출 차단 |
| 끔 | 유효한 선점 중 중복 이벤트 동시 도착 | 추가 외부 호출 차단 |
| 끔 | 외부 처리 후 응답 유실 또는 내부 완료 저장 전 종료 | UNKNOWN 보존, Q6에서 결정한 처리 검증 |
| 끔 | 외부 미처리 상태에서 동일한 timeout 발생 | 위 상황과 관측 정보가 같음을 재현; 무손실 전달·무중복 동시 보장으로 오인하지 않음 |
| 끔 | lease 만료 후 이전 Worker 재개 | 내부 version 검사만으로 외부 효과가 차단됐다고 가정하지 않음 |
| 켬 | 같은 key로 재호출 | 시뮬레이터의 설정된 중복 방지 범위만 검증 |

결과 웹훅의 지연·중복·역순·영구 미수신을 각각 재현합니다. 실제 처리 횟수는 테스트 전용 관측 기록으로 측정하며, 이 기록을 발송 로직에 제공해 UNKNOWN을 해결하지 않습니다.

## 2차 TCP 접수와 최종 결과 검증

- TCP 수신·접수 확인 응답만으로 최종 발송 성공을 기록하지 않습니다.
- 접수 확인 후 최종 HTTP 웹훅을 기다리는 동안, 웹훅 미수신만으로 TCP 발송을 재시도하지 않습니다.
- TCP 업무 응답 미수신과 최종 웹훅 미수신을 별도 장애로 주입하고 각각 재시도 정책과 만료 정책을 검증합니다.
- 최종 HTTP 웹훅이 TCP 응답보다 먼저 도착하거나 해당 단계 만료 후 도착하는 경우를 검증합니다.

## Provider Fallback 필수 검증

- 확정 실패·무응답·1차 만료를 구분합니다. 무응답 자체는 재시도하고, 만료 시에는 요청의 2차 허용 여부를 확인합니다.
- 응답과 업체 결과 웹훅 각각에서 실패 코드별 1차 지연 재시도와 2차 전환을 검증합니다.
- 최초 메시지에서 2차를 허용하지 않으면 전환 코드가 와도 다른 업체를 호출하지 않습니다.
- 동일 실패의 응답·웹훅 중복 수신이 재시도 예약이나 2차 발송을 중복 실행하지 않아야 합니다.
- 1차 무응답 재시도 3회 소진 시 허용 요청은 즉시 TCP 2차 발송으로 전환하고, 비허용 요청은 전환하지 않습니다.
- 소진 판단 시각으로 2차 만료 기준을 한 번 고정하며 중복 소진 이벤트는 전환을 중복 실행하지 않습니다.
- circuit open·명확한 실패 코드 재시도 소진·2차 자체 소진은 별도 정책 확정 후 검증합니다.
- 1차 만료 후 도착한 1차 웹훅은 로그만 남기고 폐기합니다. 업무 상태·이력을 변경하지 않고 진행 중인 2차의 정상 웹훅은 별도로 처리합니다.
- 만료 작업이 중복 실행되어도 2차 발송은 중복 예약되지 않습니다.
- 서로 다른 1차·2차 기간을 설정하고 1차 인입 시각+3시간, 2차 판단 시각+4시간, 전체 최대 7시간 계산을 검증합니다. 자동화 시험은 짧은 기간 또는 제어 가능한 시계로 같은 규칙을 검증합니다.
- 1차 조기 실패·무응답 소진이면 2차 기한이 앞당겨지며, 중복 처리·재시작으로 기한이 연장되지 않아야 합니다.
- 운영 확인 중인 1차도 만료 시 요청에서 허용했다면 자동 2차 발송하며, 운영자가 개입하지 않아도 기한이 연장되지 않습니다.
- 운영자 처리와 만료 작업이 경합할 때 전환 중복·만료 이후 이전 단계 수동 변경을 차단합니다.
- 2차 비허용 또는 2차까지 만료된 건은 고객 결과 제공으로 이어지는지 검증합니다. 기한은 테스트 기준 1차 3시간·2차 4시간이며, 허용 처리 지연·제공 채널은 Q4 확정 후 시험 조건에 반영합니다.
- 전체 Provider에 걸친 최대 attempt와 delivery deadline을 지킵니다.
- Provider별 성공률뿐 아니라 fallback 전환율과 fallback 이후 중복 부수 효과를 측정합니다.

## 테스트 결과 기록 형식

각 실행 결과에는 다음을 남깁니다.

- Git commit과 모든 서비스 image/version
- topic partition/replication/retention, Consumer group 설정
- 입력 수와 요청 속도, 실행 시간
- 장애 시작/종료 시각과 주입 설정
- accepted, rejected, terminal, in-flight, retry, recovery, unknown, dead 수
- Kafka lag/oldest age와 정상 회복까지 걸린 시간
- Provider가 기록한 unique idempotency key와 실제 부수 효과 수
- p50/p95/p99 API 및 end-to-end latency
- 판정, 관찰된 한계, 다음 변경

## 리전 내 무손실 검증 범위

Q3의 목표는 리전 전체 장애를 제외한 데이터 무손실입니다. 단일 서버·AZ 장애만 시험한 뒤 모든 비리전 장애를 통과했다고 보고하지 않습니다.

- 저장 확인 전/후 프로세스 종료, 저장 노드와 디스크 소실, AZ 손실 및 네트워크 분리를 주입하고 접수된 고유 요청 집합과 복구 후 집합을 대조합니다.
- 남은 복제 수가 부족한 상황의 추가 장애·승격을 검증합니다. 오래된 사본에서 진행을 재개해 접수 기록을 잃지 않는지 확인합니다.
- 잘못된 삭제·논리 손상·retention 초과에 대해서는 별도 원장·백업과 복원 시점 이후 기록까지 실제 복원 가능한지 확인합니다.
- Kafka·실행 DB·이력 저장소의 복구 시점 차이에도 원본과 최종 결과가 누락되지 않는지 확인합니다. Redis 소실만으로 유일한 판단 근거를 잃지 않아야 합니다.
- 각 항목에 배치·설정·살아남는 사본·복구 근거·RPO·복구 시간·미검증 범위를 기록합니다. 로컬 단일 노드 시험은 실제 다중 AZ 손실 검증을 대신하지 않습니다.
- 내구성 미확인 작업은 중단하고 정상 경로는 유지하는 Q5 방향을 검증합니다. Redis TPS·Quota 전부 우회와 장기 장애 복구 후 만료를 검증합니다. 복구 시간·장기 장애 대상 구분은 추가 정의합니다.

## 고객 HTTP 통지와 완료 데이터 정리 검증

[결과 통지·정리 설계](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)의 확정 요구와 미확정 제안을 구분해 시험합니다.

- 같은 고객 기준 100건 상한, 다른 고객 혼합 금지, 소량/연속 유입 시 대기 한도와 재시작 후 미통지 결과 복구.
- 최초 전송 + 최대 20회 재전송. 실패·응답 유실·재시작·부분 실패 후 묶음 변경에도 항목별 횟수가 초기화되지 않는지 확인합니다. 소진 시 자동 전송 중단과 결과 보존은 제안 정책 채택 후 검증합니다.
- [멱등 보관안](11-멱등-정보-보관과-완료-후-정리-방식.md) 선택 후 완료 기록 축소와 동시 선점, 이력 조회와 실행 상태 삭제 사이의 경합, 보관 종료 전후 replay를 검증합니다.
- HTTP 전송 성공 직후 종료·응답 유실·부분 실패 시 외부 발송을 다시 실행하지 않는지 확인.
- 최종 이력 저장 실패 시 정리 보류, 고객 통지용 결과 보존, 1차 종료 후 2차 입력 유지.
- 이력 기반 완료 후 중복 방지안이 확정되면 활성 상태 삭제 후 고객 재요청·Kafka 재전달·낡은 Worker 재개를 검증.
- Redis 장애 시 TPS와 Quota를 모두 우회하되 인증·내구성 조건은 유지. 복구 시 적용 정책과 사용량 불명 구간 표시.
- 장기 장애 복구 후 대상 미완료 건의 만료·고객 통지, 이미 확정된 성공 결과 불변.
