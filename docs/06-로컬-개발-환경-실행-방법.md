# 로컬 개발 환경 실행 방법

JDK 21과 Docker Compose가 필요합니다. 빌드는 Maven Wrapper(`./mvnw`, Windows에서는 `mvnw.cmd`)를 사용하므로 Maven 별도 설치는 필요하지 않습니다. 통합 검증 스크립트는 Python 3와 AWS SigV4를 지원하는 curl(7.75 이상)을 사용합니다. 현재 인증은 `auth-module` 라이브러리를 포함한 Delivery API에서 제공합니다. 별도 Auth AP는 실행하지 않습니다.

## 환경과 빌드

```bash
cp .env.example .env
# JAVA_HOME을 JDK 21 경로로 설정합니다. macOS 예시:
export JAVA_HOME="$(/usr/libexec/java_home -v 21)"
bash scripts/local.sh infra
bash scripts/local.sh init-db
bash scripts/local.sh init-policy
bash scripts/local.sh build
```

이미 `.env`가 있으면 덮어쓰지 말고 예시와 비교해 필요한 항목을 추가합니다. `build`는 기본적으로 Wrapper를 사용합니다. 기존 Maven으로 실행해야 한다면 `.env`의 `MAVEN_BIN`에 실행 파일 경로를 큰따옴표로 감싸 지정합니다.

Wrapper는 Maven 3.9.16을 다운로드하고 캐시에 보관합니다. 최초 실행에는 Maven Central 네트워크 접근, curl 또는 wget, unzip이 필요합니다. Windows Wrapper는 PowerShell을 사용합니다. 배포 파일의 SHA-256을 고정해 다운로드 시 검증합니다. [공식 Maven Wrapper 문서](https://maven.apache.org/tools/wrapper/)를 참고합니다.

`./mvnw verify`로 전체 테스트와 패키징을 수행할 수 있습니다. Maven은 `validate` 단계에서 JDK 21을 검사하며, `run` 명령도 앱 시작 전에 버전을 확인합니다. Java 17이나 25가 선택되면 `JAVA_HOME`을 JDK 21로 변경합니다. IDE의 Project SDK와 Maven Runner JRE도 JDK 21로 맞춥니다.

예시는 기존 서비스와 충돌하지 않도록 Kafka 19092, Redis 16379, PostgreSQL 15432, DynamoDB 18000, API 18080, Provider 18090을 사용합니다. 스크립트는 이 포트를 애플리케이션 연결 설정에 반영합니다. `dev` 프로필로 실행하므로 개인 `application-local.yml`의 오래된 설정을 읽지 않습니다.

DB 초기화는 로컬 `users` 테이블과 `local-user / local-password` 테스트 사용자를 만듭니다. 재실행해도 기존 사용자 정보를 변경하지 않습니다. 이 계정과 예시 JWT secret은 로컬 전용입니다. JWT secret은 디코딩 후 최소 32바이트인 Base64 문자열이어야 합니다.

`init-policy`는 DB에서 `local-user`의 실제 ID를 조회해 Redis에 TPS 100, burst 100, 월 한도 100,000 정책의 누락 필드를 채웁니다. 기존 정책과 사용량은 유지합니다. 정책이 없으면 인증에 성공해도 Delivery 접수는 `POLICY_NOT_FOUND`(503)로 거절됩니다.

DynamoDB는 초기화 컨테이너에서 전용 데이터 볼륨의 소유권을 실행 사용자에게 부여합니다. healthcheck는 서명된 `ListTables` 요청의 성공을 검사하므로 DB 파일에 접근하지 못하는 상태를 정상으로 판단하지 않습니다.

## 애플리케이션 실행

각 명령을 별도 터미널에서 순서대로 실행합니다.

```bash
bash scripts/local.sh run external-api-simulator
bash scripts/local.sh run delivery-ingress-worker
# Ingress의 DynamoDB 테이블 초기화 완료 후 Dispatch를 실행합니다.
bash scripts/local.sh run dispatch-worker
bash scripts/local.sh run event-api
```

실행 JAR는 `build`가 만든 파일입니다. 코드 수정 뒤에는 다시 빌드합니다. 네 AP 모두 시작 완료 로그와 오류 없는 상태를 확인합니다. Worker의 Kafka partition 할당 로그까지 확인해야 consume 준비를 판단할 수 있습니다. 별도 자동 AP readiness endpoint는 아직 없습니다. 아래 smoke 명령은 실행된 앱의 실제 처리 경로를 검증합니다.

## 상태와 인증 확인

```bash
bash scripts/local.sh status
curl --fail-with-body -H 'Content-Type: application/json' \
  -d '{"username":"local-user","password":"local-password"}' \
  http://localhost:18080/api/v1/auth/token
```

포트를 바꿨으면 요청 URL도 맞춥니다. 네 앱의 준비가 끝나면 다음 명령으로 현재 구현된 처리 경로를 검증합니다.

```bash
bash scripts/local.sh smoke
```

스크립트는 `.env`의 포트를 사용하며 다음을 확인합니다.

- 테스트 사용자 인증 및 토큰 발급
- 동일 멱등키로 두 번 접수했을 때 HTTP 202와 동일한 `deliveryId`
- 최대 30초 동안 DynamoDB를 조회하여 `META`와 단일 `ATTEMPT#...`의 `ACCEPTED`, `provider_processed_at` 확인

실행마다 새 멱등키를 사용하며 로컬 Kafka/DynamoDB에 검증 데이터가 남고 테스트 계정의 요청 한도를 사용합니다. 토큰은 출력하지 않습니다. 기존 정책이 차단 상태이거나 한도가 소진되면 실패합니다. 실패 시 API 및 Worker 로그를 확인합니다.

이 검증은 Kafka와 두 Worker를 거쳐 mock Provider 접수 결과가 저장되는 범위입니다. Kafka 각 레코드의 직접 비교, 장애 복구, Provider 실제 부수 효과 횟수, receipt 이후 최종 전달 완료를 검증하지는 않습니다.

## 종료와 데이터

각 AP 터미널에서 Ctrl+C로 종료한 뒤 `bash scripts/local.sh down`을 실행합니다. named volume은 유지합니다. `down --volumes`는 데이터 삭제이므로 평상시 종료에 사용하지 않습니다.

Compose 프로젝트 이름이 `reliable-event-platform`이므로 기존 `platform` 프로젝트의 DynamoDB volume을 자동으로 공유하지 않습니다. 기존 데이터와 컨테이너는 별도로 보존됩니다.

## 검증 범위

2026-09-23 Java 21에서 전체 9개 모듈 패키징과 테스트 14건을 통과했습니다. 셸 문법 검사도 통과했습니다. DynamoDB 자동 설정 등록 경로와 Worker 전용 활성화를 회귀 테스트로 확인했습니다.

실제 DB 초기화, Redis 정책 초기화, 네 앱 기동, 인증과 smoke 검증을 통과했습니다. 실행 검증에서 발견한 예시 JWT의 Base64 형식 오류, DynamoDB 볼륨 쓰기 권한 및 healthcheck 오류, Ingress JSON 직렬화 중복 설정, API 비동기 응답의 인증 누락을 수정했습니다.

비동기 인증 문제는 디버거에서 최초 요청의 사용자 ID `1`과 이후 `ASYNC` dispatch의 `InsufficientAuthenticationException`을 확인했습니다. JWT 필터가 비동기 dispatch에서도 인증하도록 수정했으며, 정상 202 응답·요청 한도 1회 차감·무인증 요청 거절을 회귀 테스트로 검증했습니다. Ingress 직렬화 테스트는 설정 적용 후 JSON type header가 없고 원시 byte 배열도 보존됨을 확인합니다.

Maven Wrapper 3.3.4 / Maven 3.9.16을 통한 전체 빌드와 테스트 14건도 통과했습니다. Java 17 빌드 및 앱 실행 거절과 새 캐시에서의 Wrapper 다운로드·체크섬 검증을 확인했습니다. 별도 AP readiness endpoint는 후속 작업입니다. 장애·재시도·복구 시나리오는 별도 통합 테스트가 필요합니다.


## 접수 오류와 DynamoDB 재처리 검증

API가 Kafka 저장 ack를 확인하지 못하면 HTTP 503과 오류 코드 `9003`을 반환하며 같은 `Idempotency-Key`와 요청 내용으로 재요청하도록 안내합니다. 503은 원본이 Kafka에 없다는 증거가 아닙니다. 동기 send 실패, 비동기 ack 실패와 MVC 비동기 timeout에 같은 오류 계약을 적용합니다.

개발 기본값은 Kafka metadata/buffer 대기 5초, 개별 요청 timeout 5초, 발행 결과 제한 10초, MVC 비동기 응답 제한 20초입니다. 각각 `KAFKA_PUBLISH_MAX_BLOCK_MS`, `KAFKA_PUBLISH_REQUEST_TIMEOUT_MS`, `KAFKA_PUBLISH_DELIVERY_TIMEOUT_MS`, `DELIVERY_HTTP_ASYNC_TIMEOUT`으로 조정할 수 있습니다. Kafka 발행 결과 제한은 요청 timeout + linger 이상이어야 합니다. 이 값은 업체 발송 재시도 간격이나 업무 만료 기간이 아닙니다. [Kafka producer 설정 근거](https://kafka.apache.org/40/generated/producer_config.html), [Spring MVC 비동기 오류 처리](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html).

DynamoDB Local이 실행 중이면 다음으로 저장·재처리 경계를 검증합니다. 포트는 로컬 환경에 맞춥니다.

```bash
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 ./mvnw verify
```

환경변수가 없으면 DynamoDB 통합 시험만 건너뜁니다. 테스트는 로컬 HTTP endpoint만 허용하고 UUID key의 전용 데이터를 생성·정리합니다. 기존 테이블과 다른 요청 데이터는 삭제하지 않습니다. 실제 DynamoDB를 사용하며 Kafka 발행은 테스트 대역으로 실패를 주입합니다. 저장 직후 중단 상태에서 재개, 후속 발행 ack 유실 후 재처리, 입력 충돌 차단, 동시 중복 20건의 최초 저장 시각 보존을 검사합니다. Kafka broker 장애나 프로세스 kill 전체를 검증한 것으로 해석하지 않습니다.

2026-09-23 이 명령으로 전체 9개 모듈 빌드와 테스트 25건을 통과했습니다(실패·오류·건너뜀 0). 기존 14건에 API 실패 계약 4건, Ingress 단위 3건, DynamoDB Local 통합 4건을 추가했습니다.


## Kafka DLT 격리와 offset 복구 검증

로컬 Kafka와 DynamoDB가 실행 중이면 다음 명령으로 전체 시험을 실행합니다.

```bash
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:19092 \
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
./mvnw verify
```

각 환경변수가 없으면 해당 저장소 통합 시험은 건너뜁니다. Kafka 시험은 `localhost` 또는 `127.0.0.1`만 허용하고 UUID 이름의 토픽·Consumer Group을 생성·정리합니다. 테스트 전용 DLT의 파티션을 일부러 부족하게 만든 뒤 복구하며, 업무 토픽·그룹은 변경하지 않습니다. 기존 앱을 중지할 필요는 없습니다.

2026-09-23 전체 9개 모듈 빌드와 테스트 34건을 통과했습니다(실패·오류·건너뜀 0). 실제 Kafka 3건과 DynamoDB Local 4건이 포함됩니다. 접수 재전달의 개발 기본값은 `INGRESS_RETRY_INTERVAL=1s`, `INGRESS_MAX_RETRIES=2`이며 외부 발송 재시도와 별도입니다. 세부 근거와 운영 재처리는 [DLT 문서](12-접수-실패-격리와-DLT-재처리-절차.md)를 참고합니다.

## 발송 결과 미기록 상태 보존 검증

위 명령에 `KAFKA_TEST_BOOTSTRAP_SERVERS`와 `DYNAMODB_TEST_ENDPOINT`를 모두 지정하면 Dispatch 복구 시험도 실행합니다. 2026-09-24 전체 9개 모듈 빌드와 테스트 46건을 통과했습니다(실패·오류·건너뜀 0). Kafka 통합 3건과 DynamoDB Local 통합 12건이 포함됩니다.

Dispatch는 lease가 만료돼도 다시 발송하지 않고 `REVIEW_REQUIRED`를 저장합니다. 추가된 DynamoDB 시험 8건은 결과 미기록 복구, 동시 복구·정상 결과 저장 경합, 복구 저장 응답 유실 등을 검증합니다. UUID key의 전용 데이터만 정리하며 Provider는 중복 제거 없는 테스트 대역입니다. 실제 프로세스 kill이나 성능 부하 시험은 별도입니다.

Dispatch Kafka 재전달 간격은 `DISPATCH_REDELIVERY_BACKOFF_MS=1000`입니다. 상태를 안전하게 넘기기 전에는 재전달을 계속하며, 이는 외부 발송 재시도 횟수가 아닙니다. 현재 Dispatch DLT가 없어 역직렬화 오류도 입력을 보존하고 재시도하므로 해당 소비 구간 처리가 지연될 수 있습니다. 상세한 보장 범위와 남은 작업은 [발송 선점 ADR](adr/ADR-008-발송-작업-선점과-외부-중복-발송-방지.md)을 참고합니다.


## 성능 계측과 시뮬레이터 관측 검증

네 앱을 새 빌드로 실행한 뒤 `bash scripts/local.sh smoke --metrics`를 실행합니다. 기본 smoke에 구간·DB·HTTP 지표와 외부 중복 제거 없는 호출/처리 횟수 대조를 추가합니다. 실행 결과를 성능 테스트로 해석하지 않습니다. 관리 포트·설정·지표 의미·보관 한도는 [성능 지표와 시뮬레이터 관측 방법](14-성능-지표와-시뮬레이터-관측-방법.md)에 정리했습니다.

2026-09-24 계측 변경 후 전체 9개 모듈 빌드와 테스트 57건을 통과했습니다(실패·오류·건너뜀 0). 기존 46건에 계측 4건·발송 성공 집계 경계 2건·시뮬레이터 5건을 추가했습니다.
