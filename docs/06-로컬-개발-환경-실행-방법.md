# 로컬 개발 환경 실행 방법

> Kafka 기존 환경 갱신: 실제 로그 경로의 명명 볼륨 마운트를 수정했습니다. 기존 부모 경로 마운트를 쓰는 컨테이너는 재생성 전에 [데이터 확인·이관 절차](47-Kafka-장애-시-접수-보류와-결과-복구-검증.md#3-시험-중-발견한-kafka-데이터-마운트)를 따릅니다. 실행 스크립트는 이전 구조를 발견하면 데이터 변경 없이 중단합니다.

> 최신 물리 테이블은 `ORIGIN`·`STEP`이다. 기존 `delivery_state`가 있는 환경은 [테이블 분리·이관 절차](36-원본과-단계-테이블-분리와-경로별-쓰기-내역.md)를 먼저 따른다.

Grafana에서 확인하려면 앱 4개와 수집 서버를 함께 띄우는 [별도 모니터링 환경 실행법](19-그라파나-대시보드-실행과-PPT-항목-대응.md)을 사용할 수 있다. 아래의 수동 개발 환경과 별도 project·포트·데이터를 사용한다.

JDK 21과 Docker Compose가 필요합니다. 빌드는 Maven Wrapper(`./mvnw`, Windows에서는 `mvnw.cmd`)를 사용하므로 Maven 별도 설치는 필요하지 않습니다. 통합 검증 스크립트는 Python 3와 AWS SigV4를 지원하는 curl(7.75 이상)을 사용합니다. 현재 인증은 `auth-module` 라이브러리를 포함한 Delivery API에서 제공합니다. 별도 Auth AP는 실행하지 않습니다.

## 환경과 빌드

Compose의 Kafka 이미지는 `apache/kafka:4.0.2`다. 기존 4.0.0에서 실제 관측한 coordinator histogram/offset commit 오류의 수정 버전이며 [공식 4.0.2 릴리스 노트](https://archive.apache.org/dist/kafka/4.0.2/RELEASE_NOTES.html)의 KAFKA-19888을 근거로 선택했다. 이미 실행 중인 컨테이너는 파일 변경만으로 바뀌지 않는다. 교체 전 입력을 멈추고 적체 해소·offset을 확인하며 데이터 볼륨을 삭제하지 않는다.

```bash
cp .env.example .env
# JAVA_HOME을 JDK 21 경로로 설정합니다. macOS 예시:
export JAVA_HOME="$(/usr/libexec/java_home -v 21)"
bash scripts/local.sh infra
bash scripts/local.sh init-db
bash scripts/local.sh init-policy
bash scripts/local.sh build
```

이미 `.env`가 있으면 덮어쓰지 말고 예시와 비교해 필요한 항목을 추가합니다. `build`는 기본적으로 Wrapper를 사용합니다. 기존 Maven으로 실행해야 한다면 `.env`의 `MAVEN_BIN`에 실행 파일 경로를 큰따옴표로 감싸 지정합니다.

기존 로컬 서비스와 포트가 겹치면 `.env`를 고치지 않고 별도 설정 파일을 지정할 수 있습니다. `LOCAL_ENV_OVERRIDE_FILE=/path/to/ports.env bash scripts/local.sh infra`처럼 실행하면 스크립트가 `.env` 다음에 해당 파일을 읽습니다. 이후 `init-db`, `init-policy`, `run`, `down` 명령에도 같은 변수를 지정합니다. 예를 들어 설정 파일에 `KAFKA_HOST_PORT`, `REDIS_HOST_PORT`, `POSTGRES_HOST_PORT`, `DYNAMODB_HOST_PORT`, `MOCK_TCP_PORT`를 적을 수 있습니다. `MOCK_TCP_PORT`의 기본값은 18091이며 로컬 TCP 시뮬레이터와 Sender가 같은 값을 사용합니다.

Wrapper는 Maven 3.9.16을 다운로드하고 캐시에 보관합니다. 최초 실행에는 Maven Central 네트워크 접근, curl 또는 wget, unzip이 필요합니다. Windows Wrapper는 PowerShell을 사용합니다. 배포 파일의 SHA-256을 고정해 다운로드 시 검증합니다. [공식 Maven Wrapper 문서](https://maven.apache.org/tools/wrapper/)를 참고합니다.

`./mvnw verify`로 전체 테스트와 패키징을 수행할 수 있습니다. Maven은 `validate` 단계에서 JDK 21을 검사하며, `run` 명령도 앱 시작 전에 버전을 확인합니다. Java 17이나 25가 선택되면 `JAVA_HOME`을 JDK 21로 변경합니다. IDE의 Project SDK와 Maven Runner JRE도 JDK 21로 맞춥니다.

예시는 기존 서비스와 충돌하지 않도록 Kafka 19092, Redis 16379, PostgreSQL 15432, DynamoDB 18000, API 18080, Provider 18090을 사용합니다. 스크립트는 이 포트를 애플리케이션 연결 설정에 반영합니다. `dev` 프로필로 실행하므로 개인 `application-local.yml`의 오래된 설정을 읽지 않습니다.

DB 초기화는 로컬 `users` 테이블과 `local-user / local-password` 테스트 사용자를 만듭니다. 재실행해도 기존 사용자 정보를 변경하지 않습니다. 이 계정과 예시 JWT secret은 로컬 전용입니다. JWT secret은 디코딩 후 최소 32바이트인 Base64 문자열이어야 합니다.

`init-policy`는 DB에서 `local-user`의 실제 ID를 조회해 Redis에 TPS 100, burst 100, 월 한도 100,000 정책의 누락 필드를 채웁니다. 기존 정책과 사용량은 유지합니다. 정책이 없으면 인증에 성공해도 Delivery 접수는 `POLICY_NOT_FOUND`(503)로 거절됩니다.

DynamoDB는 초기화 컨테이너에서 전용 데이터 볼륨의 소유권을 실행 사용자에게 부여합니다. healthcheck는 서명된 `ListTables` 요청의 성공을 검사하므로 DB 파일에 접근하지 못하는 상태를 정상으로 판단하지 않습니다.

## 애플리케이션 실행

신규 `MSG-COMPLETE-MANAGER`는 `bash scripts/local.sh run messaging-complete-manager`로 별도 실행한다. PostgreSQL의 `messaging_completion` 스키마에 Flyway가 `tbl_msg_hist`·`tbl_cdr_hist`를 만든다. 결과 Manager outbox와 TCP Sender 소비는 기본 활성화되어 1차 실패 후 2차 명령·즉시 응답 인계가 가능하다. 완료 Manager와 고객 웹훅 Sender의 Kafka 소비는 기본 활성화되어 최종 이력과 웹훅 명령을 각 PostgreSQL에 보존한다. 고객 웹훅의 실제 HTTP 발송에는 `messaging.webhook.sender.customers.<clientId>.url` 설정이 필요하며, URL이 없는 고객의 명령은 SQL 대기 상태로 남는다. 완료 관리자는 SQL 이력의 정리 대기 행을 재확인하며, 고객 웹훅 명령 발행이 끝난 뒤 DynamoDB ORIGIN·STEP에 TTL을 설정하고 삭제한다. `MSG_COMPLETE_CLEANUP_ENABLED=false`로 정리 작업을 중지할 수 있다. 운영에서 완료 관리자 실행 역할에는 `ORIGIN`·`STEP`의 TTL 조회·활성화와 항목 조회·수정·삭제 권한이 필요하다. TCP 전문은 고객 메시지 ID·수신 번호·2차 발송 내용을 담는 임시 시뮬레이터 규격이므로 실제 업체 연동 전 규격 검증이 필요하다.

신규 `/api/v1/messages` 접수는 기본 활성화다. 신규 경로 전체를 실행할 때는 `messaging-api` 외에 `messaging-pre-send-manager`, `messaging-result-manager`, `messaging-complete-manager`, `messaging-webhook-sender`를 각각 실행한다. 1차 HTTP 검증에는 통신사별 `messaging-carrier-http-sender`와 `messaging-webhook-receive-api`가 필요하고, 2차 검증에는 `messaging-tcp-sender`와 TCP 시뮬레이터가 필요하다. 계약·번호 캐시를 시험하려면 `bash scripts/local.sh cdc`와 `messaging-reference-cache`를 추가한다. `MESSAGING_ADMISSION_ENABLED=false`로 새 접수만 중지할 수 있다.

2026-10-08 로컬 검증에서 계약이 있는 고객의 `API → PRE-SEND → SKT HTTP 200 → 통신사 웹훅 success → 결과 Manager → TBL_MSG_HIST(PRIMARY/SUCCESS)·TBL_CDR_HIST 1건 → 고객 웹훅 DELIVERED`를 확인했다. 계약이 없는 고객은 `PRE-SEND → 2차 TCP → TBL_MSG_HIST(SECONDARY/SUCCESS)·TBL_CDR_HIST 0건 → 고객 웹훅 DELIVERED`로 끝났다. 두 경로 모두 로컬 통신사·TCP·고객 수신 대역을 사용했으며 실제 업체 연동 검증은 아니다.

1차 정상 경로는 저장소의 모의 통신사·고객 수신기를 이용해 반복 검증할 수 있다. JDK 21, Python 3, Docker Compose, SigV4를 지원하는 curl이 필요하다. `.env`와 `JAVA_HOME`을 준비한 뒤 저장소 루트에서 실행한다.

```bash
python3 scripts/primary-flow-local.py
```

스크립트는 인프라와 필요한 AP를 시작하고 로컬 테스트 고객의 계약을 누락 시 생성한다. 계약 캐시만 지워 PostgreSQL 조회가 가능하도록 하며 기존 계약 값과 사용량은 덮어쓰지 않는다. 매번 새로운 메시지를 접수해 TPS·월 사용량, SKT HTTP 요청, 성공 웹훅, 최종 메시지 이력 1건, 과금 대상 기록 1건, 고객 웹훅 전달, DynamoDB 원본·단계 정리를 대조한다. AP는 종료하고 Compose 인프라와 named volume은 유지한다. 실행 로그는 출력된 임시 디렉터리에 남는다. 포트가 겹치면 아래와 같이 기존 override 파일을 전달할 수 있다. 이미 빌드된 JAR 또는 실행 중인 인프라를 재사용할 때는 각각 `--skip-build`, `--skip-infra`를 사용한다.

```bash
LOCAL_ENV_OVERRIDE_FILE=/path/to/ports.env python3 scripts/primary-flow-local.py
```

`--scenario`로 1차 실패 경로도 선택할 수 있다. 각 명령은 세 통신사 Sender를 별도 프로세스로 실행하며 통신사별 요청 순서, 최종 이력, 과금 대상 기록 수, 고객 웹훅을 대조한다.

```bash
python3 scripts/primary-flow-local.py --scenario carrier-mismatch
python3 scripts/primary-flow-local.py --scenario carrier-exhausted
python3 scripts/primary-flow-local.py --scenario tps-retry --timeout 150
python3 scripts/primary-flow-local.py --scenario tps-exhausted --timeout 300
python3 scripts/primary-flow-local.py --scenario no-response-retry --timeout 150
python3 scripts/primary-flow-local.py --scenario no-response-exhausted --timeout 300
```

`carrier-mismatch`는 SKT의 불일치 응답 뒤 KT 성공, `carrier-exhausted`는 SKT → KT → LGU가 모두 불일치해 `40002` 최종 실패·미과금으로 끝나는 경로다. `tps-retry`는 SKT의 TPS 초과 응답 뒤 최소 1분을 기다려 같은 통신사에 2회차를 보내고 성공하는 경로이며, `tps-exhausted`는 네 호출 모두 TPS 초과일 때 재시도 3회 뒤 `40001` 최종 실패·미과금으로 끝나는 경로다. `no-response-retry`는 최초 HTTP 무응답 뒤 5초 타임아웃과 1분 지연을 거쳐 SKT 2회차가 성공하는지 검증한다. `no-response-exhausted`는 네 호출이 모두 무응답일 때 재시도 3회 뒤 `40003` 최종 실패·미과금으로 끝나는지 검증한다. 이 검증은 로컬 대역의 동작만 확인한다. 실제 통신사 연동과 2차 TCP 경로는 별도 검증이 필요하다.

### 기존 접수 경로 수동 실행

각 명령을 별도 터미널에서 순서대로 실행합니다.

```bash
bash scripts/local.sh run external-api-simulator
bash scripts/local.sh run delivery-ingress-worker
# Ingress의 DynamoDB 테이블 초기화 완료 후 Dispatch를 실행합니다.
bash scripts/local.sh run dispatch-worker
bash scripts/local.sh run messaging-api
```

실행 JAR는 `build`가 만든 파일입니다. 코드 수정 뒤에는 다시 빌드합니다. 네 AP 모두 시작 완료 로그와 오류 없는 상태를 확인합니다. 메인 HTTP 포트의 `/livez`·`/readyz`를 인증 없이 조회할 수 있습니다. Worker의 Kafka partition 할당 로그까지 확인해야 consume 준비를 판단할 수 있습니다. readiness는 Spring 애플리케이션 상태를 나타내며 Kafka 할당이나 저장소별 업무 가능 여부를 직접 검사하지 않습니다. [Spring Boot probe 동작](https://docs.spring.io/spring-boot/4.1/reference/actuator/endpoints.html). 아래 smoke 명령은 실행된 앱의 실제 처리 경로를 검증합니다.

신규 메시징 경로의 통신사 결과 수신은 `messaging-webhook-receive-api`가 담당한다. 통신사별 `MESSAGE_WEBHOOK_<CARRIER>_SECRET`을 지정하고 `bash scripts/local.sh run messaging-webhook-receive-api`로 실행한다. 위 자동 검증 스크립트는 SKT용 임시 secret을 직접 준비한다.

## 상태와 인증 확인

```bash
bash scripts/local.sh status
curl --fail-with-body http://localhost:18080/readyz
curl --fail-with-body -H 'Content-Type: application/json' \
  -d '{"username":"local-user","password":"local-password"}' \
  http://localhost:18080/api/v1/auth/token
```

포트를 바꿨으면 요청 URL도 맞춥니다. 네 앱의 준비가 끝나면 다음 명령으로 현재 구현된 처리 경로를 검증합니다.

```bash
bash scripts/local.sh smoke
```

스크립트는 `.env`의 포트를 사용하며 다음을 확인합니다.

- 테스트 사용자 인증 및 토큰 발급
- 동일 멱등키로 두 번 접수했을 때 HTTP 202와 동일한 `deliveryId`
- 최대 30초 동안 DynamoDB를 조회하여 `META`와 단일 `ATTEMPT#...`의 `ACCEPTED`, `provider_processed_at` 확인

실행마다 새 멱등키를 사용하며 로컬 Kafka/DynamoDB에 검증 데이터가 남고 테스트 계정의 요청 한도를 사용합니다. 토큰은 출력하지 않습니다. 기존 정책이 차단 상태이거나 한도가 소진되면 실패합니다. 실패 시 API 및 Worker 로그를 확인합니다.

이 검증은 Kafka와 두 Worker를 거쳐 mock Provider 접수 결과가 저장되는 범위입니다. Kafka 각 레코드의 직접 비교, 장애 복구, Provider 실제 부수 효과 횟수, receipt 이후 최종 전달 완료를 검증하지는 않습니다.

## 종료와 데이터

각 AP 터미널에서 Ctrl+C로 종료한 뒤 `bash scripts/local.sh down`을 실행합니다. named volume은 유지합니다. `down --volumes`는 데이터 삭제이므로 평상시 종료에 사용하지 않습니다.

Compose 프로젝트 이름이 `reliable-messaging-service`이므로 기존 `platform` 프로젝트의 DynamoDB volume을 자동으로 공유하지 않습니다. 기존 데이터와 컨테이너는 별도로 보존됩니다.

## 검증 범위

2026-09-23 Java 21에서 전체 9개 모듈 패키징과 테스트 14건을 통과했습니다. 셸 문법 검사도 통과했습니다. DynamoDB 자동 설정 등록 경로와 Worker 전용 활성화를 회귀 테스트로 확인했습니다.

실제 DB 초기화, Redis 정책 초기화, 네 앱 기동, 인증과 smoke 검증을 통과했습니다. 실행 검증에서 발견한 예시 JWT의 Base64 형식 오류, DynamoDB 볼륨 쓰기 권한 및 healthcheck 오류, Ingress JSON 직렬화 중복 설정, API 비동기 응답의 인증 누락을 수정했습니다.

비동기 인증 문제는 디버거에서 최초 요청의 사용자 ID `1`과 이후 `ASYNC` dispatch의 `InsufficientAuthenticationException`을 확인했습니다. JWT 필터가 비동기 dispatch에서도 인증하도록 수정했으며, 정상 202 응답·요청 한도 1회 차감·무인증 요청 거절을 회귀 테스트로 검증했습니다. Ingress 직렬화 테스트는 설정 적용 후 JSON type header가 없고 원시 byte 배열도 보존됨을 확인합니다.

Maven Wrapper 3.3.4 / Maven 3.9.16을 통한 전체 빌드와 테스트 14건도 통과했습니다. Java 17 빌드 및 앱 실행 거절과 새 캐시에서의 Wrapper 다운로드·체크섬 검증을 확인했습니다. 이 2026-09-23 기록 당시 별도 AP readiness endpoint는 후속 작업이었으며 현재는 위 probe가 추가됐습니다. 장애·재시도·복구 시나리오는 별도 통합 테스트가 필요합니다.


## 접수 오류와 DynamoDB 재처리 검증

API가 Kafka 저장 ack를 확인하지 못하면 HTTP 503과 오류 코드 `50003`을 반환하며 같은 `Idempotency-Key`와 요청 내용으로 재요청하도록 안내합니다. 503은 원본이 Kafka에 없다는 증거가 아닙니다. 동기 send 실패, 비동기 ack 실패와 MVC 비동기 timeout에 같은 오류 계약을 적용합니다. 기존 `9003`에서 변경한 코드는 [오류 코드 계약](54-메시징-오류-코드와-결과-인계-계약.md)을 따릅니다.

개발 기본값은 Kafka metadata/buffer 대기 5초, 개별 요청 timeout 5초, 발행 결과 제한 10초, MVC 비동기 응답 제한 20초입니다. 각각 `KAFKA_PUBLISH_MAX_BLOCK_MS`, `KAFKA_PUBLISH_REQUEST_TIMEOUT_MS`, `KAFKA_PUBLISH_DELIVERY_TIMEOUT_MS`, `DELIVERY_HTTP_ASYNC_TIMEOUT`으로 조정할 수 있습니다. Kafka 발행 결과 제한은 요청 timeout + linger 이상이어야 합니다. 이 값은 업체 발송 재시도 간격이나 업무 만료 기간이 아닙니다. [Kafka producer 설정 근거](https://kafka.apache.org/40/generated/producer_config.html), [Spring MVC 비동기 오류 처리](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html).

DynamoDB Local이 실행 중이면 다음으로 저장·재처리 경계를 검증합니다. 포트는 로컬 환경에 맞춥니다.

```bash
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 ./mvnw verify
```

환경변수가 없으면 DynamoDB 통합 시험만 건너뜁니다. 테스트는 로컬 HTTP endpoint만 허용하고 UUID key의 전용 데이터를 생성·정리합니다. 기존 테이블과 다른 요청 데이터는 삭제하지 않습니다. 실제 DynamoDB를 사용하며 Kafka 발행은 테스트 대역으로 실패를 주입합니다. 저장 직후 중단 상태에서 재개, 후속 발행 ack 유실 후 재처리, 입력 충돌 차단, 동시 중복 20건의 최초 저장 시각 보존을 검사합니다. Kafka broker 장애나 프로세스 kill 전체를 검증한 것으로 해석하지 않습니다.

2026-09-23 이 명령으로 전체 9개 모듈 빌드와 테스트 25건을 통과했습니다(실패·오류·건너뜀 0). 기존 14건에 API 실패 계약 4건, Ingress 단위 3건, DynamoDB Local 통합 4건을 추가했습니다.


## Kafka DLT 격리와 offset 복구 검증

로컬 Kafka와 DynamoDB가 실행 중이면 다음 명령으로 전체 시험을 실행합니다.

```bash
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:19092 \
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
./mvnw verify
```

각 환경변수가 없으면 해당 저장소 통합 시험은 건너뜁니다. Kafka 시험은 `localhost` 또는 `127.0.0.1`만 허용하고 UUID 이름의 토픽·Consumer Group을 생성·정리합니다. 테스트 전용 DLT의 파티션을 일부러 부족하게 만든 뒤 복구하며, 업무 토픽·그룹은 변경하지 않습니다. 기존 앱을 중지할 필요는 없습니다.

2026-09-23 전체 9개 모듈 빌드와 테스트 34건을 통과했습니다(실패·오류·건너뜀 0). 실제 Kafka 3건과 DynamoDB Local 4건이 포함됩니다. 접수 재전달의 개발 기본값은 `INGRESS_RETRY_INTERVAL=1s`, `INGRESS_MAX_RETRIES=2`이며 외부 발송 재시도와 별도입니다. 세부 근거와 운영 재처리는 [DLT 문서](12-접수-실패-격리와-DLT-재처리-절차.md)를 참고합니다.

## 발송 결과 미기록 상태 보존 검증

위 명령에 `KAFKA_TEST_BOOTSTRAP_SERVERS`와 `DYNAMODB_TEST_ENDPOINT`를 모두 지정하면 Dispatch 복구 시험도 실행합니다. 2026-09-24 전체 9개 모듈 빌드와 테스트 46건을 통과했습니다(실패·오류·건너뜀 0). Kafka 통합 3건과 DynamoDB Local 통합 12건이 포함됩니다.

Dispatch는 lease가 만료돼도 다시 발송하지 않고 `REVIEW_REQUIRED`를 저장합니다. 추가된 DynamoDB 시험 8건은 결과 미기록 복구, 동시 복구·정상 결과 저장 경합, 복구 저장 응답 유실 등을 검증합니다. UUID key의 전용 데이터만 정리하며 Provider는 중복 제거 없는 테스트 대역입니다. 실제 프로세스 kill이나 성능 부하 시험은 별도입니다.

Dispatch Kafka 재전달 간격은 `DISPATCH_REDELIVERY_BACKOFF_MS=1000`입니다. 상태를 안전하게 넘기기 전에는 재전달을 계속하며, 이는 외부 발송 재시도 횟수가 아닙니다. 현재 Dispatch DLT가 없어 역직렬화 오류도 입력을 보존하고 재시도하므로 해당 소비 구간 처리가 지연될 수 있습니다. 상세한 보장 범위와 남은 작업은 [발송 선점 ADR](adr/ADR-008-발송-작업-선점과-외부-중복-발송-방지.md)을 참고합니다.


## 성능 계측과 시뮬레이터 관측 검증

네 앱을 새 빌드로 실행한 뒤 `bash scripts/local.sh smoke --metrics`를 실행합니다. 기본 smoke에 구간·DB·HTTP 지표와 외부 중복 제거 없는 호출/처리 횟수 대조를 추가합니다. 실행 결과를 성능 테스트로 해석하지 않습니다. 관리 포트·설정·지표 의미·보관 한도는 [성능 지표와 시뮬레이터 관측 방법](14-성능-지표와-시뮬레이터-관측-방법.md)에 정리했습니다.

2026-09-24 계측 변경 후 전체 9개 모듈 빌드와 테스트 57건을 통과했습니다(실패·오류·건너뜀 0). 기존 46건에 계측 4건·발송 성공 집계 경계 2건·시뮬레이터 5건을 추가했습니다.

성능 부하는 일반 개발 Compose에 직접 넣지 않고 [격리된 PoC 실행 도구](15-격리된-성능-PoC-실행과-결과-대조.md)를 사용합니다. 해당 도구는 별도 프로젝트·포트·고객 정책과 실행별 원시 자료를 준비하고 종료 시 앱·시험 컨테이너를 멈춥니다.

## 완료 원본 정리 추가 — 2026-09-25

`DELIVERY_CLEANUP_ENABLED=false`가 기본입니다. 결과 워커의 Flyway V3는 이력·통지와 함께 정리 예약을 보관합니다. 구버전 SQL 소비자를 중지하고 이관한 뒤 Ingress·Dispatch·결과 워커를 모두 교체해야 합니다. 이후 결과 워커에서 `DELIVERY_CLEANUP_ENABLED=true`와 `DYNAMODB_ENDPOINT`를 설정하면 작은 완료 META를 유지하고 원본을 정리합니다. 정리 후에는 구버전 선점 코드로 돌아가지 않습니다.
