# 고객 결과 묶음 전송과 발송 완료 데이터 정리

> 2026-09-25 최신 정책: 완료 후 작은 DDB 기록 의무 보관은 [ADR-022](adr/ADR-022-처리-중-DynamoDB-선점과-완료-후-Redis-중복-차단.md)의 Redis TTL 차단으로 대체한다. Redis 소실 시에도 DDB 조건까지 통과하면 재발송을 허용한다. SQL 이력·통지 저장 전 원본 보존은 유지한다. 아래의 이전 완료 기록 정책은 이 결정이 우선하며, 코드 이관은 아직 하지 않았다.

작성일: 2026-09-23. 사용자 확정 요구와 아직 합의하지 않은 구현 제안을 구분한다. 관련 문서는 [설계 결정 목록](08-함께-결정할-설계-사항.md), [장애 운영 절차](09-저장소-장애-시-중단-범위와-복구-절차.md)다. 이 문서는 코드 구현 완료를 의미하지 않는다.

## 1. 확정된 요구사항

- 장기 장애에 묶인 작업은 복구 후 만료 처리한다. 복구 시 발송 기한을 새로 부여해 재발송하는 방향이 아니다. 장기 장애의 임계시간·대상 요청 구분은 추가로 정의한다.
- Redis 장애 시 TPS·Quota 제한을 모두 우회하고 요청을 계속 처리한다. 별도의 축소 TPS나 대체 Quota 제한으로 바꾸는 정책이 아니다.
- 발송 단계가 끝나면 원본·실행 상세를 정리하고 이력을 한 줄 남긴다. 후속 합의에 따라 멱등 판단에 필요한 작은 DynamoDB 완료 기록은 유지한다. 보관 기간은 미정이다.
- 고객 결과는 HTTP로 발송한다. 같은 고객의 결과를 **최대 100건**까지 묶되, 묶음을 채우려고 오래 기다리지 않는다.
- 고객 결과 웹훅은 **최대 20회 재전송**한다. 최초 전송을 제외한 20회, 즉 최대 총 21회 시도로 해석한다. 외부 업체 발송의 재시도 3회와 별도다.

고객 결과 통지는 외부 업체로 보내는 HTTP 1차·TCP 2차 발송과 별도 작업이다. 고객 HTTP 장애 때문에 이미 끝난 외부 발송을 다시 실행하지 않는다. 업체에서 들어오는 결과 웹훅과 고객에게 나가는 결과 HTTP도 구분한다.

## 2. 고객별 묶음 전송

### 묶음 생성 규칙

| 항목 | 규칙 |
|---|---|
| 고객 격리 | 다른 고객의 결과를 같은 HTTP 요청에 넣지 않음 |
| 건수 | 요청 한 번에 1~100건. 100건은 최대치이며 필수 개수가 아님 |
| 시간 | 짧은 최대 대기 시간에 도달하면 100건 미만이어도 전송 |
| 기한 | 묶음 대기를 이유로 고객 결과 기한을 뒤로 늘리지 않음 |
| 복구 | 프로세스 재시작 시 보내지 못한 결과를 다시 찾을 수 있어야 함 |

**구현 제안:** `maxBatchSize=100`, `maxWait`를 독립 설정으로 둔다. `maxWait` 초기 후보는 1초이며 사용자 확정값은 아니다. 건수 도달·가장 오래된 항목의 대기 한도·고객 결과 기한 중 먼저 도달한 조건으로 전송한다. 이미 대기한 항목의 시각을 새 항목 유입이나 재시작으로 초기화하지 않는다. HTTP 크기 한도에 도달하면 건수가 적어도 나누며 실제 바이트 상한은 구현 설정으로 정한다.

같은 고객이라도 목적지 URL·인증 정보·계약 버전이 다르면 별도 묶음으로 분리하는 안을 사용한다. 고객별 느린 HTTP 응답 때문에 다른 고객의 전송이 막히지 않게 실행 큐와 동시 처리량을 관리한다.

### 내구성 있는 대기와 재전송

메모리에만 묶음을 쌓고 원본/완료 상태를 삭제하면 재시작 때 결과가 사라진다. 전송할 결과와 수신 확인 상태는 내구성 있게 남겨야 한다.

**후보 흐름:**

```text
발송 최종 상태 결정
→ 같은 논리 완료 이벤트를 내구성 있게 인계
→ 이력 한 줄 및 고객 통지 PENDING을 저장
→ 같은 고객의 준비된 결과를 최대 100건 선택
→ 고객에게 HTTP 전송
→ 수신 확인을 기록
→ 통지용 임시 데이터 정리
```

이력 행에 결과 요약과 통지 상태를 함께 둘지, 별도 outbox를 둘지는 비용·조회 부하로 비교한다. 한 고객 묶음 전체를 이력 한 줄로 합치는 뜻은 아니며 이력은 발송 요청별 한 줄을 후보로 한다. 이력 저장과 통지 예약이 분리되어 한쪽만 남는 공백을 방지한다.

**확정된 횟수:** 고객 결과 웹훅은 최초 전송 + 최대 20회 재전송이다. 업체에서 들어오는 결과 웹훅의 재전송 계약까지 이 숫자로 확정한 것은 아니다.

**구현 제안:** 재전송 횟수·다음 시각·항목별 수신 확인을 내구성 있게 저장한다. 재시작·Kafka 재전달·묶음 재구성으로 같은 결과의 횟수를 초기화하지 않는다. 호출 직전 시도 번호를 원자적으로 예약하고, 호출 여부가 불명확한 예약도 사용한 시도로 계산하는 보수적 방식을 검토한다. 이 경우 실제 HTTP 호출은 21회보다 적을 수 있으나 프로세스 종료가 반복돼도 한도를 우회하지 않는다. 부분 실패 시 항목별 남은 예산을 유지한다.

20회 재전송을 모두 소진하면 자동 전송을 중단하고 `NOTIFICATION_EXHAUSTED`와 결과를 보존해 운영에서 조회·조치하는 안을 제안한다. 고객이 받았다고 표시하거나 결과를 삭제하지 않고, 이미 확정된 외부 발송 결과도 바꾸지 않는다. 수동 재전송의 허용·추가 예산은 별도 정책으로 남긴다.

고객 서버가 계속 응답하지 않으면 20회 재전송만으로 최대 만료 시간 내 실제 수신을 보장할 수는 없다. 내부 결과 확정·통지 준비 기한과 고객 수신 확인은 구분한다. 기존 고객 결과 제공 기한 요구를 임의로 철회하지 않으며, 고객 장애 시 제공 가능한 조회 경로와 기한 예외는 추가 논의 대상으로 남긴다.

**아직 정할 HTTP 계약:** 정상 ack의 의미, 전체 묶음/항목별 부분 실패, timeout·재전송 간격·최대 경과 시간, 한도 소진 후 운영 처리. 외부 발송의 재시도 3회를 고객 통지에 자동 적용하지 않는다. `resultEventId`처럼 항목별 안정적인 식별자를 사용하고, 같은 묶음을 재전송하면 배치 식별자·구성도 유지하는 안을 제안한다.

HTTP 응답이 유실되면 고객이 이미 받았을 수 있으므로 재전송 중복은 가능하다. 고객이 항목별 식별자로 중복을 제거하는 계약이 필요하다. 내부 전송 완료 기록만으로 고객 업무의 중복 효과까지 0회라고 보장하지 않는다. [공식 근거: AWS의 멱등 API와 늦은 재요청 설명](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). 위 식별자·ack 설계는 이 원칙에 따른 프로젝트 제안이다.

## 3. 원본과 실행 상태 정리

### 먼저 정해야 할 멱등성 범위

**초기 구상과 후속 확정:** 원본·멱등 기록 전부 정리라는 초기 구상에서, 원본·실행 상세를 정리하고 이력 한 줄과 작은 DynamoDB 완료 기록을 유지하는 방식으로 구체화했다.

**남는 문제:** 실행 기록과 중복 판단 정보를 모두 지우면 늦은 고객 재요청이나 Kafka 재전달을 새 발송으로 오인할 수 있다. 이력에 결과만 보관하고 발송 경로가 이를 확인하지 않는 경우도 같다. [AWS 공식 설명](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)은 요청 식별자 보존과 늦은 요청을 멱등 계약의 일부로 다룬다.

**사용자 확정:** 호처리에 필요한 실행·멱등 상태만 DynamoDB에 최소한으로 저장하고, 완료 후에도 작은 완료 기록을 유지한다. [삭제 위험·대안·공식 근거](11-멱등-정보-보관과-완료-후-정리-방식.md)에 선택 이유를 정리했다. PostgreSQL 이력을 유일한 멱등 원장으로 사용하는 대안은 이번에 채택하지 않았다. 보관 기간과 상세 구현은 별도다.

### 안전한 정리 순서 제안

1. **종료 범위를 판정한다.** 1차가 끝나도 2차가 필요하면 전체 발송은 미완료다. 2차 재실행 입력까지 지우지 않는다. HTTP/TCP 접수 ack만 받은 상태도 최종 발송 종료가 아니다.
2. **최종 결과와 후속 인계를 내구성 있게 만든다.** 고객 통지에 필요한 결과와 식별자를 확보한다. 최종 이벤트 발행 전에 실행 기록을 삭제하지 않는다.
3. **이력 저장을 확인한다.** 같은 발송의 중복 완료 이벤트는 유일한 이력 한 줄로 수렴하게 한다. 이력 저장 실패 시 정리를 보류한다.
4. **중복 판단의 공백을 막는다.** 안정적인 요청 key의 실행 상태를 완료 상태로 전환하고 작은 완료 기록을 유지한다. 완료 여부 확인과 시도 선점이 원자적으로 보호되는지 검증한다. 실행 상태 삭제 후 완료 항목을 새로 만드는 공백을 두지 않는다.
5. **원본·활성 상태를 정리한다.** 현재의 version/종료 상태와 인계 완료를 조건으로 제거한다. 삭제 실패·중복 정리 작업은 안전하게 재시도한다. 느린 기존 Worker가 삭제 후 작업을 되살리지 못하도록 한다.
6. **고객 통지는 독립적으로 완료한다.** 발송 원본을 없애더라도 미전송 결과를 재구성할 근거는 고객 수신 확인 전까지 유지한다. HTTP 장애를 전체 발송 재실행으로 해결하지 않는다.

이력 DB가 장애이면 원본·실행 상세 정리를 미루고 DynamoDB 완료 기록을 유지한다. 완료 여부의 판단을 이력 조회로 대체하지 않는다. 다른 필수 의존성이 정상이고 내구성·용량 조건을 만족하면 발송 경로는 계속한다. [운영 절차](09-저장소-장애-시-중단-범위와-복구-절차.md)에 따라 장애 적체와 용량을 관리한다.

### 저장소별 삭제 방식 차이

- DynamoDB TTL은 지정 시각의 즉시 삭제가 아니다. 정확한 인계 확인과 업무 상태 전이는 애플리케이션에서 처리하고 TTL은 이후 정리 수단으로 검토한다. [공식 TTL 동작](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html).
- Kafka의 공유 토픽에서 요청 한 건의 발송 종료 시 해당 record만 즉시 삭제하는 것을 일반적인 retention 처리로 구현할 수는 없다. 시간·용량 retention은 다른 요청에도 적용되고 compaction도 비동기다. 활성 저장소에서의 정리와 Kafka 원본 보관 기간을 구분해 정한다. [Kafka 4.0 topic 설정](https://kafka.apache.org/40/generated/topic_config.html).
- 이력의 보존 기간과 멱등 보장 기간은 아직 미정이다. 이력을 계속 남기는 것과 무기한 온라인 조회 비용을 감당하는 것은 별도 설계 문제다.

## 4. 장기 장애와 Redis 장애 반영

장기 장애 복구 후에는 장애에 묶인 미완료 작업을 만료 결과로 정리하고 고객에게 HTTP 통지한다. 이미 정상 완료되어 결과가 확정된 요청을 다시 만료로 덮지 않는다. 늦은 웹훅 폐기 정책도 유지한다. '장기 장애'의 판정 기준과, 장애 중 새로 접수되어 아직 기한이 남은 요청까지 일괄 만료할지는 추가 정의가 필요하다. 이 문서만으로 아직 기한이 남은 정상 요청까지 만료 대상으로 확장하지 않는다.

Redis 장애 시 TPS·Quota 제한은 모두 우회한다. 인증, 원본 저장 확인, 외부 발송 전 실행 기록, 데이터 보존을 위한 backpressure까지 생략한다는 뜻은 아니다. 장애 동안 계약상 사용량 초과가 발생할 수 있고 Redis 카운터만으로 해당 구간의 정확한 사용량을 복원할 수 없다. 독립된 사용 이벤트로 보정할지, 장애 구간을 별도 표시할지 추후 정한다.

## 5. 검증할 상황

- 같은 고객 1건·99건·100건·101건, 여러 고객 혼합, 연속 유입 중 대기 한도 유지.
- 묶음 생성 전후·HTTP 성공 직후 종료, 응답 유실, 부분 실패, 고객별 장애 격리.
- 최초 전송 + 최대 20회 재전송, 재시작·재전달·묶음 변경에도 횟수 유지, 한도 소진 후 결과 보존·자동 전송 중단.
- 이력 저장 전/후 종료, 이력 저장 실패, 원본 삭제 실패, 중복 완료·중복 정리 이벤트.
- 원본 정리 후 고객 재요청·오래된 Kafka 재전달·이전 Worker 재개. 선택한 멱등 원장의 완료 확인과 선점이 경합해도 중복 외부 발송을 차단하는지 검증.
- 1차 종료 후 2차가 남은 요청의 입력 보존, 고객 통지 대기 중 발송 원본 정리.
- 장기 장애 복구 후 만료·통지와 기존 성공 결과 불변, Redis 장애 시 TPS·Quota 우회.

이 문서의 시나리오는 시험 계획이며 현재 구현의 통과 결과가 아니다.
