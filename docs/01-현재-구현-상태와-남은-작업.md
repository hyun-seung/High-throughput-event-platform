# 현재 구현 상태와 남은 작업

분석 기준: 2026-09-25 현재 코드.

**최신 진행 순서:** 전체 최종 목표는 **10,000 TPS**입니다. 사용자의 요청에 따라 남은 기능·장애 복구·운영 처리와 통합 검증을 먼저 마무리하고, 이후 성능 설정·튜닝 → 서비스별 Pod 1개 한계 측정 → 전체 확장 검증 순서로 진행합니다. 지금의 로컬 단기 TPS는 Pod당 성능으로 환산하지 않습니다. [요구사항과 측정 계획](41-전체-만-TPS-목표와-Pod별-성능-검증-계획.md).

최신 정책을 새 API의 v2 경로에 구현했습니다. [최신 구현·검증](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md)을 기준으로 보세요. 정상 1차 성공은 DDB 쓰기 API 5회·변경 7항목, 양 단계 재시도와 운영 확인·만료를 거치는 대표 경로는 24회·28항목입니다. 삭제도 항목 변경에 포함합니다.

물리 저장소도 `ORIGIN`·`STEP` 두 테이블로 분리했습니다. [경로별 쓰기 합산과 이관 절차](36-원본과-단계-테이블-분리와-경로별-쓰기-내역.md)를 추가했습니다.

[전체 Call Flow](04-요청-접수부터-최종-결과까지의-전체-흐름.md)를 현재 v2 코드 기준으로 갱신했습니다. Redis 정상 일정 조회는 1초, DDB 누락 복구 조회는 읽기 비용을 고려해 기본 10분으로 변경했습니다. [API→업체→고객 수신·정리 격리 도구](37-전체-호출-흐름의-격리-실행과-전수-대조.md)로 **전체 6개 시나리오 전수 대조를 통과**했습니다. 첫 실행은 Docker 시작 정체로 중단됐지만, Created 상태에서만 제한적으로 재시도하는 대응으로 재검증했습니다. 성공 4건·만료 2건의 고객 수신/SQL 일치·DDB 정리, 고객 재전송·완료 중복 차단·Redis 일정 유실 복구를 확인했습니다. 패키징도 통과했습니다. [실행 근거](검증-결과/2026-09-25-Docker-시작-정체와-전체-흐름-재검증.json).

[고객 수신·정리까지의 짧은 부하 측정](38-고객-수신과-정리까지의-전체-성능-측정.md)도 완료했습니다. 두 설정에서 각각 551건의 고객 수신·SQL 결과·업체 호출·DDB 삭제를 전수 대조했고 Python 시험 29개를 통과했습니다. 100 TPS ×5초 구간에서 Redis 조회 1초→50ms 비교 시 고객 수신 p95는 118.23초→15.45초, 입력·배출을 포함한 관찰 처리량은 3.86→10.09 TPS였습니다. 각 실행 전체의 DDB 읽기는 36.5% 증가해 기본값은 바꾸지 않았습니다.

이후 [성공 웹훅 결과를 저장 직후 Kafka로 인계](39-성공-결과의-즉시-Kafka-인계와-복구-검증.md)하도록 개선했습니다. DB 저장 결과를 그대로 발행하며 ack 불확실 시 입력 재처리·기존 복구 경로를 유지합니다. Java 시험 158개 통과(별도 환경 필요 4개 미실행), 전체 기능 6개와 부하 550건 전수 대조를 통과했습니다. 기본 Redis 1초·DDB 10분에서 100 TPS ×5초 고객 p95는 16.80초, 정리 포함 관찰 처리량은 10.02 TPS였습니다. 성공 쓰기는 요청당 5회, 평균 읽기는 8.69회로 유지·감소했지만 실패 트랜잭션은 늘어 비용 감소를 단정하지 않습니다.

[정리 worker의 제한된 동시 처리](40-완료-데이터-정리의-동시-처리와-성능-검증.md)도 적용했습니다. 기본 4개 작업자·작업자당 최대 20건이며 SQL lease와 조건부 삭제를 유지합니다. Java 시험 62개·Python 29개, 전체 기능 6개와 동시성 1/4 부하 각각 552/551건 대조를 통과했습니다. 같은 코드의 100 TPS ×5초 비교에서 정리 p95는 39.83→20.27초, 정리 포함 관찰 처리량은 10.17→18.41 TPS였습니다. 성공 DDB 쓰기는 요청당 5회 그대로입니다. 고객 수신 p95는 14.30→18.65초로 늘고 DDB 개별 호출도 느려져, 앞단 Kafka 적체·DDB 지연·자원 경쟁 분석은 개발 완료 후 성능 단계에서 진행합니다. 현재 수치는 지속 처리량 목표 달성의 근거가 아니며 전체 10,000 TPS와 장애 복구 검증은 남아 있습니다.

현재 v2 흐름은 Kafka 접수 → 고객별 ORIGIN 선점 → 실행별 STEP 선점 → HTTP/TCP → 고정 회차 Kafka 재시도 또는 웹훅 결과 확정 → SQL 이력·통지·정리 예약 → DDB 삭제 → Redis 완료 TTL입니다. 별도 receipt marker·FINAL·재시도 예약 Update·Kafka 최종 ack Update를 사용하지 않습니다.

남은 작업은 기능·운영 처리 보완, 실제 프로세스 종료·재시작과 저장소 장애 복구의 통합 검증, 실행·배포 준비입니다. 개발 완료 후 확인한 성능 병목의 튜닝과 Pod별·전체 지속 부하 측정을 진행합니다. 운영 TTL/복제 배치 값과 성능 시험 환경은 해당 준비 단계에서 확정합니다. 기존 v1 완료 데이터의 일괄 이관은 자동 수행하지 않았습니다. 아래 상세 표는 v1 기준선과 기존 검증의 기록이며 v2 동작·횟수는 위 최신 문서를 우선합니다.

## 1. 현재 처리 흐름

```text
Client
→ JWT 인증
→ Redis TPS/Quota admission 확인
→ tenantId + Idempotency-Key로 안정적인 deliveryId 생성
→ DeliveryRequested를 Kafka에 발행
→ Kafka broker ack 완료
→ Client에 202 Accepted
→ Delivery Ingress Consumer가 consume
→ DynamoDB DELIVERY conditional insert
→ DispatchRequested를 Kafka에 발행
→ Dispatch Consumer가 consume
→ DynamoDB META 완료 확인 + Attempt conditional claim 트랜잭션
→ HTTP Mock Delivery Provider 호출·응답 분류
→ 유효한 접수 성공 결과를 DynamoDB에 저장
  또는 실패 저장·예약 재시도
  또는 허용 요청의 1차 전환 판단 고정 → 2차 선점 → TCP 업무 접수 확인 저장
```

API는 DynamoDB를 호출하지 않습니다. Kafka ack가 최초 접수 보장의 근거이며 DynamoDB는 Consumer가 만드는 상태 projection입니다.

업체 결과 수신은 별도 `receipt-api`에서 업체별 인증·형식 검증 → `delivery.receipt-received.v1` 발행 → Kafka ack 후 202로 처리합니다. 수신 API는 DynamoDB·Redis를 호출하지 않습니다. Dispatch 앱 안의 별도 Result Consumer가 호출 회차·중복·기한을 판정하고, 성공을 Attempt DELIVERED로 반영하거나 실패 코드에 따른 재시도·허용된 TCP 2차로 연결합니다. [결과 처리와 복구 검증](27-웹훅-결과-반영과-재시도-대체-발송-복구.md). [시뮬레이터 자동 웹훅과 실제 흐름 12개](28-시뮬레이터-자동-웹훅과-발송-결과-통합-검증.md)를 검증했습니다. [주기 만료·전체 최종화·최종 Kafka 인계](29-주기-만료와-요청-최종화-및-Kafka-인계.md)도 구현했습니다. GSI 이관 후 별도 활성화해야 합니다. 이어 [PostgreSQL 이력·고객 통지 PENDING 원자 저장](30-최종-이력과-고객-통지-대기-기록의-원자-저장.md)을 구현했습니다. [고객 HTTP 묶음 통지·재전송·복구](31-고객-HTTP-묶음-통지와-재전송-복구.md)도 구현했습니다. 기본 비활성화이며 고객별 설정 후 활성화합니다. [작은 완료 기록·원본 정리](32-완료-기록-유지와-발송-원본의-안전한-정리.md)도 구현했습니다. SQL 이력·통지·정리 예약 후 DDB 원본을 조건부로 정리합니다. 전체 쓰기 워커 교체 후 별도 활성화해야 합니다.

## 2. 현재 모듈

| 모듈 | 현재 역할 |
|---|---|
| `event-api` | JWT 인증, Redis admission control, Kafka-first Delivery 접수 |
| `delivery-result-worker` | 최종 Kafka 결과의 별도 소비, PostgreSQL 이력·고객 통지 PENDING 원자 저장, 중복·충돌·재시작 복구, 고객 HTTP 최대 100건 묶음·최초+20회 재전송, SQL 정리 예약·DDB 원본 정리 |
| `receipt-api` | 업체별 Bearer 인증, 호출 회차를 포함한 결과 웹훅 형식 검증, Kafka-first 접수 |
| `delivery-ingress-worker` | Delivery 원본 conditional 저장, Dispatch event 발행, 완료 요청의 재발행 차단 |
| `dispatch-worker` | Dispatch 소비·멱등 선점·HTTP/TCP 발송, 별도 Receipt 소비와 Attempt 결과 반영·후속 재시도/대체 발송, 선택 활성화하는 주기 만료·전체 최종화·FINAL outbox |
| `external-api-simulator` | HTTP/TCP 접수·오류 코드, TCP 응답 유실·ID 불일치, 지연·중복 제거 on/off·호출/효과 관측, 회차별 자동 웹훅·중복/미발송/응답 역전 |
| `event-common` | Delivery event 계약, Topic, DynamoDB 설정·테이블 초기화, 공통 구간/DB 계측 |
| `auth-module`, `common-security` | 사용자 인증과 JWT |
| `common-core` | 공통 API 응답과 오류 |

각 처리 단계는 독립 실행 모듈로 분리되어 별도 확장과 장애 격리가 가능합니다. 공통 계약 모듈에는 `event` 이름이 남아 있으며 업무 코드에는 `Delivery` 용어를 적용했습니다.

각 Worker의 Consumer 동시 실행 기본값은 3입니다. 기존 3개 파티션을 나눠 처리하며 `INGRESS_CONCURRENCY`·`DISPATCH_CONCURRENCY`로 조정합니다. 파티션 내부 처리 순서와 RECORD ack·DB 멱등 저장은 유지합니다. 동시성 1에서 적체되던 100 TPS가 3에서는 3분 정상 시험을 통과했습니다. [변경 과정과 측정 근거](17-워커-동시-처리와-발행-대기-성능-비교.md).

## 3. 구현된 신뢰성 경계

- 같은 tenant와 `Idempotency-Key`는 같은 `deliveryId`를 생성합니다. 최초 fallbackAllowed를 원본과 event에 유지하고 같은 key로 변경하면 충돌로 격리합니다. 생략·기존 데이터는 false입니다.
- 최초 `DeliveryRequested` event ID도 deliveryId에서 안정적으로 생성됩니다.
- API는 Kafka send future가 성공한 뒤에만 `202`를 반환합니다. 동기 발행 실패·비동기 ack 실패·HTTP 비동기 timeout은 `503 / 9003`으로 응답하고 같은 key·내용으로 재요청하도록 안내합니다. 503으로 Kafka 원본 부재를 단정하지 않습니다.
- Producer는 `acks=all`, idempotence, zstd, 짧은 linger를 사용합니다.
- Ingress Consumer는 DynamoDB 단일 item을 conditional insert합니다.
- payload key 순서를 정규화하고 중복 insert에서는 기존 원본이 같은 요청인지 consistent read로 확인합니다. 재요청의 후속 Dispatch에는 최초 저장된 인입 시각을 사용해 만료 기한이 늘어나지 않게 합니다.
- DynamoDB 저장 후 `DispatchRequested` 발행이 실패하면 listener가 실패하여 원본 record가 재전달됩니다. 접수 오류는 개발 기본값 1초 간격으로 2회 재시도 후 DLT에 격리하며 멱등 충돌·역직렬화 실패는 즉시 격리합니다.
- Ingress는 RECORD 단위로 ack하고 DLT 발행 ack를 확인한 경우에만 격리 인계를 완료합니다. DLT 실패 시 원본 offset을 유지하며 DynamoDB 실패 복사본은 추가하지 않습니다. 상세 동작과 재처리 절차는 [DLT 운영 문서](12-접수-실패-격리와-DLT-재처리-절차.md)를 따릅니다.
- Dispatch Worker는 안정적인 `attemptId`의 최초 선점과 META 완료 표시 부재 확인을 같은 트랜잭션으로 처리합니다. 최종화 시 META에 완료 표시를 기록하며, 정리 후에도 작은 완료 META를 유지해 재선점을 차단합니다.
- 유효한 `PROCESSING` lease가 있으면 Provider를 호출하지 않습니다. lease 만료 시 재선점 대신 `REVIEW_REQUIRED`와 사유를 저장하고 version을 증가시킵니다. `ACCEPTED`·`REVIEW_REQUIRED` 재전달은 추가 호출 없이 처리합니다.
- Dispatch는 오류를 로그 후 버리지 않고 원본을 재전달합니다. 운영 확인 상태 저장 실패는 listener 성공이 아니며, 전체 업무 만료·최종화는 선택 활성화 경로로 구현했고 조회/조치 도구는 후속입니다. 관찰한 무응답·재시도 코드는 내구성 예약 후 최대 3회 재시도합니다. 허용된 1차 전환 판단은 고정한 provider·deadline으로 TCP 2차에 연결하며 2차도 별도 선점·결과 저장을 거칩니다.
- Attempt version이 일치하는 Worker만 Provider 성공 결과를 기록할 수 있습니다.
- Mock Provider는 attemptId를 Idempotency-Key로 받습니다. 기본값은 외부 중복 제거 해제이며 호출마다 효과를 기록합니다. `SIMULATOR_DEDUPLICATE=true`일 때만 같은 key의 정상 응답을 재사용합니다. 내부 멱등 보장의 검증은 해제 상태로 진행합니다.
- 외부 HTTP 연결/응답 timeout을 설정했습니다. HTTP 응답의 ID·필수 필드·코드 일관성을 검증하고 재시도 대상·대체 발송 대상·영구 거절·무응답·판단 불가를 구분합니다. 분류 결과의 DB 저장·최대 3회 재시도와 최초 인입 기준 기한 검사를 연결했습니다. [실패 저장과 재시도 예약](24-실패-저장과-1차-재시도-예약.md).

## 4. 요청당 저장과 발행

정상 흐름 기준:

| 구간 | Kafka | DynamoDB |
|---|---:|---:|
| API 접수 | `DeliveryRequested` 1건 | 0 |
| Ingress Consumer | `DispatchRequested` 1건 | `DELIVERY#id / META` Put 1건 |
| Dispatch Consumer | consume 1건 | META ConditionCheck+Attempt Update 트랜잭션 + 성공 결과 Update 1건 |
| 주기 복구/최종화 | shard별 GSI Query·원본 consistent read | 기존 항목의 복구 색인 속성, 최종화 시 META 포함 3~4항목 트랜잭션, Kafka ack 후 FINAL 확인 갱신. [비용 근거](adr/ADR-013-주기-복구와-최종-결과의-내구성-인계.md) |
| 최종 이력 Consumer | finalized consume, SQL commit 후 offset commit | 0회. PostgreSQL 이력·통지·정리 예약 INSERT 각 1회 |
| 결과 Consumer(새 상태 반영 시) | Receipt consume | 기존 Attempt 변경+작은 receipt marker의 2항목 트랜잭션. API 접수 쓰기와 별도 |

기존 ingress의 원본 Put, Step Put, publish status Update 구조를 단일 conditional Put으로 줄였습니다. 완료 정리는 META/FINAL Get와 파티션 Query 후 조건부 교체·삭제 트랜잭션을 사용합니다. 선점 조건 확인의 용량과 정리 비용은 [구체적 비용표](32-완료-기록-유지와-발송-원본의-안전한-정리.md)를 참고합니다. 위 API 횟수를 과금 용량 단위로 해석하지 않습니다.

정상 전체 완료·정리는 쓰기 API 8회/항목 변경 14회입니다. 각 단계 한 번씩 처리하는 최대 대표 경로는 성공 쓰기 API 33회/항목 변경 55회이며, 실패·재전달을 포함한 총 호출 상한은 없습니다. 최소 설계는 아니며 [사용 목적·실제 계측·최소화 후보](33-DynamoDB-사용-횟수와-최소화-검토.md)에 구분했습니다. 신규 계측 시험 4건을 별도 실행해 통과했습니다. 아래 전체 package 260건은 이전 실행 기록입니다.

## 6. 현재 보장 범위

현재 설명할 수 있는 보장은 다음과 같습니다.

```text
202 Accepted
= Kafka가 DeliveryRequested를 ack함
```

```text
동일 Client 요청 재전송
→ 동일 deliveryId/eventId
→ Kafka record는 중복될 수 있음
→ DynamoDB 원본은 한 item으로 수렴
```

완료된 Attempt의 재호출과 lease 만료 후 재전달 Worker의 자동 재발송을 차단합니다. Provider 처리 후 결과 저장 전 종료 상태는 REVIEW_REQUIRED로 남으며, Provider 중복 제거를 끈 테스트 대역으로 추가 호출이 없음을 검증했습니다. 기존 Worker가 외부 호출 직전에 재개하는 문제와 관찰한 무응답 재시도의 실제 중복 가능성은 별도이므로 외부 효과의 exactly-once를 보장한다고 표현하지 않습니다. 재시도 예약 중 원본 Kafka offset을 유지하는 구현은 실제 Consumer 재시작으로 검증했습니다. 이 방식의 파티션 대기·반복 DB 조회 비용은 남아 있습니다. DECISION_PENDING은 최종 결과가 아닙니다. 허용된 전환 사유는 TCP 2차로 연결했고, 그 외 판단·2차 결과는 선택 활성화한 최종화 경로에서 FINAL에 수렴하며 고객 통지는 남아 있습니다. [현재 범위와 검증](25-대체-발송-허용과-TCP-2차-접수.md).
