# 현재 구현 상태와 남은 작업

분석 기준: 2026-09-24 현재 코드.

## 1. 현재 처리 흐름

```text
Client
→ JWT 인증
→ Redis TPS/Quota admission 확인
→ tenantId + Idempotency-Key로 안정적인 deliveryId 생성
→ DeliveryRequested를 Kafka에 발행
→ Kafka broker ack 완료
→ Client에 202 Accepted
→ Delivery Ingress Consumer가 consume
→ DynamoDB DELIVERY conditional insert
→ DispatchRequested를 Kafka에 발행
→ Dispatch Consumer가 consume
→ Mock Delivery Provider 호출
```

API는 DynamoDB를 호출하지 않습니다. Kafka ack가 최초 접수 보장의 근거이며 DynamoDB는 Consumer가 만드는 상태 projection입니다.

## 2. 현재 모듈

| 모듈 | 현재 역할 |
|---|---|
| `event-api` | JWT 인증, Redis admission control, Kafka-first Delivery 접수 |
| `delivery-ingress-worker` | Delivery 원본 conditional 저장, Dispatch event 발행 |
| `dispatch-worker` | Dispatch event 소비, 외부 Provider 호출 |
| `external-api-simulator` | 성공/강제 500·응답 지연·중복 제거 on/off·key별 호출/효과 관측 |
| `event-common` | Delivery event 계약, Topic, DynamoDB 설정·테이블 초기화, 공통 구간/DB 계측 |
| `auth-module`, `common-security` | 사용자 인증과 JWT |
| `common-core` | 공통 API 응답과 오류 |

각 처리 단계는 독립 실행 모듈로 분리되어 별도 확장과 장애 격리가 가능합니다. 공통 계약 모듈에는 `event` 이름이 남아 있으며 업무 코드에는 `Delivery` 용어를 적용했습니다.

각 Worker의 Consumer 동시 실행 기본값은 3입니다. 기존 3개 파티션을 나눠 처리하며 `INGRESS_CONCURRENCY`·`DISPATCH_CONCURRENCY`로 조정합니다. 파티션 내부 처리 순서와 RECORD ack·DB 멱등 저장은 유지합니다. 동시성 1에서 적체되던 100 TPS가 3에서는 3분 정상 시험을 통과했습니다. [변경 과정과 측정 근거](17-워커-동시-처리와-발행-대기-성능-비교.md).

## 3. 구현된 신뢰성 경계

- 같은 tenant와 `Idempotency-Key`는 같은 `deliveryId`를 생성합니다.
- 최초 `DeliveryRequested` event ID도 deliveryId에서 안정적으로 생성됩니다.
- API는 Kafka send future가 성공한 뒤에만 `202`를 반환합니다. 동기 발행 실패·비동기 ack 실패·HTTP 비동기 timeout은 `503 / 9003`으로 응답하고 같은 key·내용으로 재요청하도록 안내합니다. 503으로 Kafka 원본 부재를 단정하지 않습니다.
- Producer는 `acks=all`, idempotence, zstd, 짧은 linger를 사용합니다.
- Ingress Consumer는 DynamoDB 단일 item을 conditional insert합니다.
- payload key 순서를 정규화하고 중복 insert에서는 기존 원본이 같은 요청인지 consistent read로 확인합니다. 재요청의 후속 Dispatch에는 최초 저장된 인입 시각을 사용해 만료 기한이 늘어나지 않게 합니다.
- DynamoDB 저장 후 `DispatchRequested` 발행이 실패하면 listener가 실패하여 원본 record가 재전달됩니다. 접수 오류는 개발 기본값 1초 간격으로 2회 재시도 후 DLT에 격리하며 멱등 충돌·역직렬화 실패는 즉시 격리합니다.
- Ingress는 RECORD 단위로 ack하고 DLT 발행 ack를 확인한 경우에만 격리 인계를 완료합니다. DLT 실패 시 원본 offset을 유지하며 DynamoDB 실패 복사본은 추가하지 않습니다. 상세 동작과 재처리 절차는 [DLT 운영 문서](12-접수-실패-격리와-DLT-재처리-절차.md)를 따릅니다.
- Dispatch Worker는 안정적인 `attemptId`로 DynamoDB Attempt를 conditional claim합니다.
- 유효한 `PROCESSING` lease가 있으면 Provider를 호출하지 않습니다. lease 만료 시 재선점 대신 `REVIEW_REQUIRED`와 사유를 저장하고 version을 증가시킵니다. `ACCEPTED`·`REVIEW_REQUIRED` 재전달은 추가 호출 없이 처리합니다.
- Dispatch는 오류를 로그 후 버리지 않고 원본을 재전달합니다. 운영 확인 상태 저장 실패는 listener 성공이 아니며, 조회/조치 도구·업무 만료·관찰한 무응답의 자동 재시도는 후속입니다.
- Attempt version이 일치하는 Worker만 Provider 성공 결과를 기록할 수 있습니다.
- Mock Provider는 attemptId를 Idempotency-Key로 받습니다. 기본값은 외부 중복 제거 해제이며 호출마다 효과를 기록합니다. `SIMULATOR_DEDUPLICATE=true`일 때만 같은 key의 정상 응답을 재사용합니다. 내부 멱등 보장의 검증은 해제 상태로 진행합니다.
- 외부 HTTP 연결/응답 timeout을 설정했습니다.

## 4. 요청당 저장과 발행

정상 흐름 기준:

| 구간 | Kafka | DynamoDB |
|---|---:|---:|
| API 접수 | `DeliveryRequested` 1건 | 0 |
| Ingress Consumer | `DispatchRequested` 1건 | `DELIVERY#id / META` Put 1건 |
| Dispatch Consumer | consume 1건 | Attempt claim 1건 + 성공 결과 Update 1건 |

기존 ingress의 원본 Put, Step Put, publish status Update 구조를 단일 conditional Put으로 줄였습니다.

## 6. 현재 보장 범위

현재 설명할 수 있는 보장은 다음과 같습니다.

```text
202 Accepted
= Kafka가 DeliveryRequested를 ack함
```

```text
동일 Client 요청 재전송
→ 동일 deliveryId/eventId
→ Kafka record는 중복될 수 있음
→ DynamoDB 원본은 한 item으로 수렴
```

완료된 Attempt의 재호출과 lease 만료 후 재전달 Worker의 자동 재발송을 차단합니다. Provider 처리 후 결과 저장 전 종료 상태는 REVIEW_REQUIRED로 남으며, Provider 중복 제거를 끈 테스트 대역으로 추가 호출이 없음을 검증했습니다. 기존 Worker가 외부 호출 직전에 재개하는 문제와 관찰한 무응답 재시도의 실제 중복 가능성은 별도이므로 외부 효과의 exactly-once를 보장한다고 표현하지 않습니다.
