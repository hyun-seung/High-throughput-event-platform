# 현재 구현 상태와 남은 작업

기준: 2026-10-20. 이 문서는 현재 `/api/v1/messages` 경로만 다룹니다. 정상·실패 분기는 [케이스별 Call Flow](53-신규-메시지-케이스별-Call-Flow.md)에 있습니다.

메인 호처리의 구현·로컬 종단 기능 검증과 주요 지연 개선은 완료했습니다. **서비스 전체 목표는 접수·최종 완료 10,000 TPS**입니다. 현재는 짧은 단계별 부하로 병목을 찾아 최적화·재측정하는 단계이며 목표 처리량은 아직 달성하지 않았습니다. AP별 한 인스턴스의 관측 처리량과 1레코드 평균 처리 시간도 함께 기록합니다. 목표 처리량을 확인한 뒤 지속 시험 시간을 늘립니다.

로컬 메인 경로의 정상 1건, HTTP 최종 실패 1건, HTTP 실패 후 TCP 성공 1건은 이력·과금 대상·고객 웹훅·DynamoDB 원본 정리까지 검증했습니다. 동일 저장소의 중복 DB 7개를 정지해 Docker VM의 메모리 압력으로 발생한 지연을 해소한 뒤 재검증한 결과입니다. [실행 절차](19-그라파나-대시보드-실행과-PPT-항목-대응.md)의 `demo --errors --secondary`와 `verify`로 재현할 수 있습니다. 이 결과는 소량 기능 검증이며 목표 처리량이나 실제 통신사 연동을 입증하지 않습니다.

결과 Manager의 즉시 결과 발행 Outbox를 제거했습니다. `PRIMARY_DECISION`·`SECONDARY_DECISION` STEP 저장과 `PrimaryDecisionOutboxDispatcher`·관련 설정/지표가 없어졌고, 결과 수신 처리에서 ORIGIN에 불변 판단을 조건부 저장한 뒤 Kafka를 직접 호출해 ack를 확인합니다. 2차 TCP 명령과 최종 결과·고객 웹훅 인계에 적용했습니다. 실패·시간 초과는 입력 처리/offset을 완료하지 않고 같은 판단으로 재시도합니다. 최종 두 토픽 ack 확인을 ORIGIN에 기록해야 완료 Manager가 정리를 시작합니다. 일반 입력은 Kafka 소비자가 ack 확인까지 맡고 폴링에 등록하지 않습니다. 다른 관찰을 기다리는 입력만 inbox 인덱스로 예약합니다. 예약 HTTP 재시도, API 최초 발행 복구, 고객 HTTP 전송 대기는 유지합니다. 아래 Outbox 배치 조회·성능 수치는 제거 전 구현의 검증 기록이며 현재 경로에 적용하지 않습니다. Java 테스트 181개와 Python 18개가 통과했고 Redis 통합 환경용 Java 1개는 제외했습니다. Kafka·PostgreSQL 통합 테스트도 포함합니다. 100건 웹훅 시험 `3d82e06b`는 SQL 중단 중 원본·최종 ack 100건과 완료 토픽 lag 100을 보존한 뒤 조기 도착 사례까지 총 101건·과금 대상 51건·고객 결과·정리를 확인했습니다. 늦은 입력 103건과 추가 70초 동안 중복 외부 발송 부재도 확인했습니다. 결과 Manager producer 연결 차단 시험 `10ffd5f3`는 입력 lag 1·원본·불변 판단과 Outbox 0건을 확인했고 복원 후 같은 판단으로 이력·과금·고객 통지·정리와 lag 0이 됐습니다. 원본 증거는 `.monitoring/result-direct/`에 보존합니다.

접수 응답 계약을 Kafka 성공 ack 확인 후 `200 OK`로 변경했습니다. ORIGIN 저장만으로 성공을 반환하지 않으며, 발행 실패·ack 시간 초과·대기 중단에는 `503`·오류 코드 `50004`를 반환합니다. 원본과 중복키는 보존해 같은 실행의 재접수·발행 복구를 유지합니다. 접수·결과 outbox·공통 Java 테스트 141개와 Python 집계 테스트 19개가 통과했고, 별도 통합 환경이 필요한 Java 1개는 제외했습니다. 실제 접수 AP의 Kafka 연결 차단 시험 `6548c7a2`는 503 이후 고객 재접수 없이 같은 ID로 이력·과금·고객 웹훅 각 1건과 원본 삭제까지 완료했습니다. 브로커 pause 시험 `b6f551fc`도 신규 접수 503·원본 보존·3건의 중복 없는 복구와 추가 70초 관측을 통과했습니다. 부하 도구는 접수 200과 업체 웹훅 202를 구분합니다. Kafka ack 계약 변경 후 100 TPS·10초 재측정 `f4217bed`는 1,000건 접수·이력·고객 통지·원본 삭제와 과금 대상 800건을 대조했습니다. 실제 부하 구간 접수는 88.3 TPS, 잔여 처리 포함 평균 완료는 7.01 TPS이며 목표 달성이 아닙니다. 첫 시험은 생성기 슬롯 부족으로 330건이 미발송됐고 전송된 670건은 모두 완료됐습니다. 신규 접수 1,000건보다 RECEIVED·SKT 명령 Kafka 레코드가 각각 1,721건으로 많아 추가 레코드 처리 비용을 공유 저장소 왕복과 함께 분리하는 작업이 남습니다.

최초 Kafka 발행 실패 복구도 검증했습니다. 접수 API의 발행 연결을 끊은 상태에서 원본 저장과 발행 실패를 확인하고, 고객 재접수 없이 복구 AP가 같은 `clientMsgId`로 발행해 최종 이력·과금 대상·고객 웹훅 각 1건과 원본 삭제까지 완료했습니다.

모듈·미사용 코드 정리 이후에는 최초 발행 복구의 불필요한 재발행 경로를 보완했습니다. 기존 코드에서는 PRE-SEND가 `pre_send_dispatch`를 저장해 접수 소비를 확인한 뒤에도 복구 인덱스가 남아 있었고, 복구 AP는 이 판단을 확인하지 않아 Sender 적체 시 이미 소비한 접수를 다시 발행할 수 있었습니다. 이제 정상·발송 불가 판단의 기존 조건부 UpdateItem에서 인덱스도 함께 제거하며 추가 저장소 호출은 없습니다. 복구 AP는 일관 조회 결과의 인덱스 제거·미도래 기한을 확인하고, 구버전의 저장된 판단도 재발행 없이 정리합니다. 기존 속성명을 유지해 두 AP가 사용하는 상수만 공통으로 관리합니다. JDK 21의 전체 12개 모듈 `clean verify`는 테스트 250개 통과·환경 의존 39개 제외·실패/오류 0개이며, 실제 격리 DynamoDB의 고유 임시 테이블 시험 8개도 모두 통과했습니다. 인덱스 제거 후 후속 Kafka 발행 실패에도 입력 재처리로 같은 정상·실패 판단을 발행하는 것을 확인했습니다. 근거는 `.test-results/java-test-20261011131457-27489/`와 `.monitoring/publication-index-cleanup/`입니다. 코드 커밋 당시에는 실행 AP 재배포·부하 재측정을 수행하지 않았습니다. 이후 적용과 재측정은 아래에 기록하며, 과거 721개 추가 레코드 전체의 원인을 이 수정만으로 확정하지 않습니다.

DynamoDB SDK의 연결 획득·서비스 호출 시간과 마지막 풀 관측값, 접수 실패 원인 종류·HTTP 오류 응답을 기록하도록 보완했습니다. 네 번째 개선으로 고객 웹훅의 제한된 연속 배치 발송을 구현했습니다. 기본 고객별 4배치 또는 100ms 예산 안에서 HTTP 204와 SQL 완료를 확인한 다음 배치를 즉시 claim하고, 예산을 채우면 FIFO 대기열 뒤에서 다음 차례를 받습니다. 고객별 동시 작업 한 개·전체 worker 수·기존 SQL lease를 유지하며 대기열은 설정된 고객 수 안에서 중복을 막습니다. 빈 큐·실패·소유권/완료 반영 실패는 즉시 재예약하지 않고 기존 100ms 폴링·SQL 재시도 시각에 맡깁니다. 시간 예산은 배치 사이에 검사하며 진행 중인 HTTP·SQL을 100ms에 강제 중단하지 않습니다. 서비스·스케줄러·설정 회귀 20개와 전체 Java `clean verify` 311개가 통과했습니다(환경 의존 44개 제외·실패/오류 0개, `.test-results/java-test-20261020075013-27983/`). 제외된 항목 중 웹훅 PostgreSQL 8개는 별도 임시 DB에서 전부 실행·통과하고 종료·삭제했습니다. 실제 저장소 시험은 한 tick으로 고객 42의 201건·고객 43의 1건 완료와 고객별 in-flight 한 개, 두 번째 배치 503 시 중단·backoff·같은 본문/구성 재시도를 확인했으며 최대 처리량 측정은 아닙니다. [연속 발송 변경·검증 경계](19-그라파나-대시보드-실행과-PPT-항목-대응.md#고객-웹훅의-제한된-연속-배치-발송--2026-10-20)에 기록했습니다.

다음은 새로운 최적화를 더 늘리기 전에 누적된 네 가지 개선을 실제 AP에 적용하고 짧은 단계 부하로 기준선을 다시 측정하는 것입니다. 먼저 현재 환경의 자원·이력·lag와 적용 JAR 해시를 확인하고 파티션 3개·AP 한 인스턴스 조건에서 접수/최종 완료 TPS, 실제 AP 처리 시간과 배치 평균·평균 건수, 고객 분포·실패 비율을 기록합니다. 공유 환경이 계속 불안정하면 다른 프로젝트를 승인 없이 정지하지 않고 독립 AP 측정을 먼저 진행합니다. 이번 네 개선의 실행 AP 적용·전체 경로 비교와 10,000 TPS 검증은 아직 미완료입니다.

## 기능·성능 검증을 시작할 수 있는 시점

**메인 기능 검증은 지금 가능하며 이미 여러 차례 완료했다.** 업체·고객 수신부는 mock이고 AP·Kafka·Redis·DynamoDB·PostgreSQL은 실제 실행한다. 정상 접수부터 완료 이력·과금 대상·고객 웹훅까지 확인하는 데 추가 기능 개발은 필요하지 않다.

```bash
bash scripts/monitoring.sh demo --rate 1 --seconds 1 --errors --secondary
bash scripts/monitoring.sh verify
```

Grafana는 `http://localhost:13000`에서 볼 수 있다. 통신사 이동·재시도는 `policy-test`, 100건 웹훅·중복·SQL 장애는 `webhook-test`, 저장소 장애는 `storage-test`, Kafka 중단은 `kafka-test`, Sender 종료는 `sender-crash-test`로 따로 재현한다. 장애 시험은 같은 스택에서 동시에 실행하지 않는다. 실행 절차와 실제 통과 범위는 [모니터링 문서](19-그라파나-대시보드-실행과-PPT-항목-대응.md)에 모은다.

목표 접수·완료 처리량은 10,000 TPS다. 성능 합격 판정에는 허용 p95/p99와 오류율, 웹훅 지연·실패·TCP 전환 비율, AP 및 저장소 자원 조건도 필요하다. 나머지 기준은 측정 결과를 쌓아 제안하며 검증을 중단하는 전제 조건으로 두지 않는다.

운영 전 별도로 남는 범위는 실제 3시간·4시간 만료와 고객 웹훅 실패·지연의 장시간 종단 검증, Kafka 강제 종료·다중 브로커 리더 전환, Redis 전체 유실, 영구 오류 레코드 격리·운영 재처리, 실제 CDC 전파 검증이다. 현재 요청한 메인 기능 시연을 막지는 않으며 운영 준비 완료로 간주하지 않는다. 회차 식별자 없는 늦은 웹훅 정책은 기존 보류 사항이다.

## 코드 구조와 정리 범위

Maven 모듈은 12개이며, Java 패키지는 17개다. 접수 API 전용이던 인증·JWT·응답 공통 모듈 3개는 `messaging-api`의 인증·보안·응답 코드로 통합했다. 독립 실행 AP와 공통 라이브러리 경계를 유지하고, 인증·JWT·웹훅 수신·발송 전 준비의 작은 하위 패키지는 업무 단위로 합쳤다. 통신사별 HTTP Sender는 공통 모듈 하나를 세 Pod로 실행한다. 최초 Kafka 발행 복구는 API 접수 부하와 분리한 `messaging-publication-recovery-app`으로 유지하며, 로컬 모니터링 스택에도 포함한다. 접수 API는 메시지 업무와 보안 패키지를 구분한다.

현재 모듈의 역할과 업무용 저장소 의존성은 다음과 같다. Kafka는 각 실행 AP의 업무 전달에 사용한다. 통신사 HTTP Sender 한 모듈을 세 인스턴스로 실행하므로 로컬 메인 경로는 AP 11개이며, CDC 기준정보 AP는 별도로 실행한다.

| 모듈 | 역할 | 직접 사용하는 저장소 |
|---|---|---|
| `messaging-common` | 메시지 계약·공통 저장소 헬퍼·조건부 자동 설정 | Redis·DynamoDB 라이브러리를 선택 의존성으로 제공 |
| `messaging-api` | 인증·접수·Kafka ack 확인 | Redis, DynamoDB |
| `messaging-publication-recovery-app` | 최초 Kafka 발행 복구 | DynamoDB |
| `messaging-reference-cache` | CDC 기준정보 반영 | Redis |
| `messaging-pre-send-manager` | 기준정보 확인·발송 준비 | Redis, DynamoDB, PostgreSQL |
| `messaging-carrier-http-sender` | 통신사별 HTTP 발송·예약 및 복구 | Redis, DynamoDB |
| `messaging-webhook-receive-api` | 업체 결과 웹훅 수신 | 없음 |
| `messaging-result-manager` | 결과 판단·TCP 및 최종 결과 직접 Kafka 발행 | DynamoDB |
| `messaging-tcp-sender` | 2차 TCP 발송 | Redis, DynamoDB |
| `messaging-complete-manager` | 결과·과금 저장·DynamoDB 정리 | DynamoDB, PostgreSQL |
| `messaging-webhook-sender` | 고객 웹훅 배치 발송·재시도 | PostgreSQL |
| `verification-tools` | 로컬 관측·대시보드 검증 CLI | 실행 AP가 아니며 HTTP로 관측 |

`messaging-common`의 Redis·DynamoDB·Apache HTTP 클라이언트를 선택 의존성으로 바꾸고 실제 사용하는 AP의 POM에 직접 선언했다. 반복된 Redis 제외 설정과 결과 Manager의 중복 JSON starter 선언을 제거했다. 해당 클래스가 없는 AP에서는 공통 DynamoDB 자동 설정을 건너뛴다. 웹훅 수신·고객 웹훅 발송·CDC 기준정보 JAR에서 불필요한 AWS SDK가 빠졌으며, 웹훅 수신·발송 JAR은 각각 약 13.37 MiB 줄었다. 불필요한 Redis health 점검을 제거한 기존 동작은 유지하고, 모니터링 `verify`는 Prometheus 수집 상태와 함께 실행 AP 11개의 전체 health를 확인한다.

AP 전용 구현 6개도 사용하는 실행 모듈로 옮겼다. TCP 전문·응답·프레임의 `MessagingTcpRequest`·`MessagingTcpResponse`·`TcpFrames`는 `messaging-tcp-sender`의 기존 `messaging.tcp.sender` 패키지에서 관리한다. 통신사 재선택·재시도 판단의 `PrimaryHttpFailureDecision`·`PrimaryHttpCarrierRouting`·`PrimaryHttpRetryPolicy`와 기존 판단 테스트 2개는 `messaging-result-manager`의 `messaging.result`로 옮겼다. TCP JSON 전문과 Kafka 메시지 계약은 그대로이며, 여러 AP가 사용하는 전문·오류 코드·저장소 인덱스는 공통 모듈에 둔다. `messaging.common.tcp` 패키지가 없어져 전체 Java 패키지는 18개에서 17개로 줄었다. 실제 HTTP Sender 설정과 연결되지 않은 미사용 `RESPONSE_TIMEOUT` 상수와 이를 값만 확인하던 assertion도 제거했다.

AP 전용 코드 이관 후에도 JDK 21의 12개 모듈 `clean package`와 Java 테스트 239개가 통과했고, 환경 의존 테스트 38개는 제외됐다. 공통 JAR에서 전용 클래스 6개가 빠지고 담당 AP JAR에 들어간 것을 확인했다. 결과 Manager 테스트 87개에는 옮긴 판단 테스트가 포함되며 TCP Sender의 전문 교환 테스트는 실제 로컬 소켓으로 수행했다. 신규 JAR 적용 전부터 기존 Kafka·PostgreSQL·DynamoDB health가 타임아웃이고 `verify`도 응답 시간 초과여서 이번 이관의 로컬 AP 기동·종단 재검증은 수행하지 못했다. 근거는 `.monitoring/ap-code-ownership/`에 보존한다.

후속 HTTP 예약 발행은 `FollowupHttpDispatcher.poll`에 직접 스케줄을 등록하고, 이 메서드에 위임만 하던 `FollowupHttpDispatchSchedule` 클래스를 제거했다. 기존 초기 대기·fixed-delay 설정과 메시지별 조건부 갱신을 유지한다. 실제 Spring 스케줄러의 입력 복구·만료·후속 발행을 각각 지연시켜 나머지 두 작업이 계속 진행하고 같은 poll이 중첩되지 않는 회귀 테스트 3개가 통과했다. 공통·결과·완료 모듈의 `clean package`와 단위 테스트 135개가 통과했으며, 결과 JAR에서 위임 클래스가 빠진 것을 확인했다. 검증 기록은 `.monitoring/dispatch-cleanup/`에 보존한다.

완료 Manager는 운영에서 호출하지 않는 단건 래퍼 `FinalizedHistoryStore.store`를 제거하고, 기존 PostgreSQL 테스트도 운영 소비자가 사용하는 `storeBatch`를 직접 호출하도록 통일했다. 1건 처리·중복·동시 재전달·상충 결과 rollback·과금·정리 상태와 단건/배치 트랜잭션 비교의 기존 assertion을 유지했다. 정상 상태로 회복된 로컬 PostgreSQL의 전용 시험 스키마에서 통합 테스트 17개가 통과했고 각 스키마를 정리했다. Kafka 연동 테스트 1개는 제외했다. 기존 모니터링 Kafka 컨테이너는 `OOMKilled=true`·종료 코드 137로 종료된 상태여서 브로커를 사용하는 검증은 완료하지 못했다. 이 검증도 `.monitoring/dispatch-cleanup/`에 보존한다.

구형 `/api/v1/deliveries` 경로·실행 모듈·PoC 도구·과거 결과 문서와 호출자가 사라진 운영용 DynamoDB 클라이언트는 제거했다. 저장소의 `DELIVERY#` 키와 `delivery_id` 등 속성, PostgreSQL `delivery_results`, `delivery.dynamodb` 설정·지표 이름은 현재 코드가 실제로 사용한다. 이 이름을 바꾸려면 데이터·설정·관측 도구를 함께 이관해야 하므로 미사용 코드로 삭제하지 않는다.

결과 Outbox 제거 후 호출자가 사라진 `MessageResultInboxIndex.add`와 `ApiResponse.of`, 미사용 import 3개를 제거했다. 부하 관측 스크립트의 미사용 `scheduledLoadSeconds`와 이를 위한 추가 수집도 제거했다. 완료 정리의 `load` 지표는 Grafana와 모니터링 검증에서 계속 사용한다.
