# 현재 구현 상태와 남은 작업

기준: 2026-09-26, 운영 조치·감사 복구, 애플리케이션 장애 호출 제한과 공통 DynamoDB SDK 호출 예산까지 반영. 구현 현황과 다음 순서는 이 문서에서 관리한다. 과거 단계별 작업 기록을 모두 읽거나 오래된 “미구현” 항목을 다시 남은 작업으로 합산할 필요는 없다.

## 1. 지금 어디까지 되었나

신규 v2는 정상 1차 성공 기준 DDB **5회 호출·7항목 변경**, 대표 복잡 경로는 **24회·28항목**이다. 삭제 포함 성공 쓰기의 직렬 계측이며 전체 운영 상한·과금 단위가 아니다. 기존 v1 완료 데이터는 호환 경로로 보존하고 자동 일괄 이관하지 않았다.

## 3. 다음 개발 순서와 완료 기준

| 순서 | 남은 묶음 | 완료 기준 |
|---|---|---|
| 1 | 운영 수동 조치 | 인증·권한 연결과 통지 소진 후 처리 정책. 조회·DLT 재검토·정리 재조치·결과 불명 확정/미확정 재개 CLI는 구현. 자동 감사 재개·운영 경보는 미구현 |
| 2 | 지속 장애 중 복구 조회 조절 | 애플리케이션 호출 제한과 공통 DynamoDB client의 전체/회차 timeout·최대 시도 수 구현. Lettuce·Kafka·별도 운영 client의 내부 재접속/재시도 설정과 연결 복구 회귀 남음 |
| 3 | 실행·배포 준비와 통합 회귀 | readiness·종료·재시작, 재현 가능한 설정, 후속 단계 관측·경보 연결 범위, 주요 미검증 경계 점검 |

DLT 초기 복구는 **기본 비활성화**이며, 모든 ingress·dispatch의 보류 조건 적용과 SQL 이력 보존 확인 후 켠다. Java intake worker가 partition별 원문 보존·인계와 PENDING 재개를 수행한다. HELD는 SQL 메타데이터 조회 후 버전·조치 ID를 지정해 재검토를 요청할 수 있지만 발송 조건을 우회하지 않는다. 인증된 운영자 권한·원문 열람 UI·Grafana 경보 연결은 남아 있다.

공통 완료 조건은 요청별 위치를 설명할 수 있고, 입력/업체 호출/최종 결과/고객 통지의 정합성이 맞으며, 중복 입력·재시작·장애 후에도 원래 회차와 기한을 유지하는 것이다. 실제 업체 중복 방지를 끈 시험도 포함한다. 테스트 상세 목록은 [장애 시험 계획](03-장애-상황별-검증-계획.md), 실행 표준은 [Java 테스트 기준](48-Java-중심-테스트와-외부-도구-사용-기준.md)으로 분리한다.

## 4. 언제 함께 결정할 것인가

| 결정할 내용 | 필요한 시점 |
|---|---|
| 고객 서버 장애 시 결과 제공 경로, 21회 소진 뒤 수동 추가 전송의 권한·예산 | 운영 조치 구현 시 |
| 아직 기한이 남은 요청을 장기 장애 복구 후 강제 만료할 범위 | 해당 예외 정책을 도입할 때 |
| 완료 Redis TTL, Kafka·DLT·이력 보관 기간, 과거 재처리·백업 복원 범위 | 삭제·운영 재처리·배포 준비 시 |
| 운영 TLS·키 교체·접근 권한, 사본 배치·승격 조건, RPO/RTO·용량 | 운영 배포 준비 시 |
| 본문 크기·시나리오 비율·지연 SLO·시험 환경·비용 | 성능 시험 착수 시 |

지금 개발을 계속하려고 위 값을 모두 먼저 확정할 필요는 없다. PoC의 HTTP 204 전체 ack, 지연 간격·연결 풀 크기·완료 TTL은 구현 기본값이며 운영 합의와 구분한다. Kafka 먼저 접수한 뒤 발견하는 입력 충돌의 고객 조회·통지 계약도 운영 API 준비에서 다룬다.

## 5. 그다음 성능 단계

설정·병목 튜닝 → 서비스별 Pod 1개 최대 지속 TPS → 전체 10,000 TPS 확장·장시간 시험 순서다. API 202 TPS와 고객 최종 결과 수신 TPS를 구분하고, lag·지연·누락·실제 외부 중복을 함께 본다. 상세 기준은 [성능 검증 계획](41-전체-만-TPS-목표와-Pod별-성능-검증-계획.md)에 유지한다.

DLT 인계 묶음을 구현했고, 착수 전에는 위 **남은 3개 묶음의 최소 운영·복구·회귀 기준**을 충족한다. 운영 UI 전체나 Kubernetes 자동 확장 완성까지 기다리는 계획은 아니다. 묶음 수는 남은 커밋 수·완료 날짜의 보장이 아니며, 실제 측정 전에 Pod 자원·입력·지연 기준·비용 한도를 정한다.

Kubernetes/KEDA, CDC 기반 정책 동기화, 별도 과금·통계 Consumer는 과거 로드맵에 있던 확장 후보다. 현재 구현됐거나 이번 기능 마무리의 필수 선행 작업인 것으로 취급하지 않는다. 새 작업마다 진행 문서를 추가하지 않고 이 문서를 갱신한다.
