# 현재 구현 상태와 남은 작업

신규 경로의 정상·실패·복구 순서는 [53 케이스별 Call Flow](53-신규-메시지-케이스별-Call-Flow.md)를 우선 참고한다. 아래 표의 이전 Kafka-first·단일 worker 구현과 구분한다.

기준: 2026-09-28, 운영 조치·감사 복구, 장애 호출 제한, Kafka 복구와 기본 probe·정상 종료, Java 증거 이관 및 PENDING 감사 제한 재확인 후 전체 회귀까지 반영. 구현 현황과 다음 순서는 이 문서에서 관리한다. 과거 단계별 작업 기록을 모두 읽거나 오래된 “미구현” 항목을 다시 남은 작업으로 합산할 필요는 없다.

2026-10-04 접수·1차 발송 경로는 [ADR-026](adr/ADR-026-MESSAGE-RECEIVED와-통신사별-HTTP-발송-분리.md), API 사용량 제한은 [ADR-027](adr/ADR-027-접수-API-Redis-TPS와-유형별-월-Quota.md)을 따른다. 아래 검증 수치와 현재 구현 표는 **이관 전 Kafka-first·단일 dispatch-worker 코드**의 사실이다. 신규 `/api/v1/messages`의 Redis 10초 TPS·유형별 월 Quota, Redis 고객 중복·ORIGIN 선저장, API·복구 앱의 `message.received.v1` 발행, 통신사별 발송 토픽과 공통 전문 타입을 추가했다. API 202 응답은 하이픈 없는 UUID 32자리의 고정 `clientMsgId`를 반환하며 ORIGIN·Kafka 접수 이벤트에도 같은 값을 담는다. 고객 `messageId`는 UTF-8 40바이트까지 검사한다. 공통 `HttpProviderRequest`는 업체 발송 `clientMsgId` 최대 40바이트를 검사한다. 접수·업체 발송 요청·웹훅에는 같은 ID를 쓰고 통신사·회차는 내부 시도 상태로 관리한다. 웹훅 `status=success`에는 `error`가 없고 `status=fail`에는 5자리 JSON 숫자 `code`와 `message`가 담긴 `error`가 필수다. 신규 독립 웹훅 API는 1~100건 묶음 전체를 `MSG_RESULT` 1레코드로 발행한다. 결과 Manager는 혼합 MSG_RESULT 소비와 메시지별 STEP inbox 보존, HTTP 실패의 후속 발송 판단까지 연결했다. 웹훅 실패의 `66001` 통신사 이동·`66002` 재시도까지 연결했다. 웹훅 성공·발송 전 실패·재시도 소진의 최종 판단은 아직 구현 전이다. 웹훅 인입별 `traceId` 발급은 구현됐고 고객 API 인입별 발급은 아직 구현 전이다. [계약·번호 CDC 캐시](52-계약과-번호-통신사-CDC-캐시.md)의 로컬 PostgreSQL·Debezium·Kafka·Redis 경로도 준비했다. `messaging-pre-send-manager`에는 계약 Redis 우선·누락 시 PostgreSQL 조회, 번호 Redis 조회·누락 시 SKT 선택, 선택한 첫 통신사를 ORIGIN에 조건부로 고정하는 코드를 추가했다. 현재는 `message.received.v1` 소비·고정 판단·통신사별 발송 명령 또는 `MSG_RESULT` 사유 발행까지 연결됐다. 공통 `PrimaryHttpFailureDecision`은 `66001` 통신사 이동, `66002` 1분 뒤 최대 3회 재시도, 5초 HTTP 무응답의 1분 뒤 최대 3회 재시도·`40003` 소진, 그 외 6만 대역 실패의 1차 종료를 판단한다. HTTP 실패·타임아웃의 실제 소비와 후속 명령 승인까지 연결했고 1차 소진 뒤 2차/최종 인계는 남았다. 신규 접수는 `fallbackAllowed` 대신 선택적인 `secondarySendPayload`를 받아 ORIGIN v4에 보존한다. 2차 TCP의 Redis 중복 선점·즉시 응답 처리와 신규 HTTP 5초 타임아웃 설정은 실제 sender에 아직 연결되지 않았다. 신규 경로에 연결되지 않았던 이전 단일 `messaging-http-sender` 모듈은 제거했다. 새 API는 기본 비활성화(`MESSAGING_ADMISSION_ENABLED=false`)다. 새 목표는 1차 HTTP 200에서 Sender가 DynamoDB만 갱신하고, 명시적 비-200 실패는 Sender가 `MSG_RESULT`에 직접 발행하며, 1~100건 웹훅은 `WEBHOOK-RECEIVE-API`가 `MSG_RESULT`에 발행하는 것이다. `MSG-RESULT-MANAGER`가 최종 결과를 `MSG-RESULT-FINALIZED`로 인계하고 고객 웹훅 대상은 `WEBHOOK-SEND`에도 별도 발행하며, 1차 실패가 2차 대상이면 2차 발송을 인계한다. `MSG-COMPLETE-MANAGER`의 TBL_MSG_HIST 최종 메시지당 1건·TBL_CDR_HIST 1차 성공 과금 최대 1건, MSG-WEBHOOK-SENDER의 새 토픽 소비·발송 후 TBL_WEBHOOK_HIST 저장, ORIGIN·STEP의 DynamoDB TTL은 아직 구현 전이다. 신규 결과 inbox의 항목별 후속 처리, 1차 만료 스케줄러와 장애 검증은 아직 남아 있다.

신규 `PRE-SEND-MANAGER`는 `message.received.v1`을 소비하고, 현재 확인 가능한 계약 활성 여부와 첫 통신사 고정 결과로 결정적인 최초 HTTP 발송 명령을 준비한다. 명령 또는 계약 거절·1차 기한 만료 결과를 ORIGIN에 조건부로 고정한 뒤 해당 통신사 토픽 또는 `MSG_RESULT`에 발행하고 Kafka 저장 확인 후 접수 offset을 완료한다. ORIGIN 종료는 발송 없이 건너뛴다. `MSG_RESULT`에 실린 `PRE_SEND` 실패는 사유와 관계없이 ORIGIN에 `secondarySendPayload`가 있으면 2차 TCP로 인계하고, 없으면 최종 실패로 처리한다. 실제 결과 Manager 연결과 고객 오류 코드 배정은 아직 남아 있다. `SendAttemptKeys`와 `RedisSendAttemptGuard`는 1차의 통신사·회차별, 2차의 시도별 Redis 중복 선점 코드를 제공한다. 1차 통신사별 Sender에서는 사용하며 2차 TCP Sender 연결은 아직 남았다.

신규 `messaging-carrier-http-sender`는 같은 실행 JAR을 3사별 URL·토픽·소비 그룹으로 분리해 명령을 소비한다. ORIGIN 고정 명령 대조, STEP 예약·Redis 선점·`SENDING` 전이 뒤 공통 경로로 HTTP 호출하고, 200 응답은 STEP만 갱신한다. 비-200·무응답은 원본 코드와 정규화 코드 또는 타임아웃을 STEP에 고정한 뒤 `MSG_RESULT`에 인계한다. ack 불명 재전달에서는 업체를 다시 호출하지 않고 저장 결과만 발행한다. 30초 넘은 미관찰 `SENDING`은 타임아웃으로 복구한다. 업체 원본 4만 번대 중 `66001`·`66002`에 대응하는 코드는 운영 설정에 지정해야 실행되며, 3사 실주소·실규격 연동 및 결과 Manager 전체 흐름 검증은 아직 남았다.

후속 통신사 발송 또는 동일 통신사 재시도 명령은 `FollowupHttpCommandStore`가 ORIGIN의 현재 결과 결정 ID와 STEP 승인 전문을 원자적으로 고정할 수 있다. 통신사별 Sender는 최초 명령과 후속 승인 명령을 구분하고, 후속 명령의 정확한 전문·현재 결정·예약 시각을 확인한다. 아직 `MSG-RESULT-MANAGER`의 결과 소비 로직이 이 저장소를 호출하지는 않는다.

`messaging-result-manager` 실행 앱에는 후속 HTTP 명령의 `notBefore` 인덱스 조회·Kafka 발행·ack 후 인덱스 제거를 추가했다. STEP의 `followup_due_v1` GSI가 필요하며 DynamoDB 테이블 초기화기가 새 테이블 생성과 기존 테이블 보강을 지원한다. Kafka ack 불명확 때는 같은 명령을 다시 발행할 수 있고 Sender가 동일 시도의 업체 중복 호출을 막는다. `MSG_RESULT` 소비는 HTTP 실패·타임아웃, 발송 전 실패, 웹훅 1~100건을 디코딩해 STEP의 메시지별 `RESULT_INBOX`에 조건부 보존한 뒤 offset을 완료한다. 웹훅 배치는 Kafka 1레코드를 유지하고 STEP에 최대 100항목으로 나뉜다. STEP의 `message_result_pending_v1` GSI는 아직 업무 판단이 끝나지 않은 항목을 찾는 용도이며, 테이블 초기화기가 생성·보강한다. HTTP 실패·타임아웃 단건은 보존 후 `HttpFailureFollowupService`가 ORIGIN의 현재 명령과 STEP의 고정 관찰을 대조해 `66001` 이동·`66002`/무응답 재시도 명령을 승인 저장소에 고정한다. 후속 발송은 1차 deadline까지 남은 시간으로 차단하지 않고, 먼저 확정된 만료·완료 상태를 ORIGIN 조건으로 확인한다. 웹훅은 pending 인덱스에서 HTTP 관찰이 고정될 때까지 재확인하고, 유효한 실패 `66001`·`66002`의 후속 명령을 승인한다. 웹훅 성공·발송 전 실패 및 HTTP/웹훅 재시도 소진의 2차/최종 판단은 아직 연결 전이므로 inbox에 `PENDING`으로 남는다. 신규 1차 만료 스케줄러도 아직 연결 전이다.

독립 `messaging-webhook-receive-api`는 통신사별 Bearer 인증, JSON 배열 1~100건 검증, 요청 최대 256 KiB 제한, 인입 `traceId` 생성, Kafka `MSG_RESULT` 1레코드 발행 후 ack 응답을 구현했다. 통신사별 비밀값은 기본 비활성화이며 운영 환경에서 설정해야 한다. `MSG-RESULT-MANAGER` 소비·결과 판단은 아직 구현 전이다. 이관 전 `receipt-api`는 신규 AP로 이름만 바꾼 것이 아니라 별도 레거시 모듈로 남아 있다.

`messaging-result-manager`에는 `MSG_RESULT`의 `WEBHOOK` 묶음·1차 HTTP 단건·`PRE_SEND` 단건을 타입 헤더 없이 `source`로 해석하고 Kafka key를 검증하는 코덱을 추가했다. HTTP 200은 입력으로 거절한다. 실제 Kafka 소비, 항목별 DynamoDB 조건부 판단, 지연 재발송·최종 결과 인계는 아직 구현하지 않았다.

## 3. 다음 개발 순서와 완료 기준

새 접수·발송·결과 판단 분리 설계의 이관 작업이 추가됐다. API 계약·Redis 중복, ORIGIN 선저장·API 직접 Kafka 발행·별도 누락 복구, 기존 `delivery-ingress-worker`의 최초 원본 저장·`DispatchRequested` 인계 제거, 현재 단일 `dispatch-worker`를 통신사별 sender·2차 sender·`MSG-RESULT-MANAGER`로 분리해야 한다. 새 1차 sender의 HTTP 200 뒤 DynamoDB 기록, 명시적 비-200 응답 실패 코드의 DynamoDB 기록·`MSG_RESULT` 직접 발행·누락 복구, 웹훅 1~100건 수신·Kafka 발행, 실행별 결과 판단·2차 인계·최종 결과 복구, 중복 소비·누락 발행 복구, 상태 조회·이관 테스트가 남았다. 200을 받은 개별 발송의 최종 결과는 웹훅이며, 명시적 비-200 뒤에는 웹훅이 오지 않는다. API의 기존 4자리 오류 코드는 [54 오류 코드 계약](54-메시징-오류-코드와-결과-인계-계약.md)의 5자리 대역으로 변경했다. 6만/7만 업체 코드의 실제 매핑과 신규 sender·TCP 경로는 구현 전이다. 최신 1차 경계는 [ADR-026](adr/ADR-026-MESSAGE-RECEIVED와-통신사별-HTTP-발송-분리.md)을 따른다. 아래 표의 기존 3개 묶음은 설계 변경 전 운영 마무리 목록이며 신규 이관을 완료한 것으로 간주하지 않는다.

| 순서 | 남은 묶음 | 완료 기준 |
|---|---|---|
| 1 | 운영 수동 조치 | 인증·권한 연결과 통지 소진 후 처리 정책. 조회·DLT 재검토·정리 재조치·결과 불명 확정/미확정 재개 CLI는 구현. 기존 PENDING 감사의 제한된 자동 재확인은 opt-in이며 SQL 적체·조회 공백의 로컬 경보 규칙을 추가. 외부 경보 전달은 미구현 |
| 2 | 지속 장애 중 복구 조회 조절 | 애플리케이션 호출 제한, 공통 DynamoDB client와 로컬 DLT 복구·발송 조회 CLI의 전체/회차 timeout·최대 시도 수, Lettuce 연결 끊김 명령 거절·대기열 상한·지터, Kafka 클라이언트 재접속·재시도 간격과 단일 로컬 브로커 중단/복구 검증 완료. ingress·dispatch 복제 JVM의 60초 로그 집계도 완료. 실제 다중 Pod 장시간 연결 복구와 네트워크 수준 총 재접속량 측정 남음 |
| 3 | 실행·배포 준비와 통합 회귀 | 다섯 서비스의 메인 포트 probe, 발송 worker의 idle 및 1차 HTTP·2차 TCP 업체 호출 중 SIGTERM·재시작, 결과 worker의 고객 ACK 대기 중 SIGTERM·재시작 검증 완료. 로컬 모니터링 설정에 결과 worker 수집과 통지 소진·정리 보존 경보 추가. 다른 처리 단계의 종료·Kubernetes eviction, 재현 가능한 배포 설정, 실제 관측·경보 발화와 주요 미검증 경계 점검 남음 |

DLT 초기 복구는 **기본 비활성화**이며, 모든 ingress·dispatch의 보류 조건 적용과 SQL 이력 보존 확인 후 켠다. Java intake worker가 partition별 원문 보존·인계와 PENDING 재개를 수행한다. HELD는 SQL 메타데이터 조회 후 버전·조치 ID를 지정해 재검토를 요청할 수 있지만 발송 조건을 우회하지 않는다. 인증된 운영자 권한·원문 열람 UI·Grafana 경보 연결은 남아 있다.

공통 완료 조건은 요청별 위치를 설명할 수 있고, 입력/업체 호출/최종 결과/고객 통지의 정합성이 맞으며, 중복 입력·재시작·장애 후에도 원래 회차와 기한을 유지하는 것이다. 실제 업체 중복 방지를 끈 시험도 포함한다. 테스트 상세 목록은 [장애 시험 계획](03-장애-상황별-검증-계획.md), 실행 표준은 [Java 테스트 기준](48-Java-중심-테스트와-외부-도구-사용-기준.md)으로 분리한다.

지금 개발을 계속하려고 위 값을 모두 먼저 확정할 필요는 없다. PoC의 HTTP 204 전체 ack, 지연 간격·연결 풀 크기·완료 TTL은 구현 기본값이며 운영 합의와 구분한다. Kafka 먼저 접수한 뒤 발견하는 입력 충돌의 고객 조회·통지 계약도 운영 API 준비에서 다룬다.

## 5. 그다음 성능 단계

설정·병목 튜닝 → 서비스별 Pod 1개 최대 지속 TPS → 전체 10,000 TPS 확장·장시간 시험 순서다. API 202 TPS와 고객 최종 결과 수신 TPS를 구분하고, lag·지연·누락·실제 외부 중복을 함께 본다. 상세 기준은 [성능 검증 계획](41-전체-만-TPS-목표와-Pod별-성능-검증-계획.md)에 유지한다.

DLT 인계 묶음을 구현했고, 착수 전에는 위 **남은 3개 묶음의 최소 운영·복구·회귀 기준**을 충족한다. 운영 UI 전체나 Kubernetes 자동 확장 완성까지 기다리는 계획은 아니다. 묶음 수는 남은 커밋 수·완료 날짜의 보장이 아니며, 실제 측정 전에 Pod 자원·입력·지연 기준·비용 한도를 정한다.

Kubernetes/KEDA, CDC 기반 정책 동기화, 별도 과금·통계 Consumer는 과거 로드맵에 있던 확장 후보다. 현재 구현됐거나 이번 기능 마무리의 필수 선행 작업인 것으로 취급하지 않는다. 새 작업마다 진행 문서를 추가하지 않고 이 문서를 갱신한다.
