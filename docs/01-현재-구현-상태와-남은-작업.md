# 현재 구현 상태와 남은 작업

기준: 2026-10-10. 이 문서는 현재 `/api/v1/messages` 경로만 다룹니다. 정상·실패 분기는 [케이스별 Call Flow](53-신규-메시지-케이스별-Call-Flow.md)에 있습니다.

| 경계 | 구현 상태 |
|---|---|
| MSG-RECEIVE-API | JWT 확인, Redis 10초 TPS·분류별 월 Quota, 고객 중복 검사, DynamoDB ORIGIN 조건부 저장, `message.received.v1` 발행 및 복구 앱 연결 |
| PRE-SEND-MANAGER·CDC | 계약 Redis 우선·PostgreSQL 대체 조회, 전화번호 통신사 Redis 조회·누락 시 SKT, 발송 전문과 통신사별 명령 발행 |
| 통신사별 HTTP Sender | 하나의 JAR을 SKT/KT/LGU Pod로 분리, Redis·STEP 중복 보호, HTTP 호출·200 기록, 실패·5초 무응답의 `MSG_RESULT` 발행 |
| WEBHOOK-RECEIVE-API | 업체 결과 1~100건을 요청당 Kafka 배치 1레코드로 인계 |
| MSG-RESULT-MANAGER | 결과 inbox, `66001` 통신사 이동·`66002`/무응답 재시도, 1차 만료, 2차 TCP 또는 최종 결과·고객 웹훅 인계 |
| MSG-TCP-SENDER | 임시 길이+JSON 전문 발송, 즉시 응답을 `MSG_RESULT`에 인계 |
| MSG-COMPLETE-MANAGER | 건별 과금 판단, 최대 100건 이력·과금의 SQL 배치 트랜잭션, commit 후 Kafka offset, 별도 DynamoDB 정리·TTL 경로 |
| MSG-WEBHOOK-SENDER | 고객별 최대 100건 묶음, 고객 URL로 발송, `TBL_WEBHOOK_HIST` 기록 |
| 관측 | 메인 경로·발행 복구 11개 AP·Kafka 관측기·Redis/PostgreSQL exporter, Grafana 7개 화면과 로그 수집 |

로컬 메인 경로의 정상 1건, HTTP 최종 실패 1건, HTTP 실패 후 TCP 성공 1건은 이력·과금 대상·고객 웹훅·DynamoDB 원본 정리까지 검증했습니다. 동일 저장소의 중복 DB 7개를 정지해 Docker VM의 메모리 압력으로 발생한 지연을 해소한 뒤 재검증한 결과입니다. [실행 절차](19-그라파나-대시보드-실행과-PPT-항목-대응.md)의 `demo --errors --secondary`와 `verify`로 재현할 수 있습니다. 이 결과는 소량 기능 검증이며 목표 처리량이나 실제 통신사 연동을 입증하지 않습니다.

최초 Kafka 발행 실패 복구도 검증했습니다. 접수 API의 발행 연결을 끊은 상태에서 원본 저장과 발행 실패를 확인하고, 고객 재접수 없이 복구 AP가 같은 `clientMsgId`로 발행해 최종 이력·과금 대상·고객 웹훅 각 1건과 원본 삭제까지 완료했습니다.

통신사 이동·재시도 정책도 로컬 mock과 실제 AP·저장소로 13개 시나리오를 검증했습니다. HTTP 실패와 실패 웹훅 각각의 `66001` 이동·`66002` 재시도, 5초 무응답, 최초 이후 최대 3회 재시도, 소진 시 최종 실패 또는 TCP 전환을 확인했습니다. 이 검증에서 발견한 1차 최종 이력의 통신사 누락을 수정하고 PostgreSQL 회귀 테스트를 추가했습니다. [실행 절차](19-그라파나-대시보드-실행과-PPT-항목-대응.md)의 `policy-test`로 재현할 수 있습니다.

웹훅 100건 혼합 배치·재전송·HTTP 200 이전 도착·최종 정리 이후 중복과 상충 결과도 검증했습니다. PostgreSQL 중단 중에는 최종 상태와 원본 100건, 완료 토픽 lag 100건이 유지됐고, 복구 후에는 조기 웹훅 사례를 포함해 이력 101건·과금 대상 51건·고객 결과 101건·원본 삭제가 완료됐습니다. 완료 이후 늦은 inbox 103건은 처리 상태와 7일 TTL을 확인했습니다. `webhook-test`로 재현할 수 있습니다.

Redis 발송 키 1개 유실, Redis 응답 중단, HTTP 관찰 저장 후 DynamoDB 중단, 완료 AP의 DynamoDB 정리 연결 실패도 `storage-test`로 검증했습니다. 같은 명령 재전달의 중복 HTTP 호출을 차단하고, 장애 중 offset·원본·SQL 정리 재시도 상태를 보존했습니다. 복구 후 4건 모두 이력·과금·고객 결과·원본 정리를 완료했습니다. Redis 전체 데이터 유실이나 업체 호출 직후 관찰 저장 전에 끊기는 구간까지 검증한 것은 아닙니다.

Redis 주소 변경 복구도 검증했습니다. DNS 캐시 제한만으로는 기존 TCP 연결의 단절 감지가 늦어져, 공통 설정에 DNS 최대 TTL 5초와 Linux TCP_USER_TIMEOUT 10초를 적용하고 Redis AP에 필요한 네이티브 전송을 포함했습니다. 실제 주소 변경 후 20.38초, 원래 주소 복원 후 18.67초에 AP 재시작 없이 연결 10개와 전체 health 11개가 회복됐습니다. 변경 전후 총 6건의 이력·고객 결과·원본 삭제와 과금 대상 2건, Java 테스트 212개가 통과했습니다. Docker 기동 문제도 복구했으며 `redis-dns-test`와 `verify`의 최신 결과는 [실행 절차](19-그라파나-대시보드-실행과-PPT-항목-대응.md)에 있습니다.

Kafka 브로커 일시 중단·복구는 `kafka-test`로 검증했습니다. 장애 중 신규 접수 원본과 HTTP 실패 관찰·미발행 상태를 보존하고, 업체 웹훅에는 503을 반환했습니다. 복구 후 고객 재접수 없이 신규 메시지를 처리하고 업체 웹훅 재전송도 정상 인계해, 이력 3건·과금 대상 2건·고객 결과 3건·원본 삭제 3건을 확인했습니다. 추가 70초 관측에서도 중복 업체 호출·과금·고객 결과가 없었고 AP 재시작 없이 주요 소비 그룹 5개의 lag가 0이 됐습니다. 단일 브로커 `pause/unpause` 시험이며 강제 종료·데이터 유실·리더 전환은 별도 범위입니다.

HTTP 200 응답을 Sender가 해석한 뒤 DynamoDB 관찰 기록 전에 강제 종료하는 시험도 추가했습니다. 이 시험에서 먼저 도착한 성공 웹훅보다 복구 타임아웃이 다음 회차를 예약하는 문제가 드러나, 같은 메시지·통신사의 미처리 웹훅 inbox를 먼저 처리하도록 보완했습니다. 웹훅이 있던 메시지는 추가 HTTP 호출 없이 첫 회차 성공, 웹훅이 없던 메시지는 복구 타임아웃 판단 1분 이후 재시도 성공으로 완료했습니다. 두 메시지 모두 이력·과금 대상·고객 결과 각 1건과 원본 삭제를 확인했습니다. `sender-crash-test`로 재현할 수 있습니다.

성능 측정 도구를 추가했습니다. `performance` 명령으로 실제 접수·완료 TPS, 접수·최종 완료 지연 분포, 오류율, Kafka lag, AP CPU·힙 사용량을 실행별로 보존합니다. 최종 완료는 이력·고객 통지·DynamoDB 정리 기록 중 가장 늦은 시각이며, 도구 자체 미발송과 HTTP 오류를 구분합니다.

동일한 로컬 설정에서 5·20·10 TPS를 각각 60초씩 혼합 부하로 측정했습니다. 총 2,100건의 접수·최종 이력·고객 결과·원본 삭제와 과금 대상 1,680건이 일치했고 접수 오류·도구 미발송은 없었습니다. 전체 완료 p95는 5 TPS에서 15.5초, 10 TPS에서 25.3초, 20 TPS에서 102.8초였습니다. 20 TPS에서 PRE-SEND-MANAGER 적체와 이력 이후 정리 지연이 함께 늘어 50 TPS 증가는 생략했습니다. [측정 조건과 비교표](19-그라파나-대시보드-실행과-PPT-항목-대응.md#단계별-혼합-부하-기준선--2026-10-10)에 결과와 한계를 기록했습니다. 한 번씩 측정한 개발 환경 기준선이며 운영 처리 한계나 SLA 합격 결과가 아닙니다.

완료 정리에서는 대기 건이 남아도 100건마다 5초 쉬는 경로를 디버거로 확인했습니다. 최대 4페이지를 연속 처리하고 STEP 삭제를 배치로 묶은 뒤 20 TPS의 전체 완료 p95는 재측정 기준 100.5초에서 74.9초로, 이력→정리 p95는 48.2초에서 21.8초로 줄었습니다. 기존 완료 AP만 변경했으며 TTL·STEP 뒤 ORIGIN 삭제 순서·부분 실패 재시도를 유지했습니다. 단위·PostgreSQL 테스트 20개, 최종 버전의 혼합 부하 1,800건, 저장소 장애 4개 사례와 모니터링 재검증이 통과했습니다. 10 TPS 전체 완료 p95는 27.5초로 앞선 25.3초보다 높아 해당 부하의 개선은 확인하지 못했습니다. 세부 조건과 중간 실험은 [모니터링 문서](19-그라파나-대시보드-실행과-PPT-항목-대응.md#완료-정리-지연-개선--2026-10-10)에 있습니다.

완료 이력·과금 저장은 건별 판단을 유지하면서 최대 100건을 한 SQL 트랜잭션으로 묶도록 변경했습니다. Kafka fetch 묶음 대기는 최대 25ms이며 1건도 처리합니다. 이력·과금·정리 대기를 commit한 후 offset을 반영하고 DynamoDB 정리는 별도로 진행합니다. DB 실패·상충 결과는 배치 전체 rollback, commit 직후 재시작은 고유키와 내용 대조로 멱등 처리합니다. 실제 Kafka·PostgreSQL을 포함한 31개 테스트와 변경 후 혼합 부하 1,200건·과금 대상 960건 대조가 통과했습니다. 동일 SQL 저장 로직의 100건 집중 시험은 단건 트랜잭션 약 197~225ms, 배치 약 15~17ms였습니다. 실제 20 TPS에서는 평균 배치 크기 1.041건·전체 완료 p95 106.7초여서 전체 성능 개선으로 해석하지 않습니다. [배치 저장 조건과 검증](19-그라파나-대시보드-실행과-PPT-항목-대응.md#완료-이력과금-대상의-sql-배치-저장--2026-10-10)에 상세 결과가 있습니다.

발송 전 준비에서는 통신사 선택과 전문을 하나의 조건부 DynamoDB 갱신으로 합쳤습니다. 정상 신규 건의 조회 2회·저장 2회를 조회 1회·저장 1회로 줄였고, 별도 `InitialCarrierStore`를 제거했습니다. 실제 DynamoDB의 8개 동시 요청·구버전 상태·완료 경합을 포함한 28개 테스트가 통과했습니다. 동일한 20 TPS 전후 시험은 각각 1,200건·과금 대상 960건이 일치했고, 전체 완료 p95는 107.5초→81.4초, PRE-SEND 최대 lag은 371건→54건이었습니다. SKT Sender 최대 lag은 89건→274건으로 늘어 전체 병목 해소로 판단하지 않습니다. [전후 구간별 측정과 한계](19-그라파나-대시보드-실행과-PPT-항목-대응.md#발송-전-통신사전문-확정의-저장소-호출-축소--2026-10-10)에 정리했습니다.

결과 Manager에서는 inbox·outbox·후속 발행·만료·선택적 backfill이 스케줄러 1개를 공유해 실행을 기다리는 경로를 재현했습니다. 풀을 5개로 설정해 서로 다른 예약 작업의 대기를 분리했고 같은 poll의 중첩 실행 방지는 유지했습니다. 공통·결과 AP 테스트 101개가 통과했으며 전후 20 TPS 각 1,200건·과금 대상 960건이 일치했습니다. 이번 로컬 측정의 전체 완료 p95는 114.1초→81.1초였습니다. 변경 후 정책 13개와 100건 웹훅·PostgreSQL 장애 복구 시험도 통과했습니다. 실제 5초 조회 간격·1분 재시도·만료 정책은 그대로입니다. [스케줄러 변경과 검증](19-그라파나-대시보드-실행과-PPT-항목-대응.md#결과-manager-예약-작업의-실행-대기-분리--2026-10-10)에 범위와 한계가 있습니다.

HTTP Sender에서는 예약 시 검증한 값을 같은 소비 처리의 발송 시작 트랜잭션에 전달해 중복 GetItem을 줄였습니다. Redis 선점과 두 트랜잭션의 최신 상태 조건 검사는 유지했습니다. 충돌 없는 정상 경로에서 HTTP 호출 전 DynamoDB API 호출은 최초 4회→3회, 후속 6회→4회입니다. 실제 DynamoDB의 예약 이후 완료·회차 변경·허가 변경·중복 시작 차단을 포함한 63개 테스트가 통과했습니다. 전후 20 TPS 각 1,200건·과금 대상 960건 대조에서 접수→업체 HTTP p95는 25.6초→2.4초, 전체 완료 p95는 89.6초→67.7초였습니다. 단발 로컬 측정이며 [조건·안전성·검증 결과](19-그라파나-대시보드-실행과-PPT-항목-대응.md#http-sender의-발송-허가-재조회-축소--2026-10-10)에 한계를 기록했습니다.

배포 후 정책 13개·저장소 장애 4개·Sender 강제 종료 복구 2개 케이스도 통과했습니다. 각 시험에서 최종 이력·과금 대상·고객 결과·원본 정리와 추가 발송 부재를 확인했습니다. 장애 설정 복원 후 실행 AP 11개가 모두 UP이고 최종 모니터링 검증도 통과했습니다.

결과 Manager와 완료 Manager에 구간별 지표와 Grafana 서비스 패널 6개를 추가했습니다. 실행·실행 사이 대기·페이지 조회·건별 처리·Kafka 인계와 TTL·삭제 시간을 구분합니다. 118개 테스트와 혼합 부하 1,200건 대조, 최종 모니터링 검증이 통과했습니다. 이번 로컬 측정의 전체 완료 p95는 94.3초이며 성능 개선 판정은 아닙니다. 완료 정리 건당 평균 81.3ms 중 TTL·삭제가 62.2ms를 차지했습니다. [구간별 지표와 측정 결과](19-그라파나-대시보드-실행과-PPT-항목-대응.md#결과-판단완료-정리-구간별-관측--2026-10-10)에 수치와 해석 범위를 기록했습니다.

다음 작업은 완료 정리의 TTL·삭제 순서와 복구를 유지하면서 저장소 왕복과 제한된 메시지별 동시성을 검토하는 것입니다. 이후 지속 부하를 측정합니다. 실제 업체 HTTP 실패 코드 매핑과 TCP 규격 확인도 남아 있습니다. 같은 통신사의 새 회차 대기 중 이전 회차 웹훅이 오는 문제는 회차 식별자가 없는 기존 계약의 보류 사항입니다. 로컬 CDC 데이터 전파는 메인 호처리 관측과 별도 검증 범위입니다. 업체의 동일 `clientMsgId` 중복 차단 보장 시간과 늦은 웹훅 처리 한계는 [Call Flow](53-신규-메시지-케이스별-Call-Flow.md)와 [오류 코드 계약](54-메시징-오류-코드와-결과-인계-계약.md)에 남깁니다.

## 기능·성능 검증을 시작할 수 있는 시점

**메인 기능 검증은 지금 가능하며 이미 여러 차례 완료했다.** 업체·고객 수신부는 mock이고 AP·Kafka·Redis·DynamoDB·PostgreSQL은 실제 실행한다. 정상 접수부터 완료 이력·과금 대상·고객 웹훅까지 확인하는 데 추가 기능 개발은 필요하지 않다.

```bash
bash scripts/monitoring.sh demo --rate 1 --seconds 1 --errors --secondary
bash scripts/monitoring.sh verify
```

Grafana는 `http://localhost:13000`에서 볼 수 있다. 통신사 이동·재시도는 `policy-test`, 100건 웹훅·중복·SQL 장애는 `webhook-test`, 저장소 장애는 `storage-test`, Kafka 중단은 `kafka-test`, Sender 종료는 `sender-crash-test`로 따로 재현한다. 장애 시험은 같은 스택에서 동시에 실행하지 않는다. 실행 절차와 실제 통과 범위는 [모니터링 문서](19-그라파나-대시보드-실행과-PPT-항목-대응.md)에 모은다.

| 다음 작업 | 산출물·판단 기준 | 예상 작업 단위 |
|---|---|---|
| 성능 측정 도구 | `performance` 명령으로 실제 TPS·지연·오류·적체·AP 자원과 원본 자료 기록 | 구현 완료. 기초 측정 지금 가능 |
| 단계별 부하 기준선 | 5·10·20 TPS 혼합 2,100건 대조 완료. 20 TPS의 적체·정리 지연 관측, 최대 처리량 미확정 | 초기 기준선 완료 |
| 부하 지연 원인 확인·개선 | 완료 정리·SQL 배치·발송 전 준비·결과 스케줄러·Sender 재조회 개선 완료. 구간별 지표·혼합 부하 진단 완료. 완료 TTL·삭제 구간 개선 검토 | 다음 1개 이상. 원인과 수정 범위에 따라 추가 |
| 지속 부하·순간 증가·부하 중 복구 | 30~60분 지속 시험과 적체 해소·메모리 추세·중복/누락 확인 | 이어서 1개 이상. 병목 수정 발견 시 추가 작업 |
| 실제 업체 연동 | 실제 HTTP 코드·URL, TCP 전문·응답, 중복 차단 조건을 적용해 계약 시험 | 업체 규격·시험 환경 제공 후 별도 진행 |

위 작업 수는 새 결함·환경 제약이 없을 때의 예상이며 성능 합격을 보장하는 일정이 아니다. 현재 `demo`는 목표 1~100건/초·최대 120초의 소량 부하와 접수 p95를 확인하는 기능 도구다. 최종 완료 지연 분포나 지속 처리량을 검증한 성능 도구로 간주하지 않는다. 현재 Docker의 낮은 JVM 메모리·소비 병렬도와 단일 브로커, 로컬 DynamoDB·업체 mock 결과를 운영 처리량으로 환산하지 않는다.

성능 합격 판정에는 목표 접수/완료 TPS, 허용 p95/p99와 오류율, 웹훅 지연·실패·TCP 전환 비율, AP 및 저장소 자원 조건이 필요하다. 지금은 이 기준이 확정되지 않았으므로 먼저 기준선을 측정하고 수치로 제안한다.

운영 전 별도로 남는 범위는 실제 3시간·4시간 만료와 고객 웹훅 실패·지연의 장시간 종단 검증, Kafka 강제 종료·다중 브로커 리더 전환, Redis 전체 유실, 영구 오류 레코드 격리·운영 재처리, 실제 CDC 전파 검증이다. 현재 요청한 메인 기능 시연을 막지는 않으며 운영 준비 완료로 간주하지 않는다. 회차 식별자 없는 늦은 웹훅 정책은 기존 보류 사항이다.

## 코드 구조와 정리 범위

Maven 모듈은 12개이며, Java 패키지는 18개다. 접수 API 전용이던 인증·JWT·응답 공통 모듈 3개는 `messaging-api`의 인증·보안·응답 코드로 통합했다. 독립 실행 AP와 공통 라이브러리 경계를 유지하고, 인증·JWT·웹훅 수신·발송 전 준비의 작은 하위 패키지는 업무 단위로 합쳤다. 통신사별 HTTP Sender는 공통 모듈 하나를 세 Pod로 실행한다. 최초 Kafka 발행 복구는 API 접수 부하와 분리한 `messaging-publication-recovery-app`으로 유지하며, 로컬 모니터링 스택에도 포함한다. 접수 API는 메시지 업무와 보안 패키지를 구분한다.

웹훅 수신·결과 판단·완료·고객 웹훅 발송 AP는 Redis를 직접 사용하지 않아 전이 Redis 의존성을 제외했다. 불필요한 `localhost:6379` health 점검으로 503을 반환하던 문제를 제거했고, 모니터링 `verify`는 Prometheus 수집 상태와 함께 실행 AP 11개의 전체 health를 확인한다. 관련 Java 테스트 116개와 의존성 정리 후 정상·실패·TCP 전환 흐름이 통과했다.

구형 `/api/v1/deliveries` 경로·실행 모듈·PoC 도구·과거 결과 문서와 호출자가 사라진 운영용 DynamoDB 클라이언트는 제거했다. 저장소의 `DELIVERY#` 키와 `delivery_id` 등 속성, PostgreSQL `delivery_results`, `delivery.dynamodb` 설정·지표 이름은 현재 코드가 실제로 사용한다. 이 이름을 바꾸려면 데이터·설정·관측 도구를 함께 이관해야 하므로 미사용 코드로 삭제하지 않는다.

Docker에서도 이 저장소의 종료된 구형 컨테이너 156개, 미참조 볼륨 607개, 빈 네트워크 29개, 구형 collector 이미지 1개를 제거했다. 현재 연결 없는 볼륨은 0개이며 메시징 모니터링과 기존 `rcs` 실행 상태를 확인했다. Java 통합 시험은 고유 시험 프로젝트의 볼륨까지 종료 시 제거하도록 변경했고, 실제 정리 함수를 성공·실패 종료 양쪽에서 검증했다. 실행 로그와 테스트 결과 파일은 보존한다.
