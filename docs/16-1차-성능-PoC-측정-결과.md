## 기준선 결과

단위는 명시한 경우 외에는 ms다. k6 종료 경계의 추가 입력도 빠짐없이 대조했다.

| 목표 입력 | 실제 시작/응답 기록 | 입력 시간 | API p95 / p99 | 인입→접수 저장 시각 p95 / p99 | 관측 최대 lag | 판정 |
|---|---:|---|---:|---:|---:|---|
| 10 TPS | 1,801 / 1,801 | 180초 완료 | 14.89 / 20.56 | 42.29 / 51.44 | 21 | 통과 |
| 50 TPS | 9,001 / 9,001 | 180초 완료 | 9.64 / 13.63 | 54.48 / 135.88 | 34 | 통과 |
| 100 TPS | 3,579 / 3,578 | 약 35.96초, 조기 중단 | 8.88 / 11.81 | 26,181.48 / 28,234.33 | 1,517 | 실패·증가 중단 |

API 응답은 Kafka 접수까지만 기다리므로, 100 TPS에서 API 응답이 빨라도 실제 발송이 따라잡았다는 뜻은 아니다. 이 구간에서 접수 저장 시각의 p95는 약 26.2초로 늘었다. 50 TPS의 API 지연이 10 TPS보다 낮은 원인은 이번 순차 실험만으로 확정하지 않는다. 캐시·JIT·호스트 상태 영향을 분리하려면 순서를 바꾸고 반복해야 한다.

`인입→접수 저장 시각`은 META의 최초 occurred_at과 ACCEPTED 항목 updated_at의 차이다. updated_at은 DB Update 호출 직전에 만든 시각이며 DB ack 직후 Timer와 정확히 같지는 않다. API p95/p99는 k6에서 완료 응답이 기록된 요청 기준이다. 100 TPS의 응답 미기록 1건을 latency 표본에 임의로 추가하지 않았다.

적체 0을 두 번 관측하기까지의 종료 후 시간은 각각 약 **12.0초 / 12.3초 / 39.5초**였다. 이는 수집 간격·조회 비용을 포함한 상한이며 정확한 마지막 처리 시각이 아니다. 지표 수집 창 전체(입력 시작 전~해소 관찰)를 나눈 신규 접수 저장 평균은 약 **9.04 / 46.79 / 47.67건/초**다. 특히 100 TPS 값은 짧은 입력과 해소 시간을 합친 평균이며 최대 처리량으로 해석하지 않는다.

## 누락·중복과 100 TPS 중단 기록

기준선의 시작 요청은 총 **14,381건**, DB ACCEPTED와 업체 calls=1·effects=1로 확인한 건수도 **14,381건**이다. 대조 범위의 미설명 데이터 누락, 외부 추가 호출, DLT, REVIEW_REQUIRED는 없었다. 이 결과는 정상 기준선의 요청 대조이며 장애 시 무손실 보장을 증명한 것은 아니다.

100 TPS에서는 적체가 6회 연속 증가하고 500건을 초과해 부하 생성기를 종료했다. 최대 합계 lag는 1,517건, 첫 미커밋 record의 관측 대기 시간은 약 28.4초였다. k6는 exit code 105로 종료했고 `dropped_iterations=0`이었다. VU 부족이 아니라 적체 중단 조건으로 멈췄다.

중단 시점과 겹친 마지막 입력 1건은 start만 있고 HTTP result 로그가 없다. 해당 요청은 다음과 같이 별도 남겼다.

- deliveryId: `78466737-af20-328b-930d-cc7c4bc052b6`
- HTTP: 응답 기록 미확인. 202를 받았다고 추정하지 않는다.
- Kafka: 접수·Dispatch 각 1 record, DLT 0.
- DB: ACCEPTED.
- 업체: calls=1, effects=1.

따라서 데이터 처리는 확인됐지만 시험 전체는 `consistent=false`, `pass=false`다. 정상 응답만 골라서 성공률 100%로 보고하지 않는다. 원시 결과의 `problemRequests=1`은 이 HTTP 응답 기록 미확인을 뜻하며, DB 미저장 1건을 뜻하지 않는다.

소량 시험은 고유 요청 10건과 중복 입력 11건(고유 key 6개)이 통과했다. 워밍업 600건도 통과했으며 위 기준선 표에서 제외했다. 전체 실행에서 시작한 HTTP 요청은 15,002건, 고유 요청은 14,997건이다.

## 병목 후보와 근거

100 TPS의 토픽별 관측 최대 lag는 접수 토픽 **1,487건**, Dispatch 토픽 **116건**이다. 각 최댓값의 발생 시각은 다르므로 합산하지 않는다. 주된 적체 지점은 Ingress 앞이었다.

해당 구간의 Timer 누적 시간/호출 수로 계산한 평균은 다음과 같다. DB와 Kafka 모두 로컬 네트워크·공유 자원을 포함한다.

| 구간 | 평균 ms | 해석 |
|---|---:|---|
| Ingress 전체 listener 업무 | 11.20 | 원본 저장 후 Dispatch 발행 ack를 순차 대기 |
| Ingress 원본 저장 | 4.97 | 정상 conditional Put |
| Ingress 후속 Kafka 발행 | 6.23 | `send(...).join()`으로 ack까지 대기 |
| Dispatch 전체 업무 | 10.01 | 선점·HTTP·결과 저장 |
| Dispatch 선점 / HTTP / 결과 저장 | 4.19 / 1.67 / 4.14 | HTTP 시뮬레이터 자체보다 DB 경계의 시간이 큼 |

여기에 listener가 반환된 뒤 Kafka offset commit 비용이 더해진다. 마지막 샘플의 Kafka client `commit_latency_avg`는 Ingress **5.80ms**, Dispatch **5.92ms**였다. 이 값은 client의 이동 평균이므로 위의 전체 구간 평균과 정확히 더해서 처리량을 계산하지 않는다.

현재 설정은 `ack-mode: record`이며, Spring Kafka는 RECORD에서 각 record 처리 후 offset을 커밋한다. `syncCommits` 기본값은 true다. **추론:** 소비자 1개가 DB·후속 발행·건별 동기 commit을 차례로 기다리는 구조가 처리량 제한의 주요 후보다. CPU 포화 하나로 단정하거나 DB 자체의 운영 성능 한계로 일반화하지 않는다. [Spring Kafka commit 설정 공식 근거](https://docs.spring.io/spring-kafka/api/org/springframework/kafka/listener/ConsumerProperties.html#setSyncCommits(boolean)), [RECORD ack 동작](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html).

100 TPS 구간에서 k6의 관측 CPU 최댓값은 약 15.1%, RSS 약 64.3MiB였다. 이는 `ps` 샘플 값이며 순간 peak나 부하 생성기 무제한 여유를 증명하지는 않는다. 전체 JVM/컨테이너/수집기 지표는 원시 자료에 보관했다.

## 한계와 다음 실험

- 각 입력률은 한 번씩 시험했다. 50 TPS가 이 환경에서 3분 통과한 사실만 확인했으며 장시간 운영 용량·최대 지속 TPS를 확정하지 않았다.
- Kafka commit과 끝 offset은 서로 다른 조회 시점의 값이다. 처리 중 발생한 새 입력이 lag에 포함될 수 있고 샘플 사이 peak는 놓칠 수 있다. 종료 후에는 새 입력 없이 두 번 lag=0을 확인했다.
- DynamoDB Local·단일 broker·동일 노트북의 정상 시험이다. 다중 AZ, 리전 장애, 프로세스 kill, 실제 업체 지연과 응답 유실은 별도다.
- 준비 과정의 이전 실행 두 건은 정상 기준선에서 제외했다. 하나는 k6 경계 추가 입력에 대한 도구의 엄격한 건수 조건, 다른 하나는 장시간 시계/실행 공백과 Kafka 조회 timeout으로 종료됐다. 원시 실패 자료는 삭제하지 않았다.

다음은 **각 Worker consumer 동시성 1과 3을 비교**한다. 이미 있는 3개 파티션을 활용하되 최초 선점·완료 기록·DLT 인계·현재 ack 보장을 유지한다. 50·100 TPS를 먼저 반복하고 결과가 안정적일 때만 다음 부하를 올린다. 이후 Kafka 발행/offset commit 대기 시간을 줄일 대안을 검토하되, commit 묶음 변경은 중복 재전달·DLT 실패 경계 시험과 함께 별도 단위로 진행한다.

시험 종료 후 앱·PoC 컨테이너·유휴 절전 방지 프로세스는 종료됐고, 시험 고객 정책은 원복했다. Kafka/DB volume과 원시 결과는 보존했다.

후속으로 동시성 1 재측정과 3 비교를 수행해 100 TPS 정상 시험 통과를 확인했다. 원래의 실패 결과는 수정하지 않고 [후속 비교 보고서](17-워커-동시-처리와-발행-대기-성능-비교.md)에 변경 이유·결과·채택 판단을 이어 기록한다.
