# 성공 결과의 즉시 Kafka 인계와 복구 검증

2026-09-25. [전체 성능 측정](38-고객-수신과-정리까지의-전체-성능-측정.md)에서 확인한 정상 결과의 인계 대기를 줄이는 변경이다. 적용 범위는 v2의 1차·2차 **성공 웹훅**이다. 실패·만료 최종화와 정리 worker의 처리 방식은 이번 변경에 포함하지 않는다.

## 1. 변경 이유와 처리 순서

기존에는 성공 웹훅의 STEP·ORIGIN 트랜잭션을 마친 뒤 Redis에 즉시 후보를 등록하고 처리를 끝냈다. LifecycleScheduler가 기본 1초 간격·동시성 4로 후보를 다시 읽어 최종 결과를 Kafka에 발행했다. 이전 짧은 부하 시험에서 이 대기가 고객 결과 수신을 지연시켰다. 조회 간격을 50ms로 줄이면 빨라지지만 DDB 읽기도 늘었다.

이제 ReceiptResultRepository가 트랜잭션으로 저장한 `DeliveryFinalized`를 ReceiptResultService에 함께 반환한다. 서비스는 추가 DB 조회 없이 그 결과를 바로 발행한다.

1. 기존 STEP 강한 읽기·회차/만료/버전 검증.
2. STEP 불변 최종 결과 + ORIGIN 완료 보호 저장. 2차 성공이면 1차 STEP 종료도 같은 트랜잭션에 포함.
3. Redis에 복구 후보 등록.
4. 반환된 최종 결과를 Kafka에 발행하고 broker ack 확인.
5. Redis 후보 제거 후 웹훅 Kafka 입력의 RECORD offset commit 허용.

Kafka 발행은 기존 acks=all·멱등 producer를 사용한다. 새로운 완료 항목이나 발행 ack Update는 없다. 정상 DDB 쓰기는 **5회 API·7항목 변경**을 유지한다. 직접 인계에는 추가 읽기도 없다. 복구 worker와 경합하면 별도 읽기와 중복 발행이 발생할 수 있다.

## 2. 실패·중복 경계

| 중단/경합 시점 | 처리 |
|---|---|
| STEP 트랜잭션 실패 | 최종 결과를 반환·발행하지 않고 웹훅 입력 재처리 |
| 저장 후 발행 전 종료 | 웹훅 입력 재처리 또는 기존 Redis/DDB 복구로 저장 결과 인계 |
| Kafka ack 불확실 | 예외를 전달해 입력 offset 미완료. Redis 후보·STEP 결과 유지 |
| 같은 웹훅 재처리 | 기존 STEP 읽기에서 같은 receipt ID·fingerprint이면 저장된 결과를 반환. 결과 시각·내용과 DDB 쓰기 횟수 유지 |
| Kafka ack 뒤 offset commit 전 종료 | 같은 결과의 재발행 가능. SQL의 result eventId·본문 대조로 이력·통지 중복 제어 |
| 복구 worker와 동시 발행 | 동일 불변 결과가 중복 발행될 수 있으며 SQL에서 수렴 |
| Redis 유실 | STEP의 기존 복구 인덱스로 재인계. 기본 복구 조회 10분 유지 |
| deadline 이후 웹훅 재도착 | 기존 정책대로 로그만 남기고 폐기. deadline 이전에 저장한 최종 결과의 복구는 독립적으로 계속 가능 |
| SQL 이관 후 DDB 정리된 실행의 재도착 | STEP이 없으므로 폐기. 이전 실행을 다시 생성하지 않음 |
| lifecycle 비활성화 | 발행 bean이 없어 즉시 인계를 수행하지 않음. 기존 저장·후속 활성화 정책 유지 |

입력 consumer에서 ack를 기다리므로 Kafka가 느리면 웹훅 소비도 지연된다. 확인되지 않은 발행을 메모리에 넘겨 두고 입력만 완료하지 않는다. 이 경로는 외부 업체나 Kafka 전체에 대한 exactly-once 보장이 아니다.

관측 지표는 `delivery_receipt_finalization_total{outcome="published"}`와 `outcome="publish_failed"`다. 발행 횟수이며 고유 고객 결과 수가 아니다. 기존 `delivery_lifecycle_events_total{outcome="published"}`는 복구·기타 Lifecycle 경로의 발행을 센다.

## 3. 검증 방법

- 실제 DynamoDB에서 1차·2차 성공을 저장한 뒤 발행 ack 실패를 주입한다. 새 handler가 같은 웹훅을 재처리해 동일 결과를 발행하며, 추가 쓰기 없이 기존 STEP 읽기 1회만 사용하는지 확인한다.
- 발행 실패 후 deadline을 넘겨 웹훅을 폐기하더라도 Lifecycle이 기존 성공 결과를 복구하는지 확인한다. 정리 후 재도착은 추가 발행을 하지 않아야 한다.
- 기존 정상/재시도/만료 쓰기 예산과 발송 회귀 시험을 실행한다.
- 전체 6개 기능 시나리오와 이전과 같은 10/100 TPS ×5초 격리 측정을 실행한다. Redis 1초·DDB 10분 기본값으로 고객 수신·정리·읽기 횟수를 비교한다.

```sh
# JAVA_HOME은 JDK 21. 실제 DB 시험은 고유 ID를 쓰고 fixture가 정리한다.
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 ./mvnw -pl dispatch-worker -am test
./mvnw -DskipTests package
.poc-tools/venv/bin/python scripts/poc/full_flow.py
.poc-tools/venv/bin/python scripts/poc/full_flow_load.py --rates 10 100 --seconds 5
```

짧은 단일 측정의 처리량을 지속 최대 TPS로 해석하지 않는다.

## 4. 검증 결과

event-common 11개, dispatch-worker 147개 시험 통과(실패·오류 0). 별도 Kafka/Redis 환경 변수가 필요한 기존 시험 4개는 미실행이며 이 수에 포함하지 않았다. 새 실제 DB 시험 3개는 모두 실행했다. 상위 시험 클래스의 DB 환경 조건이 하위 v2 클래스에 적용되지 않던 부분도 명시적으로 수정했다. 전체 모듈 패키징을 통과했다.

전체 기능 실행 `full-flow-bbc2aebdc4bf`는 6개 시나리오를 모두 통과했다. 성공 4건은 즉시 인계 지표로, 만료 2건은 기존 Lifecycle 발행 지표로 관찰됐다. 고객 503 후 재전송·완료 중복 차단·Redis 일정 유실·대체 발송·원래 deadline 만료와 데이터 정리를 확인했다.

부하 실행 `full-flow-5cd69eca2588`은 50+500건, 총 **550건 전수 대조**를 통과했다. 모든 요청의 업체 호출 1회·고객 수신/SQL 일치·DDB 정리를 확인했다. Redis 조회 1초, DDB 누락 복구 10분이며 이전 기본값 실행과 같다.

| 구간 | 이전 기본값 | 즉시 인계 적용 |
|---|---:|---:|
| 10 TPS ×5초 고객 수신 p95 | 14.22초 | 3.88초 |
| 100 TPS ×5초 API p95 | 67.82ms | 43.91ms |
| 100 TPS 업체 결과 p95 | 15.30초 | 15.15초 |
| 100 TPS 최종 결과 생성 p95 | 16.18초 | 16.65초 |
| 100 TPS SQL 저장 p95 | 118.20초 | 16.72초 |
| 100 TPS 고객 수신 p95 | 118.23초 | 16.80초 |
| 100 TPS 정리 완료 p95 | 118.65초 | 42.51초 |
| 100 TPS 입력 시작~배출 관찰 시간 | 129.67초 | 49.89초 |
| 100 TPS 입력·배출 포함 관찰 처리량 | 3.86 TPS | 10.02 TPS |

최종 결과 생성과 SQL 저장의 지연 수치가 가까워졌으며, 앞단 업체 결과 지연은 약 15초로 남았다. 각 단계 p95는 서로 다른 요청일 수 있어 두 p95의 차이를 개별 요청의 구간 p95로 보지는 않는다.

### DynamoDB와 중복 인계

| 두 입력 구간 합산 | 이전 기본값 | 즉시 인계 적용 |
|---|---:|---:|
| 입력 수 | 551 | 550 |
| 읽기 API 호출 | 5,083 | 4,781 |
| 요청당 평균 읽기 API | 9.23 | 8.69 |
| 성공 쓰기 API | 2,755 | 2,750 |
| 요청당 성공 쓰기 API | 5.00 | 5.00 |
| 실패 트랜잭션 API | 13 | 72 |

입력 수 차이를 보정한 요청당 읽기는 약 **5.8% 감소**했다. 이는 실패 조건·항목 크기·GSI를 포함한 AWS 비용 감소율이 아니다. 실패 트랜잭션이 늘었고 현재 카운터만으로 각 취소 사유를 구분할 수 없어 청구 비용이나 경합이 개선됐다고 주장하지 않는다.

즉시 발행 550회 외에 Lifecycle 발행 13회도 관찰됐지만 SQL 이력과 고객 결과는 고유 입력 550건으로 일치했다. 복구 인덱스를 유지하므로 이런 중복 인계가 가능하다. Lifecycle의 `work_failed`도 9회였으며 후보를 보존한 후 전부 수렴했다. Redis 경로의 기존 실패 카운터에는 상세 예외가 없어 이 수치를 전부 같은 경합 원인으로 단정하지 않는다.

### 남은 병목과 다음 작업

고객 통지 550건 완료·Kafka lag 0·Redis due 0인 샘플에서 정리는 182건이었다. 결과 인계 대기는 줄었으나 정리 worker의 tick당 최대 20건 순차 처리·기본 1초 대기가 남는다. 다음 작업은 **SQL lease와 조건부 DDB 삭제를 유지하면서 정리를 제한된 동시 처리로 개선**하고, 읽기·실패 트랜잭션·처리량을 같은 방식으로 재측정하는 것이다. 앞단 Kafka 적체와 약 15초의 업체 결과 p95도 이후 조사 대상이다.

이번 시험은 지속 100 TPS 달성이나 운영 장애 무손실의 증거가 아니다. 결과와 재현 환경·JAR/소스 해시·구간 지연·읽기 카운터·미실행 시험은 [검증 근거 JSON](성능-측정/2026-09-25-성공-결과-즉시-인계와-전체-부하-재측정.json)에 남겼다. 원시 로그·Prometheus·요청별 대조는 위 실행 ID의 `.poc-results/`에 보존했고 소유 프로세스·컨테이너를 정지했다. 공유 앱 배포는 수행하지 않았다.

실행 중 제한된 환경의 JVM agent/socket 접근 문제와 이전 시험용 DB 컨테이너 재시작 후 호스트 포트 무응답으로 선행 시험이 중단됐다. 최종 DB 시험은 정상 응답하는 localhost:18000에서 고유 시험 ID로 실행·정리했다. 새 전체 흐름 환경은 기존 문서의 Created 상태 1회 시작 재시도로 정상 기동했다. 이 Docker 현상의 내부 원인은 확정하지 않았다.
