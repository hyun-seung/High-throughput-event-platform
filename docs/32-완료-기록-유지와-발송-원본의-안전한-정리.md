# 완료 기록 유지와 발송 원본의 안전한 정리

> 정책 갱신(2026-09-25): [ADR-022](adr/ADR-022-처리-중-DynamoDB-선점과-완료-후-Redis-중복-차단.md)에서 완료 후 Redis TTL 차단과 Redis 소실+DDB 조건 통과 시 재발송을 허용했다. 아래 작은 DDB 완료 기록 의무 보관 설명은 이전 정책/현행 구현 기준이며 새 정책에서 대체된다. 처리 중 원자 선점·SQL 인계 전 원본 보존과 제품의 공식 특성은 유지한다. v2 코드 적용을 완료했다. 아래 이전 설명은 v1 기준선이며 현재 동작은 [최신 구현·검증](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md)을 따른다.

## 구현한 흐름

발송이 끝났다는 이유만으로 DynamoDB의 모든 정보를 지우면 오래된 Kafka 이벤트가 새로운 발송으로 처리될 수 있습니다. 원본은 줄이되 같은 요청이 끝났다는 작은 기록은 유지합니다.

```text
DynamoDB 최종화 트랜잭션
  META 완료 표시 + FINAL 생성 + 1차/2차 Attempt 닫기
→ FINAL을 Kafka에 발행하고 PUBLISHED 확인
→ PostgreSQL 트랜잭션
  이력 + 고객 통지 예약 + 원본 정리 예약 저장
→ SQL 정리 예약 선점
→ DynamoDB 조건부 트랜잭션
  기존 META를 작은 완료 기록으로 교체
  + FINAL·Attempt·그 Attempt가 만든 Receipt marker 삭제
→ SQL 정리 예약 DONE
```

고객 통지 완료까지 원본을 붙잡아 두지는 않습니다. SQL에 이력과 통지 예약이 함께 저장됐으면 고객 HTTP 전송·재전송은 그 데이터로 계속할 수 있습니다. 발송 결과와 고객 통지 성공은 별도 상태입니다. 통지 EXHAUSTED가 되어도 이력·통지 기록을 삭제하지 않습니다.

SQL과 DynamoDB 사이의 분산 트랜잭션은 없습니다. 먼저 SQL에 복구 근거를 남기고 DynamoDB를 원자적으로 정리한 뒤 SQL 진행 상태를 기록합니다. 중간에 중단되면 동일 예약을 다시 처리합니다.

## 정리 전후 보관 항목

| 위치 | 정리 전 | 정리 후 |
|---|---|---|
| DynamoDB DELIVERY/META | 원본 payload·요청 메타데이터·완료 표시 | 요청 ID·고객·유형·최초 인입 시각, COMPLETED, 완료 이벤트 ID·결과·시각, 요청 fingerprint·버전, 결과 hash |
| DynamoDB DELIVERY/ATTEMPT | 선점·재시도·경로·결과·Receipt 목록 | 삭제 |
| DynamoDB DELIVERY/FINAL | 최종 이벤트 본문·발행 확인 | 삭제 |
| DynamoDB RECEIPT/META | 결과 중복 방지 marker | 해당 Attempt에 기록된 marker만 삭제 |
| PostgreSQL | 이력·고객 통지·정리 예약 | 모두 유지, 정리 예약만 DONE |
| Kafka | 접수·발송·결과 이벤트 | 기존 토픽 보관 정책 적용; 건별 삭제 없음 |

완료 META에는 TTL을 설정하지 않습니다. 보관 기간 합의 전에는 자동 삭제하지 않습니다. 삭제하면 오래된 재요청을 새 발송과 구별할 근거가 사라집니다. `request_fingerprint`는 버전 1의 SHA-256이며 길이를 붙인 UTF-8 필드(deliveryId·tenantId·deliveryType·fallbackAllowed·정규화 payload)를 해시합니다. 재요청마다 바뀌는 시각·correlationId는 제외합니다. 원본 payload는 복원할 수 없습니다. 따라서 정리 후 원문 조회·재구성이 필요해지면 별도 보관 정책을 정해야 합니다. 해시는 실용적인 충돌 저항성을 사용하며 수학적으로 충돌이 불가능하다는 뜻은 아닙니다.

## 삭제 후 재발송을 막는 방법

1. 최초 1차/2차 Attempt 선점은 META의 `completion_event_id` 부재 확인과 Attempt 생성이 같은 DynamoDB 트랜잭션입니다. 읽기 후 별도 생성 사이에 정리가 끼어드는 문제를 막습니다.
2. 최종화도 같은 META에 완료 표시를 쓰고 Attempt를 닫는 트랜잭션입니다. 원본을 지우기 전부터 새로운 선점을 막습니다.
3. Ingress는 완료 표시 또는 작은 완료 기록이 있으면 동일 요청을 확인한 뒤 Dispatch를 다시 발행하지 않습니다. 동일 키의 다른 내용·대체 발송 설정은 기존 충돌 격리 경로로 보냅니다.
4. 기존 실행자의 늦은 결과 저장은 상태·version 조건을 통과하지 못합니다. 정리된 Attempt를 다시 만들지 않습니다. 이전 2차 계획도 재생성하지 않습니다.
5. 늦은 Receipt는 작은 완료 기록을 확인하면 `late_discarded`로 처리합니다. 업무 상태나 marker를 만들지 않으며 기존 늦은 결과 로그 정책을 유지합니다.

이미 선점한 실행자가 외부 호출 직전에 멈췄다가 재개하는 경우, DB 조건만으로 외부 호출 자체를 취소할 수는 없습니다. 이 변경은 새로운 선점과 삭제 데이터의 재생성을 막으며, 외부 효과의 exactly-once를 증명하지 않습니다. 관찰한 무응답의 재시도에 남는 중복 가능성도 기존 정책과 같습니다.

## 삭제 대상을 증명하는 조건

정리 워커는 SQL의 이력·통지·정리 예약을 JOIN하여 가져옵니다. DynamoDB FINAL은 PUBLISHED여야 하고 SQL 결과와 모든 필드가 같아야 합니다. META 완료 이벤트 ID도 일치해야 합니다.

`DELIVERY#id` 한 파티션만 consistent Query합니다. META와 FINAL 외에는 정확한 경로 수만큼의 닫힌 Attempt만 허용합니다. 모르는 항목, 추가 페이지, 추적 버전이 없는 Attempt, 불일치 결과는 전부 보존합니다. Query가 트랜잭션 스냅샷이라는 가정은 하지 않습니다. 실제 교체·삭제 시 원본 내용, 완료 ID, FINAL 내용·상태, Attempt version·닫힘, Receipt 소유 delivery를 조건으로 다시 검증합니다.

새 Attempt에는 `receipt_tracking_version=1`을 기록합니다. Receipt를 반영할 때 기존 Attempt+marker 트랜잭션 안에서 marker ID를 `receipt_marker_ids` 집합에 추가합니다. 마지막 Receipt만 지우지 않고 재시도 중 만든 marker도 모두 정리합니다. 새 테이블·GSI·전체 Scan은 추가하지 않았습니다.

최대 100개 작업의 단일 트랜잭션으로 교체·삭제합니다. 한 조건이라도 실패하면 전체를 유지합니다. 한도를 넘으면 분할 삭제하지 않고 보존합니다. FINAL 또는 marker를 먼저 개별 삭제하지 않습니다.

## 실행·이관 순서

기본 `DELIVERY_CLEANUP_ENABLED=false`입니다. 이번 검증은 UUID 시험 데이터에만 수행했고, 실행 중인 공용 앱의 정리는 활성화하지 않았습니다.

1. 기존 `delivery-result-worker` 소비자를 중지한 뒤 새 버전으로 교체하여 Flyway V3를 적용합니다. V3는 기존 SQL 이력+통지가 모두 있는 건에 정리 예약을 보강합니다. 이관 중 구버전 SQL 소비자가 새 이력을 쓰지 않도록 합니다. 대규모 기존 데이터에서는 INSERT 및 인덱스 생성 부하를 별도 평가합니다.
2. Ingress·Dispatch·결과 워커를 모두 새 버전으로 교체합니다. 구버전 발송/결과 실행자가 남아 있으면 안 됩니다. 기존 주기 최종화의 GSI 이관 조건도 그대로 적용합니다.
3. 먼저 정리 비활성 상태에서 새 요청의 META 완료 표시와 Attempt 추적 버전을 확인합니다. 기존 데이터에 추적 버전만 임의로 붙이지 않습니다. 과거 marker 목록의 완전성을 입증할 수 없기 때문입니다.
4. 격리 환경에서 아래 검증을 실행한 뒤 결과 워커만 `DELIVERY_CLEANUP_ENABLED=true`, `DYNAMODB_ENDPOINT=http://localhost:18000`으로 실행합니다. 운영에서는 지역·권한과 실제 endpoint 설정을 별도로 적용합니다.
5. DONE 증가와 retained 원인, 고객 통지 지속, 같은 요청 재입력 시 외부 호출 불증가를 확인합니다. 중단하려면 정리 설정을 false로 되돌립니다. 이미 정리한 원문은 되돌릴 수 없으며 작은 완료 기록은 계속 보존해야 합니다. 정리 후 구버전 발송 코드로 되돌리면 보호 조건이 없어지므로 허용하지 않습니다.

결과 워커는 기존 DynamoDB 테이블을 사용하며 자동 테이블 초기화는 끕니다. 필요한 권한은 해당 테이블 GetItem·Query·트랜잭션의 조건 확인/Put/Delete입니다. Kafka·SQL 권한은 기존과 같습니다.

구버전 데이터에 완료 표시 또는 Receipt 추적 정보가 없으면 정리 예약은 PENDING으로 남습니다. 자동 Scan·추정 삭제·강제 보강은 구현하지 않았습니다. 검증된 별도 이관 없이 이 조건을 우회하지 않습니다.

## 장애와 관측

| 중단 지점 | 남는 근거 | 복구 |
|---|---|---|
| SQL 이력/통지/정리 예약 중 하나 실패 | Kafka offset 유지, DDB 원본 유지 | SQL 전체 rollback 후 재소비 |
| SQL commit 후 정리 전 종료 | SQL PENDING + 원본 | 다음 워커가 예약 선점 |
| DynamoDB 장애·조건 불일치 | SQL PENDING + 원본 전체 | 기본 30초 후 재시도; 불일치는 운영 확인 |
| DDB 정리 성공 후 응답 유실 | 작은 완료 기록 + SQL PENDING | 완료 ID·결과 hash 일치 확인 후 DONE |
| DDB 정리 후 SQL DONE 저장 실패 | 작은 완료 기록 + SQL 예약 | 재시도 또는 lease 만료 후 동일 확인 |
| 정리 워커가 선점 후 종료 | SQL lease | 60초 후 다른 워커가 선점 |
| 늦은 이전 실행자의 완료/재시도 갱신 | 새 lease token 또는 DONE | token 조건으로 이전 실행자의 SQL 갱신 차단 |

현재 기본 poll은 1초(`DELIVERY_CLEANUP_POLL_MS`), 정리 동시성은 4(`DELIVERY_CLEANUP_CONCURRENCY`), 작업자당 tick 최대 20건(`DELIVERY_CLEANUP_BATCH_SIZE`)입니다. 한 건을 선점·정리·완료한 뒤 다음 건을 가져오며 현재 tick이 끝나야 다음 tick이 시작됩니다. 외부 DDB 호출 중 SQL row lock을 유지하지 않습니다. DDB 개별 API 전체 제한 10초·시도 제한 5초이며 통지와 정리 스케줄러를 분리했습니다. 이 설정은 고 TPS 처리량을 보장하는 값이 아닙니다. [동시 처리·lease 보호·성능 비교](40-완료-데이터-정리의-동시-처리와-성능-검증.md).

Prometheus `delivery_cleanup_events_total{outcome="compacted|already_compacted|retained"}`를 제공합니다. counter는 고유 작업 수가 아니라 처리 시도 집계입니다. 현재 Grafana 전용 패널·SQL backlog 게이지는 후속 작업입니다. 예약 현황은 결과 스키마에서 확인합니다.

```sql
SELECT status, count(*), min(created_at) AS oldest_created_at
FROM delivery_cleanup_outbox GROUP BY status;
```

`retained` 로그에는 eventId와 예외 종류를 남기며 payload를 출력하지 않습니다. 영구 조건 불일치와 일시 장애의 상세 운영 분류·수동 조치 도구는 후속입니다. DB·Kafka 장애 시 최종 고객 수신 시각을 절대 보장하지 않으며 복구 후 기한 판단 정책을 유지합니다.

## 비용과 검증 범위

| 경계 | 추가/변경되는 비용 |
|---|---|
| 최초 Attempt 선점 | 기존 조건부 Update에서 META ConditionCheck+Attempt Update 트랜잭션으로 변경. 큰 META의 조건 확인 비용도 고려 |
| 최종화 | 기존 FINAL+Attempt 트랜잭션에 META Update 1개 추가: 1차 종료 3항목, 2차 종료 4항목 |
| Receipt 반영 | 추가 item 쓰기 없이 기존 Attempt에 marker ID 집합 추가. item 크기는 증가 |
| SQL 최종 저장 | 이력·통지 외 정리 예약 INSERT 1회 추가 |
| 정상 정리 | META Get·FINAL Get·단일 파티션 Query 후 META 교체+FINAL/Attempt/marker 삭제 트랜잭션 |
| 정리 성공 재확인 | 작은 META Get 후 SQL DONE. DDB 재삭제 없음 |

Query projection은 응답 데이터량을 줄이지만 읽기 용량을 줄이는 근거는 아닙니다. 트랜잭션은 일반 쓰기보다 용량 비용이 늘어납니다. 큰 payload·충돌·재전달·정리 적체를 포함해 다음 전체 흐름 PoC에서 측정해야 합니다. 이전 HTTP 접수 구간 100 TPS 결과를 변경 후 처리량으로 인용하지 않습니다.

2026-09-25 전체 `package` 260건 통과, 실패·오류·제외 0건입니다. 실제 DynamoDB Local·PostgreSQL·Kafka와 loopback HTTP를 사용했습니다. [기계 판독 결과·시험 목록·소스 해시](검증-결과/2026-09-25-완료-기록과-발송-원본-정리.json)를 보존합니다.

신규 18건은 Ingress 2건, Dispatch 10건, SQL+DDB 통합 6건입니다. 완료 전후 중복 접수, 변경된 업체로 재선점, 오래된 2차 계획, 늦은 Receipt/결과 저장, 여러 Receipt marker 정리, 구버전·미발행·불일치 보존, 조건 실패 전체 rollback, 선점/정리 성공 응답 유실, 선점 직전 멈춘 실행자의 재개, SQL 동시 선점·lease 복구, 세 번째 SQL 예약 실패 rollback, 정리 후 실제 고객 HTTP 통지, Spring 스케줄러 실행을 확인했습니다.

```bash
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
POSTGRES_TEST_URL=jdbc:postgresql://localhost:15432/delivery \
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:39092 \
JAVA_HOME=/path/to/jdk-21 ./mvnw -q package
```

환경변수를 빼면 해당 통합 시험은 제외됩니다. 시험은 UUID 스키마·키·토픽을 사용합니다. JVM SIGKILL·실제 DB 디스크 장애·다중 AZ 전환·전체 흐름 고 TPS·Grafana 추가 패널은 이번 검증에 포함하지 않았습니다. 다음 작업은 이력·고객 통지·정리까지 포함한 격리 실행/관측 연결과 소량 전수 대조, 이어 구간별 부하 및 장애 복구 측정입니다.

전체 요청 기준의 정상·최대 대표 경로 쓰기 횟수와 최소화 여부는 [DynamoDB 사용 횟수와 최소화 검토](33-DynamoDB-사용-횟수와-최소화-검토.md)에 실제 계측으로 추가했습니다.
