# PostgreSQL 장애 중 결과 보존과 자동 복구 검증

2026-09-25. [프로세스 재시작 복구 검증](42-프로세스-강제-종료와-재시작-복구-검증.md)에 이어 PostgreSQL 서비스 중단 시 v2의 보존·복구 경계를 검증한다. [전체 만 TPS와 Pod별 성능 측정](41-전체-만-TPS-목표와-Pod별-성능-검증-계획.md)은 기능·복구 개발 완료 후 진행한다.

## 1. 이번에 확인하는 경계

SQL 이력·통지·정리 예약을 저장할 수 없으면 결과 소비자는 Kafka offset을 넘기지 않아야 한다. ORIGIN·STEP은 SQL 인계 전 삭제하면 안 된다. Kafka·DynamoDB·Redis가 정상이고 이미 발급된 유효 JWT로 접수하면 업체 발송과 결과 확정은 계속 가능해야 한다.

시험 도구는 `scripts/poc/postgres_recovery.py`다. [전체 격리 실행 도구](37-전체-호출-흐름의-격리-실행과-전수-대조.md)를 재사용하고, 실행별 Compose project/service label로 소유권을 확인한 PostgreSQL 컨테이너 ID에만 stop/start를 수행한다. 여섯 JVM은 시험 중 재시작하지 않으며 PID가 모두 유지돼야 통과한다. 같은 컨테이너·볼륨으로 복구하고 Kafka offset이나 DB 데이터를 수정하지 않는다.

| 요청 | PostgreSQL 중단 중 기대 동작 | 복구 후 판정 |
|---|---|---|
| S-01: 정상 웹훅 | 202 접수 → HTTP 효과 1회 → 성공 웹훅 → STEP의 DELIVERED 결과 확정. SQL 오류로 결과 소비 보류 | 기존 결과와 같은 SQL 이력·고객 본문, 통지 완료 후에도 추가 업체 호출 없음, DDB 정리 완료 |
| S-02: 웹훅 미수신 | 202 접수 → HTTP 효과 1회 → 최초 기한에 STEP의 EXPIRED 결과 확정. 결과와 원본 보존 | 기한·결과를 바꾸지 않고 SQL 이력·고객 통지·정리로 인계 |

두 요청 모두 2차 발송은 비허용이다. 시험에서만 1차 만료 30초·2차 40초·DDB 누락 복구 3초를 사용하며 운영 기본값 3시간/4시간·10분은 유지한다. 업체 중복 제거를 끈 상태에서 호출 수와 실제 효과 수를 각각 확인한다. JDBC timeout·풀 설정은 현재 앱 기본값을 사용한다.

## 2. 장애·복구 판정 방법

1. SQL 이력이 없는 새 환경에서 consumer offset과 JVM PID, 결과 저장 실패 계측을 기록한다.
2. PostgreSQL을 중단하고 컨테이너 Exited, SQL 탐침 실패를 확인한 후 두 요청을 보낸다. 로그인은 중단 전에 완료한다.
3. 앱의 `delivery_result_records_total{outcome="failed"}`가 2회 이상 증가해야 한다. 정상 실행 중인 consumer가 실제 저장 오류를 경험했는지 확인한다.
4. 두 요청의 STEP에 각각 불변 최종 결과가 생길 때까지 기다린다. PostgreSQL이 계속 중단된 상태에서 ORIGIN·STEP 존재, 완료 Redis 표식 부재, 고객 HTTP 수신 0건, 최종 Kafka committed offset 불변·lag 2 이상을 대조한다.
5. 동일 컨테이너·볼륨을 다시 시작한다. SQL 연결을 확인한 뒤 앱 재시작 없이 실제 이력 저장·고객 수신·정리가 끝날 때까지 기다린다.
6. SQL 고유 이력 2건과 접수 ID 집합·중단 중 STEP 결과·고객 수신 본문을 대조한다. 각 요청의 업체 호출/효과는 1/1, 통지 시도는 1회여야 한다. ORIGIN·STEP 삭제, Redis 완료 TTL, 네 토픽의 모든 파티션 lag 0, JVM PID 불변을 확인한다.

offset 조회용 consumer는 subscribe/commit하지 않는다. 미커밋 offset의 음수 표기는 시작 offset 0과 같은 위치로 비교한다. 이 비교는 retention·offset 초기화가 없는 새 격리 토픽을 전제로 한다.

```sh
# JDK 21과 Docker 및 scripts/poc/setup.py 도구 준비 후
./mvnw -DskipTests package
.poc-tools/venv/bin/python -m unittest discover -s scripts/poc -p 'test_*.py'
.poc-tools/venv/bin/python scripts/poc/postgres_recovery.py
```

실행별 `.poc-results/<실행 ID>/`에 중단 전·중·복구 후 자료, 저장 실패 Prometheus 원문, 고객 수신 원문, SQL 이력, 환경·도구/JAR 해시를 남긴다. 실패 시에도 자료를 보존하며, 종료 시 소유 앱과 컨테이너만 정지하고 볼륨을 유지한다.

## 3. 검증 한계와 다음 범위

이번 시험은 **단일 로컬 PostgreSQL 서비스의 연결 불가와 동일 볼륨 복구**다. DB commit 순간의 응답 유실, WAL 손실, replica 승격, 디스크 손상, 노드/AZ 장애를 주입하지 않는다. 새 로그인·토큰 발급도 장애 중 계속된다고 주장하지 않는다.

만료 결과 확정과 고객 수신 시각은 다르다. PostgreSQL이 중단돼 있으면 고객 통지가 지연되며 복구 후 전달한다. 이미 확정된 성공 결과를 장애 기간이 길다는 이유로 만료로 바꾸지 않는다. 저장소 복제 구성이나 모든 장애의 무손실 보장을 입증하는 시험은 아니다.

다음은 DynamoDB·Redis·Kafka 불가용 시 영향 범위와 복구 검증, 운영 조회·조치 기능 보완이다. 이 문서의 PostgreSQL 통과를 다른 저장소의 통과로 간주하지 않는다.

최초 실행 `full-flow-8976fe59f112`는 업무 시나리오 시작 전 인프라 healthcheck의 Docker inspect 10초 timeout으로 종료됐다. 이전에 종료했던 PoC 컨테이너들이 다시 실행 중인 것을 확인했다. 완료 기록·소유 project/service label·활성 앱 포트 부재를 대조한 42개만 정지한 뒤 동일 코드로 재실행했다. 공유 개발·모니터링 환경과 볼륨은 유지했다. Docker 내부 지연 원인이나 이전 컨테이너가 다시 실행된 이유까지 확정한 것은 아니다.

두 실행의 소유 컨테이너 정리를 확인했다. 다음부터도 시험 전 실행 중인 PoC와 자원 여유를 확인하되, 이름 패턴만으로 공유·활성 환경을 일괄 정지하지 않는다.
