# 단계별 처리 절차와 실패 대응

> 2026-09-25 v2 적용: ORIGIN/STEP, Kafka 고정 회차 재시도, STEP 최종 이벤트와 SQL 이후 삭제, Redis 완료 TTL을 구현했다. 아래 이전 저장 구조는 v1 기준선이다. 현재 단계별 경계·장애 대응은 [최신 구현·검증](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md)을 우선한다.

각 구간을 `입력 → 검사 → 저장/발행 → 완료 기준 → 실패 동작` 순서로 정리합니다.

구현 상태:

- **구현**: 현재 코드에 존재
- **일부**: 기본 흐름만 있고 신뢰성 처리가 남음
- **예정**: 설계 단계

## 1. API 인입

**구현**

```text
Client 요청
→ JWT 인증
→ Request validation
→ Redis TPS/Quota admission 확인
→ Idempotency-Key 검증
→ deliveryId와 DeliveryRequested eventId 생성
```

입력:

```http
POST /api/v1/deliveries
Authorization: Bearer ...
Idempotency-Key: client-request-001
```

```json
{
  "deliveryType": "ORDER_COMPLETED",
  "payload": {
    "orderId": "100"
  }
}
```

`deliveryId`는 `tenantId + Idempotency-Key`에서 안정적으로 생성합니다. 같은 tenant가 같은 key로 재요청하면 동일한 ID가 됩니다.

## 2. Kafka 최초 접수

**구현**

```text
DeliveryRequested 생성
→ delivery.requested.v1 발행
→ Kafka acks=all 확인
→ 202 Accepted + deliveryId
```

`202`의 의미:

```text
DeliveryRequested가 Kafka에 저장되어 비동기 처리를 시작할 수 있다.
```

Kafka send가 실패하면 future가 실패하므로 `202`가 완성되지 않습니다. 명시적 `503` 오류 계약은 다음 작업입니다.

API 요청 thread에서는 DynamoDB에 쓰지 않습니다.

## 3. Delivery 원본 Projection

**구현**

```text
Delivery Ingress Consumer
→ DeliveryRequested consume
→ event type 검증
→ DynamoDB DELIVERY conditional insert
→ 중복이면 기존 원본 동일성 확인
```

DynamoDB key:

```text
PK = DELIVERY#{deliveryId}
SK = META
```

정상 요청의 ingress DynamoDB write는 한 건입니다.

중복 record이면 Put 조건이 실패하고 consistent read로 `eventId`, `tenantId`, `deliveryType`, `payload`가 같은지 확인합니다. 내용이 다르면 idempotency 충돌로 실패시킵니다.

## 4. Dispatch 단계 발행

**구현**

```text
DynamoDB 원본 저장 또는 동일 원본 확인
→ DispatchRequested 생성
→ delivery.dispatch-requested.v1 발행
→ Kafka ack 확인
→ DeliveryRequested listener 완료
```

DynamoDB 저장 후 Dispatch 발행 전에 종료되면 최초 record가 다시 전달됩니다. 원본 conditional insert는 중복을 허용하고 Dispatch event를 다시 발행합니다.

Dispatch 발행 후 최초 record commit 전에 종료되면 Dispatch event가 중복될 수 있습니다. 따라서 Dispatch Consumer 멱등성은 필수입니다.

## 5. Dispatch Consumer와 Provider 호출

**구현**

```text
DispatchRequested consume
→ event type 검증
→ deliveryId + provider + routeOrder + attemptNumber로 안정적인 attemptId 생성
→ DISPATCH_ATTEMPT conditional claim
→ PROCESSING + leaseUntil + version 저장
→ attemptId를 Provider Idempotency-Key로 사용
→ Mock Provider HTTP 호출
→ version 조건으로 ACCEPTED 저장
```

완료된 Attempt는 Provider 호출 없이 listener를 완료합니다. 유효한 lease가 있으면 중복 호출하지 않고 record 처리를 실패시켜 offset을 commit하지 않습니다. lease가 만료되면 같은 항목을 `REVIEW_REQUIRED`로 조건부 전환하고 version을 증가시킵니다. 추가 외부 호출은 하지 않으며 상태 저장이 확인된 뒤에만 운영 확인으로 인계합니다. Dispatch 오류는 기본 재시도 소진으로 버리지 않고 다시 전달합니다. [ADR-008](adr/ADR-008-발송-작업-선점과-외부-중복-발송-방지.md)에 구현 범위와 한계를 기록합니다.

현재 남은 흐름:

```text
Provider 호출 예외 분류
→ ACCEPTED / FAILED / UNKNOWN 저장
→ Retry 또는 조정 경로 선택
```

Provider가 key를 지원하지 않는 mode에서는 Attempt claim만으로 HTTP 응답 유실 뒤의 중복 부수 효과를 완전히 막을 수 없습니다.

## 6. Retry

**예정**

```text
응답 또는 업체 결과 웹훅에서 재시도 대상으로 분류한 실패 코드 수신
→ attempt와 전체 deadline 확인
→ 해당 코드의 지연 시간 적용 (구체적인 한도와 지연 정책은 미정)
→ nextAttemptAt 저장
→ 시각 도달 후 DispatchRequested 재발행
```

응답 미수신을 관찰한 Worker는 Q6에 따라 사유·재시도 계획을 기록하고 최대 3회 재시도합니다. 외부 미처리가 확정된 것은 아니므로 외부 중복 가능성은 남습니다. 시작 기록만 남은 채 Worker가 종료된 경우는 운영 확인으로 인계합니다. 상세 구분은 [Q6 결정 기록](08-함께-결정할-설계-사항.md#q6-확정-내용과-남은-결정)을 따릅니다.

## 7. Provider Fallback

**예정**

```text
2차 전환 대상 실패 코드 수신, 1차 만료 또는 1차 무응답 재시도 3회 소진
→ 최초 메시지의 2차 발송 허용 설정 확인 (미허용이면 전환 금지)
→ Fallback 허용 정책 확인
→ 2차 TCP Provider 선택
→ 1차 결과 판단 시각으로 2차 만료 기준 고정
→ 새 attemptId와 routeOrder
→ TCP Dispatch
→ TCP 수신·접수 확인 응답 기록
→ HTTP 웹훅으로 최종 결과 대기
```

첫 무응답에는 재시도하고, 1차 무응답 재시도 3회를 소진하면 요청에서 허용한 경우 즉시 TCP 2차 발송으로 전환합니다. 1차 만료 시에도 요청에서 허용했다면 2차 발송합니다. 실제 1차 처리 여부가 불명확하면 외부 중복 가능성이 남습니다. 운영 확인 중인 건도 만료 시 동일하게 전환합니다. 수동 처리는 만료 시간 내에만 가능하고 기한을 연장하지 않습니다. 2차 비허용 또는 2차까지 만료된 건은 고객 결과 제공으로 이어지며 전체 최대 기한은 테스트 기준 7시간입니다. 장기 장애 대상은 복구 후 만료 처리하며 고객 결과는 같은 고객별 최대 100건으로 짧게 묶어 HTTP 전송합니다.

## 8. Receipt 인입

**예정**

```text
Provider callback
→ 인증/서명 검증
→ DeliveryReceiptReceived Kafka 발행
→ Kafka ack
→ Provider에 2xx
```

Receipt API는 요청 thread에서 최종 상태를 계산하거나 PostgreSQL 이력을 저장하지 않습니다. 웹훅 장기 미수신은 만료 처리합니다. 테스트 기준은 1차 3시간·2차 4시간이며 각각 설정으로 변경할 수 있게 합니다. 전체 최대 기한은 인입부터 7시간입니다. 1차는 인입 시각, 2차는 1차 결과 판단 시각(전환 대상 응답/웹훅 수신, 1차 만료 또는 무응답 재시도 소진 판단)을 기준으로 고정합니다. 만료 후 해당 단계의 웹훅은 로그만 남기고 폐기하며 업무 데이터에 저장·연결하지 않습니다. 만료 경계의 경합 처리는 Q6에서 추가 결정합니다. 2차 최종 결과도 HTTP 웹훅으로 수신합니다. TCP 응답은 수신·접수 확인이며 최종 발송 성공을 뜻하지 않습니다.

## 9. 최종 상태 확정

**예정**

```text
DeliveryReceiptReceived consume
→ providerEventId dedupe
→ 허용된 상태 전이 검사
→ DynamoDB terminal 상태 conditional update
→ DeliveryFinalized 발행
```

Receipt가 Provider HTTP 응답보다 먼저 도착해도 terminal 상태가 이전 상태로 돌아가지 않게 합니다.

## 10. 최종 결과 Fan-out

**예정**

```text
delivery.finalized.v1
├─ History Consumer Group
├─ Usage Consumer Group
├─ Client Callback Consumer Group
└─ Statistics Consumer Group
```

각 Consumer Group은 독립 offset과 멱등성 key를 사용합니다.

## 11. 구간별 DynamoDB write 기준

| 구간 | Write | 이유 |
|---|---|---|
| API 접수 | 없음 | Kafka ack가 접수 원장 |
| Delivery 원본 projection | 1회 | 조회와 idempotency 충돌 확인 |
| 단순 payload 변환 | 생략 | 원본에서 재계산 가능 |
| Provider Attempt claim | 1회 | 외부 호출 중복 방지 |
| Provider 성공 응답 | 1회 | 완료 중복 skip와 복구 판단 |
| Provider 실패/UNKNOWN | 예정 | Retry/Fallback 판단 |
| Retry 예약 | 필수 | 횟수, deadline, 다음 실행 시각 |
| Receipt 상태 전이 | 필수 | 중복과 순서 역전 방지 |
| 로그/메트릭 | 생략 | Loki/Prometheus 사용 |

완료 후 원본·활성 상태 정리와 고객 HTTP 통지의 안전한 인계는 [상세 설계](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)를 따릅니다. 호처리에 필요한 실행·멱등 상태만 DynamoDB에 최소 저장하고 종료 후 작은 완료 기록을 유지하기로 확정했습니다. 보관 기간 확정 전에는 완료 기록을 자동 삭제하지 않습니다.
