# 함께 결정할 설계 사항

작성일: 2026-09-23. 완료 후 멱등 정책 갱신: 2026-09-25. 사용자와 합의한 요구사항과 미확정 제안을 구분합니다. 답변이 없는 항목을 기본 선택으로 확정하지 않습니다. 기술 근거는 [저장소 특성과 내구성](07-저장소별-특성과-데이터-유실-복구-조건.md), 저장소 배치 제안은 [ADR-002](adr/ADR-002-저장소-역할과-선택-이유.md)에 분리합니다.

## 1. 확인된 요구사항

- DynamoDB는 호처리에 필요한 실행·멱등 상태에 최소한으로 사용한다. 멱등성이 필요한 구간에 저장하며, 불필요한 원본 복제·상세 데이터·갱신을 줄인다.
- 무손실을 유지하면서 최대한 무중단 운영한다. 내구성 조건을 만족하지 못한 구간만 중단하고, 정상 구간의 접수·처리는 계속한다.
- 리전 전체 장애를 제외하면 데이터 유실을 허용하지 않는 것을 설계 목표로 한다. 접수 원본과 실행·복구·최종 결과 기록을 보존하며, 구체적인 장애 조합과 실제 보장은 Q3의 배치·설정·시험으로 입증한다.
- 고객에게 웹훅을 보내는 기능보다 외부 1차·2차 발송이 핵심이다.
- 발송 멱등성은 우리 시스템에서 책임진다. 외부의 중복 방지는 보조 수단이며 정확성 보장의 전제로 삼지 않는다.
- 실제 업체·API 대신 직접 만든 외부 발송 시뮬레이터를 사용한다. 발송 결과 조회 API는 제공하지 않는다.
- 1차 발송은 HTTP, 2차 발송은 TCP/IP 소켓 통신으로 구현한다.
- 2차 TCP 업무 응답은 요청 수신·접수 확인이며 최종 발송 성공을 뜻하지 않는다. 최종 결과는 HTTP 웹훅으로 받는다.
- 2차는 다른 업체로의 대체 발송이다. 최초 메시지에서 2차 발송을 설정한 경우에만 허용한다.
- 1차 응답 또는 업체의 결과 웹훅으로 받은 실패 에러 코드에 따라, 지정 시간 후 1차 재시도와 2차 발송을 구분한다.
- 응답이 없으면 최대 3회 재시도한다. 1차 무응답 재시도를 소진하면 최초 요청에서 2차를 허용한 경우 만료까지 기다리지 않고 즉시 TCP 2차 발송으로 전환한다.
- 발송 시도 기록 이후 프로세스 종료로 결과가 남지 않은 건은 운영 확인으로 넘긴다. 운영 확인 중에도 만료 시간은 연장·중지하지 않으며, 운영자는 만료 시간 내에 처리해야 한다.
- 운영 확인 중인 1차도 만료 시 요청에서 2차를 허용했다면 자동 TCP 2차 발송으로 전환한다. 고객에게 최대 만료 시간 내 결과를 제공해야 한다.
- 1차 만료는 인입 시각, 2차 만료는 1차 결과를 판단하여 2차 전환을 결정한 시각을 기준으로 한다. 응답·웹훅에 의한 전환이면 해당 응답 수신 시각, 1차 만료에 의한 전환이면 1차 만료 시각, 무응답 재시도 소진에 의한 전환이면 소진을 판단한 시각으로 한 번 고정하며 중복 응답으로 연장하지 않는다. 테스트 기준값은 1차 3시간, 2차 4시간으로 다르게 두며 각 기간은 독립적으로 설정할 수 있게 한다.
- 1차 만료 시 최초 메시지에서 2차를 허용했다면 대체 발송한다.
- 만료 후 해당 단계의 웹훅은 로그만 남기고 폐기한다. 업무 데이터와 연결·저장하거나 결과를 정정하지 않는다.
- 장기 장애에 묶인 작업은 복구 후 만료 처리한다. 장기 장애 대상의 판정 기준은 구체화한다.
- Redis 장애 시 TPS·Quota는 모두 제한 없이 우회한다.
- 완료 후에는 PostgreSQL 이력·통지 예약 저장 확인 뒤 DynamoDB 원본·STEP을 정리하고 Redis TTL로 고객+ClientMsgId를 차단한다. Redis 유실 시에도 DDB 선점·멱등 조건까지 통과하면 재발송을 허용한다. 작은 DDB 완료 기록 의무 보관의 이전 정책을 대체한다. [최신 멱등 정책](11-멱등-정보-보관과-완료-후-정리-방식.md)은 확정, v2 코드에 적용했다. TTL은 최종 확정+24시간을 PoC 기본값으로 두었으며 운영 값은 조정할 수 있다.
- 고객 결과는 HTTP로 같은 고객끼리 최대 100건 묶어 전송하되, 건수를 채우느라 오래 기다리지 않는다.
- 설계의 이유와 한계를 공식 문서에 근거해 남긴다.

Provider에서 결과를 수신하는 Receipt API는 실패 판단의 입력이다. 고객에게 결과 웹훅을 발송하는 기능과 구분한다.

## 2. 함께 결정할 항목과 논의 순서

### 구현 착수 기준 — 논의는 필요한 시점으로 미룬다

사용자는 세부 운영값을 모두 확정하기보다 꼭 필요한 논의만 하고 구현을 진행하도록 요청했다. 현재 접수·외부 발송·멱등 상태·단계별 만료의 핵심 정책은 정해져 있으며, **현재 접수 구간 구현을 시작하기 전에 추가로 답변받아야 하는 항목은 없다.** 아래 미정 목록은 구현 전체의 선행 승인 목록이 아니다.

- **호환 경로:** 신규 v2는 최신 Redis 완료 정책을 사용한다. 기존 v1 완료 기록은 유지하며 일괄 삭제하지 않는다. 새 정책에서도 SQL 이력·통지 예약의 내구성 인계 전에는 원본을 삭제하지 않는다.
- **설정으로 분리:** timeout·재시도 간격·묶음 대기 시간은 개발 기본값과 운영 확정값을 구분한다. 테스트용 업체 코드표와 통신 형식은 확정된 업무 규칙에 맞춰 구현자가 작성한다.
- **해당 기능에서만 필요:** 고객 서버 장애 때의 결과 제공 방식과 20회 재전송 소진 처리, 아직 기한이 남은 요청을 장기 장애 복구 후 강제로 만료할 범위는 업무 결과에 영향을 주므로 해당 기능 구현 시 미정 상태를 확인한다. 정상 요청의 기한을 임의로 줄이지 않는다.
- **운영 준비로 연기:** 멱등·Kafka·이력 보관 기간, 과거 수동 재처리 허용 기간, 용량·비용·복구 시간은 삭제·운영 재처리·배포 전에 확정한다. 전체 목표 TPS는 10,000으로 확정했으며 Pod별 한계 측정과 튜닝은 개발 완료 후 진행한다. 개발 시작의 차단 조건으로 두지 않는다.

### 기존 결정과 추적 목록

한 번에 하나씩 논의한다. **발송 경로·재시도 3회·소진 후 전환·운영 확인 중 만료·늦은 웹훅 폐기·TCP 접수와 HTTP 최종 결과 통지는 확정했다. 만료 테스트 기준은 1차 3시간, 2차 4시간이며 전체 최대 기한은 7시간이다. Q3은 리전 전체 장애를 제외한 무손실 목표로 확정했다. Q5는 무손실을 유지하면서 필요한 구간만 중단하고 최대한 서비스 지속하는 방향으로 확정했다. [저장소별 중단·복구 절차](09-저장소-장애-시-중단-범위와-복구-절차.md)를 추가했다. 장기 장애 복구 후 만료, Redis TPS·Quota 우회, 고객별 최대 100건 HTTP 결과 통지도 확정했다. 고객 결과 웹훅은 최대 20회 재전송(최초 포함 최대 21회)한다. 완료 후 작은 DynamoDB 기록 의무 보관은 최신 Redis TTL 정책으로 대체했다. Redis 유실 시에도 DDB 선점 조건까지 통과하면 재발송을 허용한다. TTL 길이·기준은 설정으로 분리했고 v2 코드·식별자에 적용했다.** 확정된 답과 구현 제안은 구분해 기록하며 재시도 간격 등 남은 세부 정책은 목록에서 계속 추적한다.

1. **1차·2차 발송의 관계 — 확정**: 요청에서 허용한 경우에만 다른 업체로 대체하며, 에러 코드별 1차 재시도도 지원한다.
2. **외부 연동 전제 — 확정**: 자체 시뮬레이터 사용, 외부 중복 방지에 의존하지 않음, 결과 조회 API 없음.
3. **유실 방지 범위 — 목표 확정**: 리전 전체 장애는 제외하고 그 외 장애에서 접수 데이터·복구 기록 유실을 허용하지 않는다. 구체적 장애 조합별 충족 여부는 설계·검증으로 확인한다.
4. **발송 완료의 기준 — 확정**: 업체 접수 응답과 최종 결과를 구분한다. 결과 웹훅 또는 만료로 종료하며 고객 결과 통지는 별도로 처리한다.
5. **장애 중 접수·발송 정책 — 기본 방향 확정**: 내구성 미충족 구간만 중단하고 정상 구간은 유지. 장기 장애 복구 후 만료와 Redis TPS·Quota 전부 우회 확정. 장기 장애 대상·허용 복구 시간은 미정.
6. **결과 불명 처리 — 기본 방향 확정**: 무응답 재시도, 프로세스 종료 후 미완료 시도는 운영 확인, 웹훅 장기 미수신은 만료. 3회 재시도와 만료 후 조건부 2차 전환·늦은 웹훅 폐기를 확정. 2차 기준은 1차 결과 판단 시점으로 확정. 1차 무응답 소진 시 즉시 2차 전환도 확정. 운영 확인 중에도 만료 정책 적용을 확정. 테스트 기준 1차 3시간·2차 4시간·전체 최대 7시간 확정. 재시도 간격 등은 논의 중.
7. **종료 후 정리 — 최신 방식 확정**: SQL 이력·통지 저장 후 DDB 정리, 완료 후 Redis TTL 차단. Redis 유실+DDB 조건 통과 시 재발송 허용. TTL 길이·기준 시점 미정.
8. **DynamoDB 사용 범위 — 방향 확정**: 호처리의 실행·멱등 판단에 필요한 구간에 최소 저장. 전체 목표는 10,000 TPS로 확정. Pod별 성능·payload 크기·실제 비용 측정은 개발 완료 후 성능 단계에서 진행.

Q1~Q8은 위 목록 번호에 대응한다. Q2의 확정 결과에 따라 Q6를 먼저 논의한다. AZ는 한 리전 안의 분리된 장애 영역이며, 리전 전체 장애 요구는 다른 AZ 배치만으로 충족되지 않는다.

### Q1 확정 내용과 남은 세부 정책

**근거:** 2026-09-23 사용자 요구사항 확인. 업체 기능에 대한 공식 문서상의 보장이 아니라 이 시스템이 지원해야 할 업무 규칙이다.

| 입력·조건 | 요구되는 처리 |
|---|---|
| 1차 응답 또는 결과 웹훅의 실패 코드가 1차 재시도 대상으로 설정됨 | 지정된 지연 후 같은 1차 업체로 재시도. 1초·10초는 사용자 예시이며 공통 기본값은 미정 |
| 실패 코드가 2차 전환 대상으로 설정되고 최초 메시지에서 2차를 허용함 | 다른 업체로 2차 발송 |
| 최초 메시지에서 2차를 허용하지 않음 | 2차 발송 금지. 1차 재시도 허용 여부는 해당 코드의 정책으로 판단 |

**선택 이유:** 일시적인 실패에는 1차 재시도를 적용하고, 대체 발송은 요청자의 최초 의사와 오류 정책에 따라 제한한다.

**남은 결정:** 업체별 코드 분류·지연 시간·재시도 3회의 적용 범위, 한도 소진 시 처리, 분류되지 않은 코드, 2차 비허용 시 종료 처리, 2차 자체의 재시도 정책. 1차 무응답 재시도 소진 시에는 즉시 2차 전환한다. 명확한 실패 코드의 재시도 소진·2차 비허용·2차 자체 소진의 처리는 별도 미정 사항이다. 코드가 실제 미접수 또는 최종 전달 실패를 뜻하는지는 아래 시뮬레이터 계약에 명시한다. 응답이 없거나 결과가 불명확한 경우의 처리는 Q6에서 정한다.

**검증할 조건:** 응답과 결과 웹훅 양쪽의 코드 분류, 지정 지연 후 재시도, 최초 메시지의 2차 허용 여부, 중복·역순 결과 수신 시 재시도 또는 2차 발송 중복 실행 방지.

### Q2 확정 내용과 보장 한계

**근거:** 2026-09-23 사용자 요구사항 확인. 실제 업체와 API는 없으며, 임의의 URL을 갖는 테스트 서버로 외부 발송을 재현한다. 외부의 중복 방지는 일부 존재할 수 있으나 신뢰하지 않고, 우리 시스템의 중복 제어를 검증한다. 발송 결과 조회 API는 없다. Q1의 결과 웹훅 수신은 유지한다.

**공식 근거:** [AWS Builders’ Library — Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)는 응답이 없을 때 호출자가 외부 처리 여부를 알 수 없으며 단순 재시도가 중복 효과를 만들 수 있음을 설명한다. 검토일: 2026-09-23, 웹 문서(고정 제품 버전 없음).

**프로젝트 판단:** 내부 요청·이벤트 중복 제거, 동시 작업 선점, 기록된 완료의 재발송 차단은 우리 시스템의 책임이다. 그러나 외부 처리와 내부 완료 저장 사이를 하나의 트랜잭션으로 묶을 수 없으므로, 내부 DB만으로 다음 두 상황을 구분할 수 없다.

| 실제 외부 상태 | 우리 시스템에 남은 정보 |
|---|---|
| 외부가 발송을 처리했지만 응답과 결과 웹훅을 받지 못함 | 호출 진행 기록만 있고 결과 없음 |
| 외부가 발송을 처리하지 못했고 응답과 결과 웹훅도 없음 | 호출 진행 기록만 있고 결과 없음 |

두 상황에서 자동 재발송하면 전자는 중복될 수 있고, 재발송하지 않으면 후자는 전달을 완료하지 못할 수 있다. 호출 전 완료로 기록하는 방식이나 lease 만료 후 무조건 재호출하는 방식으로 이 차이를 해결할 수 없다. 원본과 UNKNOWN을 보존하는 것은 업무 유실 방지에 필요하지만 최종 전달 성공의 보장은 아니다. 사람이 확인하더라도 새로운 증거가 없으면 한계는 같다.

**Q6 후속 결정:** 사용자는 응답 미수신 시 재시도, 프로세스 종료 후 결과 미기록 건은 운영 확인, 웹훅 장기 미수신은 만료로 처리하도록 정했다. 이는 앞선 일괄 보류 제안을 대체한다. 무응답 재시도에는 외부 중복 가능성이 남으며, 외부 효과 0회 중복을 보장하는 설계라고 표현하지 않는다.

### Q2 통신 방식과 TCP 계약

**사용자 확정:** 1차는 HTTP 발송, 2차는 TCP/IP 발송이다. 2차는 HTTP 호출로 대체하지 않고 TCP 소켓으로 업무 메시지를 교환하는 형태로 해석한다. 현재 구현은 HTTP 시뮬레이터만 있으므로 TCP 송신 클라이언트와 수신 서버를 추가해야 한다.

**공식 사실:** TCP는 신뢰성 있는 순서 보장 바이트 스트림을 제공하며, 송수신 메시지 경계를 보장하지 않는다. SEND 호출은 애플리케이션 구현에 따라 로컬에서 바로 반환할 수도 있다. [RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2), [§3.7](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.7), [§3.9.1.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.9.1.2). 검토일: 2026-09-23, 표준 RFC 9293.

**프로젝트 판단:** 연결 성공·소켓 쓰기 완료·TCP 계층 ACK만으로 업체 애플리케이션의 발송 접수나 최종 전달 성공을 판정하지 않는다. 업무 메시지 단위의 응답과 요청 식별자 연결이 필요하다. TCP를 사용해도 외부 처리 후 응답 유실 문제는 동일하다.

**사용자 확정 — 응답 계약:** A안으로 결정했다. 2차 TCP 서버는 요청을 잘 수신했다는 업무 응답을 보내고, 최종 발송 결과는 HTTP 웹훅으로 통지한다. TCP 접수 확인만으로 발송 성공·전체 완료를 기록하지 않는다. 결과 웹훅은 기존 단계별 만료 정책을 적용하며 만료 후에는 로그만 남기고 폐기한다.

**구현할 계약:** 응답을 올바른 요청과 연결할 식별자를 포함한다. 접수 거절이 필요한 경우의 형식·오류 코드, 응답 전 시뮬레이터가 보장할 저장 범위는 세부 명세로 남긴다. TCP 업무 응답은 전송 계층 ACK와 구분한다. 성공 접수 응답을 기록한 요청은 최종 웹훅이 아직 없다는 이유로 다시 발송하지 않고, 응답 미수신 재시도와 웹훅 대기를 구분한다.

**설계자가 구체화할 사항:** 메시지 길이 표시와 인코딩, 최대 길이, 부분 수신·여러 메시지 합쳐 수신 처리, 요청-응답 식별자, 연결 재사용·동시 요청 수, 연결·응답 제한 시간·재연결 처리. 길이 헤더와 UTF-8 JSON을 사용하는 형식은 후보이며 코드 규격 확정이 아니다. 사용자에게 모든 필드와 소켓 설정을 하나씩 선택하도록 요구하지 않고, 확정한 업무 응답 계약에 맞춰 설계안을 만든다.

### Q3 리전 전체 장애를 제외한 무손실 목표

**사용자 확정:** 리전 전체 장애가 아니라면 데이터가 유실되어서는 안 된다. 이 목표를 단일 서버나 단일 AZ 장애만의 요구로 축소하지 않는다. 리전 전체 장애 시 무손실 전환은 현재 필수 범위에서 제외한다.

**설계에 반영할 내용:** 접수 원본뿐 아니라 실행 상태·재시도 예약·단계 전환·멱등 판단·최종 결과 발행의 복구 근거를 유지한다. 프로세스 종료, 서버·디스크 손실, AZ 손실, 네트워크 분리, 저장소 장애, 잘못된 삭제·논리 손상 및 복합 장애에 대해 어떤 사본/원장으로 복구할지 정한다. 아래는 구현 후보이며 운영 보장 검증 완료를 의미하지 않는다.

| 영역 | 반영할 설계 | 근거와 확인 사항 |
|---|---|---|
| Kafka 최초 접수 | 장애 영역을 분리한 복제와 쓰기 확인 후에만 접수 성공. 복제 조건 미충족 시 성공 응답 금지 | `acks=all`과 `min.insync.replicas`를 함께 설정. RF=3·minISR=2는 검토 출발점이며 모든 비리전 장애를 보장하는 설정은 아님 |
| 실행·멱등 상태 | 성공 저장과 조건부 갱신을 기준으로 복구하고, 외부 호출 전에 필요한 기록을 남김 | DynamoDB 리전 내 다중 AZ 복제와 성공 쓰기 내구성은 선택 근거. Kafka·HTTP/TCP와 단일 트랜잭션이 되는 것은 아님 |
| PostgreSQL 원장/이력 | 원장으로 쓸 데이터는 확인된 복제와 승격 조건 검증. 재구축할 이력은 원본과 재생 기간 확보 | 비동기 복제의 미반영 commit 손실을 무손실로 간주하지 않음 |
| Redis | 소실돼도 원본·발송 판단·결과를 복구할 수 있게 역할 제한 | 기본 비동기 복제와 WAIT는 모든 failover의 무손실을 보장하지 않음 |
| 단계 인계·보관 | 저장 후 다음 이벤트 발행 누락을 복구하고 원본의 조기 삭제를 막음 | Kafka retention은 미처리 여부와 무관하게 작동. 업무 만료 3/4시간과 데이터 보관 기간은 별개 |
| 논리 손상·삭제 | 복제 외에 보호·백업·변경 기록과 복원 절차 설계 | 삭제가 복제되거나 백업 시점 이후 쓰기가 사라지는 경우까지 단순 다중 AZ로 해결됐다고 주장하지 않음 |

**공식 근거:** [Kafka 4.0 topic 설정](https://kafka.apache.org/40/generated/topic_config.html#min.insync.replicas), [DynamoDB 복원력](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/disaster-recovery-resiliency.html), [DynamoDB 성공 쓰기 내구성](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html), [PostgreSQL 17 복제](https://www.postgresql.org/docs/17/warm-standby.html), [Redis 복제](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/). 검토일: 2026-09-23. 제품의 사실과 위 프로젝트 적용 판단을 구분한다.

**충족 판정:** '리전이 살아 있으므로 무조건 안전'이라는 제품 보장은 없다. 저장 사본 전체 소실이나 복제되는 논리 손상은 리전 전체 장애가 없어도 발생 가능한 장애 유형이므로 각각 복구 근거를 입증해야 한다. 현재 로컬 단일 노드 구성은 이 범위를 충족했다고 볼 수 없다. 각 장애 조합의 RPO 0 충족·미충족·미검증을 명시하고, 증거가 없는 항목을 통과로 처리하지 않는다. 무손실 데이터 보존은 외부 중복 0회나 장애 중 서비스 무중단과 다른 조건이다.

**Q5 사용자 확정 — 운영 방향:** 필요한 내구성 조건을 확인할 수 없으면 해당 작업을 중단하되 최대한 서비스는 지속한다. Kafka 접수 원장이 안전하면 실행 DB 장애 중에도 접수·보관은 가능하지만, Kafka 저장 확인이 안 되면 접수 성공을 반환하지 않는다. 발송 상태를 안전하게 저장·판단할 수 없으면 외부 호출을 보류하고 회복 후 원장에서 재개한다. 이는 모든 저장소 장애에 API 전체를 일괄 중단한다는 뜻이 아니다. 저장소별 감지·중단·복구와 현행 코드의 차이는 [운영 절차](09-저장소-장애-시-중단-범위와-복구-절차.md)에 분리한다. 문서의 세부 구현안이 모두 구현·검증되었다는 뜻은 아니다.

무손실을 위해 중단하는 시간이 고객 결과 기한을 넘을 수 있는 상황은 기한 내 결과 제공 요구와 함께 검토해야 한다. 만료 시각은 계속 유지하며 장애를 이유로 재계산하지 않는다. 데이터 보존을 유지한 것만으로 장애 중에도 고객에게 결과를 제때 전달했다고 주장하지 않는다. 장기 장애 복구 후 미완료 대상은 만료 결과를 HTTP로 제공하는 방향으로 확정했다. 장기 장애의 대상 구분과 허용 복구 시간은 미정이다.

### Q6 확정 내용과 남은 결정

**근거:** 2026-09-23 사용자 요구사항 확인. 아래 정책은 이전의 '만료 후 전환 금지·늦은 웹훅 보존 및 정정' 제안을 대체한다.

| 상황 | 확정된 처리 | 남은 세부 사항 |
|---|---|---|
| 응답 미수신 | 최대 3회 재시도 | 최초 호출 제외 3회(최대 총 4회)로 해석한다. 단계별 한도 적용·간격은 미정 |
| 1차 무응답 재시도 3회 소진 | 요청에서 2차를 허용했다면 즉시 TCP 2차 발송 | 만료까지 기다리지 않음. 소진 판단 시각으로 2차 만료 기준 고정. 2차 비허용 시 종료 처리는 미정 |
| 발송 전 DB에 시도 기록 후 프로세스 종료, 결과 미기록 | 만료 시간 내 운영 확인. 만료 시 자동 정책 적용 | 운영 확인이 기한을 중지·연장하지 않음. 1차 만료 시 허용 요청은 자동 2차 발송 |
| 1차 만료 | 인입 시각 기준. 최초 메시지에서 2차를 허용한 경우 대체 발송 | 테스트 기준 3시간. 운영 확인 중인 건도 동일하게 전환 |
| 2차 만료 | 테스트 기준 4시간. 1차 결과 판단 시점 기준으로 한 번 고정. 전환 대상 응답/웹훅 수신 시각, 1차 만료 시각 또는 무응답 재시도 소진 판단 시각 | 중복 응답·재처리로 기한을 연장하지 않음. 2차 실제 발송 시작 시각으로 다시 계산하지 않음 |
| 만료 후 해당 단계의 웹훅 도착 | 로그만 남기고 폐기 | 업무 데이터·이력에 연결·저장하지 않고, 결과 정정·후속 발송에 사용하지 않음 |

**구현 제안:** 무응답을 관찰한 Worker는 사유와 다음 재시도 일정을 내구성 있게 저장한 뒤 재시도한다. 복구 Worker는 저장된 재시도 예정 건과 시작 기록만 남은 오래된 건을 구분하고 후자를 운영 확인 대상으로 인계한다. 무응답을 관찰했지만 기록을 저장하기 전에 종료된 경우도 후자에 포함한다. DB 기록 없이 재호출을 이어가면 이 구분을 유지할 수 없다.

lease 만료는 의심 작업을 찾는 기준이며 Worker의 사망이나 외부 미처리 증거가 아니다. 이전 Worker가 재개할 수 있으므로 상태·version 검사를 적용하되 진행 중인 외부 요청을 내부 version만으로 취소할 수 있다고 가정하지 않는다. 운영 확인은 만료 처리를 막지 않는다. 만료된 1차는 요청에서 허용한 경우 자동 2차 전환하며 운영자 개입도 정해진 시간 안에서만 처리한다. 구현에서는 운영자 변경과 만료 처리에 같은 상태·version·기한 조건을 적용해 어느 한쪽의 전이만 성립하게 하고, 만료 후 기존 단계의 수동 재발송이나 결과 덮어쓰기를 막는다.

**자동화 범위:** 대상 탐지·알림·시도 이력·운영 판단 기록은 자동화할 수 있다. 만료 전 유효한 결과 웹훅은 판단 근거로 사용할 수 있다. 만료 후 웹훅은 사용자 정책에 따라 업무 데이터와 연결하지 않는다. 외부 조회·신뢰할 수 있는 멱등성·수신 결과 증거가 없으면 실제 발송 여부는 완전히 자동 판별할 수 없다. 운영자도 내부 기록만으로 판정할 수 없으며 증거가 없는 건은 미확인 상태 또는 명시적인 재발송 결정을 기록해야 한다.

**보장 범위:** 무응답 재시도와 1차 만료 후 2차 발송은 이미 처리된 외부 발송과 중복될 수 있다. 만료는 정책상 대기 종료이며 실제 외부 미발송의 증거가 아니다. 만료 후 웹훅을 폐기하면 업무 상태는 그 결과로 정정되지 않는다. 이 설계를 외부 중복 0회 또는 외부 실제 결과와 항상 일치하는 상태 보장으로 설명하지 않는다. 기술 근거는 Q2의 AWS 공식 설명과 위 내부·외부 기록 경계 분석을 따른다.

**남은 결정:**

1. 재시도 간격·단계별 한도 적용 범위. 1차 무응답 소진 시 허용 요청의 즉시 2차 전환은 확정했다. 명확한 실패 코드의 재시도 소진, 2차 비허용 요청과 2차 자체 재시도 소진 후 처리만 남는다.
2. 인입 시각의 정확한 정의와 고객 HTTP 통지의 ack·재전송 세부 계약. 테스트 기준 1차 3시간·2차 4시간·전체 최대 7시간, 운영 확인 건의 자동 만료·허용된 2차 전환은 확정이다. 운영 환경의 기간은 별도 설정으로 둔다.
3. 만료 경계에 먼저 수신되어 큐에서 대기한 웹훅과 만료 처리의 경합. **개발 구현 기준:** 처리 진입 시각도 만료 전이어야 결과를 반영하며, 이미 기한이 지난 큐 대기 결과는 폐기한다. 장기 장애 복구 시 만료 우선 요구를 적용한 구현 판단이며, 주기 만료·수동 처리와의 동시 실행 검증은 후속이다. [현재 구현과 검증](27-웹훅-결과-반영과-재시도-대체-발송-복구.md).

만료 판정과 물리 삭제를 같은 작업으로 처리하지 않는다. 발송 종료 후 SQL 이력·고객 통지 예약 저장을 확인하고 DDB를 정리하는 최신 방식은 [멱등 정책](11-멱등-정보-보관과-완료-후-정리-방식.md)에 따른다. 이후 Redis TTL로 중복을 차단하며 Redis 소실+DDB 조건 통과 시 재발송을 허용한다. 늦은 웹훅의 로그는 업무 결과 저장소나 자동 복구 근거로 사용하지 않는다. 어떤 단계에 대한 늦은 결과인지 구분해, 1차 만료 뒤의 1차 웹훅은 폐기하되 진행 중인 2차의 정상 웹훅까지 버리지 않아야 한다.

**검증 계획:** 운영 확인 중 만료 시 허용/비허용 분기, 수동 처리와 만료 전환의 동시 실행, 만료 후 수동 변경 차단, 고객 결과 기한 초과 탐지, 재시도 한도, 1차 무응답 소진 즉시 2차 허용/비허용 분기, 소진 판단 시각의 고정과 중복 소진 이벤트의 전환 중복 차단, 무응답 기록 저장 전/후 종료, 외부 처리 전/후 timeout, 만료 시 2차 허용/비허용 분기, 중복 만료 작업의 2차 발송 중복 차단, 늦은 1차 웹훅의 로그 후 폐기와 진행 중 2차 상태 불변, 늦은 2차 웹훅 폐기, 만료·웹훅·재시도 예약의 경합을 검증한다. 업무 데이터 미변경과 로그 기록을 각각 검사한다.

### Q4 고객 결과 제공 기한

**사용자 확정:** 고객은 최대 만료 시간 내 결과를 받아야 한다. 운영 확인 때문에 결과가 무기한 보류되어서는 안 되며 운영자도 만료 시간 내에 처리해야 한다.

**현재 단계별 규칙의 의미:** 1차 만료 시 2차가 허용되어 있으면 전체 요청을 종료하지 않고 2차를 시작한다. 2차가 없거나 2차까지 만료되면 더 기다리지 않고 고객에게 종료 결과를 제공해야 한다. 이를 '실제 외부 발송 실패 확인'과 혼동하지 않도록 고객 결과에서 성공·확정 실패·결과 미확인 만료를 구분하는 표현을 제안한다. 응답 코드와 전체 종료 상태 이름은 아직 구현 계약으로 확정하지 않았다.

**기간 결정:** 인입 시각을 T0, 단계별 기간을 D1·D2라 하면 1차 기한은 T0+D1, 2차 기한은 1차 결과 판단 시각+D2다. 1차 만료에서 전환하는 최장 경로는 T0+D1+D2가 된다. 사용자 요청에 따라 테스트 기준은 서로 다른 **D1=3시간, D2=4시간**으로 둔다. 2차 미사용은 최대 3시간, 2차 사용은 최대 7시간이며 1차 결과가 일찍 확정되면 2차 기한도 앞당겨진다. 만료 작업 실행이나 재시작이 늦었다고 기준 시각을 뒤로 옮겨 기한을 늘리지 않는다.

**설정·검증 설계:** 1차와 2차 기간을 별도 설정으로 제공한다. 자동화 시험에서는 예를 들어 3초·4초의 짧은 설정 또는 제어 가능한 시계를 사용해 실제로 7시간을 기다리지 않고 경계 조건을 검증한다. 두 기간이 다르므로 2차가 1차 기간을 잘못 재사용하는 오류도 검사한다. 진행 중 요청에 설정 변경이 소급되지 않도록 접수 당시의 기간/정책 버전과 계산된 만료 시각을 유지하는 안을 제안한다. 설정 키·저장 위치는 구현 단계에서 정하며 현재 코드에 반영된 값은 아니다.

**후속 결정:** 장기 장애에 묶인 미완료 건은 복구 후 만료 처리한다. 이미 정상 완료된 결과는 유지한다. 아직 기한이 남은 요청까지 일괄 만료할지 등 대상 선정 기준은 구체화한다. 고객 결과는 HTTP로 같은 고객끼리 최대 100건까지 묶어 전송하며 장시간 대기하지 않는다. 최대 20회 재전송(최초 포함 최대 21회)은 확정했다. 짧은 대기 한도·ack·재전송 간격·소진 처리와 정리는 [고객 결과 통지 설계](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)에 정리한다. 발송 Worker와 독립된 만료 탐지·결과 발행 복구가 필요하다. 내부 상태를 만료로 바꾼 것만으로 고객이 결과를 수신했다고 판정하지 않는다. 현재 문서의 요구사항 기록은 운영 환경에서 이 기한 보장이 검증됐다는 뜻이 아니다.

### 시뮬레이터 개발·검증 항목

기존 `external-api-simulator`에는 `POST /api/v1/deliveries`, 메모리 기반 키 중복 제거, 성공/강제 500 응답이 구현되어 있다. 아래는 추가 개발 목록이며 구현 완료를 뜻하지 않는다.

- 1차 HTTP URL과 2차 TCP host/port를 분리한 클라이언트·테스트 서버 및 업체별 시나리오. 2차는 TCP 수신 확인과 HTTP 최종 결과 웹훅을 각각 생성한다.
- TCP 접수 확인 수신 후에는 최종 결과를 기다리며, 최종 웹훅 미수신만으로 TCP 발송 재시도가 발생하지 않는지 검증한다.
- TCP 메시지 부분 수신·합쳐 수신·중간 연결 종료·업무 응답 유실·응답 식별자 불일치 시험. 재연결 성공을 이전 요청 성공으로 판정하지 않는지 검증.
- 시도 순서별 응답 코드·지연: 1차 재시도 코드 후 성공, 2차 전환 코드, 2차 자체 실패.
- 외부 중복 방지 켜기/끄기와 기록 소실·보존 만료. 중복 방지를 끈 조건을 기본 검증에 포함하고 켠 조건은 비교 실험으로 사용한다.
- 미처리 후 응답 단절과 실제 처리 후 응답 단절을 별도 재현한다. 동일한 클라이언트 timeout으로도 외부 효과는 다를 수 있다.
- 성공·실패 결과 웹훅, 지연·중복·역순 수신, 영구 미수신 시나리오. 웹훅에 우리 요청/시도 식별자를 돌려주는 계약을 정한다.
- 테스트 전용 실제 처리 기록·건수로 내부 상태와 외부 효과를 대조한다. 이 기록을 운영 발송 로직이 조회해 복구하면 '결과 조회 API 없음' 전제를 우회하므로 금지한다.
- 동시 중복 요청, 완료 후 재전달, 발송 직후 프로세스 종료, lease 만료 후 이전 Worker 재개를 검증한다. 만료만으로 이전 Worker의 외부 호출이 차단됐다고 가정하지 않는다.

## 3. 시뮬레이터에서 정의할 외부 계약

가상 업체별 코드와 결과의 의미를 명세하고 테스트로 검증한다. 실제 외부 계약을 나중에 연결하면 공식 문서 URL·버전·확인 일자를 추가한다. 결과 조회는 이번 설계에서 제공하지 않으며, 중복 방지는 보조 기능의 동작 범위만 정의한다.

| 항목 | 확인할 내용 |
|---|---|
| key scope | 고객 계정, API, 수신 대상 중 어디까지 key가 유일해야 하는가 |
| 보존 기간 | 시작 시점, 갱신 여부, 최대 시간, 만료 후 동일 key 처리 |
| 동시 요청 | 같은 key의 동시 요청을 실제 업무 효과 한 번으로 수렴시키는가 |
| 입력 충돌 | 같은 key의 다른 payload를 거절하는가 |
| 불명확한 응답 | timeout/500/503 후 동일 key 재호출의 의미와 캐시된 오류 응답 처리 |
| 결과 조회 | 제공하지 않음. 내부 발송 로직에서 테스트 전용 관측 기록 접근 금지 |
| 결과 불명 | 응답·웹훅 미수신은 실패 확정 아님. Q6 정책으로 처리 |
| 2차 전환 근거 | 확정 미접수, 취소 완료, 최종 전달 실패를 증명하는 응답은 무엇인가 |
| 최종 결과 | 접수 후 실패·늦은 receipt·정정 이벤트·receipt 재시도 계약 |

이 목록은 [AWS의 멱등 API 계약 설명](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)을 참고한 프로젝트 연동 요구이며, 실제 Provider가 지원한다고 가정하지 않는다.

## 4. 기존 설계 검토에서 남은 항목

아래는 문서 검토 결과를 추적하는 목록이다. 신규 기능 완료나 ADR 변경 승인을 의미하지 않는다. 중요도 P0는 유실·실제 중복 가능성, P1은 비용·운영·정합성에 관한 항목이다.

요구사항을 정한 뒤에는 다음 순서로 기술 설계를 정리한다. 이 단계에서는 요구사항을 만족하는 대안과 공식 근거를 비교한다.

1. **저장소 역할** — 반드시 남겨야 할 원본·발송 상태·중복 방지 기록과 Redis에서 재구축할 수 있는 데이터를 구분한다.
2. **발송과 재시도 규칙** — 논리 발송 식별자, 시도 식별자, 작업 선점, 결과 불명 상태와 2차 전환 조건을 정한다.
3. **단계 사이의 유실 방지** — DB 저장과 다음 이벤트 발행 사이에 멈춘 작업을 찾아 이어가는 방법을 정한다.
4. **최종 결과 확정** — 늦은 응답·중복 결과·1차와 2차 결과의 순서 역전을 처리하는 규칙을 정한다.
5. **복구·비용·검증** — 보관 기간과 복구 절차, 실제 저장 비용, 장애 시험의 통과 기준을 정한다.

## 5. 설계를 확정하기 전 필요한 검증

### 데이터 보존과 업무 효과를 따로 측정

접수된 고유 Delivery 집합을 기준으로 각 건이 완료·미완료·UNKNOWN·격리 중 정확히 어느 상태인지 대조한다. retry는 미완료의 하위 분류로 두어 중복 합산하지 않는다. HTTP 202를 client가 관찰한 수만 세면 ack 후 응답 유실 건을 놓치므로 Kafka에 내구성 있게 접수된 집합과 구분한다.

원본 수와 Provider의 실제 부수 효과 수를 함께 기록한다. “재처리에서 원본이 복구됐다”만으로 중복 발송 방지가 검증되는 것은 아니다.

### 추가할 시험 후보

1. 완료 쓰기 직후 Redis primary 손실·오래된 replica 승격 및 snapshot 복원.
2. WAIT/WAITAOF 확인 수 미달, 연결 교체, 확인한 사본 소실 시 완료 판정.
3. 캐시 재구축 중 요청·오래된 완료 cache와 복원 원장의 불일치.
4. Provider 처리 후 응답/내부 완료 기록 유실, key 만료 후 replay.
5. Worker 정지 → lease 만료 → 새 Worker 실행 → 이전 Worker 재개.
6. 1차 UNKNOWN 상태와 2차 전환 경쟁, 늦은 1차 성공.
7. DB 상태 저장 후 다음 Kafka 발행 전 종료, DLT 자체 발행 실패.
8. retention을 넘는 Consumer 중단과 archive에서의 실제 복원.
9. PostgreSQL failover와 DynamoDB PITR 복원 후 원장·Provider 결과 대조.
10. Q3에 따라 서버·디스크·AZ 손실과 네트워크 분리·복합 장애에서 접수 집합 보존·상태 복구 시험. 리전 전체 장애 시 무손실 전환은 현재 필수 시험 범위에서 제외한다.

시험 통과는 명시한 조건의 증거다. 가능한 모든 장애에서 손실 확률이 0임을 실험으로 증명했다고 표현하지 않는다.

## 6. 앞으로 ADR에 남길 형식

각 결정에는 다음을 기록한다.

- 요구사항과 답해야 하는 질문.
- 공식 문서의 사실: URL, 해당 기능·설정, 검토 버전·날짜.
- 프로젝트 판단: 그 사실이 왜 이 선택을 지지하는지, 추론임을 표시.
- 대안과 기각 이유: 비용·지연·복잡도·복구 차이.
- 보장 범위와 반례: 어떤 장애를 다루고 무엇이 남는지.
- 데이터별 보존·복구 원본·멱등 key·단계 인계 방법.
- 선택한 실제 설정, 장애 시험과 측정 결과, 미확정 조건.

제품 문서에 기능이 있다는 사실은 운영 환경에서 그 기능을 켜고 검증했다는 뜻이 아니다.
