# 완료 데이터 정리의 동시 처리와 성능 검증

2026-09-25. [성공 결과 즉시 인계](39-성공-결과의-즉시-Kafka-인계와-복구-검증.md) 다음 작업이다. 이전 시험에서 고객 통지는 550건 모두 완료됐는데 정리는 182건만 끝난 시점이 있었다. 단일 worker가 최대 20건을 순차 정리한 뒤 1초 기다리는 구조를 개선한다.

## 1. 무엇을 바꿨나

기본 4개 작업자가 각각 최대 20건을 정리한다. 각 작업자는 **SQL에서 1건 선점 → DDB 검증·조건부 삭제 → SQL 완료**를 끝낸 뒤 다음 건을 선점한다. DDB 작업 동안 SQL 트랜잭션이나 연결을 잡아 두지 않는다. 현재 tick의 모든 작업자가 끝난 후 1초를 기다리며 같은 인스턴스의 tick이 겹치지 않는다.

| 설정 | 기본값 | 범위·의미 |
|---|---:|---|
| `DELIVERY_CLEANUP_ENABLED` | false | 정리 활성화 여부 |
| `DELIVERY_CLEANUP_CONCURRENCY` | 4 | 1~16개 작업자. 인스턴스당 실제 동시 정리 상한 |
| `DELIVERY_CLEANUP_BATCH_SIZE` | 20 | 작업자당 tick 최대 1~1000건 |
| `DELIVERY_CLEANUP_POLL_MS` | 1000 | 모든 작업자의 batch 종료 후 다음 tick까지 대기 |

기본값에서 tick당 최대 80건이다. 이는 80 TPS 보장이 아니다. DB 지연과 입력 적체에 따라 처리량이 달라진다. 선점한 데이터를 메모리 대기열에 대량 적재하지 않으며 빈 대기열이나 SQL 선점 오류를 만나면 해당 작업자는 그 tick을 끝낸다. DDB 실패는 기존 30초 뒤 재시도 규칙을 유지한다.

SQL 연결 풀 기본값 6은 유지한다. 4개 정리 작업자 외에도 결과 저장·고객 통지가 같은 풀을 쓰므로 연결 대기와 SQL 지연을 함께 봐야 한다. 동시성을 높이는 것은 DDB 사용 횟수를 줄이는 조치가 아니며 순간 요청량은 늘어날 수 있다.

## 2. 보존한 무결성·복구 경계

| 경계 | 보장 방식 |
|---|---|
| SQL 이관 전 원문 보존 | 이력·고객 통지 예약·정리 예약이 있어야 claim 가능. 저장 트랜잭션은 기존 그대로 |
| 같은 결과 동시 선점 방지 | `FOR UPDATE OF c SKIP LOCKED`와 UUID lease token·60초 lease 유지 |
| 다른 결과 병렬 정리 | 고정 작업자 수로 제한. 각 결과의 원자적 DDB 삭제는 그대로 |
| 오래된 worker의 SQL 완료·재시도 | `PENDING AND lease_token = ?` 조건 유지. token이 바뀌면 새 소유자의 상태를 수정하지 못함 |
| DDB 삭제 후 SQL 응답 유실 | SQL 예약을 유지하고 재시도. 이미 정리됐으면 중복 삭제 없이 수렴 |
| 같은 ClientMsgId의 새 실행 | DDB 실행 UUID·완료 이벤트·원문·STEP 버전 조건이 이전 실행과 새 실행을 구분 |
| DDB 장애 | SQL DONE으로 만들지 않음. retry 저장도 실패하면 lease 만료로 복구 |
| 종료·인터럽트 | 신규 작업 중지. 정상 종료는 최대 10초 기다린 뒤 작업 중단 요청. 미완료 예약은 SQL에 남음 |

`CleanupRepository.done()`은 SQL 변경 행 수를 반환한다. lease token을 잃어 변경 행이 0이면 `lease_lost`로 관측한다. DDB 삭제를 수행했다는 사실만으로 SQL 정리 완료 건수를 올리지 않는다. 이 변경은 추가 SQL 조회나 DDB 쓰기를 만들지 않는다.

lease는 DDB 외부 작업 자체의 중복 실행을 완전히 막는 잠금이 아니다. 60초를 넘기는 정지·장애에서는 여러 작업자가 같은 결과를 정리하려 할 수 있고, 이때 최종 방어는 기존 조건부 트랜잭션·불변 결과 대조·SQL token이다. lease 갱신이나 장기 장애 정책은 이번 변경에서 추가하지 않았다.

## 3. 관측과 검증 방법

- `delivery_cleanup_active`: 동작 중인 정리 작업자 수. 인스턴스의 설정 동시성 이하.
- `delivery_cleanup_duration_seconds`: 선점이 성공한 1건의 SQL 선점 시작부터 DDB 처리·SQL 완료/재시도까지. 실패·lease 상실도 포함하며 비어 있던 조회는 제외.
- `delivery_cleanup_events_total`: 기존 `compacted`, `already_compacted`, `retained`와 새 `lease_lost`.
- 기존 SQL cleanup PENDING/DONE, DDB API 호출·실패, 고객 수신 지연, Kafka lag를 함께 확인.

동시성 시험은 작업자를 의도적으로 멈춰 4건만 선점됐는지, 두 tick이 겹치지 않는지, 작업자당 최대 건수를 지키는지 검사한다. SQL 장애 시 반복 조회 중단, DDB 실패와 retry 저장 실패, 인터럽트, lease 상실의 관측도 확인한다.

실제 PostgreSQL·DynamoDB 시험은 두 worker 인스턴스가 같은 대기열의 12건을 처리하도록 하고, 각 건의 DDB 호출 1회·정리 완료·미저장 원문 보존을 대조한다. lease를 강제로 만료시킨 뒤 이전 token의 완료·재시도가 새 소유권을 훼손하지 않는지도 확인한다. 기존 SQL 원자 저장·통지·삭제 실패·새 실행 보호 시험도 실행한다.

```sh
# JAVA_HOME=JDK 21. UUID 시험 스키마·항목을 생성하고 정리한다.
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
POSTGRES_TEST_URL=jdbc:postgresql://localhost:15432/delivery \
./mvnw -pl delivery-result-worker -am test
./mvnw -DskipTests package
.poc-tools/venv/bin/python -m unittest discover -s scripts/poc -p 'test_*.py'
.poc-tools/venv/bin/python scripts/poc/full_flow.py

# 같은 새 코드·같은 입력에서 동시성만 비교한다. 실행별 별도 Docker 환경.
.poc-tools/venv/bin/python scripts/poc/full_flow_load.py --cleanup-concurrency 1
.poc-tools/venv/bin/python scripts/poc/full_flow_load.py --cleanup-concurrency 4
```

부하는 각 실행에서 10 TPS·100 TPS를 각각 5초 입력한다. Redis 조회 1초·DDB 복구 10분·성공 결과 즉시 인계는 동일하다. 입력 ID·고객 수신·SQL 결과·업체 호출·DDB 삭제를 전수 대조한 뒤 결과를 비교한다. 짧은 단일 측정이므로 지속 최대 TPS·다중 AZ 무손실·운영 비용 검증으로 해석하지 않는다.

## 4. 검증 결과

event-common 11개·delivery-result-worker 51개, 총 **Java 시험 62개 통과**(실패·오류 0). Kafka 환경 변수를 별도로 요구하는 기존 3개 시험은 미실행으로 구분했다. 새 정리 단위 시험 6개와 실제 DB 시험 2개는 모두 실행했다. 전체 모듈 패키징과 Python 시험 29개도 통과했다.

`full-flow-2626f4921959`에서 전체 기능 6개 시나리오를 모두 통과했다. 실제 Kafka·Redis·PostgreSQL·DynamoDB와 6개 앱을 연결해 고객 503 후 재전송, 정상 성공, 재시도, TCP 대체 발송, Redis 유실 복구, 1차·2차 만료를 대조했다. 최종 성공 4건·만료 2건의 고객 수신·이력·DDB 정리가 일치했다.

### 같은 코드의 동시성 1·4 비교

동시성 1 실행은 `full-flow-2b04503e20b8`, 동시성 4 실행은 `full-flow-30f9055cab1c`다. 두 실행의 모든 앱 JAR·검증 도구·부하 스크립트 해시가 같고, 정리 동시성만 다르다. 각각 552건(51+501), 551건(50+501)을 전수 대조했다. 경계 시각의 추가 iteration도 제외하지 않았으며, 모든 업체 호출은 요청당 1회이고 고객 결과·SQL 이력·DDB 정리가 일치했다.

| 100 TPS ×5초 입력, 실제 각 501건 | 동시성 1 | 동시성 4 |
|---|---:|---:|
| 업체 결과 p95 | 13.53초 | 17.33초 |
| SQL 저장 p95 | 14.26초 | 18.57초 |
| 고객 수신 p95 | 14.30초 | 18.65초 |
| 정리 완료 p95 | 39.83초 | 20.27초 |
| 입력 시작~모든 정리·적체 해소 관찰 | 49.25초 | 27.21초 |
| 입력·배출 포함 관찰 처리량 | 10.17 TPS | 18.41 TPS |

정리 p95는 약 49% 짧아졌고 관찰 처리량은 약 1.81배가 됐다. 반면 **고객 수신 p95는 약 30% 증가**했다. 전체 완료 시간은 개선됐지만 모든 구간이 빨라진 것은 아니다. 10 TPS 구간에서는 고객 수신 p95 3.77→3.61초, 정리 p95 5.26→4.63초였다.

### DDB 호출 횟수와 자원 대기

다음은 각 실행의 10/100 TPS 구간 합산이며 startup·검증 도구의 후속 DDB 읽기는 제외한다.

| 항목 | 동시성 1 | 동시성 4 |
|---|---:|---:|
| 입력 수 | 552 | 551 |
| 업무 읽기 API 호출 | 4,766 | 4,736 |
| 요청당 평균 읽기 | 8.63 | 8.60 |
| 성공 쓰기 API 호출 | 2,760 | 2,755 |
| 요청당 성공 쓰기 | 5.00 | 5.00 |
| 실패 트랜잭션 API 호출 | 73 | 68 |
| 결과 worker 정리 읽기/요청 | 3.00 | 3.00 |
| 결과 worker 정리 쓰기/요청 | 1.00 | 1.00 |

정리 자체의 DDB 호출 수는 같다. 두 실행 모두 정리의 `retained`·`lease_lost`는 발생하지 않았으며 최종 `compacted` 수가 입력 수와 같았다. 실패 트랜잭션은 dispatch 쪽 계측이며, 현재 카운터만으로 취소 사유를 모두 분류할 수 없다. 이 API 횟수는 실제 AWS RCU/WCU나 청구 금액이 아니다.

관측된 동시 정리 작업자 최대는 각각 1·4였다. SQL 연결 timeout은 양쪽 모두 0, 샘플 시점의 연결 대기 최대도 0이었다. 샘플 간 짧은 대기가 없었다는 뜻은 아니다.

정리 1건 평균 처리 시간(SQL 선점~완료 포함)은 **41.6ms→121.0ms**로 늘었다. 결과 worker의 DDB API 평균도 GetItem 6.13→18.43ms, Query 6.37→16.28ms, 삭제 트랜잭션 13.69→54.04ms로 증가했다. 개별 작업은 느려졌지만 여러 건을 동시에 진행해 전체 정리가 빨라진 것이다. 로컬 DDB 호출 지연과 앞단 업체 결과 지연이 함께 늘어 자원 경쟁이 후속 조사 대상이다. 단일 측정으로 그 내부 원인이나 운영 AWS에서의 동일 현상을 확정하지 않는다.

## 5. 다음 작업과 근거

기본 동시성 4를 적용하며, 배치 20·대기 1초·SQL 풀 6·Redis 1초·DDB 복구 10분은 유지한다. 더 큰 동시성을 기본으로 올리지 않는다. 다음은 **인입·발송 Kafka 적체와 DDB 호출 지연을 구간별로 분해**하고, 정리가 고객 수신에 주는 영향까지 고려해 동시성과 읽기 경로를 조정하는 작업이다. 이후 반복·지속 부하에서 안정적인 완료 TPS와 장애 복구 시간을 검증해야 한다. 이번 결과로 지속 100 TPS를 달성했다고 볼 수 없다.
