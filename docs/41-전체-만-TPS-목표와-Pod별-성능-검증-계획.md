# 전체 만 TPS 목표와 Pod별 성능 검증 계획

2026-09-25 사용자 요구사항과 진행 순서. 기존 [개발 중 병목 측정](40-완료-데이터-정리의-동시-처리와-성능-검증.md) 이후의 성능 작업은 이 계획을 따른다.

## 1. 확정된 요구사항

- 성능 부하 생성은 **k6**를 사용한다. Java/JUnit은 기능·저장소 통합 회귀를 맡고 외부 실행/수집 도구는 이름·역할을 별도로 기록한다. [도구 기준과 실행법](48-Java-중심-테스트와-외부-도구-사용-기준.md).
- 서비스 전체 최종 목표는 **10,000 TPS**다.
- 서비스별 **Pod 1개당 최대 성능**과 전체 목표를 만족하는 배치 구성을 알아야 한다.
- **전반적인 개발을 마친 뒤** 성능 관련 튜닝·설정을 진행하고, 그 구성을 기준으로 성능을 측정한다.
- 현재는 기능·장애 복구·운영 처리와 통합 검증을 우선한다. 진행 중 발견한 성능 병목은 기록하고 본격 튜닝 단계에서 다룬다.

기존 로컬 JVM·DynamoDB Local·5초 부하의 결과는 개발 중 병목 확인 자료다. Pod 자원을 제한한 지속 부하 측정이 아니므로 해당 TPS로 Pod당 한계를 정하거나 `10,000 / 로컬 TPS`로 운영 Pod 수를 산정하지 않는다.

## 2. 개발 완료 후 실행 순서

### 성능 단계는 언제 시작하는가 (2026-09-26)

최초 착수 기준은 다음 4개 작업 묶음이다. **DLT 인계 묶음은 로컬 PoC로 구현·검증했고, 현재 2~4번의 3개 묶음이 남았다.** 각 묶음이 커밋 1개라는 뜻은 아니며, 회귀에서 발견되는 문제에 따라 작업량이 달라진다. 특정 날짜나 작업 횟수로 완료를 보장하지 않는다.

1. DLT 미완료 조치 자동 재개, 미등록 DLT의 SQL 원문 보존·인계·보류·보관 공백 중단: 구현. partition별 명시 실행과 JSON 적체 출력 범위이며 운영 경보·보류 재조치는 아래 운영 작업에서 연결한다.
2. 결과 불명·고객 통지 소진·정리 보류를 확인하고 기한·감사를 지키며 처리하는 최소 운영 경로.
3. 지속 장애에서 복구 조회·재접속이 몰리지 않도록 제한하고, 복구 후 원래 기한으로 수렴하는지 검증. Redis/Lifecycle 애플리케이션 호출 제한은 구현했으며 SQL 통지/정리·DLT 및 클라이언트 내부 재접속 설정 점검은 남아 있다.
4. 종료·재시작·readiness와 주요 통합 회귀, 측정에 필요한 지표·실행 설정 확인.

이 기준을 통과하면 **성능 설정 점검·초기 튜닝 → k6로 Pod 1개 지속 성능 → 전체 10,000 TPS → 장시간·혼합·장애 시험**에 착수한다. 운영 화면 전체, Kubernetes 자동 확장, CDC·별도 과금 기능의 완성을 성능 착수 조건으로 추가하지 않는다. 다만 Pod별 결과를 내기 위해 CPU/메모리를 고정할 측정 환경은 준비해야 한다.

### 운영 조회 구현 후 바로 가능한 시험

| 단계 | 지금 가능한 범위 | 남은 조건 |
|---|---|---|
| Java 기능·저장소 통합 회귀 | 정상/재시도/대체/만료·DLT 복구·통지·정리와 운영 조회를 실제 로컬 저장소에서 검증 | 현재 실행 중인 표준 검증이며, 전체 결과는 진행 현황에 기록 |
| 운영 시나리오 PoC | 상태 조회·정리 재조치·결과 불명 수동 확정, 버전·기한·감사·응답 유실 후 재개와 기존 worker 인계 검증 | 인증·권한 연결, 소진 후 추가 전송 정책과 후속 운영 경보는 남음 |
| 전체 흐름·장애 재검증 | 기존 전체 흐름과 종료 시험을 새 변경 범위에 맞춰 수행 가능 | 실제 종료와 예외 주입을 구분. 모든 종료/장애 조합 검증 완료를 뜻하지 않음 |
| k6 기준 성능·Pod별 한계·전체 만 TPS | 아직 본격 측정 단계에 진입하지 않음 | 남은 운영 조치·복구 제한·종료/재시작 회귀 후 설정·자원·시나리오/SLO 확정 |

현재는 **기존 기능 회귀에 운영 상태 확인·정리 재조치·결과 불명 수동 확정을 추가한 단계**다. 정상 경로 DB 호출 수를 유지하고 운영 조치가 기존 발송·만료·정리 보호를 지키는지 검증하며, 위 착수 조건을 충족한 뒤 k6로 본격 성능 측정을 진행한다.

성능 작업 시작 시 메시지 크기·업체 지연·시나리오 비율, 지연 SLO, 자원·비용 한도를 정한다. 로컬 기능 시험 통과와 실제 AWS/다중 Pod에서의 10,000 TPS 입증은 별개다. 이 착수 기준을 [현재 진행 현황](01-현재-구현-상태와-남은-작업.md)의 남은 작업과 함께 관리한다.

| 순서 | 작업 | 완료 시 남길 결과 |
|---|---|---|
| 1 | 기능·장애 복구·운영 처리의 남은 구현과 회귀 검증 마무리 | 미구현/미검증 목록, 본격 성능 시험 착수 기준 |
| 2 | 측정 환경·입력·지연 기준 정의 | Pod CPU/메모리, 노드/저장소 배치, 메시지 크기·고객 수·업체 지연·실패 비율, 시험 시간과 SLO |
| 3 | 성능 설정 점검·초기 튜닝 | 설정별 변경 이유, 적용 전후 값, 재현 가능한 배포 설정 |
| 4 | 각 서비스 Pod 1개 한계 측정 | 포화 지점, 지연·오류·적체 조건을 만족하는 최대 지속 TPS, 병목 자원 |
| 5 | Pod 수를 늘려 전체 경로 검증 | 실제 확장 효과, 공유 저장소 병목, 10,000 TPS를 지속 처리하는 서비스별 Pod 수 |
| 6 | 장시간·혼합 시나리오·장애 중 복구 확인 | 지속 처리량, 복구 시간, 적체 해소, 유실·중복 대조, 운영 여유 용량 |

초기 튜닝을 마친 구성에서 기준선을 측정하고, 병목이 확인되면 한 번에 한 요인씩 변경해 재측정한다. 성능을 위해 선점 조건, 내구성 있는 인계, SQL commit 전 원본 보존, 재시도·만료 정책을 약화하지 않는다. 운영 자원 생성·배포와 과금 규모 확정은 이 문서 작성만으로 실행하지 않는다.

## 3. 튜닝·설정 점검 대상

| 대상 | 확인할 설정·제약 |
|---|---|
| Pod·JVM | CPU/메모리 requests·limits, heap·GC, 스레드 수, throttling·재시작, 종료 대기 |
| Kafka | 토픽별 파티션·복제·내구성 설정, consumer 동시성, poll/fetch·commit, producer batch/linger·압축, 재균형 |
| HTTP·TCP | 연결 풀·동시 요청·대기열 상한, timeout, 시뮬레이터 처리 능력·지연 |
| DynamoDB | 실제 서비스의 처리 용량·스로틀링·지연, 키/GSI 분포, 조건 실패, 요청당 읽기·쓰기와 항목 크기 |
| PostgreSQL | 풀·인덱스·트랜잭션·잠금, 이력/통지/정리 간 경쟁, 보관량 증가 영향 |
| Redis | 연결 풀·메모리·지연, 일정 조회량, 장애 중 경로와 복구 |
| 배경 작업·관측 | 고객 묶음 통지·정리·복구 동시성, 로그/지표 비용, 부하 생성기·수신기의 여유 용량 |

구체적인 값은 측정 환경을 정할 때 선택한다. 현재 로컬 기본값을 운영의 최적값으로 간주하지 않는다. 성능 단계에서 실제 사용하는 버전의 공식 문서와 측정 근거를 설정별로 남긴다.

## 4. Pod별 측정과 전체 처리량의 구분

API, Ingress, Dispatch(재시도·결과 처리·Lifecycle 포함), Receipt API, Result worker(이력·고객 통지·정리 포함)를 각각 대상 Pod 1개로 측정한다. 의존 서비스와 부하 생성기·업체/고객 시뮬레이터의 용량이 먼저 한계에 도달하지 않는지 함께 확인한다. 한 Pod 안에 여러 작업이 있으면 단독 구간 시험과 함께 실행하는 시험을 구분한다.

Pod당 최고 순간 TPS와 **지연·오류·적체 기준을 지키는 최대 지속 TPS**를 별도로 보고한다. CPU·메모리 사양, 설정, 입력 조합, 워밍업·측정 시간, 반복 측정 편차, DB 지연을 붙여야 다른 Pod와 비교할 수 있다.

전체 경로에서는 다음을 따로 측정한다. 상세 승인 기준은 성능 단계 착수 전에 확정한다.

- API의 고유 접수 TPS와 최종 결과 확정 TPS.
- SQL 이력·통지 예약 저장 TPS, 고객 HTTP 수신 확인 기준의 고유 메시지 TPS.
- 데이터 정리 TPS와 정리/통지/Kafka의 적체·최고 대기 시간.
- 전체 지연 p95/p99, 오류·재시도·대체 발송 비율, 설명되지 않는 누락과 예상 밖 외부 중복.

**전체 성능의 측정 기준안:** 정상 시나리오에서 최종 결과의 고객 수신까지 10,000개의 고유 메시지/초를 지속 처리하고, 이력·통지·정리 적체가 계속 증가하지 않는지 확인한다. 고객 HTTP 한 묶음에 100건이 들어가도 HTTP 1회가 아닌 메시지 100건으로 센다. 재시도·중복 Kafka 이벤트·같은 결과의 재전송을 새 메시지 TPS에 더하지 않는다. 수신 완료와 데이터 정리의 시점은 별도로 보고한다.

혼합 시나리오에서는 1차·2차·재시도 비율에 따라 원본 메시지당 각 서비스에 들어오는 작업량이 달라진다. 따라서 Pod 수의 초안은 `목표 원본 TPS × 해당 단계 작업량 / 해당 서비스 Pod당 지속 처리량`으로 계산하되, 여유율·장애 시 용량·공유 저장소 한계를 반영하고 **실제 전체 시험으로 검증**한다. 이는 초기 산정식이며 선형 확장 보장이 아니다.

## 5. 지금 결정하지 않아도 되는 항목

Pod CPU/메모리 사양, 메시지 크기와 고객 분포, 업체 응답·웹훅 지연, 실패·재시도·대체 발송 조합, 지연 SLO, 지속 시간·반복 횟수, 여유율·장애 중 유지 목표, 비용 한도는 성능 시험 환경을 준비할 때 확정한다. 현재 개발을 멈추고 추가 답변을 받을 필요는 없다.

이번에 확정한 것은 **전체 목표 10,000 TPS, Pod별 한계 측정 필요, 개발 완료 후 튜닝·본격 측정 순서**다. 위 측정 기준안과 세부 환경값을 사용자 확정값으로 취급하지 않는다.
