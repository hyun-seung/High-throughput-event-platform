# ADR-008 발송 작업 선점과 외부 중복 발송 방지

- Status: Accepted — 발송 선점·완료 skip·결과 미기록 운영 확인 인계. 자동 재시도·업무 만료·운영 조치 도구는 후속 구현.
- Date: 2026-09-22
- 개정: 2026-09-24. [Q2·Q6 합의](../08-함께-결정할-설계-사항.md)에 따라 lease 만료 후 자동 재점유를 제거했다. 외부 멱등성과 결과 조회는 정확성의 전제가 아니다.

## 문제

Dispatch Consumer가 Provider 호출 뒤 결과 저장 전에 종료되면 내부에는 PROCESSING만 남는다. 호출 전 종료와 외부 처리 후 종료를 내부 정보만으로 구분할 수 없다. lease가 끝났다는 이유로 새 Worker가 다시 발송하면 외부 중복 효과를 만들 수 있다.

## 검토한 대안

1. lease 만료 후 재점유·재호출: 외부 처리 여부를 알 수 없으므로 채택하지 않는다.
2. Redis lock만으로 재호출 차단: 내구성 있는 완료·운영 확인 근거를 대체하지 못한다.
3. DynamoDB의 최초 선점과 결과 상태를 유지하고, lease 만료 시 동일 항목을 운영 확인 상태로 전환한다: 채택한다.

## 결정

| 기존 상태 | Kafka 재전달 처리 | 외부 호출 |
|---|---|---|
| Attempt 없음 | 조건부 최초 선점, PROCESSING·leaseUntil·version=1 저장 | 선점 성공한 Worker만 호출 |
| PROCESSING, lease 유효 | 진행 중 오류로 재전달 대기. lease·version을 연장하지 않음 | 추가 호출 금지 |
| PROCESSING, lease 만료 | 조건부로 REVIEW_REQUIRED·사유·갱신 시각 저장, version 증가 | 추가 호출 금지 |
| REVIEW_REQUIRED | 이미 내구성 있게 인계된 운영 확인 건으로 처리 | 추가 호출 금지 |
| ACCEPTED | 기존 업체 접수 결과를 유지하고 skip | 추가 호출 금지 |
| 읽기/쓰기 실패·알 수 없는 상태 | 처리 성공으로 간주하지 않고 원본 재전달 | 새 호출 금지 |

항목은 `PK=DELIVERY#{deliveryId}`, `SK=ATTEMPT#{attemptId}`를 사용한다. attemptId는 현재 `deliveryId + provider + routeOrder + attemptNumber`로 생성하며 Provider에도 전달하지만 Provider 중복 제거에는 의존하지 않는다.

운영 확인 전이는 현재 status=PROCESSING, version 일치, leaseUntil 이하 시각 조건을 함께 확인한다. `review_reason=LEASE_EXPIRED_WITHOUT_RESULT`와 `updated_at`을 기록하고 원래 leaseUntil을 남긴다. REVIEW_REQUIRED는 최종 성공·실패 또는 업무 만료가 아니다. 상태를 삭제하거나 TTL을 추가하지 않는다.

## 동시성과 결과 저장

- 최초 Worker의 결과 저장은 PROCESSING과 선점 당시 version이 맞을 때만 ACCEPTED로 전환한다.
- 결과 저장과 운영 확인 전이 중 하나만 성공한다. 조건 충돌 시 상태를 다시 읽어 ACCEPTED 또는 REVIEW_REQUIRED로 수렴한다.
- 운영 확인 전이가 먼저 이기면 version이 증가하므로 이전 Worker의 결과 저장은 거절된다. 무조건 update나 새 Attempt 생성으로 우회하지 않는다.
- 결과 저장이 먼저 성공하면 재전달은 ACCEPTED를 확인한다. lease 시각이 지났어도 아직 상태 전이가 없고 원래 version이 유효하면 실제 받은 접수 응답을 저장할 수 있다. lease는 업무 만료 기한이 아니다.
- 운영 확인 저장이 실제 성공했지만 응답을 잃으면 해당 호출은 실패로 반환한다. 다음 재전달에서 consistent read로 저장 상태를 확인하고, 추가 외부 호출 없이 인계를 끝낸다.

**공식 근거:** DynamoDB의 조건식은 조건이 맞는 항목 변경만 허용한다. **프로젝트 판단:** 정상 발송의 write를 늘리지 않고, 예외 경로에서만 같은 항목을 운영 확인으로 바꾸어 복구 근거와 소유권 변경을 함께 기록한다. [DynamoDB 조건부 변경](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html).

## Kafka 오류 처리

Dispatch는 RECORD ack mode를 사용한다. 유효 lease 대기·상태 저장 오류를 기본 재시도 소진 후 로그만 남기고 건너뛰지 않도록 DefaultErrorHandler를 명시한다. `DISPATCH_REDELIVERY_BACKOFF_MS`는 개발 기본값 1,000ms이며 재전달 자체에는 횟수 상한을 두지 않는다. 이것은 외부 발송 3회 재시도 정책이 아니라 **미완료 Kafka 입력의 상태 확인 재시도**다.

REVIEW_REQUIRED 저장을 확인하면 해당 record의 listener는 정상 반환할 수 있다. 업무 책임은 DynamoDB 운영 확인 상태에 남아 있으며 실제 전달 성공으로 집계하지 않는다. [Spring Kafka 오류 처리](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html)에 따라 처리 실패가 계속되는 동안 원본을 보존한다.

Dispatch 전용 DLT 인계는 아직 없으므로 malformed record도 삭제 없이 계속 실패한다. 해당 파티션과 같은 Consumer가 담당한 처리의 지연이 발생할 수 있다. Ingress DLT 구현을 Dispatch에 적용했다고 표현하지 않으며, 운영 격리 경로는 별도 후속 작업이다.

## 복구와 남은 범위

- 재전달이 만료된 PROCESSING을 발견하면 운영 확인 상태로 전환한다. 별도 주기 탐색기·운영 목록 조회·수동 조치 API는 아직 없다.
- 운영 확인 중에도 업무 만료는 연장하지 않는 요구사항을 유지한다. 1차 3시간·2차 4시간 만료와 허용된 2차 전환은 후속 구현이다. lease 기본값 30초를 업무 만료로 사용하지 않는다.
- 관찰한 HTTP 무응답을 기록하고 최대 3회 재시도하는 기능과 업체 오류 코드 분류는 아직 없다. 현재는 호출 실패 후 PROCESSING이 남을 수 있고 재전달에서 lease가 끝나면 운영 확인으로 보존한다. 이것이 최종 재시도 정책 구현 완료를 뜻하지 않는다.
- 느려졌던 기존 Worker가 외부 호출 직전에 재개하는 경우, DB version만으로 그 외부 호출을 취소할 수 없다. 이번 검증은 **재전달 Worker의 자동 재호출 차단**이며 외부 효과 전체의 exactly-once 보장이 아니다.
- 후기 결과 웹훅과 업무 만료의 경합, 최종 완료 기록 축소·삭제 정책은 해당 기능 구현에서 다룬다.

## 성능 영향

정상 발송은 기존대로 claim과 접수 결과 저장의 DynamoDB write 2회다. 중복은 실패한 조건부 write 및 consistent read 비용이 발생한다. 운영 확인 전이는 예외 경로의 조건부 write 1회를 추가하며 완료된 운영 확인 상태를 계속 갱신하지 않는다. PROCESSING 대기 중에는 재전달 간격만큼 상태 확인 부하가 생기므로 첫 PoC에서 별도 집계한다.

## 검증 방법

- 단위: ACCEPTED·유효 lease·REVIEW_REQUIRED의 외부 호출 제어, 운영 확인 인계 실패 전파, 12회 연속 오류 이후에도 입력을 성공 처리하지 않는지 확인.
- 실제 DynamoDB Local: 호출 전 중단, 외부 처리 후 결과 저장 전 중단 상태, 기존 접수 완료, 유효 lease 유지, 20개 복구 경합, 낡은 소유자의 결과 저장 차단, 결과 저장과 복구 경합 10회, 운영 확인 write 응답 유실.
- 테스트용 Provider는 모든 호출에 효과가 생기며 중복 제거하지 않는다. 실제 프로세스 kill이나 HTTP 네트워크 장애 자체를 재현한 시험은 아니다.
