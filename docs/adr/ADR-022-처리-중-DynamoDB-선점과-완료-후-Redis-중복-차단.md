# ADR-022 처리 중 DynamoDB 선점과 완료 후 Redis 중복 차단

- Status: Accepted
- Date: 2026-09-25
- 근거: 사용자가 ORIGIN/STEP 최소 저장과 완료 후 Redis TTL 정책을 설명하고, Redis 유실 시에도 DDB 선점·멱등 조건을 통과하면 재발송하도록 확정했다.
- 적용 상태: **업무 정책 확정, 코드 이관 전**. 현재 코드는 작은 DDB 완료 META를 유지한다.
- 대체 범위: ADR-020 및 ADR-021 제안 중 ‘완료 후에도 작은 DDB 기록으로 재발송을 계속 차단’하는 정책. SQL 인계 전 원본 보존·처리 중 원자 선점은 유지한다.

## 결정

중복 판단 키는 고객 범위를 포함한 `tenantId + ClientMsgId`로 관리한다. 인입/PRESEND에서 Redis에 업무 만료 판단에 필요한 시각·단계 정보를 둔다. 활성 원본·STEP과 내구성 일정/인계 근거는 필요한 동안 유지한다. Redis만 사라졌다고 진행 중 실행의 횟수·기한·선점을 초기화하지 않는다.

외부 1차·2차 발송은 DDB의 조건부 선점과 실행 정보 저장을 거친다. 재시도 명령은 이전 회차·목표 회차를 고정하며, 같은 명령을 다시 소비해도 attemptNo를 다시 증가시키지 않는다. 응답 후 재시도 토픽으로 인계하기 전 종료한 결과 미기록 상태는 기존 운영 확인·만료 정책을 따른다.

단계 결과가 확정되면 해당 업무 만료 감시를 해제한다. HTTP/TCP 접수 응답만으로 웹훅 대기를 끝내지는 않는다. 1차에서 2차로 전환하면 1차 감시를 종료하고 기존 규칙의 2차 기한을 유지한다.

최종 결과를 PostgreSQL 이력과 고객 통지 예약에 내구성 있게 저장한 뒤 DDB 원본·STEP 및 해당 처리의 임시 기록을 정리한다. 완료 후 중복 차단용으로는 Redis 표식과 TTL을 유지한다. 작은 DDB 완료 기록을 의무적으로 장기 보관하는 이전 정책은 대체한다.

Redis 표식이 유효하면 같은 고객의 같은 ClientMsgId에 대한 새 처리를 차단한다. Redis 기록이 없거나 사용할 수 없을 때도 DDB에 남은 활성 선점·멱등 조건이 재발송을 막을 수 있다. **그 DDB 조건까지 통과한 경우에는 재발송을 허용한다.** DDB 오류/timeout을 조건 통과로 취급하지 않는다.

## 처리 흐름

| 시점 | Redis | DynamoDB / PostgreSQL |
|---|---|---|
| 인입 | ClientMsgId별 중복 제어 정보와 최초 시각 | Kafka 접수 후 ORIGIN 최초 저장을 우선 설계; 상세 시점은 이관에서 검증 |
| PRESEND | 현재 처리 소유자·단계의 만료 일정 유지 | STEP 실행 설정·조건부 선점 |
| 응답/웹훅 대기 | 업무 만료 감시 | 결과·기한·회차에 필요한 내구성 상태 유지 |
| 해당 단계 종료 | 해당 만료 일정 제거, 2차가 있으면 새 단계 일정 | 2차도 동일 선점 규칙 적용 |
| 전체 종료·SQL 인계 | 중복 제어 표식 유지 | 이력+통지 예약 commit 확인, 실패하면 DDB 보존 |
| DDB 정리 후 | 중복 차단 표식과 TTL만 유지 | 이력/통지는 SQL에 보존, 이전 DDB 완료 표식의 장기 유지 요구 해제 |
| TTL 종료 또는 Redis 소실 | 차단 표식 없음 | DDB 선점·기한·회차 조건까지 통과하면 재발송 허용 |

‘추가 정보 없이 TTL만 유지’는 Redis에 빈 시간만 존재한다는 뜻이 아니라, 업무 만료 일정과 원문을 제거하고 최소 중복 차단 표식이 붙은 키를 유지한다는 뜻이다.

## 구분할 두 시간

- **업무 deadline:** 1차는 최초 인입 기준 3시간, 2차는 1차 결과 판단 기준 4시간이라는 기존 기본값·규칙을 유지한다. 재시도와 Redis 재구축으로 연장하지 않는다.
- **완료 후 중복 차단 TTL:** ClientMsgId를 얼마 동안 추가 차단할지 정하는 별도 설정이다. 길이와 기준 시점은 아직 확정하지 않았다. 업무 deadline이 끝났다는 이유로 동일 시점에 키가 반드시 사라져야 하는 것은 아니다.

Redis 일정 데이터와 중복 표식의 수명을 분리한다. 하나의 키/자료구조로 표현할지 별도 키로 둘지는 구현 선택이며, 키 TTL 하나가 활성 일정과 완료 보관을 동시에 부정확하게 제어하도록 만들지 않는다.

## 보장 범위의 변경

처리 중 조건부 선점과 결과·이력 유실 방지 목표는 유지한다. 완료 후에는 Redis TTL/기록 보존에 의존한 중복 차단이다. Redis 소실로 발생할 수 있는 완료 요청의 재발송은 사용자가 허용한 정책이며, Redis가 무손실로 바뀌었다는 뜻이 아니다.

같은 ClientMsgId의 고객 재요청뿐 아니라 과거 Kafka/DLT 입력 재처리에서도 새 처리 진입 조건을 통과하면 재발송 가능성이 있다. 내부 이벤트 종류별로 새 처리에 진입할 수 있는 경로와 낡은 실행자의 직접 STEP 갱신은 구분한다. 낡은 실행자가 새 처리의 상태를 덮어쓰도록 허용하는 결정은 아니다.

영속화·TTL·복제의 실제 한계는 [공식 근거 문서](../07-저장소별-특성과-데이터-유실-복구-조건.md)에 그대로 적용된다. 이번 결정은 그 한계를 없애는 기술 변경이 아니라 완료 후 허용하는 중복 범위의 변경이다.

## 구현 시 유지할 조건

1. Redis 중복 표식은 새로운 인입과 이미 승인된 같은 처리의 PRESEND/재시도를 구별한다. 인입에서 만든 키 때문에 자기 자신을 중복으로 버리지 않는다. 처리 중 표식만으로 Kafka 입력을 완료 처리하거나 유일한 원본을 버리지 않는다.
2. DDB의 현재 조건은 원본 생성·실행 선점·기한·version·회차의 조건이다. 키가 없다는 사실만으로 무조건 외부를 호출하지 않는다. 활성 STEP이 남았다면 기존 상태로 처리한다.
3. 기존 deliveryId는 고객+Idempotency-Key에서 결정적으로 생성되고 SQL 이력도 deliveryId로 중복을 막는다. 허용된 새 처리에는 별도 처리 세대/실행 ID를 부여하는 식별자 이관이 필요하다. 같은 ClientMsgId의 이전 이력과 새 이력·통지가 합쳐지면 안 된다.
4. 웹훅은 ClientMsgId뿐 아니라 처리 세대·단계·호출 회차로 연결한다. 삭제된 이전 STEP의 늦은 웹훅이 새 처리를 완료시키지 못하게 한다.
5. SQL 저장 후 DDB 정리와 동시에 새 요청이 들어오는 경합, Redis 오류, Kafka 등록 전후 종료를 시험한다. 새 정책을 적용하려고 기존 완료 META를 먼저 일괄 삭제하지 않는다.
6. 재시도 토픽이 인계 근거인 경우 Kafka 저장 확인·원본 offset 처리 순서를 검증한다. 만료의 유일한 근거를 Redis TTL 알림에 맡기지 않는다.

## 검증 및 남은 값

정책 결정에 추가 사용자 승인은 필요하지 않다. TTL 길이·기준 시점은 설정으로 분리할 미정 값이며 이 문서에서 임의 확정하지 않는다. 이관 설계와 테스트에서는 Redis 소실+DDB 활성 상태의 발송 차단, Redis 소실+DDB 정리 후 허용된 새 처리, 중복 명령의 고정 회차, 기존 웹훅 격리, SQL 이력·통지의 세대별 분리를 확인한다.

현재 구현과 계측값은 변경하지 않았다. ADR-020의 작은 완료 META를 유지하는 코드·기존 시험을 새 정책에 맞게 바꾼 뒤 실제 쓰기 횟수를 다시 측정한다.
