# ADR-021 Redis 보조 일정과 발송 원장의 역할 분리

- Status: Accepted in part; completion policy superseded by ADR-022
- 갱신: [ADR-022](ADR-022-처리-중-DynamoDB-선점과-완료-후-Redis-중복-차단.md)의 완료 후 Redis TTL 정책을 우선한다. 아래 내구성 완료 캐시 전제는 이전 제안이며, 일정 검색·처리 중 원장 보호 제안은 계속 검토한다.
- Date: 2026-09-25
- 사용자 방향: DynamoDB 사용 최소화, 사용 가능한 구간에 Redis 활용.
- Redis Sorted Set 일정과 DDB 주기 복구는 v2에 적용했다. 완료 캐시는 ADR-022를 따른다. [구현 경계](../35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md) 이외의 아래 제안은 별도 구현 완료를 뜻하지 않는다.

## 문제

현재 정상 전체 흐름은 성공 쓰기 API 8회·항목 변경 14회다. 재시도 대기 중 최초 선점 트랜잭션 실패와 반복 조회가 있고, 만료 검색은 GSI polling을 사용한다. 중복·중간 쓰기를 줄이고 Redis를 활용할 수 있지만, Redis 등록 전 종료나 failover로 일정이 누락되어도 요청을 잃으면 안 된다.

## 검토한 대안

- Redis TTL 만료 알림만으로 처리: 알림 지연·구독 단절 중 손실 때문에 채택하지 않는다.
- Redis Sorted Set만을 유일한 일정 원장으로 사용: 등록과 업무 DB commit의 간극·복제/영속화 복구를 별도로 해결해야 하므로 현재 제안에서 제외한다.
- DDB 일정만 계속 조회: 현재의 복구 근거를 유지하지만 고빈도 검색·재전달 비용이 남는다.
- Redis 검색 + DDB 일정·조건부 판단 + 주기 누락 점검: 제안한다. 기존 GSI 쓰기는 당장 없애지 않는다.

## 제안하는 결정

먼저 terminal 경로의 중복 색인 갱신·최초 선점 실패·중복 조회를 줄인다. Redis에는 내구성 있게 저장된 일정의 파생 목록과 검증된 완료 캐시를 둔다. TTL은 캐시 수명 관리에 사용한다. 업무 만료 확정·외부 호출 허가·재시도 예산은 DDB의 조건부 상태 전환으로 유지한다.

SQL 이력·고객 웹훅·정리 예약은 PostgreSQL에 유지한다. 원본·완료·Receipt/FINAL의 저장 구조를 줄이는 작업은 단계별로 별도 검증한다.

## 선택 이유와 공식 근거

Redis TTL의 만료 정확도와 알림의 정시·무손실 전달은 다른 보장이다. Redis 영속화·복제도 구성별 확인 범위가 다르다. [공식 문서의 직접 인용·링크·실패 사례](../07-저장소별-특성과-데이터-유실-복구-조건.md#231-redis-ttl은-무엇을-보장하는가--2026-09-25-보강)에 정리했다. 검토일 2026-09-25, Redis OSS 7.4에 적용되는 공통 동작을 확인했으며 다른 관리형 상품의 보장은 별도다.

DDB 쓰기 제거보다 Redis 검색으로 먼저 줄어드는 것은 반복 읽기다. API 병합·항목 변경 감소·항목 크기 감소는 별도로 계산한다. [공식 용량 근거와 현재 계측](../33-DynamoDB-사용-횟수와-최소화-검토.md)을 따른다.

## 장점과 제약

Redis의 빠른 조회·TTL을 활용하면서 데이터 소실이 업무 소실로 번지지 않도록 한다. 대신 DDB GSI 누락 점검은 계속 필요하고, 복구 주기를 늘리면 누락된 만료 작업의 발견이 늦어진다. DDB 쓰기 비용을 전부 없애거나 고객 장애 중 수신 기한을 절대 보장하는 설계는 아니다.

완료 캐시로 조회를 생략하려면 확정 사실·요청 fingerprint·복원 세대 검증이 필요하다. 진행 중 상태 캐시만 보고 offset을 완료하지 않는다. GSI는 최종적 일관성이므로 단일 조회의 부재를 최종 판단에 사용하지 않는다.

## 장애 상황과 복구

DDB commit 후 Redis 등록 전 종료는 GSI에서 복구한다. Redis 정상 상태에서도 주기 점검하여 조용한 누락을 발견한다. 전체 Redis 소실은 원래 기한·횟수로 재생성한다. 일정 관리에서 Redis 장애는 DDB 경로 전환이며, TPS/Quota의 제한 우회 정책과 구별한다. DDB 판단 자체가 실패하면 발송 권한을 우회하지 않는다.

## 성능 영향과 검증 방법

구현 전후 동일 경로에서 성공/실패 API, 항목 변경, 읽기, AWS 기본 테이블·GSI 용량, Redis 부하, 누락 복구 지연을 비교한다. 실제 절감량을 검증하기 전 새로운 최소 횟수를 선언하지 않는다. [구간별 유지/이전/축소 표와 장애 검증 목록](../34-Redis-TTL의-보장과-DynamoDB-최소화-계획.md)을 구현 기준으로 사용한다.
