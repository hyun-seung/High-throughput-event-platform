# ADR-002 저장소 역할과 선택 이유

- Status: Proposed (DynamoDB 최소 사용과 작은 완료 기록 유지는 사용자 확정; 나머지 배치·보관·검증은 미완료)
- Date: 2026-09-23
- 공식 특성: [저장소 특성과 내구성](../07-저장소별-특성과-데이터-유실-복구-조건.md)
- 미확정 요구사항: [설계 논의 목록](../08-함께-결정할-설계-사항.md)

## 문제

DynamoDB 사용 최소화와 유실 방지·외부 발송 멱등성을 함께 만족해야 한다. Q3에 따라 리전 전체 장애를 제외한 무손실이 목표로 확정됐다. 사본 배치와 장애 조합별 검증은 남아 있으며, 이 요구만으로 특정 저장소 안이 Accepted가 되지는 않는다. 데이터를 저장하는 이유와 없애도 되는 조건이 불명확하면 중간 상태를 과도하게 저장하거나, 반대로 복구에 필요한 기록까지 제거하게 된다.

“Redis는 휘발성이므로 불가”, “DynamoDB는 영구 저장이므로 안전”처럼 제품 이름만으로 판단하지 않는다. 필요한 것은 실제 장애 모델에 맞는 쓰기 확인·동시성 제어·보존·복구와 Provider 계약이다.

## 검토한 대안

| 선택지 | 장점 | 부담·남는 조건 |
|---|---|---|
| Kafka 접수 + 작은 DynamoDB 실행 상태 + PostgreSQL 이력 | API 동기 DB write 제거, key 기반 조건부 갱신, 역할별 확장 | 저장소 운영과 이중 write 경계, retention·복구 계약 필요 |
| PostgreSQL 실행 원장 + transactional outbox + Kafka | 실행 상태와 outbox를 하나의 DB transaction으로 저장 가능 | 접수/실행 DB의 쓰기 부하·인덱스·복제·복구 성능 검증 필요 |
| Kafka 기반 상태 처리와 changelog 중심 | DynamoDB 사용을 더 줄일 여지 | 상태 복원, 조회, rebalance, 예약과 외부 효과 조정의 복잡도. HTTP exactly-once가 자동 해결되지 않음 |
| Redis 실행 원장 | 낮은 접근 지연, 자료구조·원자 연산 활용 | 요구 장애 범위에서 persistence·승격·삭제·복원 보장을 별도 입증해야 함. 현재 로컬 구성으로는 근거 부족 |

비교는 설계 분석이다. 부하와 장애 범위가 확정되지 않아 특정 제품이 항상 저렴하거나 빠르다고 단정하지 않는다.

## 결정 제안

사용자는 호처리에 필요한 실행·멱등 상태를 DynamoDB에 최소한으로 저장하고 작은 완료 기록을 유지하는 방향을 확정했다. 기존 Kafka-first 구조에서 각 DynamoDB 저장·갱신이 멱등 판단과 안전한 실행·복구에 필요한지 검증한다. 원본 projection을 반드시 별도 DynamoDB write로 유지할지, 다른 내구성 원본과 역할을 합칠지는 미확정이다.

| 데이터 | 저장 목적 | 우선 후보 | 없애거나 옮길 때 필요한 조건 |
|---|---|---|---|
| 최초 요청 원본 | 접수 응답 근거와 재실행 입력 | Kafka, 필요 시 장기 보관 | retention 이후까지 모든 미완료 요청의 payload를 복원할 수 있어야 함 |
| 고객 멱등키·입력 동일성 정보 | 같은 key의 다른 발송 차단 | 내구성 있는 실행/원본 상태 | 동기 또는 비동기 충돌 계약과 판단 원본을 유지 |
| 발송 claim·version·활성 경로 | 동시 실행·낡은 상태 변경 제어 | DynamoDB 작은 item | 동일 동시성 보장을 하는 원장으로 대체. Redis lock만으로 생략하지 않음 |
| 확정 발송 결과·Provider 식별자 | 완료 재호출 방지, UNKNOWN 조정 | DynamoDB 실행 상태 | 현재 외부 조회는 없으므로 독립적인 내구성 원장 등 동등한 복구 근거를 입증해야 함 |
| 다음 action·시각·정체 탐지 정보 | 실행 중단 뒤 재개, Attempt 생성 전 누락도 탐지 | 실행 상태와 필요한 조회 인덱스 | Kafka/다른 scheduler로 옮길 때 예약과 인계의 내구성을 보장 |
| 통신 시도 상세 이력 | 장애 분석·감사 | Kafka → PostgreSQL | 실행 원장과 연결할 key를 유지. 모든 호출 로그를 실행 item에 누적하지 않음 |
| 최종 이력·기준정보 | 운영 조회·관계 제약·정산 근거 | PostgreSQL | 원본·재구축 가능 기간·장애 시 backlog 정책 유지 |
| TPS·정책 cache·조회 cache | 빠른 admission·반복 조회 비용 절감 | Redis | 재구축 가능성과 장애 중 정책 확정. 발송 완료의 유일한 원장으로 사용하지 않음 |

## 선택 이유

### 왜 DynamoDB에 실행 상태를 두는가

**공식 사실:** 성공 쓰기의 내구성과 key별 조건부 변경 기능이 있다. **프로젝트 판단:** 재시작 후에도 남아야 하는 claim·완료·복구 상태에 적합한 후보다. 처리량 요구에 맞는지는 실제 크기·경합·비용 측정으로 판단한다. [Read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html), [Condition expressions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html)

### 왜 Redis를 유일한 발송 원장으로 두지 않는가

**공식 사실:** 기본 복제와 WAIT/WAITAOF에는 failover 보장 범위가 있다. **프로젝트 판단:** 현재 요구에서는 key 부재를 미발송 증거로 사용하면 위험하다. cache·보조 dedupe는 허용 후보이며, 재구축할 수 있는 원장과 판단 절차를 유지한다. [Replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [WAIT](https://redis.io/docs/latest/commands/wait/), [WAITAOF](https://redis.io/docs/latest/commands/waitaof/)

### 왜 PostgreSQL을 이력에 사용하며 대안으로도 남기는가

**공식 사실:** WAL과 관계 제약을 제공한다. **프로젝트 판단:** 이력 조회·정산·운영 기준정보에 유용하며 실행 상태와 outbox를 합치는 대안도 가능하다. 이 프로젝트에서 DynamoDB가 반드시 필요한지는 부하·운영비와 요구사항으로 판정한다. [WAL](https://www.postgresql.org/docs/17/wal-intro.html), [Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html)

### 왜 Kafka에 먼저 접수하는가

**공식 사실:** 복제된 로그, 재소비, Kafka 내 transaction 기능을 제공한다. **프로젝트 판단:** API 동기 DB write를 줄이는 데 유리하다. 복제·retention과 외부 상태 인계 경계를 확정해야 채택 이유가 성립한다. [Kafka design](https://kafka.apache.org/40/design/design/)

## 장점과 제약

- DynamoDB write 절감은 목표지만, 절감 후 사라진 복구 근거의 대체 위치와 비용을 설명해야 한다.
- 원본·상태·이력을 여러 저장소에 복사하면 보존과 복구 시점이 달라져 조정 비용이 생긴다.
- 모든 단계에 transaction이나 별도 outbox item을 일괄 추가하지 않는다. 동일 확정 상태에서 안정적으로 재발행할 수 있는지 먼저 평가한다.
- RPO 0에 필요한 사본 확인이 안 되면 일부 가용성을 포기할 수 있다. Q5에서 필요한 구간만 중단하고 정상 구간은 유지하는 방향을 확정했다. [저장소별 복구 절차](../09-저장소-장애-시-중단-범위와-복구-절차.md)에 적용하며 장기 장애 대상은 복구 후 만료 처리하며, 대상 구분과 복구 시간은 미정이다.
- 어떤 DB를 선택해도 Provider가 수행한 효과와 로컬 commit 사이의 공백은 남는다.

## 장애 상황

1. Redis 완료 cache 소실: 원장 확인 또는 재구축으로 전환하고 신규 발송으로 단정하지 않는다.
2. Provider 처리 후 실행 상태 저장 실패: 결과 기록의 반영 여부와 소유권을 확인하고 저장을 재시도한다. 외부 조회는 없으며 DB 저장 실패를 외부 재발송으로 대체하지 않는다. 프로세스까지 종료되면 Q6의 기한 내 운영 확인·만료 정책을 적용한다.
3. DB 결과 저장 후 Kafka 후속 발행 전 종료: 재처리에서 후속 발행까지 복구하는 경로가 있어야 한다.
4. 과거 DB backup 복원: 복원 시점 이후 외부 발송 사실을 잃었을 수 있으므로 자동 replay 전에 원장·독립적으로 보존된 결과 기록을 대조한다. 외부 조회는 없으므로 복구 근거가 없으면 무손실 달성을 주장하지 않는다.
5. 원본 retention 초과: 경보만으로 복구되지 않는다. 보관 원본에서 재구성할 수 없다면 요구사항 미충족이다.

## 복구 방법

접수 원본, 실행 상태, Provider 결과, 이력의 복구 원천·checkpoint·보존 기간을 명시한다. Redis는 이 자료에서 재구축하는 역할을 우선한다. Kafka와 DB의 복구 시점이 다를 때 자동 발송을 시작하기 전에 완료·UNKNOWN 집합을 대조한다. Q3에 따라 리전 전체 장애 시 무손실 전환은 현재 필수 범위에서 제외한다. 리전 내 장애와 논리 손상에 대한 복구·중단 절차는 [저장소별 운영 절차](../09-저장소-장애-시-중단-범위와-복구-절차.md)를 기준으로 구체적인 배치·장애 시험에서 검증한다.

## 완료 후 정리의 추가 검토

사용자는 초기 전부 정리 구상을 구체화해 원본·실행 상세 정리, 이력 한 줄 보존, 작은 DynamoDB 완료 기록 유지를 확정했다. [선택 이유와 검토한 대안](../11-멱등-정보-보관과-완료-후-정리-방식.md), [완료 정리 설계](../10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)를 따른다. 이력 저장·통지 인계 전에 원본을 삭제하지 않고, 실행 상태에서 완료 기록으로 전환하는 동안 중복 판단의 공백을 만들지 않는다. 보관 기간은 미정이며 Kafka 원본 보관 정책과 구분한다.

## 성능 영향

정상 1차 성공, 2차 전환, UNKNOWN 조회, 중복 replay를 별도 workload로 측정한다. 요청당 DynamoDB read/write뿐 아니라 item 크기, GSI, transaction, PostgreSQL WAL/인덱스, Kafka 보관·재생, Redis 재구축 비용을 비교한다. 절대 최소 write 수는 아직 확정하지 않는다.

## 검증 방법

[설계 논의 목록의 장애 시험](../08-함께-결정할-설계-사항.md#5-설계를-확정하기-전-필요한-검증)을 통과하고 Q1~Q8의 합의 결과를 반영한 뒤 Accepted로 전환한다. 이 ADR 추가만으로 기존 운영 보장이나 발송 key 규칙을 변경하지 않는다.
