# ADR-019 고객 통지 묶음과 재전송 횟수의 내구성 관리

- Status: Accepted
- Date: 2026-09-25
- 범위: PoC의 같은 고객 최대 100건 HTTP 통지, 최초 + 최대 20회 재전송. 운영 고객 HTTP 계약 확정과 부분 수신 확인은 별도다.

## 문제와 대안

메모리에서 묶음을 만들고 HTTP 후 횟수를 증가시키면 호출 직후 종료 시 묶음 구성과 횟수가 사라진다. 반복 재시작으로 고객 통지 한도를 우회할 수도 있다. 항목을 매번 새로 섞어 재전송하면 고객의 묶음 ID 중복 제거도 어렵다.

| 방식 | 판단 |
|---|---|
| 메모리 묶음·횟수 | 재시작 후 동일 요청·예산 복구 불가 |
| HTTP 동안 DB 잠금 유지 | 고객 지연이 DB 연결·잠금으로 전파 |
| 매번 새 묶음 구성 | 부분 실패 유연성은 있으나 ID·항목별 예산 복잡성 증가 |
| 고정 SQL 묶음 + 호출 전 회차·lease 예약 | 이번 선택. 보수적인 회차 소비와 반복 가능한 재전송 |

## 결정

PostgreSQL에 묶음 ID·본문·목적지를 고정하고, 항목 연결·회차 증가·선점을 같은 트랜잭션으로 저장한 뒤 HTTP를 호출한다. 최대 21회이며 호출 여부가 불명인 예약도 예산에 포함한다. 결과 저장에는 token·회차·미만료 조건을 사용한다. 고객별 IN_FLIGHT 하나, 앱 전체 슬롯은 유한하게 둔다. 미래 시각 재전송은 새 묶음의 진행을 막지 않는다.

PoC는 204를 전체 묶음 수신 확인으로 정하고 나머지 응답과 통신 실패에는 같은 묶음을 재전송한다. 부분 응답과 자동 묶음 재구성은 지원하지 않는다. 100ms poll에서 즉시 준비된 항목을 묶고 100건을 채우려고 기다리지 않는다.

## 공식 근거와 프로젝트 판단

확인일 2026-09-25. 아래 공식 동작과 이 프로젝트가 선택한 상한·계약을 구분한다.

- PostgreSQL 17의 행 잠금과 SKIP LOCKED는 큐 형태의 동시 소비 경합을 피하는 데 사용할 수 있다. 고객 lane과 항목을 짧게 잠그는 구조는 이를 적용한 선택이다. SQL 잠금은 외부 HTTP 효과까지 보호하지 않는다. [공식 SELECT 잠금 절](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE).
- Java 21 HttpRequest timeout은 응답 시간 제한이며 미설정은 무한 대기에 해당한다. 기본 3초의 요청/연결 제한과 Future 제한을 함께 두고 응답 본문은 버퍼링하지 않는다. 3초·lease 30초는 운영 측정 전 PoC 기본값이다. [공식 timeout 설명](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html#timeout(java.time.Duration)).
- Java HttpClient의 Redirect.NEVER는 자동 이동을 하지 않는다. 고객의 3xx를 다른 목적지로 따라가지 않고 실패로 처리한다. [공식 redirect 정책](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.Redirect.html).
- RFC 9110의 204는 요청 성공을 나타낸다. 이것만으로 외부의 저장 내구성을 증명하지는 못한다. 고객이 전체 묶음을 내구성 있게 수신한 뒤 204를 반환하도록 요구하는 것은 별도 계약이다. [공식 HTTP 의미](https://www.rfc-editor.org/rfc/rfc9110.html#name-204-no-content).
- 응답 유실에서 재시도하면 이미 실행된 효과가 반복될 수 있다. 고정 batchId/eventId는 고객 중복 제거를 위한 식별자이며 외부 효과 무중복의 증명이 아니다. [AWS의 멱등 API와 재시도](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

## 장애와 보장 한계

예약 전 SQL 실패는 HTTP를 만들지 않는다. 예약 후 종료는 lease 복구로 이어지고 같은 본문으로 다음 회차를 사용한다. HTTP 성공 후 저장 실패·응답 유실에서는 고객 중복 제거가 필요하다. 오래 멈춘 작업자가 lease 확인 직후 다시 실행되는 네트워크 호출까지 DB가 막아주지는 않는다.

21회 모두 호출 여부 불명이라면 실제 HTTP가 0회였어도 자동 시도를 소진할 수 있다. 전송 한도를 지키는 보수적인 선택이며 EXHAUSTED 결과는 삭제하지 않는다. 자동 소진 해제·수동 추가 예산은 구현하지 않았다. 고객 장애 시 최대 만료 시간 내 수신 보장은 별도 미해결 조건이다.

운영 토큰은 외부 설정에만 두고 URL을 묶음에 고정한다. 설정에서 목적지가 바뀐 기존 묶음을 다른 URL로 자동 전달하지 않는다. 토큰 교체와 목적지 이관의 운영 절차가 필요하다. 같은 고객의 여러 목적지·인증 버전을 동시에 라우팅하는 기능은 후속이다.

## 비용과 검증

DynamoDB·Redis 비용은 추가하지 않는다. PostgreSQL에 묶음당 본문 1개와 선점/결과 갱신, 항목별 상태·횟수 갱신이 추가된다. 고객별 poll과 건별 결과 인입은 고 TPS 측정 후 개선 대상이다. HTTP 중 DB 연결을 점유하지 않는다.

실제 SQL과 HTTP로 동시 선점, 예약 rollback, 성공 후 저장 실패, 동일 본문 재전송, 횟수 소진, 고객 격리, V1 이관을 검증한다. Kafka부터 실제 HTTP·최종 통지 상태까지 앱 설정으로 실행했다. 시험 결과·남는 장애·실행 방법은 [고객 통지 문서](../31-고객-HTTP-묶음-통지와-재전송-복구.md)에 기록한다.
