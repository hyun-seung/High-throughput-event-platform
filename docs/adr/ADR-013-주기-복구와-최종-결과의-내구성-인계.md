# ADR-013 주기 복구와 최종 결과의 내구성 인계

- Status: Accepted — 개발 구현. 기존 데이터 이관·운영 용량 검증 후 활성화
- Date: 2026-09-25

## 문제

웹훅이 오지 않거나, Dispatch 입력 처리 전에 서비스가 멈추면 다음 입력 없이도 원래 기한에 맞춰 작업을 찾아야 한다. 최종 상태를 DB에 저장한 직후 Kafka 발행 전에 종료돼도 결과가 사라지면 안 된다. DynamoDB는 호처리·멱등 판단에 필요한 만큼만 사용한다.

## 공식 문서의 사실

2026-09-25 공식 문서를 확인했다. 아래 사실과 프로젝트의 선택은 구분한다.

- GSI는 키가 있는 항목만 포함하며 KEYS_ONLY는 원본 키와 색인 키만 저장한다. GSI 읽기는 최종적 일관성이며 별도 읽기·쓰기·저장 비용이 있다. 색인 비용과 용량이 테이블 쓰기에 영향을 줄 수 있다. [AWS GSI 문서](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html).
- DynamoDB TTL은 기한의 정확한 업무 상태 전이 기능이 아니다. 만료된 항목의 실제 삭제는 지연될 수 있다. [AWS TTL 문서](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html).
- DynamoDB 트랜잭션은 포함한 항목들의 변경을 원자적으로 처리한다. 내부 준비·커밋 단계가 각각 읽기/쓰기를 수행하므로 항목 수만으로 일반 쓰기와 비용을 같다고 계산하지 않는다. Kafka 발행은 이 트랜잭션에 포함되지 않는다. [AWS 트랜잭션 문서](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).
- DB 변경과 메시지 발행의 이중 쓰기 공백에는 outbox가 대안이다. 메시지 중복은 가능하며 소비자 멱등 처리가 필요하다. [AWS transactional outbox 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

## 결정과 프로젝트 판단

기존 META·Attempt에 `lifecycle_bucket`·`lifecycle_due` 속성을 넣고, 16개 bucket의 KEYS_ONLY GSI 하나를 Query한다. 추가 업무 큐 항목을 매번 만들지 않는다. META는 아직 Attempt가 없는 원본을 찾는 용도이며 Attempt가 생기면 색인에서 제외한다. Attempt는 기한·재시도 시각·최종화 준비 상태를 나타낸다.

GSI는 후보 탐색에만 사용하고 실제 판정은 원본의 consistent read와 조건부 갱신으로 한다. 오래된 색인 결과를 발송 허가로 보지 않는다. 실패 항목이 있어도 페이지와 bucket 순서를 이어가며 다른 요청의 진행을 막지 않는다. Redis에는 복구의 유일한 근거를 두지 않는다.

요청별 작은 `FINAL` 항목에 불변 결과 JSON과 발행 상태를 함께 둔다. 최종화 트랜잭션은 FINAL 생성과 관련 Attempt의 복구 색인 종료를 묶는다. 별도 outbox 항목은 만들지 않는다. Kafka ack 뒤에만 PUBLISHED로 바꾸고 발행 대기 색인에서 제외한다. ack 유실·발행 확인 저장 실패·다중 Worker 경쟁은 같은 eventId·같은 본문의 재발행으로 복구한다.

## 대안

| 대안 | 이번에 선택하지 않은 이유 |
|---|---|
| 전체 테이블 Scan 반복 | 완료 항목·본문까지 읽는 비용과 장애 적체 증가에 비례하는 탐색 부담 |
| 메모리 타이머·Redis만 사용 | 종료·데이터 손실 후 복구할 유일한 원장을 없앨 수 없음 |
| DynamoDB TTL로 만료 처리 | 사용자 기한의 상태 전이·2차 발송·고객 결과 확정을 대신하지 못함 |
| 별도 예약 테이블·메시지마다 예약 항목 | 현 단계에는 기존 실행 항목에 색인 속성을 붙이는 편이 별도 중복 저장을 줄임 |
| 최종화 후 Kafka에 한 번만 발행 | DB 커밋과 발행 사이 종료 또는 ack 유실의 공백 |
| FINAL과 별도 outbox 각각 저장 | 작은 결과와 미인계 상태를 한 항목으로 유지할 수 있음 |

## 비용과 한계

기존 META·Attempt 쓰기에 색인 속성이 추가되고 GSI 쓰기·저장 비용이 발생한다. META의 복구 인계, 부모의 2차 대기 기한 조정, 최종화 트랜잭션, Kafka ack 후 확인 쓰기도 추가된다. 최종화는 1차 종료 시 2개 항목, 2차 종료 시 부모 포함 3개 항목의 트랜잭션이다. 이는 **DynamoDB 비용 0 또는 최소 비용의 증명이 아니다.** 별도 복제 payload·큐 항목을 피한 설계이며 실제 WCU/RCU·GSI 지연·TPS는 후속 PoC에서 측정한다.

GSI 반영 지연·poll 주기·Worker 적체·의존성 장애가 있으므로 실제 처리 완료를 기한과 같은 밀리초로 보장하지 않는다. 원래 deadline은 고정하고 초과한 요청을 늦은 신규 발송으로 살리지 않는다. 고객 서버 수신 확인과 고객 통지 구현은 별도다.

구형 항목에는 색인 속성이 없으므로 GSI 추가만으로 전부 발견할 수 없다. 알려진 미완료 Delivery ID 목록으로 조건부 보강한 뒤 활성화해야 한다. ID 목록이 불완전하면 복구 범위도 불완전하다. Kafka에만 있고 Ingress가 아직 저장하지 않은 원본은 기존 Kafka 보존·소비 복구 경계에 남는다.

## 장애와 복구

DB 실패 시 최종화를 확정하지 않는다. Kafka 실패 시 FINAL PENDING을 유지한다. 발행 후 확인 저장 실패는 같은 결과 재발행을 허용한다. 완료된 FINAL은 보관하고 원본·Attempt·receipt marker도 아직 삭제하지 않는다. Kafka 보관 기간이 지난 후의 자동 재인계와 이력·고객 통지 확인 후 정리는 후속이다.

## 검증

구체적인 시나리오·실행 명령·측정 증거는 [주기 만료와 최종화 검증](../29-주기-만료와-요청-최종화-및-Kafka-인계.md)에 기록한다. 단일 로컬 DynamoDB/Kafka 통과는 다중 AZ 무손실·고부하 기한 보장의 증거가 아니다.
