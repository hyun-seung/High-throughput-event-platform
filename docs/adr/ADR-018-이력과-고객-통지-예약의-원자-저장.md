# ADR-018 이력과 고객 통지 예약의 원자 저장

- Status: Accepted
- Date: 2026-09-25
- 범위: 최종 이벤트를 PostgreSQL 이력·고객 HTTP 통지 예약으로 인계하는 경계. 고객 HTTP 전송 자체와 운영 고가용성은 후속이다.

## 문제

발송 최종 이벤트는 DynamoDB FINAL과 Kafka에 남지만 고객에게 통지할 작업은 아직 없다. 이력을 먼저 저장하고 다른 경로에서 통지를 예약하면 두 단계 사이 종료 시 누락을 복구할 근거가 필요하다. 중복 최종 이벤트로 기존 통지 횟수를 초기화해서도 안 된다.

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 이력과 통지를 독립 Kafka 그룹에서 각각 저장 | 독립 확장은 가능하나 이력·통지 인계 확인과 원본 정리 조건이 복잡해짐 |
| Redis에 통지 대기 저장 | 이력과의 원자성이 없고 Redis 내구성·장애 승격 조건에 고객 결과 보존을 추가 의존 |
| DynamoDB에 통지 상태 추가 | 이미 PostgreSQL에 남길 이력과 별도 쓰기·확인 경로가 필요하며 호처리 외 저장 증가 |
| PostgreSQL 이력·통지 예약을 한 트랜잭션으로 저장 | 이번 선택. 두 행의 유무를 함께 결정하고 ID 제약으로 재처리 가능 |

## 결정

독립 실행 모듈 `delivery-result-worker`와 별도 소비 그룹을 둔다. PostgreSQL `delivery_results` 스키마에서 이력 1행과 통지 예약 1행을 함께 commit한 뒤 Kafka record 처리를 끝낸다. Kafka commit 실패는 재전달로 복구한다. 결과 ID뿐 아니라 최초 불변 내용 전체를 비교하고, 중복에서는 통지 상태를 변경하지 않는다. 누락·충돌을 자동으로 덮어쓰지 않는다.

## 선택 이유와 공식 근거

공식 문서 확인일은 2026-09-25다. 아래 사실에 적용한 테이블 구성·워커 분리는 프로젝트의 설계 판단이다.

- **PostgreSQL 17 트랜잭션:** 여러 변경의 원자성과 commit 전 변경 비노출을 제공한다. 이력과 통지 예약이 함께 존재하는 경계를 만들 수 있다. [공식 설명](https://www.postgresql.org/docs/17/tutorial-transactions.html).
- **PostgreSQL 17 READ COMMITTED:** 각 SQL 문장 시작 시 commit된 데이터를 읽는다. `ON CONFLICT DO NOTHING`은 동시 삽입 결과 때문에 삽입하지 않을 수 있으므로 별도 SELECT로 승자의 불변 내용을 읽고 확인한다. [공식 설명](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED).
- **Spring Kafka RECORD ack:** listener가 반환한 뒤 offset을 commit한다. SQL 트랜잭션 종료 후에만 반환하는 서비스와 결합한다. DB와 Kafka를 하나의 원자 commit으로 만들었다는 뜻은 아니다. [공식 설명](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html#committing-offsets).
- **Spring Boot Flyway:** 버전 SQL로 스키마를 관리하며 PostgreSQL 전용 Flyway 모듈을 함께 사용한다. 인증 DB 초기화 SQL과 섞지 않고 별도 스키마를 버전 관리한다. [공식 설명](https://docs.spring.io/spring-boot/how-to/data-initialization.html#howto.data-initialization.migration-tool.flyway).

## 장점과 제약

추가 DynamoDB 쓰기 없이 통지 예약을 내구성 있게 인계하며, PostgreSQL 장애가 별도 발송 소비자의 직접 의존성이 되지 않는다. 다만 결과 적체·보관 기한·디스크 용량 관리가 필요하다. 기본 구현은 건별 트랜잭션이며 고 TPS를 위한 batch 저장 최적화는 측정 후 검토한다.

**PostgreSQL이라는 제품명만으로 100% 무손실은 성립하지 않는다.** PostgreSQL 17의 `synchronous_commit=off`는 성공 응답 후에도 최근 commit 유실을 허용한다. `fsync`를 끄는 것도 이번 요구에 맞지 않는다. 기본 `on`이라도 동기 standby가 없으면 로컬 WAL 영속화만 기다린다. `on`과 적절한 동기 standby 구성이 함께 있어야 원격의 내구성 저장 확인도 기다린다. `remote_write`는 standby OS 장애까지 보호하는 설정이 아니다. [공식 WAL 설정과 보장 표](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT).

따라서 운영의 리전 외 장애 무손실 목표에는 동기 복제·AZ 배치·승격 대상 선택·스토리지 보장·백업/복구를 포함한 검증이 별도로 필요하다. 이번 로컬 PostgreSQL 17 시험은 `fsync=on`, `synchronous_commit=on`인 단일 인스턴스다. 애플리케이션이 서버의 복제 설정을 구성하거나 강제하지 않는다. 백업 존재만으로 직전 commit까지 유실이 없다고 간주하지 않는다.

## 장애 상황과 복구 방법

SQL 실패에는 offset을 유지하고 복구 후 같은 record를 재처리한다. SQL commit 응답/offset 확인 유실이면 최초 결과를 읽어 통지 예약 추가 없이 성공 처리한다. 내용 충돌·형식 오류는 내구성 DLT가 생기기 전까지 해당 파티션에서 재처리하며 운영 조사 대상으로 둔다. Kafka 보관 기간 초과와 FINAL→PostgreSQL 자동 대조 복구는 아직 해결된 범위가 아니다.

## 성능 영향

최초 결과마다 INSERT 2회와 commit 1회다. 중복은 삽입 시도 후 이력 내용·예약 존재를 읽는다. 이력의 PK/UNIQUE·고객 시각 색인, 통지 PK·PENDING 예정 시각 색인을 유지한다. 기본 동시성 3과 DB 풀 6으로 시작하며, 저장 지연·중복 비율·소비 지연을 보고 조정한다. 요청당 추가 DynamoDB 작업은 없다.

## 검증 방법

실제 PostgreSQL의 동시 중복·전체 rollback·내용 충돌·기존 통지 상태 보존을 검증한다. 실제 Kafka와 연결해 SQL 실패/commit 후 listener 실패 시 offset 유지 및 container 재시작 복구를 확인한다. 빈 스키마에서 앱 기동과 관리 endpoint도 확인한다. [시험 상세와 한계](../30-최종-이력과-고객-통지-대기-기록의-원자-저장.md).
