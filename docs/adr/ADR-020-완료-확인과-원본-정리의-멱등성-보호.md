# ADR-020 완료 확인과 원본 정리의 멱등성 보호

- Status: Accepted
- Date: 2026-09-25
- 범위: 완료 META 유지, SQL 정리 예약, 조건부 원자 정리. 구버전 데이터 자동 이관·운영 무손실 인증은 포함하지 않음.

## 문제

발송 완료 후 원본과 멱등 정보를 모두 삭제하면 오래된 Dispatch 이벤트가 존재하지 않는 Attempt를 다시 만들 수 있다. SQL 이력에 성공 한 줄이 있어도 발송 선점과 같은 경계에서 검사하지 않으면 재발송을 막지 못한다. 반대로 큰 payload와 모든 Attempt를 계속 보관하면 완료 후 저장량을 줄이려는 요구를 충족하지 못한다.

## 검토한 대안

- 모두 삭제: 이후 중복을 구별할 근거가 없으므로 제외한다.
- Redis에 완료 캐시만 유지: cache 부재를 미완료로 판단하면 만료·퇴거·복구 손실이 새 발송으로 이어진다. [저장소별 내구성 조건](../07-저장소별-특성과-데이터-유실-복구-조건.md)의 근거대로 발송 허가의 유일한 기준으로 사용하지 않는다.
- SQL 조회 후 DDB 선점: 두 저장소 사이 경합과 장애를 별도로 해결해야 한다.
- 작은 DynamoDB META 유지: 발송 선점과 같은 저장소의 트랜잭션으로 완료 검사를 묶을 수 있다. 채택한다.
- TTL 또는 개별 BatchWrite로 원본 정리: SQL 인계 확인이나 전체 조건 검증을 대신하지 못하므로 채택하지 않는다.

## 결정

최종화 시 기존 META에 완료 이벤트 ID를 기록하고, 모든 새 Attempt는 같은 트랜잭션의 ConditionCheck로 완료 여부를 검사한다. SQL에는 이력·고객 통지·정리 예약을 함께 저장한다. 정리 워커는 SQL 예약을 선점하여 일치하는 PUBLISHED FINAL과 닫힌 Attempt를 확인한 뒤, META 교체와 관련 항목 삭제를 단일 조건부 트랜잭션으로 수행한다. 기존 META 키를 유지하며 삭제 후 재생성하는 틈을 만들지 않는다.

Receipt marker ID는 기존 결과 반영 트랜잭션에서 Attempt에 추적한다. 추적이 없는 구버전은 보존한다. 모든 신규 쓰기 코드가 교체되기 전에는 정리를 켜지 않는다. 완료 기록에 TTL을 적용하지 않는다. 외부 호출 exactly-once나 전체 리전 밖 장애의 절대 무손실을 이 결정만으로 주장하지 않는다.

## 공식 근거와 프로젝트 판단

검토일 2026-09-25, AWS 현행 개발자 가이드 및 PostgreSQL 17 문서를 사용했다.

| 공식 문서의 사실 | 이 프로젝트에 적용한 판단 |
|---|---|
| [DynamoDB 트랜잭션](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)은 서로 다른 최대 100항목·총 4MB 안에서 전부 성공하거나 전부 실패한다. BatchWrite는 부분 성공할 수 있다. | 완료 기록 교체와 원본/marker 삭제를 한 번에 수행한다. 한도 초과·조건 불일치는 보존한다. |
| 같은 문서: 여러 일반 Get·Query는 원자 스냅샷이 아니며, 트랜잭션에는 조건 확인을 넣을 수 있다. | 읽기로 후보를 준비하고 최종 쓰기 시 version·내용·소유권 조건으로 재검증한다. |
| 같은 문서: 트랜잭션 client token의 멱등 유효 기간은 10분이다. 준비·commit에 따른 추가 용량도 필요하다. | 장기 중복 방지는 작은 완료 META가 담당한다. 저장량 감소와 요청 비용 감소를 동일시하지 않는다. |
| [조건부 표현식](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html)은 조건이 맞는 경우에만 쓰기를 수행한다. | 완료 검사와 Attempt 생성을 묶어 정리와 재선점의 경합을 막는다. |
| [DynamoDB TTL](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html)은 만료 후 삭제가 지연될 수 있다. | 업무 만료·SQL 인계·멱등 보관 기간을 TTL에 맡기지 않는다. |
| [PostgreSQL 트랜잭션](https://www.postgresql.org/docs/17/tutorial-transactions.html)은 여러 변경을 하나의 전체 작업으로 commit/rollback한다. | 이력·통지·정리 예약의 일부만 남는 상태를 막는다. DynamoDB까지 원자적으로 묶인다는 뜻은 아니다. |
| [PostgreSQL SELECT](https://www.postgresql.org/docs/17/sql-select.html)의 SKIP LOCKED는 일반 조회의 일관된 스냅샷 용도가 아니며 큐 형태의 복수 소비자가 잠금 경합을 피하는 데 쓰일 수 있다. | 짧은 SQL 예약 선점에 사용한다. 외부 DDB 호출 동안 row lock을 유지하지 않고 lease·token으로 재개한다. |

## 장점과 제약

새 DynamoDB 테이블·GSI·상시 SQL 발송 조회를 추가하지 않는다. 큰 원본은 지우되 동일 요청 완료 여부를 같은 키에 남긴다. SQL 이력과 통지가 있으므로 정리 후에도 고객 전달을 계속한다.

완료 기록은 기간 합의 전 계속 쌓인다. SHA-256 fingerprint는 원문 비교를 대체하는 실용적인 충돌 저항성을 전제로 한다. 정리 후 원문 복원은 제공하지 않는다. 구버전 완료·Receipt marker 자동 탐색은 제공하지 않는다. 오래 멈춘 실행자의 외부 호출 자체를 취소하는 기능은 아니다. PostgreSQL과 Kafka의 운영 내구성·보관 기간 조건은 기존 ADR을 따른다.

## 장애·복구·성능·검증

DDB 실패는 원본을 유지하며 SQL 예약으로 재시도한다. DDB 성공 응답 또는 SQL DONE 기록이 유실돼도 완료 META의 이벤트 ID·결과 hash를 확인해 수렴한다. SQL 장애 중에는 새 정리를 진행하지 않는다. 고객 통지 스케줄러와 정리 스케줄러를 분리한다.

최초 선점의 트랜잭션 전환, 최종화 META 쓰기, 정리 읽기/삭제의 추가 비용이 있다. 기존 100 TPS 결과는 이 비용을 측정한 자료가 아니다. [구체적 비용·활성화·장애표·260건 검증](../32-완료-기록-유지와-발송-원본의-안전한-정리.md)에 남겼다. 다음 전체 흐름 PoC에서 지연·용량·적체를 함께 평가한다.
