# 전체 호출 흐름의 격리 실행과 전수 대조

기준: 2026-09-25. [전체 Call Flow](04-요청-접수부터-최종-결과까지의-전체-흐름.md)를 신규 v2 API부터 고객 HTTP 수신·발송 데이터 정리까지 연결해 검증하는 도구다. 기존 `run.py`는 API→업체 접수 성능, `receipt_flow.py`·`lifecycle_flow.py`는 v1 구간 검증이므로 전체 v2 성공의 증거로 대신 사용하지 않는다.

## 1. 실행 범위와 격리

`scripts/poc/full_flow.py`는 실행마다 `full-flow-<UUID>` Compose 프로젝트를 만들고 Kafka·Redis·PostgreSQL·DynamoDB Local을 별도로 실행한다. HTTP/TCP·관리 포트도 사용 가능한 포트로 배정한다. 고정 물리 테이블 ORIGIN·STEP과 재시도 토픽이 공용 데이터에 영향을 주지 않도록 인프라 자체를 분리한다.

앱은 event-api, ingress-worker, dispatch-worker, receipt-api, 외부 시뮬레이터, result-worker까지 여섯 개를 실행한다. 고객 HTTP 수신기는 localhost에만 열고 Bearer token, 고객 ID, 묶음 ID, 최대 100건 조건을 검사한다. 첫 고객 호출만 503을 반환하고 다음부터 204를 반환해 동일 묶음 재전송도 확인한다.

인프라는 `compose create`로 만든 뒤, 볼륨 초기화 컨테이너의 시작·종료 코드 0을 확인하고 Redis·PostgreSQL·Kafka·DynamoDB를 순서대로 시작한다. 각 컨테이너의 healthcheck가 모두 healthy여야 앱 실행으로 넘어간다. 현재 로컬 Docker Desktop에서 새 컨테이너의 첫 start가 Created 상태로 정체되는 현상을 재현했다. 시작이 10초를 넘으면 상태를 조회하고 **여전히 Created인 경우에만 한 번 재시도**한다. 이미 Running이면 재시작하지 않고, 실패 종료나 두 번째 timeout은 실행 실패로 남긴다. 컨테이너별 `*-start.json`에 시간·상태·재시도를 기록한다.

종료 시 이 실행이 시작한 앱·컨테이너만 정지한다. 증거와 볼륨은 보존하며 공용 서비스 재시작, 기존 offset 초기화, 기존 테이블 Scan/삭제를 수행하지 않는다. 반복 실행 시 보존된 컨테이너·볼륨의 디스크 사용량은 별도로 관리해야 한다.

## 2. 재현 명령

JDK 21, 실행 가능한 Docker, `scripts/poc/setup.py`로 준비한 Python 환경이 필요하다. 루트에서 실행한다.

```sh
./mvnw -DskipTests package
.poc-tools/venv/bin/python -m unittest discover -s scripts/poc -p 'test_*.py'
.poc-tools/venv/bin/python scripts/poc/full_flow.py
```

실행 로그의 `EVIDENCE` 경로에 환경·JAR/도구 해시·애플리케이션 로그·케이스별 대조·고객 수신·최종 SQL 스냅샷·Prometheus 지표·정리 결과를 저장한다. 실패하면 `failure.json`을 남긴다. `summary.json`의 통과 결과는 전체 시나리오가 성공한 경우에만 생성된다.

## 3. 시나리오

| 번호 | 입력·장애 | 기대 결과 / HTTP·TCP 업체 호출 수 |
|---|---|---|
| 1 | 1차 성공, 고객 첫 응답 503 | DELIVERED / 1·0, 동일 묶음 재전송 후 고객 204 |
| 1 추가 | 정리 완료 후 같은 ClientMsgId 재접수 | 이력 1건 유지·업체 추가 호출 없음, Redis 완료 차단 |
| 2 | 1차 실패 웹훅 FALLBACK, 대체 허용 | 2차 DELIVERED / 1·1 |
| 3 | 1차 RETRY_1S 웹훅 후 성공 | 1차 DELIVERED / 2·0 |
| 4 | 1차 웹훅 미수신, ACCEPTED 뒤 Redis 일정 ZREM | DDB 복구로 1차 EXPIRED / 1·0 |
| 5 | 1차 웹훅 미수신, 대체 허용 | 1차 만료 뒤 2차 DELIVERED / 1·1 |
| 6 | 양 단계 웹훅 미수신 | 2차 EXPIRED / 1·1, 전체 deadline=인입+20초 |

각 케이스는 SQL 이력·통지 DELIVERED·정리 DONE, 고객 204 수신 본문과 SQL 결과의 완전 일치, 업체 호출 수, ORIGIN/STEP 부재, Redis 완료 표식 TTL을 함께 대조한다. 이력만 존재하거나 고객이 503만 응답한 경우는 통과하지 않는다. 마지막에 실행 ID 집합과 이력 총 6건을 대조한다. 이는 동일 고객 소량 실행이므로 고객 간 격리·최대 크기 묶음·최대 재전송 소진 시험은 기존 SQL 통합 시험의 별도 범위다.

## 4. 시간 설정과 측정 한계

- 이 도구 안에서만 1차 8초·2차 12초·DDB 복구 조회 3초를 명시해 기능 시험을 줄인다.
- 애플리케이션 기본값은 1차 3시간·2차 4시간·복구 조회 **10분**이다. 도구가 이 기본 설정을 바꾸지 않는다.
- 기본 10분 조회 경계와 중간 Redis 일정 처리는 `LifecycleSchedulerTest`의 제어 가능한 시계로 검증했다. 이 전체 실행이 실제 10분을 기다리는 시험은 아니다.
- 모든 인프라는 로컬 단일 노드다. AWS GSI 지연·RCU 청구·다중 AZ 무손실·운영 장애 복구 상한을 검증하지 않는다.
- 성능 테스트가 아니다. 외부 중복 제거는 끄며, 재시도에서 생길 수 있는 외부 효과 중복을 exactly-once로 주장하지 않는다.

## 5. 이번 검증 상태

Java 애플리케이션 전체 패키징 성공. Python 시험 22개 통과(기존 증거 시험 10개 + 전체 흐름 대조 시험 6개 + 인프라 시작 시험 6개). 대조 시험은 고객 ack 부재, 고객·SQL 결과 불일치, 잔존 ORIGIN/STEP, 예상 밖 업체 호출, Redis 완료 표식 부재, SQL 미완료 상태를 성공으로 오판하지 않는지 확인한다. 시작 시험은 초기화 실패 시 서비스 시작 차단, healthy 확인, Created에서만 제한된 재시도, Running 중복 시작 방지, 재시도 소진을 검증한다.

**전체 6개 시나리오 통과:** `full-flow-779f51a8ecbc`에서 성공 4건·만료 2건, SQL 이력 총 6건을 전수 대조했다. 고객 첫 503 이후 같은 묶음으로 재전송, 정리 후 동일 요청 차단, Redis 일정 삭제 뒤 복구, 고객 204 결과와 SQL의 일치, ORIGIN·STEP 삭제까지 확인했다. [재검증 원본과 Docker 진단](검증-결과/2026-09-25-Docker-시작-정체와-전체-흐름-재검증.json)에 환경·JAR/소스 해시·케이스·컨테이너 시작 기록을 남겼다. 테스트 프로세스와 소유 컨테이너 정지도 완료했다.

최초 실행 `full-flow-79bd19f72117`은 Docker Compose up의 240초 제한으로 중단됐다. 당시 컨테이너는 `Created`, `Running=false`, `Pid=0`이고 앱은 시작되지 않아 시나리오 통과 수가 0이었다. 이 [최초 실패 기록](검증-결과/2026-09-25-전체-호출-흐름-격리-실행.json)은 보존한다. 이후 아래 현상을 재현하고 도구의 시작 절차를 보완해 전체 재검증에 성공했다.

## 6. Docker 연결·시작 정체 재확인

2026-09-25 Docker Desktop 4.89.0, Engine 29.7.2, Compose v5.5.0, `desktop-linux` context에서 확인했다.

| 확인 | 실제 관찰 |
|---|---|
| 데몬 연결 | `docker version/info/ps` 정상, 조회 1초 이내 |
| 기존 서비스 | 실행 중인 컨테이너 조회 가능. 공용 서비스 전체 재시작 없음 |
| 새 컨테이너 첫 시작 | Compose와 일반 docker start 모두 Created·Running=false·Pid=0에서 timeout 재현 |
| 포트/볼륨 없는 Redis | 동일 현상 재현. 프로젝트 앱·마운트·포트 설정만의 문제로 설명할 수 없음 |
| 동일 컨테이너 재시도 | 일회용 Redis는 첫 시작 10초 timeout, 두 번째 시작 약 0.15초 성공 |
| 인프라 재검증 | 볼륨 초기화·Redis·PostgreSQL·Kafka·DynamoDB 모두 첫 timeout 뒤 두 번째 시작 성공, 4개 서비스 healthy 확인 |

이는 **Docker 연결 실패가 아니라 신규 컨테이너 시작 경로의 정체**다. 처음에는 Compose 한정 문제로 의심했지만 직접 시작에서도 재현되어 이 가설을 수정했다. Docker 내부에서 첫 요청이 멈추는 정확한 원인은 확정하지 못했으며, 특정 버전의 알려진 버그라고 단정하지 않는다. Docker Desktop 로그와 상태 조회에서도 해당 컨테이너의 명시적 시작 오류·OOM은 확인되지 않았다.

PoC 도구에는 위의 제한된 상태 확인·재시도만 적용했다. Docker 업데이트·초기화·전역 설정 변경은 하지 않았다. 재시도는 실제 동작을 확인한 국소 대응이며 Docker 내부 원인을 해결한 패치는 아니다. 컨테이너별 원본 기록과 전체 실행 결과는 후속 검증 JSON에 보존한다.
