# 카프카 패치와 성능 재검증

검증일: 2026-09-24. [이전 모니터링 성능 시험](20-모니터링-동시-실행-성능-검증.md)에서 Kafka 4.0.0 coordinator 오류와 offset 재처리가 관측되어, 같은 4.0 계열의 수정 버전으로 바꾸고 동일 부하를 재검증한다.

## 왜 이 버전을 선택했나

이전 broker 로그에는 음수 histogram, `__consumer_offsets` 상태 불일치, coordinator 재적재가 있었다. Dispatch에서는 commit 실패 뒤 한 건을 재처리했고 멱등 완료 기록으로 추가 외부 호출을 차단했다. 데이터 정합성은 통과했지만 무장애 성능 기준선으로 쓰기에는 부적절했다.

[Apache KAFKA-19888](https://issues.apache.org/jira/browse/KAFKA-19888)은 동일 증상을 기술하며 4.0.0을 영향 버전, 4.0.2를 수정 버전 중 하나로 명시한다. [공식 Kafka 4.0.2 릴리스 노트](https://archive.apache.org/dist/kafka/4.0.2/RELEASE_NOTES.html)에도 해당 수정이 포함된다. 따라서 Compose의 `apache/kafka:4.0.0`을 `apache/kafka:4.0.2`로 변경했다. 로컬 시계 변화 자체는 계측하지 않아 이전 장애의 트리거를 확정하지 않는다.

## 교체 범위와 데이터 보존

실제 교체는 `platform-monitoring`의 Kafka 컨테이너 한 개만 수행했다. 루트 Compose의 버전 변경은 이후 개발·PoC 환경을 생성할 때도 적용되지만 이미 실행 중인 다른 프로젝트를 재시작하지 않았다.

1. 이미지 다운로드를 완료하고 데모/부하 실행 lock을 획득했다.
2. 기존 committed lag=0을 확인하고 모든 업무 토픽의 partition별 보관 시작·끝·group committed offset을 저장했다.
3. 클러스터 `meta.properties`, 실행 중인 컨테이너 ID·시작 시각·image를 기록했다.
4. 전용 포트를 지정한 Compose에서 `up -d --no-deps --wait kafka`로 broker만 교체했다.
5. 모든 업무 토픽의 offset·보관 범위와 클러스터 메타데이터가 교체 전과 동일하고, 다른 컨테이너 ID·시작 시각도 그대로인지 대조했다.
6. 적체 0과 Grafana 76개 질의·10개 수집 대상 복구를 확인했다.

데이터 볼륨 삭제, offset reset, 토픽 재생성, metadata feature version 변경은 수행하지 않았다. 교체 자료는 `.monitoring/kafka-patch/`에 남겼다. 로컬 broker가 한 개이므로 이 교체 절차는 무중단 rolling upgrade 검증이 아니다.

| 토픽 | 파티션 수 | 교체 전/후 보관 record 수 | 교체 후 group committed 합계 |
|---|---:|---:|---:|
| delivery.requested.v1 | 3 | 32,255 / 32,255 | 32,255 |
| delivery.dispatch-requested.v1 | 3 | 32,255 / 32,255 | 32,255 |
| delivery.requested.dlt.v1 | 3 | 0 / 0 | 소비 group 없음 |

표는 요약이며 실제 검사는 합계만이 아니라 partition별 시작·끝·commit 값을 비교했다.

교체 후 이미지: `apache/kafka:4.0.2`, 실제 image ID `sha256:836cafdad9f4825880d7cf1d5a21202915ae2527bd0ef1c3600c526ed7814d1f`.

## 시험 판정 보강

이전 시험은 완주·정합성이 맞으면 commit 오류가 일시 발생해도 `pass=true`가 될 수 있었다. 이제 모니터링용 benchmark는 각 단계 시간 범위의 Kafka·API·Ingress·Dispatch 로그를 압축 보존하고 다음을 함께 검사한다.

- 음수 histogram과 coordinator 상태 불일치.
- WARN을 포함한 offset commit 실패.
- ERROR 수준 로그.
- 로그 수집 자체의 실패.

`dataAndLoadPass`는 기존의 입력·응답·Kafka·DB·업체 대조, `runtimeHealthy`는 로그 검사 결과다. 최종 `pass`는 둘 다 참이어야 하며 런타임 오류를 찾으면 다음 입력률 단계로 진행하지 않는다. 수집은 해당 단계의 입력·배출·데이터 대조 이후 수행하므로 그 단계의 즉시 장애 차단 장치는 아니다. 입력 중 기존 적체 증가·DLT·운영 확인·앱 재시작 등 중단 조건은 그대로 적용된다.

기존 실제 장애 로그를 새 판정기에 넣으면 실패로 검출된다. broker 자료는 histogram 신호 5줄·상태 불일치 1줄·ERROR 7줄, Dispatch 자료는 commit 실패 3줄·ERROR 1줄이었다. 여러 signal이 한 줄에 중복될 수 있으며 이 수치는 고유 장애 건수가 아니다.

Python 로그 판정 회귀 시험 4건과 기존 요청별 대조 시험 8건을 통과했다. 애플리케이션 Java 코드는 변경하지 않았으므로 이번 패치 검증을 위해 Java 단위 시험을 반복하지 않았다.

## 동일 부하 재검증

```bash
bash scripts/monitoring.sh benchmark --suite baseline
```

- 실행 ID: `20260924T121505Z-075d4b00`.
- 기준 커밋: `565728e`, 시작 시 작업 트리 clean.
- Worker 동시성 3, Ingress linger 5ms, RECORD ack, 앱 JAR·시뮬레이터 설정 유지.
- 고객 1개, JSON 1,009byte, 외부 중복 제거 off, 업체 지연 0ms.
- 소량 고유·중복 → 10 TPS 1분 워밍업 → 100 TPS 20초 중복 → 50/100 TPS 각 3분.
- Prometheus·Loki·Alloy·collector·exporter와 Grafana는 계속 실행.
- 원시 자료: `.poc-results/20260924T121505Z-075d4b00/`.

**모든 단계가 완주·정합성 및 런타임 로그 검사를 통과했다.** 고유 28,617건(HTTP 제출·응답 29,622회)에서 미응답·dropped iteration·미설명 누락·외부 추가 호출·DLT·신규 운영 확인이 없었다. 검사한 로그에서는 음수 histogram·coordinator 상태 불일치·commit 실패·ERROR가 모두 0이었다.

지연 단위는 ms. ‘접수 저장’은 최종 전달 완료가 아니라 최초 인입부터 업체 접수 결과를 저장하는 단계다.

| 단계 | 제출/응답 | 고유 요청 | API p95 | 접수 저장 p50 / p95 / p99 | 최대 lag | 데이터/로그 |
|---|---:|---:|---:|---:|---:|---|
| 소량 고유 | 11 / 11 | 11 | 101.58 | 43.85 / 153.30 / 217.98 | 7 | 통과 / 통과 |
| 소량 중복 | 10 / 10 | 5 | 38.61 | 38.25 / 69.98 / 76.32 | 7 | 통과 / 통과 |
| 10 TPS 워밍업 | 600 / 600 | 600 | 15.81 | 30.82 / 40.21 / 47.40 | 23 | 통과 / 통과 |
| 100 TPS 중복 20초 | 2,000 / 2,000 | 1,000 | 21.20 | 63.49 / 1207.61 / 1426.15 | 59 | 통과 / 통과 |
| 50 TPS 180초 | 9,001 / 9,001 | 9,001 | 10.62 | 21.81 / 33.46 / 66.44 | 29 | 통과 / 통과 |

50/100 TPS의 종료 후 두 번 lag=0 관측까지 각각 12.49/12.44초였다. 수집 간격을 포함한 상한으로, 개별 메시지의 실제 대기 시간과 다르다. 100 TPS의 최장 Kafka 대기 관측은 2.38초였다.

정상 고유 입력에서 50 TPS는 Put 성공 9,001회·Update 성공 18,002회, 100 TPS는 Put 성공 18,000회·Update 성공 36,000회였다. 두 단계 모두 추가 Get·조건 불일치가 0이었다. 이전 100 TPS의 재처리에 동반됐던 추가 조건 불일치 1회·Get 1회도 이번 단계에서는 관측되지 않았다.

### 이전 실행과 비교

| 항목 | 4.0.0 이전 실행 | 4.0.2 이번 실행 |
|---|---:|---:|
| 50 TPS 접수 저장 p95 | 43.15ms | 33.46ms |
| 100 TPS 접수 저장 p95 | 414.53ms | 2,231.73ms |
| 100 TPS 최대 lag | 51 | 292 |
| 100 TPS API 응답 p95 | 10.64ms | 11.40ms |
| 100 TPS 데이터 대조 | 통과 | 통과 |
| 시험 중 broker/commit 오류 | 있음 | 검사 대상 오류 0 |

**패치 후 해당 오류는 이번 시험에서 재발하지 않았지만 지연 품질이 개선됐다고 볼 수는 없다.** 100 TPS의 API 응답은 빠르게 유지됐으나 일부 요청은 큐에서 기다렸다. 자동 통과에는 특정 latency SLO가 없으므로 `pass=true`를 지연 목표 달성으로 해석하지 않는다.

실제 100 TPS 입력 시작 후 약 172.0초의 최대 적체 292건은 Ingress 앞 200건·Dispatch 앞 92건이었다. 약 29.0초에도 233건이 관측됐다. 입력 iteration을 10초 구간으로 나눠 DB 시각 기반 지연을 계산하면 170~180초 구간의 p95는 3,179.74ms, 160~170초는 2,859.96ms, 20~30초는 2,297.01ms였다. 이는 입력 시점별 묶음이며 샘플 간 순간 최고 적체를 뜻하지 않는다.

구간 Timer 평균은 100 TPS에서 Ingress 전체 12.88ms(저장 7.70ms·발행 5.08ms), Dispatch 전체 14.18ms(claim 6.20ms·HTTP 1.72ms·결과 저장 6.18ms)였다. Consumer commit max 지표에서 관측한 최댓값은 Ingress 263ms, Dispatch 143ms였다. 서로 집계 창이 다르므로 이 수치를 단순 합산해 느린 요청 한 건의 원인으로 확정하지 않는다.

모든 부하 종료 후 Grafana 76개 질의·10개 수집 대상·처리 기록·Kafka 적체 해소를 재검증했다. 앱과 대시보드는 계속 실행 중이다.


## 한계와 후속 판단

이번 교체는 로컬 단일 broker의 패치 적용과 단기 부하 검증이다. 다중 AZ 무손실·운영 rolling upgrade·모든 실패 경로를 보장하지 않는다. 로그에서 오류를 찾지 못한 것만으로 모든 장애가 없었다고 증명하지도 않는다. 메트릭·전수 대조·로그를 함께 해석한다.

이전 실행과 앱 배치는 같지만, broker 재시작·누적 데이터·앱 warm 상태·호스트 부하·실행 순서는 다르다. 지연 수치의 차이를 모두 Kafka 패치 효과로 단정하지 않는다. 해당 오류를 일부러 재현하기 위한 시스템 시계 변경도 수행하지 않았다.

다음 성능 작업은 입력률을 바로 올리기 전에 **100 TPS에서 일시 정체가 생기는 구간을 분리하는 것**이다. Ingress/Dispatch별 파티션 처리량, DB 구간의 순간 지연, commit 대기와 Kafka·DynamoDB Local·JVM 자원 시계열을 같은 시간 범위로 맞춰 비교한다. 충분한 근거 없이 멱등 저장이나 ack 대기를 제거하지 않는다. 이후 동일 조건 반복과 업체 지연 조건을 검증한 뒤 200 TPS 이상으로 확장한다.

보존 자료의 구간 평균과 audit 관측을 다시 비교한 [100 TPS 일시 적체 구간 분석](22-백-TPS-일시-적체-구간-분석.md)을 추가했다. 기존 적체 시각은 첫 수집 표본 기준이어서 최초 입력 기준으로 정정했다. DB 호출과 API ack 대기가 함께 늘었지만 단일 원인은 미확정이며, 후속 계측을 남기고 업무 기능 개발을 진행한다.
