# 요청 접수부터 최종 결과까지의 전체 호출 흐름

> **1차 발송 경로 변경:** [ADR-026](adr/ADR-026-EVENT-RECEIVED와-통신사별-HTTP-발송-분리.md)이 아래의 API → 단일 HTTP sender 직접 토픽, 발송 전 STEP 선점, 단일 sender Pod 서술을 대체한다. API는 `event.received.v1`에 발행하고, PRE-SEND-MANAGER가 계약·전화번호별 통신사를 확인해 통신사별 HTTP 발송 토픽으로 완성된 전문을 보낸다. 통신사별 sender는 Redis로 발송 중복을 처리하고 발송 후 DynamoDB에 결과·시각을 저장한다. 아래의 나머지 전체 흐름은 이 변경을 반영하기 전의 목표 기록이며 신규 경로의 구현 완료를 뜻하지 않는다.

기준: 2026-10-02 목표 접수·HTTP/TCP 분리 경로와 기존 v2 후속 발송 정책. ORIGIN 선접수·API 직접 발행·고객 중복·발송 Pod 분리는 이관 중이다. 현재 코드와 검증 범위는 [01 구현 상태](01-현재-구현-상태와-남은-작업.md), 결정 근거는 [ADR-025](adr/ADR-025-API-직접-Kafka-발행과-계약-조회-제거.md)·[ADR-024](adr/ADR-024-HTTP와-TCP-발송-워커-분리.md)를 따른다. 기존 v1 호환 경로는 [이전 구현 문서](29-주기-만료와-요청-최종화-및-Kafka-인계.md)를 참고한다.

## 1. 참여자와 저장소

| 참여자 | 역할 |
|---|---|
| 고객 → EVENT-RECEIVE-API | JWT·본문 처리·중복 확인, ORIGIN 저장 직후 Kafka 직접 발행과 202 |
| event-publication-recovery-app | API 발행 실패·응답 불명 시 ORIGIN·STEP 대조 후 동일 실행 재발행 |
| event-http-sender | 최초·재시도 Kafka 명령 소비, 1차 STEP 선점·HTTP 호출·즉시 응답 기록과 결과 이벤트 인계 |
| event-tcp-sender | 2차·재시도 Kafka 명령 소비, 2차 STEP 선점·TCP 호출·즉시 응답 기록과 결과 이벤트 인계 |
| EVENT-RESULT-MANAGER | 두 단계의 즉시 응답·업체 웹훅·기한을 한 곳에서 판단해 재시도·2차 전환·최종 결과 인계 |
| 외부 업체 / external-api-simulator | 접수 응답과 별도 HTTP 결과 웹훅. TCP 응답도 접수 확인 |
| receipt-api | 업체 인증·형식 검증, Kafka 저장 확인 뒤 웹훅 접수 응답 |
| delivery-result-worker | PostgreSQL 이력·통지·정리 예약 저장, 고객 HTTP 통지, DDB 정리 |
| Redis | 고객 중복키, 만료 후보 일정 |
| ORIGIN | 실행별 최초 접수 원본·현재 상태·완료 보호 |
| STEP | 실행별 단계 선점·설정·회차·deadline·결과·최종 이벤트 |
| PostgreSQL | 최종 이력, 고객 통지 상태와 묶음/재전송, 정리 예약 |

## 2. 정상 1차 성공 Call Flow

```mermaid
sequenceDiagram
    autonumber
    actor C as 고객
    participant A as EVENT-RECEIVE-API
    participant B as 발행 복구 앱
    participant K as Kafka
    participant R as Redis
    participant D as DynamoDB ORIGIN·STEP
    participant S as event-http-sender
    participant M as EVENT-RESULT-MANAGER
    participant P as HTTP 1차 업체
    participant W as receipt-api
    participant H as result-worker
    participant Q as PostgreSQL
    C->>A: POST /api/v1/events (본문 eventId·수신번호·eventType 등)
    A->>R: 고객 중복 확인
    A->>D: 새 executionId의 ORIGIN RECEIVED 조건부 Put
    D-->>A: 저장 확인
    A->>K: event.http.requested.v1 send 시작 (ack 비동기, executionId 고정)
    A-->>C: 202 + executionId (영속 접수)
    opt API 발행 실패·ack 불명확 또는 저장 직후 종료
        B->>D: 미진행 ORIGIN·STEP 대조
        B->>K: 같은 executionId로 재발행
    end
    K->>S: EventRequested
    S->>D: ORIGIN 미완료 검사 + STEP 최초 선점
    S->>P: HTTP 발송
    P-->>S: 접수 확인
    S->>D: STEP 즉시 관찰 결과 기록
    S->>K: event.http.outcome.v1 / 접수 결과 (저장 ack 확인)
    K->>M: 1차 접수 결과
    M->>R: 실행 UUID·1차 deadline 등록
    P->>W: 성공 결과 HTTP 웹훅
    W->>K: event.http.outcome.v1 / 성공 웹훅 (저장 ack 확인)
    W-->>P: 202
    K->>M: 1차 성공 웹훅
    M->>D: STEP 결과·최종 이벤트 + ORIGIN 완료 보호 (트랜잭션)
    M->>R: 실패 시 재인계할 즉시 후보 등록
    Note over M,K: 성공 결과 저장 직후 동일 소비자가 최종 이벤트 즉시 인계
    M->>K: event.finalized.v1 (저장 ack 확인)
    M->>R: 만료 일정 제거
    K->>H: 최종 이벤트
    H->>Q: 이력 + 통지 예약 + 정리 예약 (단일 트랜잭션 commit)
    par 고객 통지 작업
        H->>Q: 동일 고객 최대 100건 묶음 선점
        H->>C: 결과 HTTP POST + 묶음 Idempotency-Key
        C-->>H: 204
        H->>Q: 통지 완료 기록
    and 발송 데이터 정리 작업
        H->>Q: 이력·통지 예약의 저장 확인
        H->>R: 성공 시 executionId 일치 확인 후 성공 시각부터 2시간 차단
        H->>D: 해당 실행 ORIGIN·STEP 조건부 삭제
        H->>Q: 정리 완료 기록
    end
```

- API의 202는 ORIGIN 저장 확인이다. Kafka 발행·업체 접수·최종 성공·고객 결과 수신은 별도 단계다.
- 업체의 HTTP·TCP 접수 확인은 발송 요청을 받았다는 뜻이며 최종 성공이 아니다. 해당 sender는 자기 STEP에 즉시 응답을 기록하고 단계별 outcome 토픽에 인계한다. `EVENT-RESULT-MANAGER`가 업체 웹훅·즉시 실패·deadline을 함께 판단해 코드별 재시도·허용된 2차 전환·최종 성공/실패/만료를 결정한다. 웹훅이 없으면 Manager가 원래 deadline에 만료를 판단한다.
- API가 ORIGIN 저장 직후 Kafka 발행을 시작한다. 실패·ack 불명확이나 저장 직후 종료에 대비해 미진행 ORIGIN을 STEP·최종 이력과 대조해 재발행한다. API의 ack가 불명확해도 `event-http-sender`가 Kafka 레코드를 읽으면 진행할 수 있다. 같은 `executionId`로 재발행할 수 있어 Kafka 기록은 중복 가능하며, 업체 발송은 단계별 STEP 선점으로 제어한다. 목표 구조에서는 `delivery-ingress-worker`의 ORIGIN 저장 역할이 API로 이동하므로 별도 ingress 워커와 `DispatchRequested` 인계가 없다.
- ORIGIN 완료 Update는 **현재 구현**이다. 이를 STEP 조건으로 대체하는 최소화는 검토안이며 아직 적용하지 않았다.
- 최종 이벤트는 terminal STEP에 보존한다. 별도 FINAL 항목이나 Kafka ack 이후 DDB Update를 만들지 않는다. SQL 인계 전 종료하면 같은 결과를 다시 발행할 수 있다.
- 현재 v2 단일 worker의 성공 웹훅 즉시 인계와 만료·실패 Lifecycle 경로는 목표 구조에서 Manager로 이관한다. STEP의 불변 최종 이벤트를 저장한 직후 같은 결과를 Kafka에 발행하고 broker ack 뒤에 입력 처리를 마친다. 발행 실패 시 입력을 재처리하고 STEP에서 같은 결과를 복구한다. [현재 구현의 즉시 인계 검증](39-성공-결과의-즉시-Kafka-인계와-복구-검증.md).
- 고객 통지와 발송 데이터 정리는 SQL commit 이후 독립 진행한다. 고객 204를 기다려야만 ORIGIN·STEP을 지우는 구조가 아니다. 통지 재시도에 필요한 데이터는 SQL에 있다.
- 정리는 기본 4개 작업자가 각 SQL lease로 다른 결과를 처리한다. 작업자마다 한 건씩 선점·정리·완료하고 tick당 최대 20건을 처리한다. SQL 선점 token과 DDB 실행·버전 조건은 유지한다. [동시 정리와 검증](40-완료-데이터-정리의-동시-처리와-성능-검증.md).
- 기존 구현의 정상 DDB 쓰기는 **5회 API 호출·7항목 변경**이다. 목표 경로는 API의 ORIGIN 선저장과 발송 전 조건 확인·복구 조회가 추가되므로 다시 계측해야 한다. 최초 발행 ack 후 ORIGIN 갱신은 없다. [기존 세부 합산](36-원본과-단계-테이블-분리와-경로별-쓰기-내역.md).

## 3. 식별자와 중복 요청

| 값 | 의미 |
|---|---|
| 고객 중복키 | `(clientId, eventId, recipientNumber)`. Redis에서 활성 상태와 성공 후 2시간 차단 |
| executionId | API가 허용된 새 실행마다 생성하는 UUID. 업체 호출·웹훅·SQL 이력의 실행 구분 |
| attemptId | 실행·업체·단계로 구분하는 단계 ID. 같은 단계 재시도마다 새 항목을 만들지 않음 |
| retryCount / invocation / version | 최대 3회 재시도와 호출 회차·조건부 갱신을 구분 |
| 고객 eventId / 결과 event ID | 전자는 요청 본문에서 받는 고객 ID, 후자는 같은 실행의 최종 Kafka 기록 ID. SQL에서는 실행별 결과로 수렴 |

활성 중복 요청은 Redis에 저장된 기존 `executionId`를 반환·조회하며 새 실행을 만들지 않는다. 같은 고객 중복키에 다른 내용이면 충돌로 처리한다. 성공 시 SQL 이력 정리와 함께 성공 시각부터 2시간 차단하고, 실패·만료 등 나머지 최종 상태에서는 실행 ID가 일치하는 Redis 키를 제거한다. Redis 장애 중에는 같은 고객 이벤트에 별도 실행이 생길 수 있지만, 동일 `executionId`의 Kafka 중복은 STEP 선점으로 제어한다.

## 4. 실패 응답·실패 웹훅과 재시도

```mermaid
sequenceDiagram
    participant P as 업체 HTTP 또는 TCP
    participant S as 해당 단계의 sender
    participant K as 단계별 Kafka outcome·retry topic
    participant M as EVENT-RESULT-MANAGER
    participant D as STEP
    P-->>S: 재시도 코드 또는 관찰한 무응답
    S->>D: 해당 회차의 즉시 결과 기록
    S->>K: 단계별 outcome 발행 (ack 확인)
    K->>M: 즉시 결과
    M->>M: deadline·3회 한도·실패 코드 판단
    M->>K: source version·회차·target 회차·notBefore 고정 재시도 명령
    K-->>M: 저장 ack
    K->>S: 해당 단계 Retry Consumer (notBefore까지 대기)
    S->>D: 원래 version·회차·deadline·미종료 조건으로 다음 회차 선점
    alt 선점 성공
        S->>P: 같은 단계 재시도
    else 이미 완료·다른 회차·만료
        Note over S,P: 추가 발송 차단, 만료 판단은 복구 경로
    end
```

실패 웹훅도 receipt-api → 단계별 outcome 토픽 → Manager를 거쳐 같은 판단으로 연결된다. Manager는 HTTP 재시도를 `event.http.retry.v1`, TCP 재시도를 `event.tcp.retry.v1`로 인계한다. 각 단계는 최초 1회 + 재시도 최대 3회다. 고정 명령을 재소비해도 회차를 임의로 더 올리지 않는다. 재시도 시간 때문에 deadline을 연장하지 않는다.

외부 호출과 DB 저장은 원자적이지 않다. 무응답 재시도는 업체가 이미 처리한 경우 외부 중복 가능성이 있다. 선점 후 종료되어 결과를 기록하지 못한 경우는 운영 확인 대상이며 lease 만료만으로 무조건 재발송하지 않는다. 운영 확인 중에도 업무 만료는 적용한다.

## 5. TCP 2차 대체 발송

```mermaid
sequenceDiagram
    participant M as EVENT-RESULT-MANAGER
    participant K as Kafka
    participant S as event-tcp-sender
    participant D as ORIGIN·STEP
    participant R as Redis
    participant T as TCP 2차 업체
    participant W as receipt-api
    M->>D: 1차 DECISION_PENDING·사유·판단 시각 저장
    alt fallbackAllowed이고 대체 가능한 사유
        M->>D: 1차 STEP에 2차 업체·단계 ID·deadline 고정
        M->>K: event.tcp.requested.v1 발행 (ack 확인)
        K->>S: 같은 executionId의 2차 요청
        S->>D: 1차 판단·바인딩 확인 + 2차 STEP 선점
        S->>T: TCP 메시지 발송
        T-->>S: 접수 확인
        S->>D: 2차 STEP ACCEPTED
        S->>K: event.tcp.outcome.v1 / 접수 결과
        K->>M: 2차 접수 결과
        M->>R: 2차 deadline 일정 등록
        T->>W: 최종 결과 HTTP 웹훅
        W->>K: event.tcp.outcome.v1 / 최종 웹훅
        K->>M: 2차 결과 이벤트
        M->>D: 성공 시 2차 결과·최종 이벤트 + 1차 종료 + ORIGIN 완료 보호
    else 대체 비허용 또는 대체 대상 아닌 영구 실패
        M->>D: 1차 결과로 전체 최종화
    end
```

대체 사유는 `FALLBACK_REQUIRED`, `PRIMARY_EXPIRED`, `RETRY_EXHAUSTED_NO_RESPONSE`다. 모든 실패나 모든 재시도 소진이 대체 발송으로 이어지지는 않는다. Manager가 1차 판단과 2차 바인딩을 STEP에 저장한 뒤 Kafka로 인계하므로 발행 ack 유실·중단 시 같은 인계 내용을 재발행할 수 있다. TCP sender는 2차 STEP 조건부 선점으로 중복 호출을 막는다. 2차도 재시도·미수신 만료를 적용하며 세 번째 업체로 넘어가지 않는다. 어느 단계에서 확정되든 Manager가 `event.finalized.v1` → SQL → 고객 통지·정리로 인계한다.

## 6. 만료와 Redis 누락 복구

| 항목 | 기준 |
|---|---|
| 1차 deadline | 최초 인입 +3시간 |
| 2차 deadline | 1차 결과 판단 시각 +4시간 |
| Redis 정상 후보 조회 | Sorted Set, 기본 1초 |
| DDB 누락 복구 | ORIGIN·STEP GSI, 시작 직후 1회 이후 기본 10분 |
| 최종 판정 | STEP 상태·version·deadline을 조건부 확인 |

```mermaid
flowchart TD
    R[Redis 일정 조회] --> C[처리 후보]
    G[DDB GSI 10분 주기 누락 복구] --> C
    C --> F{이미 최종 이벤트가 있는가}
    F -- 예 --> K[동일 최종 이벤트 Kafka 재인계]
    F -- 아니오 --> D[원본·STEP 최신 상태 읽기]
    D --> E{미완료이며 deadline 경과}
    E -- 아니오 --> W[필요한 인계 복구 또는 대기]
    E -- 예 --> X[조건부 만료 판단 저장]
    X --> S{1차이며 대체 허용}
    S -- 예 --> T[원래 1차 deadline 기준으로 2차 경로 결정]
    S -- 아니오 --> Z[전체 EXPIRED 결과 확정]
    T --> U{2차 deadline도 경과}
    U -- 예 --> Z
    U -- 아니오 --> P[TCP 2차 발송]
```

Redis 일부 일정만 유실될 수도 있어, Redis가 비어 있을 때만 DDB를 조회하지 않는다. DDB TTL 삭제 이벤트는 복구 수단으로 사용하지 않는다. 10분은 조회 간격이며 페이지 적체·장애까지 포함한 복구 완료 상한이 아니다. 1차 만료를 늦게 처리해도 2차 기준은 처리 시각이 아니라 원래 1차 deadline이다. 장기 장애 뒤 양쪽 기한이 지났으면 외부 발송 없이 만료 결과를 만든다.

만료 후 웹훅은 로그/관측만 남기고 업무 상태에 반영하지 않는다. 먼저 확정된 성공을 만료로 덮어쓰지 않도록 상태·버전 조건으로 경합을 막는다. [Redis·DDB 역할 및 공식 근거](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md).

## 7. 고객 결과 HTTP 실패·중복

같은 고객의 준비된 결과를 최대 100건으로 묶고, 건수를 채우기 위해 오래 대기하지 않는다. HTTP 204가 묶음 전체 ack이며 그 외 응답·무응답은 SQL에 다음 재시도를 기록한다. 최초 + 최대 20회 재전송, 총 21회다. 소진하면 EXHAUSTED로 남겨 운영 확인한다.

고객이 처리한 뒤 응답만 유실되면 같은 묶음이 다시 도착할 수 있다. 같은 묶음 ID와 결과 이벤트 ID를 유지하므로 고객도 중복 처리를 막아야 한다. 우리 SQL 선점은 동시 발송·회차 혼선을 제어하지만 고객의 외부 효과까지 exactly-once로 만들지는 못한다. [묶음·응답·소진 계약](31-고객-HTTP-묶음-통지와-재전송-복구.md).

## 8. 토픽과 장애 경계

목표 토픽은 [ADR-024](adr/ADR-024-HTTP와-TCP-발송-워커-분리.md)에 정한다. 최초 이벤트는 HTTP sender가 직접 소비하고, sender·receipt-api의 단계별 결과는 Manager가 판단한다. Manager가 재시도·2차 전환·최종 토픽으로 인계한다. 아래 `delivery.*`는 현재 코드의 이관 전 토픽이다.

| 목표 토픽 | 생산 → 소비 |
|---|---|
| `event.http.requested.v1` | EVENT-RECEIVE-API·발행 복구 앱 → event-http-sender |
| `event.http.outcome.v1` | event-http-sender·receipt-api → EVENT-RESULT-MANAGER |
| `event.http.retry.v1` | EVENT-RESULT-MANAGER → event-http-sender |
| `event.tcp.requested.v1` | EVENT-RESULT-MANAGER → event-tcp-sender |
| `event.tcp.outcome.v1` | event-tcp-sender·receipt-api → EVENT-RESULT-MANAGER |
| `event.tcp.retry.v1` | EVENT-RESULT-MANAGER → event-tcp-sender |
| `event.finalized.v1` | EVENT-RESULT-MANAGER → result-worker |

| 현재 구현 토픽 | 생산 → 소비 |
|---|---|
| delivery.requested.v1 | event-api → ingress-worker |
| delivery.dispatch-requested.v1 | ingress-worker → dispatch-worker |
| delivery.receipt-received.v1 | receipt-api → dispatch-worker 결과 소비자 |
| delivery.retry.v1 | dispatch-worker → 별도 재시도 소비자 |
| delivery.finalized.v1 | dispatch-worker → result-worker |

| 멈춘 위치 | 남는 근거와 재개 |
|---|---|
| API ORIGIN 저장 뒤 응답 전 | 고객 재요청 가능. 응답 유실만으로 미접수나 미발송을 단정하지 않고 고객 중복키·원문·실행을 대조 |
| ORIGIN 저장 뒤 최초 Kafka 발행 전 | ORIGIN·STEP·이력 대조 복구 |
| sender의 STEP 결과 저장 뒤 outcome Kafka 발행 전 | STEP의 동일 회차 결과를 조회해 outcome 재발행. 호출 결과 미기록이면 운영 확인 |
| Manager의 1차 STEP 전환 저장 뒤 TCP Kafka 인계 전 | 고정된 1차 판단·2차 바인딩을 대조해 같은 2차 이벤트 재발행 |
| STEP 선점 뒤 외부 결과 저장 전 | STEP 보존, 운영 확인·원래 기한 만료 |
| 최종 STEP 저장 뒤 Kafka 인계 전 | 불변 최종 이벤트·GSI로 재발행 |
| SQL commit 전 | Kafka offset 미완료, 동일 이벤트 재소비 |
| SQL commit 뒤 DDB 삭제 전 | SQL 정리 예약 재처리 |
| DDB 삭제 뒤 정리 DONE 전 | 같은 실행의 삭제 여부 확인, 새 실행 원본 보존 |
| Redis 일정 소실 | 10분 주기 DDB 복구, 원래 deadline 유지 |

## 9. 검증과 미구현 경계

실제 코드 근거는 `DeliveryRepository`, `DispatchAttemptRepository`, `ReceiptResultRepository`, `LifecycleService/Repository/Scheduler`, `FinalizedStore`, `NotificationService/Repository`, `DeliveryCompactor`다. 구간별 검증과 쓰기 횟수는 [35번](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md)·[36번](36-원본과-단계-테이블-분리와-경로별-쓰기-내역.md)을 참고한다.

전체 v2 경로의 격리 실행 도구·케이스별 전수 대조·실행 결과는 [37번 문서](37-전체-호출-흐름의-격리-실행과-전수-대조.md)에 구분한다.

이 문서는 현재 코드의 호출 순서를 설명한다. 운영 배포·다중 AZ 무손실·고 TPS 전체 흐름의 검증 완료를 뜻하지 않는다. 주기 만료, 고객 통지, 정리는 각각 설정으로 활성화해야 한다. 별도 과금·통계 Consumer나 운영 조회/수동 조치 API는 이 Call Flow에 구현된 기능으로 포함하지 않는다.
