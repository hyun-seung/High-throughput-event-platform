# 대체 발송 허용과 TCP 2차 접수

> 2026-09-25 전송 계층 갱신: Java Socket 요청별 연결을 Netty의 제한된 지속 연결 풀로 바꿨습니다. [현행 연결 계약·설정·검증](46-Netty-TCP와-HTTP-연결-풀-적용.md). 아래 업무 정책은 유지하며 이전 전송 구현 설명보다 이 갱신을 우선합니다.

구현·검증일: 2026-09-24. 1차 HTTP의 판단 결과를 저장한 뒤, 허용된 요청만 TCP 2차 업체로 보내는 경로를 연결했다. **TCP 접수 확인은 최종 전달 성공이 아니다.** 업체 최종 웹훅·주기 만료·고객 결과 통지는 아직 없다.

이 문서는 `06f76df` 구현 당시의 범위와 시험 기록이다. 후속으로 [업체 웹훅의 인증·Kafka 접수](26-업체-결과-웹훅의-인증과-Kafka-접수.md)를 추가했으며, 실제 결과 상태 처리·주기 만료·고객 통지는 계속 남아 있다.

## 최초 요청에서 허용 여부 고정

```json
{
  "deliveryType": "SMS",
  "fallbackAllowed": true,
  "payload": {"message": "test", "simulatorResultCode": "FALLBACK"}
}
```

`fallbackAllowed`는 payload가 아닌 최상위 필드다. 생략·null은 false이며 이전 요청·Kafka event·META 항목도 false로 읽는다. API → Kafka → 원본 저장 → Dispatch에 값을 전달한다. 같은 고객 멱등키로 허용 여부를 변경하면 Ingress에서 멱등 충돌로 격리한다. 기존 요청에 나중에 2차 발송을 추가하는 기능은 아니다.

현재 전환 조건은 `fallbackAllowed=true`이면서 1차 판단 사유가 다음 중 하나일 때다.

| 사유 | 2차 만료 기준 시각 |
|---|---|
| FALLBACK_REQUIRED | 1차 코드 수신·판단 시각 |
| RETRY_EXHAUSTED_NO_RESPONSE | 최초 외 3회 무응답 재시도 소진 판단 시각 |
| PRIMARY_EXPIRED | 1차 만료 시각. 늦게 복구된 시각을 사용하지 않음 |

명시적 영구 거절과 RETRY_1S·RETRY_10S 코드 재시도 소진은 자동 2차로 전환하지 않고 DECISION_PENDING에 보존한다. 명시적 실패 코드 소진 후 처리는 [기존 미정 범위](08-함께-결정할-설계-사항.md)에 남아 있다. 허용하지 않은 요청도 판단 기록은 유지하며, 고객 최종화로 연결하는 기능은 후속이다.

## 저장과 복구 순서

1. 1차 Attempt의 DECISION_PENDING·사유·판단 시각을 저장한다.
2. 같은 1차 항목에 `secondary_attempt_id`, `secondary_provider`, `secondary_deadline`을 조건부로 한 번 고정한다.
3. 별도 2차 Attempt를 조건부 선점한다. ID는 deliveryId·2차 provider·routeOrder=2·attemptNumber=1로 결정한다.
4. TCP 업무 응답을 검증하고 2차 Attempt에 ACCEPTED를 저장한다. 최종 성공 상태는 만들지 않는다.
5. 그 뒤 원본 Kafka listener가 완료된다. 중간 저장·통신 오류는 기존 재전달 경로로 복구한다.

새 항목은 공통 기한 필드 `deadline_at`과 `route_order`를 사용한다. 기존 1차 항목의 `primary_deadline`도 읽을 수 있으며, 기존 항목 전체를 일괄 갱신하지 않는다. 구형 primary_deadline 예약의 재선점도 실제 DB에서 검증했다. 적용 순서는 새 event·기한 필드를 읽는 소비자 업데이트 후 새 API producer 업데이트다. 구버전 Worker와의 혼합 실행·롤백은 이번에 검증하지 않았다. 2차의 기본 기간은 4시간으로 1차 3시간과 다르다. 이미 고정된 2차 provider·deadline은 재시작이나 설정 변경으로 덮어쓰지 않는다. 고정된 업체가 현재 TCP 설정과 다르면 다른 업체로 보내지 않고 입력을 실패시켜 복구 대기한다.

1차 판단 저장 직후 종료하거나 2차 경로 저장의 응답을 잃어도, 재전달은 기존 1차 판단과 고정 경로를 사용한다. 2차 효과 발생 후 결과 저장 전 종료는 2차 PROCESSING lease 만료 후 REVIEW_REQUIRED로 남기며 자동 재발송하지 않는다. 무응답을 실제 관찰·저장한 2차 요청은 현재 개발 정책으로 최초 외 최대 3회 재시도하고, 2차 deadline을 유지한다. 접수 성공 기록이 있으면 최종 웹훅이 없다는 이유로 다시 보내지 않는다.

**왜 DynamoDB 저장을 추가하는가:** 2차 발송을 허용한 1차 판단과 대상·기한을 복구 가능하게 고정하고, 외부 TCP 부수 효과 전에 한 Worker만 선점해야 하기 때문이다. 이 설계는 DynamoDB의 조건부 Update를 사용한다. 두 항목과 외부 소켓을 하나의 트랜잭션으로 취급하지 않으며, 완료되지 않은 Kafka 입력과 조건부 기록을 이용해 중간 단계를 다시 진행한다. [AWS 공식 조건부 변경](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), 확인일 2026-09-24.

1차 정상 경로의 쓰기 수는 원본 Put 1회+선점/접수 Update 2회로 동일하다. 대체 경로에서만 1차 판단 저장 뒤 경로 고정 1회, 2차 선점·접수 저장 2회가 추가된다. 중복 조회·조건 실패·재시도 비용은 별도다. payload는 원본 META와 Kafka event에 유지하고 2차 항목에 복사하지 않는다.

## TCP 개발 계약

한 연결에서 요청 한 건과 응답 한 건을 교환한다. 프레임은 **4바이트 big-endian 길이 + UTF-8 JSON**이며 본문 최대 1MiB다. 헤더나 본문이 나뉘어 와도 선언된 길이까지 읽는다. 연결 성공·쓰기 성공·바이트 일부 수신만으로 접수 성공을 기록하지 않는다.

요청에는 deliveryId·attemptId·tenantId·deliveryType·payload·occurredAt을 넣는다. 응답 예시는 다음과 같다.

```json
{
  "deliveryId": "delivery-id",
  "attemptId": "secondary-attempt-id",
  "accepted": true,
  "processedAt": "2026-09-24T00:00:00Z",
  "code": "RECEIVED"
}
```

두 ID 일치, accepted·processedAt·code 존재, accepted=true와 RECEIVED 조합을 확인한다. 거절 응답은 RETRY_1S·RETRY_10S·REJECTED를 구분한다. 잘못된 ID·코드·JSON·길이는 INVALID_RESPONSE, EOF·불완전 프레임·연결/응답 timeout은 NO_RESPONSE다. 원시 업체 응답을 예외 로그로 전파하지 않는다.

TCP는 메시지 경계를 제공하지 않는 바이트 스트림이므로 애플리케이션 프레이밍을 별도로 정의했다. TCP 전송 확인과 업체 애플리케이션 접수를 분리하는 것은 프로젝트 계약이다. [RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2), [§3.7](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.7), 확인일 2026-09-24.

연결 timeout 기본 2초, 전체 소켓 교환 timeout 기본 5초다. 읽기 timeout 외에 전체 기한에 소켓을 닫는 타이머를 두어 쓰기 대기와 조금씩 들어오는 응답도 제한한다. 연결 pool·여러 요청의 다중화는 아직 없으며 TCP 성능 기준선도 측정하지 않았다.

## 테스트 서버와 실행 설정

기존 external-api-simulator가 HTTP와 별도 TCP 포트를 함께 연다. 업체 역할과 attemptId는 분리한다. Ledger는 **프로세스 메모리의 시험 관측 자료**이며 실제 업체의 영구 저장이나 무손실 보장이 아니다. TCP도 외부 중복 제거 기본값은 off다.

| 항목 | 기본값 / 설명 |
|---|---|
| SECONDARY_PROVIDER / SECONDARY_TTL | tcp-provider / 4h |
| EXTERNAL_TCP_HOST / EXTERNAL_TCP_PORT | localhost / 8093 |
| EXTERNAL_TCP_CONNECT_TIMEOUT / EXTERNAL_TCP_EXCHANGE_TIMEOUT | 2s / 5s |
| SIMULATOR_TCP_ENABLED / SIMULATOR_TCP_PORT | true / 8093 |
| SIMULATOR_TCP_BIND_ADDRESS | 127.0.0.1. 모니터링 Compose 내부는 0.0.0.0 |
| MOCK_TCP_PORT | local.sh 실행에서 양쪽 포트에 적용. .env.example은 18091 |

TCP 서버는 동시 연결 기본 128개, 교환 기본 5초로 제한한다. HTTP 전용 성능 PoC 실행기는 TCP 서버를 꺼 기존 격리 포트와의 충돌을 피한다. 모니터링 Compose는 내부 `simulator:8093`을 사용하며 TCP 포트를 호스트에 공개하지 않는다.

테스트 payload의 `simulatorTcpResultCode`는 2차 응답을 선택한다. 생략하면 ACCEPTED→RECEIVED다. 1차의 simulatorResultCode·forceFail을 2차에 그대로 적용하지 않는다. `simulatorTcpMode`는 normal, close-after-effect(효과 기록 후 응답 없이 종료), wrong-attempt(잘못된 attemptId 응답)를 지원한다. 관리용 관측 key는 `tcp:attemptId`다. 이 기록은 Worker 발송 판단에 사용하지 않는다.

로컬에서는 JDK 21로 빌드 후 시뮬레이터·API·Ingress·Dispatch를 기존 local.sh로 실행하고 위 요청을 인증된 API에 보낸다. `.env`의 MOCK_TCP_PORT를 양쪽에 동일하게 적용한다. 모니터링 앱은 기존 immutable JAR를 유지했으므로 새 기능을 그 환경에서 사용하려면 새 앱 빌드를 적용해야 한다.

## 검증 결과와 범위

```bash
DYNAMODB_TEST_ENDPOINT=http://localhost:18000 \
KAFKA_TEST_BOOTSTRAP_SERVERS=localhost:39092 \
JAVA_HOME=/path/to/jdk-21 ./mvnw -q test
```

**전체 133건 통과, 실패·제외 0건.** API 9, 공통 10, Ingress 19, Dispatch 82, 시뮬레이터 13건이다. 실행 대상에 실제 DynamoDB·Kafka 통합 검증을 포함했다.

- 기존 JSON에서 허용 필드 생략 시 접수·이벤트 호환, 허용 값 변경의 멱등 충돌, 원래 인입 시각 유지.
- 실제 HTTP 503/FALLBACK 응답 → 실제 TCP RECEIVED 응답 → DynamoDB 2차 ACCEPTED, 재전달 시 양쪽 추가 호출 없음.
- 외부 중복 제거 없는 20개 재처리 경합에서 1차 호출 1회·2차 효과 1회.
- 2차 비허용·영구 거절의 TCP 미호출, 1차 무응답 3회 소진 즉시 전환, 1차 만료 기준 고정, 2차 기한 경과 시 미발송.
- 경로 저장 응답 유실 후 복구, 고정된 provider·TTL 유지, 2차 효과 후 결과 저장 실패의 운영 확인 인계.
- TCP 분할 프레임·잘못된 ID·응답 코드·중간 종료·과대 길이·timeout, 시뮬레이터 응답 유실과 호출/효과 관측.
- 기존 Kafka Consumer 재시작·offset 보존 검증도 함께 통과.

`package` 빌드도 통과했다. 이후 구형 deadline 필드 호환 시험 1건을 추가해 위 133건을 최종 실행했다. 별도로 새 시뮬레이터·Dispatch JAR를 임시 로컬 포트에서 기동해 health=UP과 실제 TCP RECEIVED·호출/효과 각 1회를 확인했다. 이 기동 시험은 업무 Kafka 소비를 끄고 실행했으며 테스트 자식 프로세스만 종료했다. OS 강제 종료·AZ 장애·고 TPS 오류 부하 시험은 아니다.

Grafana 외부 업체 화면에 TCP 시도 TPS, TCP 접수 저장 TPS, 응답 p95, 전체 재시도 예약 관측을 추가했다. 총 7개 화면·92개 패널·80개 질의다. 기존 앱 JAR가 실행 중일 때 새 TCP 지표가 없는 것은 정상이며, 관측 횟수는 고유 미해결 상태 수가 아니다.

추가한 4개 PromQL은 실행 중인 Prometheus에 직접 요청해 모두 성공 응답을 확인했다(기존 앱이므로 시계열 0개). **Grafana 화면 반영 검증은 완료하지 못했다.** 기존 대시보드 API가 timeout이었고, 해당 컨테이너만 재시작하려 하자 Docker가 PID 14896을 종료할 수 없는 zombie로 보고했다. 영구 볼륨을 유지한 단일 컨테이너 재생성도 완료되지 않아 대기 중인 Compose CLI를 종료했다. Grafana API는 이후 정상 응답하지 않는다. 데이터 볼륨 삭제나 Docker Desktop 전체 재시작은 수행하지 않았다. 로컬 Docker 런타임 복구 후 `bash scripts/monitoring.sh verify`로 provisioning·전체 질의·로그를 다시 검증해야 한다.

## 남은 작업

- 업체 최종 결과 웹훅의 Kafka-first 수신, 단계·ID 연결, 중복·역순·늦은 웹훅 처리.
- 이미 ACCEPTED 또는 REVIEW_REQUIRED인 요청을 포함한 주기 만료·운영 조치 경합. 이번 만료 처리는 Dispatch가 다시 실행되는 요청의 호출 기한 검사다.
- 2차 비허용·거절·소진·만료 판단을 고객 최종 결과로 인계하고 고객별 최대 100건 HTTP 통지·최대 20회 재전송.
- 재시도 소비 경로 분리와 TCP 부하 기준선. 현재 대기 중 Kafka 파티션 지연은 계속 존재한다.
- 이전 버전에서 이미 offset을 완료한 DECISION_PENDING 기록의 운영 재처리 도구. 새 코드는 자동 Scan이나 offset reset으로 과거 기록을 일괄 발송하지 않는다.
