# 멱등 정보 보관과 완료 후 정리 방식

갱신일: 2026-09-25. **최신 사용자 결정은 [ADR-022](adr/ADR-022-처리-중-DynamoDB-선점과-완료-후-Redis-중복-차단.md)**이다. 처리 중 DDB 선점은 유지하고, SQL 이력 저장·DDB 정리 후에는 Redis TTL로 같은 ClientMsgId를 차단한다. Redis 유실 시에도 DDB 조건까지 통과하면 재발송을 허용한다.

새 API의 v2 경로에 정책을 구현했다. [최신 구현·검증](35-원본과-단계-최소-저장-및-Redis-완료-중복-차단.md)에서 실행 식별자·재시도·SQL 인계·정리 경합을 설명한다. 작은 완료 META 유지 방식은 기존 v1 데이터의 호환 경로에만 남긴다. 완료 TTL은 PoC 기본값으로 최종 결과 확정 시각+24시간을 사용하며 설정으로 변경한다. 사용자 확정 보관 기간이라는 뜻은 아니다.

## 1. 확정한 방향

| 단계 | 중복 방지·보존 방식 |
|---|---|
| 최초 인입 | ORIGIN 원문 1회 저장을 목표로 함. Redis에 고객+ClientMsgId 중복 제어 및 업무 시각 정보 |
| 1차·2차 발송 전 | STEP에 실행 설정·회차·조건부 선점 저장 |
| 재시도 | 내구성 재시도 명령에 이전/다음 회차 고정. 같은 명령으로 회차를 여러 번 올리지 않음 |
| 업무 만료 대기 | 원래 기한 유지, Redis 검색 활용. Redis 소실로 STEP 선점·기한을 우회하지 않음 |
| 단계 종료 | 해당 업무 만료 일정 제거. 접수 응답은 최종 성공과 구별 |
| 전체 종료 | PostgreSQL 이력·고객 통지 예약 저장 확인 후 DDB 원본·실행 데이터 정리 |
| 완료 후 | Redis 최소 표식과 TTL로 같은 ClientMsgId 차단 |
| Redis 부재/장애 | DDB 선점·멱등 조건까지 통과한 경우 재발송 허용. DDB 오류를 허가로 간주하지 않음 |

완료 후 작은 DDB 기록을 반드시 보관하던 이전 정책은 대체한다. 완료 후 Redis 기록 소실에 따른 재발송은 허용 범위이며, 처리 중 원본/결과 유실을 허용하는 것은 아니다.

## 2. 두 시간과 식별자를 구분

업무 deadline과 완료 후 중복 차단 TTL은 다르다. 1차는 인입 시각 기준, 2차는 최초 1차 결과 판단 시각 기준이라는 기존 규칙을 유지한다. 완료 후 TTL의 길이·시작 기준은 미정 설정으로 둔다.

ClientMsgId는 고객 범위로 구분한다. 허용된 재발송이 새 처리로 시작될 때는 이전 SQL 이력·통지·웹훅과 섞이지 않도록 별도 실행 세대를 식별해야 한다. 현재 deliveryId 생성 규칙과 SQL 유일 키를 그대로 둔 채 DDB 완료 META만 지우는 변경은 충분하지 않다.

## 3. 삭제와 재처리

이력으로 ‘보냈다’는 사실만으로 원본을 삭제하지 않는다. PostgreSQL 이력과 고객 통지 예약의 commit을 확인한다. 실패하면 원본·STEP을 보존하고 재개한다. 고객 HTTP는 SQL에 보존된 결과로 최초+최대 20회 재전송을 이어간다.

진행 중 STEP이 있으면 상태·회차·version을 검사한다. 없으면 중복 웹훅이라고 단정하지 않고 이전 처리의 완료/정리 또는 연결할 대상 없음으로 구분한다. 새 처리와 오래된 웹훅은 실행 세대로 분리한다.

## 4. 기존 선택과 공식 근거의 관계

이전에는 완료 이후에도 오래된 요청 재발송을 막기 위해 [ADR-020](adr/ADR-020-완료-확인과-원본-정리의-멱등성-보호.md)의 작은 DDB 완료 기록을 선택했다. 이번에는 사용자가 Redis 소실과 DDB 조건 통과 후 재발송을 허용했으므로 보장 범위가 바뀌었다.

Redis AOF·복제·TTL/알림의 한계는 그대로다. 이를 인지하고 완료 후 중복을 허용하는 정책이지, Redis에 100% 무손실 보장이 생긴 것이 아니다. [저장소별 공식 근거](07-저장소별-특성과-데이터-유실-복구-조건.md), [최신 결정·이관 조건](adr/ADR-022-처리-중-DynamoDB-선점과-완료-후-Redis-중복-차단.md)을 따른다.
