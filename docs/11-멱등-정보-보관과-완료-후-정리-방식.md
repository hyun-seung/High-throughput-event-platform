# 멱등 정보 보관과 완료 후 정리 방식

작성일: 2026-09-23. 완료 직후 원본·멱등 정보를 정리하고 이력 한 줄을 남기는 초기 구상을 검토한다. **사용자 확정: 호처리에 필요한 실행·멱등 상태를 DynamoDB에 최소한으로 저장하고, 종료 후 작은 완료 기록을 유지한다.** 아래 상세 필드·동시성 구현·보관 기간은 설계안이며 구현 완료를 뜻하지 않는다. 고객 결과 웹훅 최대 20회 재전송은 확정 요구로 [결과 통지 설계](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)에 별도 기록한다.

## 1. 확정한 방향

큰 원본과 실행 상세는 안전하게 인계한 뒤 정리하되, **이미 처리한 요청이라는 최소한의 정보는 중복 방지 기간 동안 내구성 있는 저장소에 남긴다.** 현재의 DynamoDB 실행 상태·PostgreSQL 비동기 이력 구조에서 실행 상태를 작은 완료 기록으로 축소하는 안을 채택한다. DynamoDB는 호처리의 멱등 판단과 안전한 실행에 필요한 구간에만 사용하고, 각 저장·갱신의 필요성을 설명한다. 별도 완료 테이블을 무조건 추가하라는 뜻은 아니다.

PostgreSQL 이력으로 중복을 판단하거나 실행 원장까지 통합하는 방법은 검토했던 대안으로 남긴다. 이번 결정으로 이 대안의 선택을 다시 요청하지 않는다. DynamoDB 최소화는 필요한 상태까지 없애는 것이 아니라, 멱등 판단과 실행 복구에 불필요한 복제·상세 데이터·갱신을 줄이는 방향이다. 각 항목의 크기·읽기·쓰기·인덱스 비용과 장애 복구는 계속 검증한다.

## 2. 왜 완료 직후 전부 삭제하면 위험한가

다음은 프로젝트 흐름에서 가능한 예시다.

```text
요청 A 발송 완료 → 이력 저장 → 멱등 상태 삭제
→ Kafka 처리 위치 저장 전에 Worker 종료
→ 같은 요청 A가 다시 전달됨
→ 발송 경로에서 완료 사실을 찾지 못함
→ 신규 작업으로 판단해 외부에 다시 발송
```

고객이 접수 응답을 받지 못해 같은 요청을 다시 보내거나, 운영자가 오래된 실패 큐를 재처리해도 같은 문제가 생긴다. 이력이 있어도 발송 경로에서 확인하지 않으면 중복 방지에는 쓰이지 않는다. 성공뿐 아니라 최종 실패·만료도 종료 사실을 유지해야 한다. 실패 이력을 지웠다고 원래 요청에 새로운 3시간·4시간을 부여해서는 안 된다.

**공식 근거:** AWS는 늦게 도착하는 재요청과 같은 요청 ID에 다른 입력이 들어오는 경우를 멱등 API 계약의 문제로 설명한다. Kafka는 처리 후 offset 기록 전에 장애가 발생하면 재처리가 가능한 전달 의미를 설명한다. **프로젝트 판단:** 업무 완료와 중복 가능성의 종료는 다른 시점이므로 완료 직후 판단 근거를 없애는 정책은 맞지 않는다. [AWS 멱등 API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), [Kafka 4.0 설계](https://kafka.apache.org/40/design/design/).

### 이력을 먼저 저장하고 삭제하면 충분한가

그 순서는 유실 방지에 필요하지만, 서로 다른 저장소를 확인하는 사이의 경합까지 해결하지는 않는다.

1. Worker A가 PostgreSQL에서 이력이 없음을 확인하고 잠시 멈춘다.
2. Worker B가 발송을 완료하고 이력을 저장한 다음 DynamoDB 실행 상태를 삭제한다.
3. A가 재개해 DynamoDB 항목이 없다는 조건으로 작업을 새로 선점한다.
4. A가 외부 발송을 실행하면 이미 완료된 요청이 중복 발송된다.

이는 제안 설계의 반례이며 현재 코드에서 재현 검증한 결과는 아니다. 이력에 UNIQUE 제약을 걸어도 **외부 발송 후 이력 INSERT**만 막는다면 이미 발생한 중복 발송은 되돌릴 수 없다. PostgreSQL의 유일성 제약은 DB 행의 중복을 제한한다. 외부 호출을 그 제약 안에 포함시키는 기능은 아니다. [PostgreSQL 17 제약 조건](https://www.postgresql.org/docs/17/ddl-constraints.html).

## 3. 보관 방식 비교

| 방식 | 장점 | 필요한 조건·부담 | 판단 |
|---|---|---|---|
| 완료 즉시 멱등 정보 전부 삭제, 이력은 조회용 | 활성 저장량 감소 | 늦은 중복을 새 발송으로 판단할 수 있음 | 현재 요구에 부적합 |
| PostgreSQL 이력을 완료 후 멱등 원장으로 사용 | DynamoDB 완료 기록 장기 보관 감소, 이력 한 줄 활용 | 발송 전 이력 확인, 원장 전환 경합 제어, 이력 장애 시 관련 발송 보류 | 가능하나 단순 삭제 변경으로 구현 불가 |
| 작은 DynamoDB 완료 기록 + PostgreSQL 이력 한 줄 | 기존 실행 원장에서 완료 중복을 차단, 이력 저장 장애와 발송 판단의 의존성을 줄임 | 보관 기간의 저장 비용, 조건부 갱신·정리 비용, 과거 replay 제한 | 사용자 채택 |
| 진행 중 상태·완료 이력·통지 예약을 PostgreSQL로 통합 | 내부 상태 인계의 DB 간 경계와 DynamoDB 의존성 감소 | PostgreSQL 처리량·복제·장애 복구 검증, 발송 경로 변경 | DynamoDB 최소화 우선순위가 높으면 비교할 대안 |

Redis는 완료 여부의 cache로 쓸 수 있지만, cache 부재를 곧 미발송으로 판단하면 안 된다. persistence·복제·failover 한계는 [저장소 특성 문서](07-저장소별-특성과-데이터-유실-복구-조건.md)에 정리했다. 이번에 확정한 Redis 장애 시 TPS·Quota 우회 정책을 멱등 판단 우회까지 확대하지 않는다.

## 4. 채택한 방식의 상세 설계안

### 남길 정보와 줄일 정보

| 남길 정보 | 이유 |
|---|---|
| 고객 식별자 + 안정적인 고객 요청 key | 고객 간 key 충돌 없이 같은 논리 요청을 다시 찾음 |
| deliveryId | 이력·단계 상태·통지와의 식별자 연결 |
| 입력 fingerprint와 계산 규칙 버전 | 같은 key에 수신자·본문·2차 허용 등 다른 의미의 입력을 넣는 충돌 감지 |
| 최종 상태, 완료 시각, 기존 결과 또는 결과 참조 | 재발송하지 않고 이전 처리 사실을 반환/조회 |
| version과 보관 종료 기준 | 낡은 Worker의 상태 변경 및 조기 삭제 방지 |

본문 전체·수신자 상세·매번의 통신 로그를 완료 판단 항목에 계속 누적하지 않는다. 단, 아직 2차가 진행 중이면 필요한 입력을 보존하고, 고객 통지 대기 중이면 통지용 결과를 별도 내구성 저장소에 남긴다. 요청 key는 업무 요청을 식별하며 재시도마다 새로 만들지 않는다. 시도 번호는 별도로 관리한다.

### 동시성 규칙

실행 상태를 지웠다가 완료 기록을 새로 넣는 공백을 만들지 않는다. 같은 안정적인 요청 key의 상태를 조건부로 완료 상태로 전환하고 상세만 줄인다. 후속 선점은 완료 상태와 현재 단계·version을 원자적으로 확인해야 한다. 1차 종료 후 2차가 진행 중인 동안에도 완료된 1차의 중복 실행은 차단한다.

단일 항목으로 표현할 수 있으면 조건부 갱신을 사용한다. 요청 상태와 시도 항목을 분리한다면 상태 확인과 시도 선점을 하나의 DynamoDB transaction으로 묶는 등의 방법을 검토한다. '먼저 완료 여부 읽기 → 조건 없이 시도 생성'으로 대체하지 않는다. 현재 Attempt 단위 선점만으로 이 요청 단위 규칙이 구현됐다고 간주하지 않는다.

**공식 근거:** DynamoDB 조건식은 조건을 만족하는 변경만 허용하고, transaction은 여러 DynamoDB 항목의 변경을 원자적으로 처리할 수 있다. PostgreSQL·Kafka·외부 HTTP/TCP까지 같은 transaction이 되지는 않는다. **프로젝트 판단:** 이미 사용하는 실행 원장에서 상태 전이를 끊김 없이 보호할 수 있다는 점이 선택 이유다. [조건식](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [트랜잭션](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).

### 정리 순서

1. 필요한 1차·2차 처리가 모두 종료되면 요청을 최종 상태로 확정한다. 고객 HTTP 통지는 별도 수명으로 관리한다.
2. 이력 한 줄과 통지 예약이 내구성 있게 저장됐는지 확인한다. 실패하면 정리를 보류한다.
3. 요청 상태의 완료 여부·version을 조건으로 큰 실행 데이터를 줄이고 최소 완료 정보는 유지한다. 상세를 지우기 전에 최종 상태에서 중복 발송이 차단돼야 한다.
4. 통지는 수신 확인 또는 재전송 한도 소진까지 진행한다. 소진 결과의 보존·운영 처리는 [통지 설계 제안](10-고객-결과-묶음-전송과-발송-완료-데이터-정리.md)을 따른다.
5. 합의된 중복 방지 기간과 복구 조건을 충족한 뒤 완료 기록을 정리한다. 미완료 작업이나 통지의 유일한 복구 근거를 TTL로 삭제하지 않는다.

PostgreSQL 이력 장애 동안에는 정리 대상이 쌓인다. 이 방식도 무제한 장애를 무제한 저장 용량으로 버틸 수 있다는 뜻은 아니므로 용량·backpressure를 운영 절차에 포함한다.

## 5. 얼마나 보관해야 하는가

**발송 만료 최대 7시간과 멱등 정보 보관 기간은 다르다.** 고객 재요청, Kafka 재전달, 실패 큐 재처리, 백업 복구 후 재생의 허용 범위에서 가장 늦게 중복이 들어올 수 있는 시각까지 보호해야 한다. 고객 웹훅 20회라는 횟수만으로도 기간은 계산되지 않는다. 재전송 간격·최대 경과 시간은 별도다.

임의로 1일이나 7일을 확정하지 않는다. **구현 착수 시에는 완료 기록 자동 삭제를 비활성화하고, 보관 기간 결정은 운영 준비 단계로 미룬다.** 보관 기간 미정으로 접수·발송 구현을 중단하지 않는다. 먼저 고객의 같은 key 재요청 허용 기간과 Kafka·실패 큐·수동 replay 허용 기간을 정하고, 그 범위를 덮는 보관 종료 시각을 계산한다. 그보다 오래된 요청은 이력을 확인하거나 발송을 보류하는 정책이 필요하다. 오래된 요청을 판별할 신뢰할 수 있는 시각/원장이 없다면 기록 삭제 후 key만 보고 과거 요청인지 알 수 없다. 기록 삭제와 무기한 중복 방지를 동시에 약속하지 않는다.

TTL은 정리 수단이다. DynamoDB는 TTL 시각 후 보통 수일 내 삭제하며 정확한 시각의 삭제를 보장하지 않는다. 업무 만료 판단과 분리하고, 보관 기간이 지났지만 남아 있는 완료 항목도 임의로 신규 실행 항목으로 덮어쓰지 않는다. [공식 TTL 설명](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html).

비용은 측정해야 한다. 일정한 완료 TPS를 가정하면 `보관 항목 수 ≈ 완료 TPS × 보관 초`다. 예를 들어 1,000건/초를 하루 보관하면 약 8,640만 건이며, 작은 항목이어도 무시할 저장량은 아니다. 크기를 줄이는 update도 무료가 아니며 DynamoDB는 변경 전후 중 큰 항목 크기로 쓰기 용량을 계산한다. 따라서 최초 실행 항목부터 작게 유지하고 중복 상세·불필요한 인덱스를 줄이는 방향을 함께 평가한다. [읽기·쓰기 용량 계산](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html).

## 6. 해결하는 문제와 남는 한계

이 안은 기록된 완료를 잊어서 재발송하는 문제와, 중복 이벤트·상태 전이에 의한 불필요한 호출을 막기 위한 설계다. 이미 외부로 나간 요청의 실제 효과까지 DB만으로 제어하지는 못한다. 외부가 처리했는데 응답이 없어 합의된 정책대로 재시도하면 실제 중복 가능성이 남는다. 멈췄던 Worker가 외부 호출 직전에 재개하는 문제도 완료 기록 보관만으로 해결됐다고 주장하지 않는다. 해당 경계와 운영 확인은 [Q2·Q6](08-함께-결정할-설계-사항.md) 및 [ADR-008](adr/ADR-008-발송-작업-선점과-외부-중복-발송-방지.md)을 함께 따른다.

보관 방식은 확정했다. 구현은 진행하며 운영 준비 단계에서 정할 내용은 **고객 재요청·내부 replay 허용 기간과 완료 기록 보관 기간**, **목표 TPS**다. 채택한 방식에 대해 완료 전후 종료·동시 선점·이력 장애·보관 경계·과거 재생을 시험한다. 이 문서 작성만으로 무손실이나 외부 중복 0회가 검증된 것은 아니다.

이 문서의 원본 정리 미구현 표시는 당시 범위입니다. 현재는 [작은 완료 기록과 안전한 원본 정리](32-완료-기록-유지와-발송-원본의-안전한-정리.md)를 구현했습니다. SQL 이력·통지·정리 예약을 함께 저장한 뒤, 완료 META 교체와 FINAL/Attempt/추적된 Receipt marker 삭제를 조건부 트랜잭션으로 처리합니다. 고객 통지는 SQL에 남은 결과로 계속합니다. 완료 META에는 TTL을 두지 않습니다.

전체 쓰기 워커 교체 후 별도 활성화하며, 구버전 추적 정보가 없는 데이터는 보존합니다. 신규 18건을 포함해 전체 260건을 통과했습니다. 선점 트랜잭션의 추가 비용·정리 성능·전체 흐름 부하·실제 서버 장애 시험은 후속입니다. [공식 근거와 결정](adr/ADR-020-완료-확인과-원본-정리의-멱등성-보호.md)을 별도로 남겼습니다.
