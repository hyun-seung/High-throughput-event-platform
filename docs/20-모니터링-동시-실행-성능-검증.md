# 모니터링 동시 실행 성능 검증

측정일: 2026-09-24. Grafana 구축 이후 Prometheus·Loki·Alloy·collector·DB exporter를 켠 상태에서 HTTP 1차 접수 경로를 다시 검증한다. 기존 화면용 `demo`와 달리 k6의 일정 입력률을 사용하고 모든 요청의 Kafka·DynamoDB·업체 처리 증거를 대조한다.

후속 패치 적용과 재측정은 [카프카 패치와 성능 재검증](21-카프카-패치와-성능-재검증.md)에 분리한다. 이 문서의 4.0.0 측정 기록은 그대로 보존한다.

## 목적과 범위

앞선 [워커 동시 처리 비교](17-워커-동시-처리와-발행-대기-성능-비교.md)는 앱을 호스트 JVM에서 실행했다. 이번에는 Grafana용 Docker 앱 환경과 구조화 로그 수집이 추가됐다. 이전 100 TPS 통과를 그대로 적용하지 않고 **현재 구성에서 100 TPS 단기 정상 부하를 감당하는지** 확인한다.

모니터링을 끈 동일 조건 대조군은 이번 범위에 없다. 결과 차이를 모니터링 비용으로 단정하지 않는다. 업체 응답 지연 0ms, 고객 1명, HTTP 1차 접수까지만 검증하며 최종 전달·TCP 2차·결과 웹훅·고객 통지 성능은 포함하지 않는다.

## 실행 방법과 증거

```bash
# 모니터링 환경이 이미 실행 중이어야 한다.
# 도구가 없으면 먼저 python3 scripts/poc/setup.py 실행
bash scripts/monitoring.sh benchmark --suite smoke
bash scripts/monitoring.sh benchmark --suite baseline
```

실행 중 [Grafana 통합 관제](http://localhost:13000/d/delivery-overview), [서비스](http://localhost:13000/d/delivery-services), [인프라](http://localhost:13000/d/delivery-infra)에서 입력·접수 저장 TPS, 구간 지연, committed lag, DB 작업, 자원 사용을 확인할 수 있다. 시간 범위를 시험 구간에 맞춘다.

모니터링용 DB·앱을 그대로 사용하되 실행별 고유 요청 ID와 전후 Kafka offset 범위를 사용한다. 기존 요청·offset·DB 기록을 지우거나 시험 종료 시 서비스를 멈추지 않는다. 정책도 변경하지 않으며 입력은 데모 고객 quota에 반영된다. `demo`와 `benchmark`는 같은 파일 lock으로 동시 실행을 막는다. 수동 입력이나 서비스 재시작도 시험과 겹치지 않게 한다.

원시 파일은 `.poc-results/<실행 ID>/`에 보관한다. 요청 시작·응답, k6 결과, 앱 지표, Kafka offset·record 식별자, 해당 ID의 DB 상태, 업체 calls/effects 대조, Docker 자원 자료를 남긴다. 실제 실행 중인 JAR의 SHA-256을 컨테이너에서 읽고 image ID·시작 시각·설정을 기록한다. 관리 포트는 추가 공개하지 않고 collector 안에서 읽기 전용으로 조회한다. 토큰은 stdin으로 전달하며 결과 파일에 저장하지 않는다.

## 결과

**50 TPS와 100 TPS 각 3분의 완주·요청별 정합성 기준은 통과했다. 다만 100 TPS 중 Kafka broker의 일시적인 commit 오류가 발생했으므로 무장애 성능 기준선으로는 보류한다.**

단위는 ms. 중복 시험의 지연 분포는 HTTP 제출 횟수가 아닌 고유 메시지의 최초 인입→접수 저장 기준이다.

| 단계 | HTTP 제출/응답 | 고유 요청 | API p95 | 인입→접수 저장 p50 / p95 / p99 | 관측 최대 lag | 판정 |
|---|---:|---:|---:|---:|---:|---|
| 소량 고유 5 TPS × 2초 | 10 / 10 | 10 | 42.04 | 42.27 / 98.59 / 102.56 | 0 | 통과 |
| 소량 중복 5 TPS × 2초 | 11 / 11 | 6 | 41.94 | 41.92 / 81.11 / 87.58 | 5 | 통과 |
| 워밍업 10 TPS × 60초 | 601 / 601 | 601 | 17.38 | 32.33 / 42.62 / 50.81 | 21 | 통과 |
| 중복 100 TPS × 20초 | 2,000 / 2,000 | 1,000 | 15.31 | 38.54 / 300.87 / 468.49 | 38 | 통과 |
| 고유 50 TPS × 180초 | 9,001 / 9,001 | 9,001 | 11.86 | 22.10 / 43.15 / 229.23 | 32 | 완주·대조 통과 |
| 고유 100 TPS × 180초 | 18,000 / 18,000 | 18,000 | 10.64 | 30.62 / 414.53 / 638.41 | 51 | 완주·대조 통과, broker 오류 포함 |

전체 29,623회 제출·응답, 고유 28,618건 모두 DB ACCEPTED·외부 calls=1/effects=1이었다. 미응답·dropped iteration·미설명 누락·예상 밖 Kafka ID·DLT·신규 운영 확인은 0이다. 정상 시험이 모든 장애의 무손실을 증명하는 것은 아니다.

50/100 TPS의 최장 Kafka 대기 관측은 각각 0.57/0.94초였다. 마지막 입력 후 두 번 lag=0을 확인한 시간은 각각 12.33/12.63초다. 이는 수집 시간·간격을 포함한 확인 상한이며, 메시지가 실제로 그 시간만큼 대기했다는 뜻은 아니다.

### 구간별로 무엇을 봤나

입력 전부터 배출 확인까지 Timer 누적 시간 차이를 호출 수 차이로 나눈 평균이다. API 응답과 전체 접수 지연의 차이가 크면 API만 보고 처리 완료가 빠르다고 판단하지 않는다.

| 구간 평균 ms | 50 TPS | 100 TPS |
|---|---:|---:|
| API Kafka ack | 5.94 | 5.78 |
| Ingress 전체 | 11.39 | 12.83 |
| Ingress 원본 저장 | 5.17 | 7.64 |
| Ingress Kafka 발행 | 6.09 | 5.06 |
| Dispatch 전체 | 11.55 | 14.38 |
| Dispatch claim | 4.88 | 6.28 |
| 외부 HTTP | 1.97 | 1.74 |
| 결과 저장 | 4.59 | 6.28 |

50 TPS에서는 Put 성공 9,001회·Update 성공 18,002회, 100 TPS에서는 Put 성공 18,000회·Update 성공 36,000회다. **성공 쓰기는 요청당 3회로 유지됐다.** 100 TPS에서 추가 Update 조건 불일치 1회·Get 성공 1회·내부 중복 차단 1회가 있었으며 다음 절의 Kafka 재처리와 연결했다. 이를 쓰기나 조회가 전혀 추가되지 않았다고 표현하지 않는다.

Docker stats의 100 TPS 구간 표본에서는 Kafka CPU 최대 152.79%, Alloy 13.22%, Grafana 29.00%가 관측됐다. 이는 Docker가 표시하는 컨테이너 CPU 백분율로 호스트 전체 사용률과 같지 않으며 순간값을 놓칠 수 있다. raw 자원 자료를 보관했다. Grafana 화면 조회 부하도 엄격하게 통제한 대조 실험은 아니다.

### Kafka 오류와 멱등 처리 확인

100 TPS 단계는 UTC 12:01:56~12:05:11(입력·배출 관측 포함)에 진행됐다. UTC 12:03:38에 broker의 coordinator가 `Histogram recorded value cannot be negative` 오류를 기록했다. 이후 `__consumer_offsets` 상태 불일치와 coordinator 재적재, Dispatch offset commit 실패, 12:03:39의 partition 2 offset 7917 재처리를 확인했다.

해당 deliveryId `6805372f-aacf-331b-be21-bb91850d8fa2`는 같은 시험의 요청이다. Loki에는 `already_accepted`가 남았고 대조 결과는 다음과 같다.

- Kafka 접수·Dispatch record 각각 1건, DLT 0건.
- META/Attempt의 접수 완료 상태와 HTTP 202 확인.
- 외부 호출 1회·처리 효과 1회. 재처리에서 추가 외부 발송 없이 완료 기록으로 차단.
- broker/Dispatch 로그 구간을 실행 폴더의 `kafka-commit-error-window.log`, `dispatch-commit-error-window.log`에 보존.

[Apache KAFKA-19888](https://issues.apache.org/jira/browse/KAFKA-19888)은 같은 coordinator histogram 증상을 기술하며 영향 버전에 4.0.0, 수정 버전에 4.0.2·4.1.2·4.2.0을 명시한다. **로컬 로그와 알려진 증상이 일치한다는 판단**이며, 로컬 VM 시계 변화 자체는 별도로 측정하지 않아 트리거를 확정하지 않는다. 또한 100 TPS p95 증가 전체를 이 한 번의 오류 탓으로 단정하지 않는다.

따라서 다음 우선순위는 높은 TPS로 올리기 전에 로컬 broker 수정 버전을 적용하고 같은 조건을 재측정하는 것이다. 이번 자동 판정은 commit 오류가 복구되고 모든 데이터가 대조되면 통과할 수 있다. 자동 `pass=true`와 무장애·지연 품질 만족을 구분한다.

부하 종료 후 대시보드 76개 질의, 수집 대상 10개, 실제 처리 로그, Kafka 적체 해소를 다시 검증했고 모두 통과했다. Grafana와 앱은 계속 실행 중이다.

## 준비 및 도구 검증 기록

- Python 요청별 대조 회귀 시험 8건 통과.
- 초기 준비 실행 `20260924T115353Z-b9c957f0`은 Docker Desktop의 `/host_mnt/...` 경로를 호스트에서 읽으려다 실패했다. 부하 입력 전 중단됐으며 실패 자료를 보존했다. JAR 해시를 컨테이너 내부에서 읽도록 수정했다.
- 수정 후 소량 실행 `20260924T115427Z-5b838630`: 고유 입력 10회/10개 ID, 중복 입력 10회/5개 ID 모두 통과. DB ACCEPTED, 업체 calls=1/effects=1을 ID별로 대조했다.
- 기준선 실행 중 `demo --rate 1 --seconds 1`의 동시 실행을 시도해 lock에서 제출 전 차단되는 것을 확인했다.

## 해석상의 한계와 다음 판단

- API 202는 Kafka 접수 ack이며 최종 전달 완료가 아니다. 이 시험의 완료 기준은 신규 업체 접수 결과 저장이다.
- DB 지연은 `updated_at - occurred_at`이다. `updated_at`은 결과 Update 호출 전 시각이므로 DB ack 직후 Timer와 조금 다르다.
- 최대 lag는 약 5초 간격의 관측값이다. 수집·Docker stats 비용이 더해져 실제 간격이 늘어나며 순간 최댓값을 놓칠 수 있다.
- 종료 경계에서 k6가 추가한 1건도 대조한다. 부족한 입력·미응답·dropped iteration은 실패이며 DB에 저장됐다는 이유로 정상 응답으로 보정하지 않는다.
- 정상 흐름의 DB SDK 호출 비율은 AWS의 물리 HTTP 재시도·WCU/RCU와 같지 않다.
- 앱·인프라·관측·부하 생성기가 한 호스트 자원을 공유한다. 기존 데이터와 순차 실행 순서도 이전 측정과 다르다. 단일 실행의 p95 차이로 인과관계나 최대 용량을 확정하지 않는다.
- 이번 요청별 정상 대조는 장애 시 무손실·외부 효과 exactly-once·다중 AZ 복구를 증명하지 않는다. 실제 프로세스 중단 경계와 미해결 운영 상태 시험은 별도다.

이후 입력률을 올리거나 업체 지연을 추가할 때도 관측과 요청별 대조를 함께 유지한다. 모니터링 자체의 오버헤드를 구하려면 동일 앱 배치·입력·데이터 조건의 수집 on/off 교차 반복 시험을 별도로 해야 한다.
