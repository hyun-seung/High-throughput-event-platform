# 이벤트 기반 처리 전환 계획

기준: 2026-10-22. 적용 기준은 [아키텍처 명세](55-이벤트-기반-처리-아키텍처-적용-명세.md)다. **이번 작업은 역할 대응·변경 범위·검증·전환 계획 작성이며 새 동작 구현은 아직 시작하지 않았다.**

소스 기준은 `f4de673`과 현재 작업 트리다. 이전 작업의 DynamoDB 측정 CLI·테스트·측정 문서는 보존한다. 기존 빌드·기능 시험·실측 결과는 새 계약의 합격 근거로 사용하지 않는다. 현재 코드 이름은 위치를 찾기 위한 대응 정보이며 기존 업체 규격·업무 판단·운영값을 목표 계약으로 가져오지 않는다.

## 1. 역할 대응과 변경 범위

결과 보관은 통지·완료와 별도 책임/소비 그룹이 필요해 모듈 추가 대상이다. 결과 판단의 작은 복구 기능이나 예약 작업을 위한 추가 AP는 만들지 않는다. 주 실행기의 여러 외부 대상도 코드/JAR 하나를 유지한다.

### Outbox와 복구 상태의 적용 범위

API·결과 판단의 일반 발행 Outbox를 되살리는 계획은 아니다. 기존 고객 통지의 SQL 전송 대기 구조도 새 통지 계약으로 전환한다. 다만 최신 명세가 요구하는 **콜백 사실 저장 후 Kafka 미확인 발행의 내구성 있는 복구 보관·임대**는 구현 대상이다. 이름과 무관하게 이 부분은 저장-발행 사이의 복구 책임을 갖는다. 결과 판단의 정상 DynamoDB 쓰기 0회와 충돌하지 않도록 수신 AP/복구 작업자가 소유한다.

## 3. 공통 계약의 첫 설계 단위

기존 이름과 새 의미를 바로 동일시하지 않는다. 다음은 대응 초안이며 실제 record·키 산식·직렬화는 1단계에서 계약 시험과 함께 확정한다.

| 목표 개념 | 현재 대응 | 전환 규칙 |
|---|---|---|
| `scopeId` | `clientId` | 모든 조회·조건·digest·키의 격리 검증. ID 값만 바꾸는 이관이 아님. |
| `requestKey` | `messageId` | scope 내 요청 중복 키. 내용 불일치는 충돌이며 새 실행을 허용하지 않음. |
| `executionId` | `clientMsgId` | 내부 재처리에서 유지. 새 이벤트 Kafka key로 사용. |
| `operationId`, `attempt` | `attemptId`, `invocation`, 전달 ID | 외부 실행·후속 실행·최종 전달의 의미를 구분. 같은 명령 재처리에서 재발급하지 않음. |
| `schemaVersion`, `contentDigest` | 일부 저장 항목의 버전·개별 내용 비교 | 이벤트 전체와 Redis 상태의 버전 경계를 새로 고정. 저장 테이블의 기존 버전 숫자와 혼용하지 않음. |
| `expiresAt`, `retainUntil` | 일부 명령 기한·개별 TTL | 새 실행 허용 기한과 보관 절대 기한을 분리. 새 입력·재처리로 수명 연장 금지. |

예상 이벤트는 접수, 고정 실행 명령, 관찰 사실, 사실 보정, 재구축 요청, 최종 통지/보관 명령과 완료다. 최종 전달 명령에는 대상·모드·결과·고정 시각·digest·안정 전달 ID를 포함해 원본 삭제 뒤 처리 가능하게 한다. `traceId`는 추적 정보이며 실행 key가 아니다.

준비 snapshot과 정책 버전은 고정 명령·필요한 실행 사실에 보관한다. Redis 전체 유실 시 원본/사실/재처리 입력으로 동일 명령을 만들 수 있는지 시험한다. 복원이 안 되는 경우 현재 참조값으로 다시 선택하지 않고 근거 부족으로 중단한다.

정책 구현은 담당 AP에 둔다. 공통에는 교체 가능한 입력/출력과 포트만 둔다. 합성 정책은 참조 부재, 즉시 응답, 콜백 판단, 후속/보조 허가, 배타적 전달, 후처리를 구분하며 실제 업무 규칙을 넣지 않는다.

## 4. 단계별 적용과 장애 게이트

한 단계의 코드·계약 시험·관련 장애 시험을 함께 완료한다. 앞 단계 통과 전 후속 구현을 완료로 표시하지 않는다. v2는 격리된 합성 자료로 검증하며 기존 경로에 일부만 연결하지 않는다.

| 단계 | 변경 단위 | 완료·장애 검증 조건 | 현재 상태 |
|---|---|---|---|
| 0 역할 대응 | 본 명세·현재 차이·소유권·시험·전환 절차 정리 | 소스 근거와 미구현 범위 연결, 기존 작업 보존 | 문서 작성 완료 |
| 1 공통 계약 | ID·버전·digest·절대 기한·고정 명령·정책 포트·합성 fixture, Kafka 트랜잭션 공통 경계 | 재처리 ID/내용 동일, scope 충돌·미지원 버전·상충 내용은 부작용 전 거절. 출력/offset·미커밋 비가시성·커밋 불명 복구 기반 시험 | 미착수 |
| 2 접수 | 전체 검증 우선, Token Bucket/사용량 포트, 원본 INSERT·제한 발행·실패 기록, v2 자동 원본 발행 차단 | 원본 저장 불명·늦은 ACK·최종 불명·실패 기록 불명·고객 중복 재입력·제한 오류. 최종 실패 뒤 추가 자동 발행 없음 | 미착수 |
| 3 핵심 처리 | 준비·HTTP·콜백·결과를 함께 전환. Redis 선점/응답·불변 사실·완료 가드·보정·건별 key·재구축·콜백 복구 보관 | 외부 호출 뒤 각 저장 실패/종료, 사실/콜백/보정 역전, 상충·이전 시도, 준비/결정 유실. 정상 결과 DynamoDB 쓰기 0회 | 미착수 |
| 4 완료·전달 | 선택한 전달+완료를 Kafka 원자 확정. 통지 Redis 성공 표시, 새 결과 보관 AP, 독립 SQL 기록·완료 가드·삭제 후 offset | 양쪽 소비 순서 역전, 원본 삭제 뒤 전달, 통지 표시 전 종료, 보관 중복/상충, 완료 6단계 사이 종료·미처리 삭제·가드 오류 | 미착수 |
| 5 보조·복구 | TCP 접수/상태/리포트와 보정. 콜백 복구 보관·임대/재발행, 준비 재구축의 전체 경로 | ACK 유실·근거 유실·늦은 리포트, 수신 사실 후 종료/발행 불명·임대 만료·ACK 후 기록 전 종료 | 미착수 |
| 6 부하·확장·전환 | 제한 병렬·메모리 상한·소유 세대·전체 경로 전후 계측, 배수·기동·복귀 리허설 | 실제 평균 ms와 접수/완료 TPS, prefix/재할당/커밋 불명, 동일 조건 전후·단계적 확장·장애 정합성 | 미착수 |

3단계는 기존 DynamoDB 상태만 먼저 삭제하지 않는 **하나의 전환 묶음**이다. 내부 구현 커밋을 나누더라도 새 경로 활성화는 선점·응답·사실·보정·가드가 함께 준비된 뒤다. 완료 가드 포트·실패 정책은 1단계에 정의하고 3단계에서 수신/보정에 적용하며 4단계에서 실제 완료 표시와 통합한다. 3단계 저장 보정·재구축 기반과 5단계의 전체 장애 복구 검증을 구분한다. Kafka 트랜잭션 기반은 1단계부터 검증하고 각 AP 전환 때 같은 조건을 통과시킨다.

기존 예약 실행도 정상 결과 DynamoDB 쓰기를 유발하므로 전환 범위다. 예약 명령의 안정 ID·기한·정책 버전, Redis 진행 유실과 Kafka 재소비를 함께 검증하며 예약 상태만 제거하지 않는다.

### 구현에서 먼저 확인할 복구 경계

| 경계 | 설계·시험 게이트 |
|---|---|
| 콜백 사실 저장 직후 종료 | 실패를 감지한 뒤 복구 항목을 쓰는 코드만으로는 그 사이 종료를 복구하지 못한다. 원자적으로 남길 발행 책임/조회 근거 또는 명시된 재수신 계약을 정하고, 재수신이 없는 경우까지 T19로 확인한다. 현재 해결 완료로 보지 않는다. |
| Redis 유실 후 판단 재현 | 원본·사실·고정 입력이 정책/참조 snapshot을 충분히 담는지 T09에서 확인한다. 부족하면 현재 정책으로 새 결정을 만들지 않는다. |
| 완료 가드와 지연 사실의 경합 | 이중 확인도 서로 다른 저장소의 원자성을 만들지 않는다. 재조회 전 종료·조건부 정리 실패·가드 유실/만료는 T17/T18에서 잔여 자료와 함께 기록한다. |
| Kafka 커밋 응답 불명 | 사용하는 트랜잭션 제어/오류 처리기가 추정 abort·재발행을 자동 반복하지 않는지 T11로 검증한다. 소유자 중단·재초기화와 재할당 후 늦은 응답 차단을 함께 확인한다. |
| 삭제가 느린 완료 처리 | 삭제를 offset 뒤로 밀어 성능을 맞추지 않는다. 제한 병렬 작업·poll/heartbeat·연속 prefix와 전체 메모리 상한을 유지하는지 T12/T16으로 확인한다. |

## 5. 합성 시험 설정 초안

아래는 **새 POC용 제안값**이다. 실행 코드에 적용되지 않았고 기존 운영값/실측에서 도출하지 않았다. 해당 단계에서 설정 fixture·기대 결과와 함께 확정한다. 실제 사용량 정책·장기 보관의 결정으로 해석하지 않는다.

| 항목 | 합성 시험 설정/계약 |
|---|---|
| 격리 | 새 run ID·scope·UUID 실행, 전용 테이블/SQL schema/토픽·Redis v2 prefix. 다른 프로젝트 자료 미사용. |
| payload | 256B/4KiB 두 크기, 내용은 의미 해석 없는 합성 값. |
| 처리율 | scope별 Token Bucket 용량 16·보충 초당 8. 내부 동시 상한과 별도 시험. |
| 사용량 | 포트의 허용/정상 거절/가용성 장애/손상 응답 fixture. 기간별 차감·영속 정책은 보류. |
| 검사 가용성 오류 | 처리율/사용량의 연결·시간 초과만 설정으로 우회, 기본 차단. 내부 결함·손상·선점·완료 가드는 차단. |
| 최초 발행 | 애플리케이션 최대 2회·총 ACK 대기 예산 4초. 하위 transport 재시도도 유한 설정하며 별도 시도로 계측. 최종 불명 뒤 새 자동 발행 없음. |
| 기한 | 새 외부 실행 허용 60초, 관련 준비/선점/응답/가드의 절대 보관 30분. 테스트 clock으로 만료·수명 비연장 검증. |
| 참조 | 정상 부재는 합성 거절, Redis 가용성 오류/miss는 SQL 조회. SQL 장애는 기술 실패 결과. 손상 값은 부재로 보지 않음. |
| 합성 HTTP | `ACCEPTED`는 콜백 대기, `REJECTED`는 고정 정책으로 다음 대상/보조/최종 거절 중 선택. `UNCERTAIN`만으로 새 외부 실행을 허가하지 않음. |
| Mock·콜백 | HTTP 응답 20ms·콜백 50ms 기준, 실행/명령/시도 포함. 선후 역전·상충·지연은 별도 주입. |
| 제한된 사실 재조회 | 최대 3회·회당 간격 50ms 후 보정/미확정 경로. 무한 업무 재조회 금지. |
| 복구 | 임대 15초, 재시도 간격 1/3/9초, 소진 뒤 격리·명시적 실패 기록. 보관 기한 연장 없음. |
| 최종 전달 | 접수 시 고정한 `NOTIFY`/`ARCHIVE` 합성 모드를 최종 명령에 반영. 둘 다 발행하지 않음. |
| 통지 | 합성 성공은 HTTP 204의 응답 종료 확인. 안정 멱등 키, 최대 2회 후 성공 표시 없이 정지/격리; 임의 성공/offset 건너뛰기 금지. |
| TCP | `SUBMIT`/`QUERY`/`REPORT` 합성 프레임. 접수 ACK 뒤 지연 리포트, ACK 유실 시 같은 operation 조회. |
| 병렬·메모리 | 최초 기능 시험 worker 1, 이후 4로 비교. 실행/대기/미커밋 합계 64건 상한. 새 실행 수락 전 상한 적용. |
| 배치 | 기능 계약 단건과 콜백 8건, 이후 콜백/SQL 배치 64건으로 단계 검증. Kafka 내부 key는 계속 실행별. |
| 성능 | 무장애 합성 시험 p95 초안: 접수 1초·최종 완료 5초, 기대하지 않은 오류 0. 최종 판단까지, 완료 정리까지, 외부 전달까지의 시각을 각각 기록. |
| 부하 | 같은 파티션·인스턴스부터 짧은 5초 입력, 성공·적체 조건 충족 시 단계 증가. 목표 접수/완료 각 10,000 TPS 이후 지속 시험. 장애 주입의 의도된 실패는 별도 판정. |

완료 지표는 offset 확정 조건을 충족한 완료 AP 처리와 선택 전달 완료를 모두 확인한다. 입력 창과 잔여 처리 창을 구분하고, 목표 지연/오류 및 소진 뒤 조치의 최종 합성 fixture는 시험 코드에서 고정한다. 재시도 예산과 보관 기한은 서로 다른 설정이며 유실된 증거를 시간 경과만으로 성공/실패로 바꾸지 않는다.

## 6. 데이터·이벤트 소유권과 전환

### 새 상태의 접근 경로

| 대상 | 소유자·변경 규칙 |
|---|---|
| 접수 원본 | API만 정상 INSERT. 완료만 scope/execution 조건으로 삭제. 최종 접수 실패 메타데이터는 별도 예외 항목으로 설계. |
| HTTP/TCP 관찰 사실 | 실행기가 고정 사실 조건부 저장. 같은 키 재입력은 digest/전체 내용 대조. 결과 판단은 보정 이벤트일 때만 동일 사실을 저장. |
| 콜백 사실 | 수신 AP가 조건부 저장·완료 재확인. 자신이 생성한 지연 사실만 조건부 정리. |
| 콜백 발행 복구 | 수신 AP가 미확인 이벤트 보관, 복구 작업자가 임대·재발행/ACK 완료 기록. |
| Redis 진행·응답 | 해당 실행 AP가 scope/execution/operation/version/digest/retainUntil을 확인. 완료 힌트는 Kafka 확정 뒤. |
| 최종 통지 성공 | 통지 AP가 확인된 HTTP 성공 뒤 기록. 재처리로 기한 연장 금지. |
| 최종 이력·합성 후처리 | 완료 AP의 별도 트랜잭션. 동일 키 상충은 실패. |
| 조회용 불변 결과 | 결과 보관 AP만 저장/대조하며 임시 데이터 정리에서 제외. |

Kafka 토픽·소비 그룹·Redis 키·저장소 namespace에 새 계약 버전을 분리한다. 개념상 `execution.v2.*`를 사용하되 실제 이름은 1단계에서 확정한다. 기존 이벤트에 필드만 추가해 구형 소비자가 새 의미로 처리하게 하지 않는다. 새 scope·실행이 구형 자동 원본 복구 대상에 잡히지 않도록 저장소 접근 경로도 분리한다.

### 배수·활성화·복귀 절차

1. 기존 미커밋 변경의 patch·파일 해시를 보존한다. 구현은 별도 branch/worktree에서 진행하고 기존 측정 도구 작업을 임의 커밋·폐기·reset하지 않는다. 문서 정리는 현재 작업 트리의 별도 파일/추가 블록으로 구분한다.
2. 전용 v2 환경·소비 그룹·토픽·자료로 단계 시험한다. 현재 실행 AP/자료와 다른 프로젝트는 변경하지 않는다. 공통·접수 단계만 준비된 상태에서 기존 전체 경로를 v2로 바꾸지 않는다.
3. 전환 리허설에서 기존 신규 접수를 멈추고 구형 Kafka lag뿐 아니라 예약·TCP 미확정·콜백 복구·통지·완료 정리까지 배수/분리한다. 정리할 수 없는 실행과 늦은 콜백의 소유 버전을 목록화한다. 자료를 삭제해 배수 완료로 만들지 않는다.
4. 구형 자료를 신형으로 자동 해석하지 않는다. 이관이 필요하면 버전·digest·소유권을 대조하는 별도 절차/시험을 추가한다. 두 버전이 같은 외부 실행을 처리하지 않게 한다.
5. 공통 버전, 모든 필수 AP, 읽기 격리·트랜잭션 설정과 합성 종단/장애 게이트 통과 후 새 접수를 v2로 전환한다. 최초 원본 자동 재발행은 v2에서 켜지지 않아야 한다.
6. 장애 시 v2 신규 접수/소비를 중단하고 확정 offset·트랜잭션 상태·외부 미확정을 보존한다. 기존 버전이 새 자료를 읽게 하거나 추정 abort/재발행하지 않는다. 소유권 재초기화 뒤 같은 v2에서 재개하는 것을 기본 복구로 한다.
7. 구형으로 복귀하려면 신형 자료 해석·변환/격리 검증과 외부 중복 방지 근거가 있어야 한다. 그 전에는 구형 경로를 **새로운 별도 실행**에만 재개하며 진행 중 v2는 버전별 소유자가 끝낸다. JAR 교체만으로 데이터 복귀를 선언하지 않는다.
