# 안정적인 외부 발송 플랫폼

외부 시스템으로 Event를 안정적으로 전달하는 Kafka 기반 비동기 플랫폼입니다. 유실, 중복, 외부 Provider 장애, 재시도와 복구를 코드와 테스트로 검증합니다.

업무 처리 단위는 `Delivery`, Kafka에서 전달되는 불변 사실은 `DeliveryEvent`, 외부 호출 한 번은 `DispatchAttempt`로 구분합니다.

## Grafana 대시보드

앱 빌드 후 `bash scripts/monitoring.sh up`으로 별도 로컬 환경을 실행합니다. [통합 관제 열기](http://localhost:13000/d/delivery-overview). 실제 데이터 생성·검증 방법과 PPT 항목별 구현 범위는 [실행 문서](docs/19-그라파나-대시보드-실행과-PPT-항목-대응.md)를 참고하세요.

## 가장 먼저 할 일

전체 최종 목표는 **10,000 TPS**입니다. 남은 기능·장애 복구·운영 처리의 개발과 통합 검증을 먼저 마무리합니다. 이후 성능 튜닝·설정, 서비스별 Pod당 최대 지속 성능 측정, 전체 10,000 TPS 확장 검증 순서로 진행합니다. 아래 기존 성능 병목 후속 작업도 이 순서를 따릅니다.

1. 로컬 애플리케이션 readiness 자동 확인과 한 명령 실행을 완성합니다. Maven Wrapper·JDK 21 검사·수동 실행 및 smoke 검증은 추가했습니다.
2. HTTP 재시도·TCP 2차 접수와 웹훅 결과 반영·후속 발송 복구, 주기 만료·요청 최종화·최종 Kafka 인계를 구현했습니다(GSI 이관 후 활성화). PostgreSQL 이력과 고객 통지 대기 기록의 원자 저장도 구현·검증했습니다. 고객 HTTP 묶음 통지·최대 20회 재전송과 복구도 구현했습니다(고객 설정 후 활성화). 신규 v2는 ORIGIN·STEP 최소 저장, Kafka 고정 회차 재시도, SQL 저장 후 DDB 삭제와 Redis 완료 TTL을 구현·검증했습니다(전체 워커 교체 후 활성화). 정상 DDB 쓰기는 5회·7항목입니다. 성공 결과 즉시 인계와 정리 worker의 동시 처리 4개를 적용했습니다. 전체 기능 6개와 정리 동시성 1/4의 부하 552/551건을 전수 대조했습니다. 기능·장애 검증을 우선하고 앞단 Kafka 적체·DDB 지연 분석과 본격 부하는 개발 완료 후 진행합니다.
3. 각 단계에 중복 event를 넣고 상태 전이와 외부 호출 횟수를 검증합니다.
4. Sender timeout 후 결과 불명 상태를 Provider의 멱등키 지원 여부별로 검증합니다.
5. 실제 SIGKILL·재시작 3개 시나리오(SQL 인계 전·고객 응답 미확인·업체 효과 후)를 통과했습니다. PostgreSQL 서비스 중단 중 결과 보존과 앱 재시작 없는 복구도 검증했습니다. DynamoDB 선점 전 발송 차단과 기한 경과 후 만료 복구 2개 경계도 검증했습니다. Redis 연결 장애 중 제한 우회·활성 중복 차단·만료와 재연결 후 정책 적용도 검증했습니다. Kafka 중단 중 접수/웹훅 503과 DB 결과 보존·복구 후 인계도 검증했습니다. 다음은 DLT·운영 조회·조치와 장애 중 조회 backoff, 배포·통합 회귀 보완입니다. 성능 단계 전 남은 범위는 약 4~6개 작업 단위로 추정합니다. 개발 완료 후 성능 튜닝과 Pod별·전체 부하 시험을 진행합니다.

단계별 순서와 통과 기준은 [개발 순서와 단계별 완료 기준](docs/02-개발-순서와-단계별-완료-기준.md)을 기준으로 합니다.
