# 안정적인 외부 발송 플랫폼

HTTP 1차·TCP/IP 2차 발송, 재시도·웹훅·만료·고객 결과 전달을 처리하는 Kafka 기반 비동기 플랫폼입니다. DynamoDB 사용을 최소화하면서 원본·멱등·복구 경계를 코드와 테스트로 검증합니다.

## 먼저 읽을 문서

문서를 번호순으로 모두 읽을 필요는 없습니다. 현재 설계를 이해하려면 아래 5개면 됩니다.

1. [요구사항과 전체 설계](docs/00-요구사항과-전체-설계.md)
2. [접수부터 최종 결과까지의 Call Flow](docs/04-요청-접수부터-최종-결과까지의-전체-흐름.md)
3. [저장소 특성과 공식 근거](docs/07-저장소별-특성과-데이터-유실-복구-조건.md)
4. [저장소 장애 시 중단과 복구](docs/09-저장소-장애-시-중단-범위와-복구-절차.md)
5. [현재 구현 상태와 남은 작업](docs/01-현재-구현-상태와-남은-작업.md)

나머지는 [문서 안내](docs/문서-안내.md)에서 작업별로 찾습니다. 상세 연동 계약·공식 설계 근거·과거 시험 기록은 보존하며, 과거의 “미구현” 표시는 최신 상태와 구분합니다.

## 현재 단계

핵심 발송 흐름·DLT 복구, 운영 조회·수동 조치·감사 복구와 Redis/Lifecycle 장애 중 호출 제한까지 구현했습니다. 나머지 운영 권한·장애 복구·실행 준비를 마무리한 뒤 성능 설정·튜닝 → 서비스별 Pod 지속 성능 → 전체 **10,000 TPS** 확장 시험을 진행합니다. 완료 여부·시험 수치는 위 진행 현황 문서에서 관리합니다.

## 실행과 Grafana

로컬 앱은 [실행 방법](docs/06-로컬-개발-환경-실행-방법.md)을 따릅니다. 모니터링 환경은 앱 빌드 후 `bash scripts/monitoring.sh up`으로 실행합니다.

[Grafana 통합 관제 열기](http://localhost:13000/d/delivery-overview). 수집 대상·화면별 연결 범위와 기존 Kafka 볼륨 주의사항은 [대시보드 문서](docs/19-그라파나-대시보드-실행과-PPT-항목-대응.md)를 확인합니다.

## 표준 테스트

JDK 21에서 실행합니다. 통합 시험은 Docker도 필요합니다.

```sh
bash scripts/test-java.sh unit
bash scripts/test-java.sh integration
```

업무 검증은 Java/JUnit, 환경 실행은 Bash + Docker Compose, 성능 부하 생성기는 **k6**입니다. 기존 외부 도구의 역할과 미실행 판정은 [테스트 기준](docs/48-Java-중심-테스트와-외부-도구-사용-기준.md)에 명시합니다.
